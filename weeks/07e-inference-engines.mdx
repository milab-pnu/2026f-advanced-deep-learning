Inference 최적화 기법은 따로따로 쓰이는 일이 드물다.
요청 하나가 서버에 들어오면 scheduler가 그 요청을 batch에 넣는다.
KV(key-value) cache manager는 블록을 내주고 재사용할 prefix cache를 찾는다.
Kernel은 필요하면 양자화(quantization)한 weight로 계산하고, 경우에 따라 draft가 다음 토큰을 추측한다.
이 모두를 한 프로그램 안에서 맞물려 돌리는 것이 **inference engine**이다.
Park 등은 오픈소스와 상용 엔진 25개를 살펴보고, 엔진들이 쓰는 최적화를 batching, 병렬화, 압축, caching, attention 등으로 분류했다.[^survey]
이 노트는 그 가운데 대표적인 공개 엔진인 vLLM과 SGLang이 이 기법들을 어떻게 묶는지 보고,
엔진의 성능을 재는 절차를 정리한다.

## 1. 엔진의 구성

### 1-1. 요청의 처리 경로

요청 하나가 엔진 안에서 거치는 길은 엔진마다 이름이 달라도 대체로 같다.

1. <strong>API(application programming interface) 서버</strong>가 HTTP(hypertext transfer protocol) 요청을 받아 프롬프트를 토큰으로 바꾸고,
   생성된 토큰을 다시 텍스트로 되돌려(detokenize) 스트리밍한다.
2. **Scheduler**가 대기열의 요청 가운데 이번 스텝에 넣을 것과 각 요청에서 처리할 토큰 수를 정하고,
   블록이 모자라면 실행 중인 요청 하나를 골라 선점(preemption)해 블록을 비운다.
3. **KV cache manager**가 요청에 블록을 배정·해제하고, 일치하는 prefix의 블록을 찾아 재사용한다.
4. **Model runner**가 batch의 입력 텐서를 준비하고,
   attention·선형층 kernel과 CUDA graph로 모델을 한 번 실행한다.
5. **Sampler**가 일반 decode에서는 마지막 위치의 logits로 다음 토큰을 고르고,
   speculative decoding에서는 추측한 토큰 위치들의 logits로 각 토큰의 수락 여부를 정한다.

예를 들어 새 요청 A의 프롬프트가 4토큰이고, 생성 중인 요청 B는 직전에 출력한 토큰 하나를 입력으로 이어 간다고 하자.
Scheduler는 이번 스텝에 A의 프롬프트 4토큰과 B의 입력 1토큰을 넣고, KV cache manager는 A에 블록을 배정한다.
Model runner가 다섯 토큰을 한 번에 처리하면, sampler는 A의 마지막 프롬프트 위치에서 A의 첫 출력 토큰을, B의 위치에서 B의 다음 토큰을 고른다.
두 토큰은 다음 스텝의 입력이 된다.

### 1-2. CPU overhead

모델이 작으면 GPU(graphics processing unit) 실행은 decode 스텝당 수 ms에 끝나기도 한다(H100의 Llama 8B는 약 5 ms까지 짧아질 수 있다).[^vllm-v1]
그래서 kernel launch뿐 아니라 다음 스텝의 scheduling과 입력 텐서 준비 같은 CPU(central processing unit) 쪽 작업이 늦어져도 GPU에 빈 구간이 생긴다.
SGLang 팀은 최적화하지 않은 엔진이 시간의 절반까지를 이런 CPU 작업에 쓸 수 있다고 보았다.[^sglang-v04]

해법은 두 갈래로 나뉜다.
하나는 CPU 작업 자체를 줄이거나, CPU 작업끼리 나누어 겹치는 것이다.
스텝마다 입력 텐서를 새로 만들지 않고 바뀐 부분만 고치고, API 서버의 일과 scheduling을 다른 프로세스로 떼어 서로 겹쳐 돌리는 vLLM V1의 설계가 이쪽이다.
다른 하나는 남은 CPU 작업을 GPU 실행과 겹치는 것이다.
GPU가 스텝 N을 실행하는 동안 CPU가 스텝 N+1의 scheduling과 입력 준비를 미리 해 둔다.
SGLang은 v0.4에서 이런 scheduler를 도입했다.
다음 스텝에 입력할 토큰은 GPU가 아직 계산 중이므로, CPU는 그 토큰이 들어갈 자리만 비워 둔 채 나머지 입력을 준비한다.
현재 스텝의 출력이 나오면 그 자리에 토큰을 넣고 바로 다음 스텝을 실행한다.[^sglang-v04]
vLLM은 같은 방식을 async scheduling이라 부르며,[^vllm-mrv2]
v0.31.0에서는 호환되지 않는 설정이 아니면 기본으로 켠다.[^vllm-config]

## 2. vLLM

### 2-1. V1 구조

vLLM은 PagedAttention 논문과 함께 공개된 엔진이다.
2025년의 V1 구조 개편은 코드 단순화, 최적화 통합과 함께 **CPU overhead를 거의 없애는 것**을 주요 목표로 삼았다.[^vllm-v1]

V1의 주요 설계는 다음과 같다.[^vllm-v1][^vllm-arch]

- **프로세스 분리.** Scheduling과 GPU worker의 모델 실행 조율만 맡는 Engine Core를 별도 프로세스의 반복문으로 두고,
  토큰화·detokenize·스트리밍은 API 서버 프로세스가 맡아 겹쳐 실행한다.
  모델은 GPU worker가 실행하는데, GPU가 한 대이면 worker가 Engine Core 프로세스 안에서 돌고 여러 대이면 GPU마다 worker 프로세스가 하나씩 뜬다.
- **단계 구분이 없는 scheduler.** Scheduler의 결정은 "요청마다 이번에 처리할 토큰 수"라는 하나의 표에 담기고,
  그 합이 스텝당 토큰 예산을 넘지 않게 정해진다.
  예를 들어 새 요청 A에 4, 생성 중인 요청 B에 1을 적으면 A의 prefill 네 토큰과 B의 decode 한 토큰을 같은 스텝에 처리한다.
  새 요청의 prefill 조각도, 기존 요청의 decode 한 토큰도,
  speculative decoding으로 검증할 토큰 여러 개도 모두 같은 형식이다.
  그래서 chunked prefill도 별도 단계 없이 이 형식 안에서 처리된다.
- **부담이 거의 없는 prefix caching.** Hash 기반 prefix caching을 다시 구현해,
  vLLM 팀의 측정에서 cache 적중률이 0%여도 처리량(throughput) 감소가 1% 미만이었고, 그래서 기본으로 켰다.
- **Persistent batch.** 이어지는 두 스텝의 batch는 요청 몇 개가 들어오거나 끝나는 것 말고는 거의 같다.
  그래서 block table처럼 큰 입력 텐서를 스텝마다 새로 만들지 않고, 이전 스텝의 텐서를 그대로 둔 채 바뀐 부분만 고쳐 CPU 시간을 줄인다.[^vllm-mrv2]

vLLM 팀은 V1의 처리량이 V0보다 최대 1.7배 높다고 보고했다.[^vllm-v1]
이 비교에서는 V0의 multi-step scheduling을 껐다.
여러 decode 스텝을 한 번에 scheduling해 V0의 CPU 부담을 덜어 주던 기능이라, 켜면 V0와의 차이가 줄 수 있다.
두 버전은 GPU kernel을 대부분 공유하며, vLLM 팀은 이 향상을 실행 경로 전체의 CPU overhead를 줄인 결과로 설명한다.

### 2-2. 주요 설정

vLLM의 주요 설정 인자는 batching, KV cache, 병렬화, 양자화 같은 기법의 동작을 조절한다.[^vllm-args][^vllm-opt]

| 인자 | 기본값 | 무엇을 정하나 |
|---|---|---|
| `--gpu-memory-utilization` | 0.92 | 엔진이 쓸 GPU 메모리 비율. Weight와 workspace를 뺀 나머지가 KV cache |
| `--max-num-seqs` | GPU에 따라 다름 | 동시에 실행할 요청 수의 상한 |
| `--max-num-batched-tokens` | GPU와 사용 방식에 따라 다름 | 스텝당 토큰 예산. 작으면 ITL(inter-token latency), 크면 TTFT(time to first token)와 처리량에 유리 |
| `--enable-prefix-caching` | 지원하는 모델에서 켜짐 | Prefix 재사용 |
| `--tensor-parallel-size` | 1 | TP(tensor parallelism)로 나눌 GPU 수 |
| `--kv-cache-dtype` | auto | KV cache의 정밀도(`fp8` 등) |
| `--quantization` | 모델 설정을 따름 | 양자화 방식(weight, 방식에 따라 activation도) |
| `--speculative-config` | 없음 | Draft 방식(EAGLE, n-gram, MTP(multi-token prediction) 등)과 추측 길이 |
| `--enforce-eager` | False | `torch.compile`과 CUDA graph를 끄고 실행 |

`--max-num-seqs`와 `--max-num-batched-tokens`의 기본값은 GPU와 사용 방식에 따라 달라지므로,
실험 결과를 보고할 때는 기본값에 기대지 말고 실제 값을 함께 적는다.

vLLM은 서버 내부 지표를 모니터링 도구 Prometheus가 수집할 수 있는 형식으로 내보내므로, 설정을 바꾸기 전후의 지표를 비교해 효과를 확인한다.[^vllm-metrics]
KV cache 사용률은 `vllm:kv_cache_usage_perc`, 실행·대기 요청 수는 `vllm:num_requests_running`과 `vllm:num_requests_waiting`이다.
Prefix cache 적중률은 토큰 수를 세는 `vllm:prefix_cache_hits`를 `vllm:prefix_cache_queries`로 나누어 구한다.
Speculative decoding에서 요청 하나가 검증 한 번에 얻는 평균 토큰 수는 `vllm:spec_decode_num_accepted_tokens`를 `vllm:spec_decode_num_drafts`로 나눈 값에 1을 더해 구한다.[^vllm-spec-metrics]
vLLM이 수락률이라 부르는 값은 수락 토큰 수를 draft 토큰 수(`vllm:spec_decode_num_draft_tokens`)로 나눈 것으로, 첫 거부 뒤에 버린 추측까지 분모에 세므로 추측 하나가 수락될 확률보다 대개 작다.
따라서 이 비율을 독립 수락을 가정한 이론식의 확률에 그대로 넣기보다, 검증 한 번에 얻은 평균 토큰 수와 실제 지연·처리량을 함께 비교한다.
같은 요청 분포와 부하에서 draft 방식과 추측 길이를 바꾸어 재면, 추측 비용까지 포함해 어느 설정이 이득인지 판단할 수 있다.

## 3. SGLang

### 3-1. 설계

SGLang은 LLM(large language model)을 여러 번 부르는 프로그램,
곧 생성·분기·도구 호출이 섞인 구조화된 생성을 빠르게 실행하려는 목표에서 출발했다.[^sglang]
그래서 생성 과정을 짜는 작은 프론트엔드 언어와, 그것을 실행하는 런타임을 함께 설계했다.
런타임의 핵심은 RadixAttention이다.
같은 프로그램 안에서 여러 호출이 공통 prefix를 공유하는 일이 잦기 때문이다.

정해진 형식으로 출력을 내게 하는 constrained decoding도 런타임이 맡는다.
출력이 JSON(JavaScript Object Notation) 스키마를 따라야 한다면,
생성 도중 스키마가 허용하는 토큰만 고르도록 매 스텝 마스크를 씌운다.
SGLang 논문은 스키마 같은 형식을 정규식(regular expression)으로 나타내고 이를 유한 상태 기계(finite state machine, FSM)로 바꾼다.[^sglang]
FSM은 생성한 내용에 따라 상태를 바꾸고, 각 상태는 그 뒤에 어떤 문자열이 올 수 있는지를 제한한다.
다음에 올 수 있는 문자열이 하나뿐인 구간은 한 단계로 압축한다.
예를 들어 다음이 `{"name": "`로 정해져 있다면 모델에게 토큰을 하나씩 고르게 하지 않는다.
그 문자열을 프롬프트와 지금까지의 출력에 이어 붙여 다시 토큰화한다(이어 붙인 문자가 기존 마지막 토큰과 합쳐질 수 있기 때문이다).
이전과 일치하는 앞부분의 KV cache는 재사용하고, 나머지 토큰은 prefill처럼 forward 한 번에 처리한다.
사람 이름처럼 여러 문자열이 가능한 부분에서만 모델이 한 토큰씩 고른다.
SGLang 팀은 이렇게 정해진 구간을 건너뛰는 decoding을 jump-forward decoding이라 부른다.[^sglang-fsm]
고정된 부분도 KV cache는 계산해야 하지만 순차 decode 스텝 수가 그만큼 줄어든다.

<Figure src="https://raw.githubusercontent.com/lm-sys/lm-sys.github.io/105adb035528f55f3d1823329f170a30b48f2b19/public/images/blog/compressed_fsm/compare.png" alt="같은 프롬프트(Please fill in the following information about Harry Potter.)로 JSON을 생성하는 두 방식의 비교. 위의 Jump-Forward Decoding With Compressed FSM에서는 초록 prefill 상자 뒤에 여는 중괄호와 name 키를 담은 주황 상자 하나가 붙고, 파랑 decode 상자 Har, ry, _Pot, ter와 닫는 따옴표·쉼표를 담은 파랑 상자 뒤에 age 키를 담은 주황 상자, 파랑 1, 1, house 키를 담은 주황 상자, 파랑 G, ryffindor와 닫는 중괄호를 담은 주황 상자, 종료 토큰이 이어진다. 아래의 Normal Decoding With FSM에서는 비슷한 출력을 파랑 decode 상자로 한 토큰씩 만들어 상자가 네 줄에 걸친다. 왼쪽의 나이 토큰은 1, 1인데 오른쪽 JSON에는 age가 15로 적혀 있어 원본 그림 안의 값이 맞지 않는다. 범례는 초록 Prefill, 파랑 Decode, 주황 Jump-Forward다." caption="Compressed FSM을 쓴 jump-forward decoding(위)과 FSM으로 한 토큰씩 decode하는 일반 방식(아래). 초록은 프롬프트의 prefill, 파랑은 한 토큰씩 decode한 토큰, 주황은 형식이 정해진 문자열을 forward 한 번에 처리한 jump-forward 구간이다. 왼쪽 나이 토큰은 11인데 오른쪽 JSON은 15로, 원본 그림 안의 값이 일치하지 않으므로 토큰별 출력 예가 아닌 처리 방식의 비교로 읽는다." source="LMSYS Org (2024), Compressed FSM 블로그 · © 2023 LMSYS Org, MIT License" wide />

엔진을 여러 인스턴스로 띄우면, 요청을 어느 인스턴스로 보내느냐도 prefix 재사용에 영향을 준다.
SGLang v0.4는 이를 위한 cache-aware routing을 cache-aware load balancer로 구현했다.
엔진 인스턴스마다 radix tree가 따로 있으므로, 요청을 돌아가며 나누면 같은 prefix를 가진 요청이 여러 인스턴스에 흩어져 cache 적중률이 떨어진다.
이 load balancer는 인스턴스마다 어떤 prefix가 cache에 있을지 근사한 radix tree를 따로 유지하며, prefix가 많이 맞을 인스턴스를 고르되 부하가 한쪽에 몰리지 않게 요청을 보낸다.
SGLang 팀은 긴 공통 prefix를 공유하는 요청 그룹 여러 개가 같은 크기로 들어 있는 workload로 이를 쟀다.
A100 80 GB 8대에서 Llama 3.1 8B를 서빙했을 때, 이 방식은 v0.3보다 cache 적중률을 3.8배 높여 처리량을 최대 1.9배 늘렸다.[^sglang-v04]

같은 버전은 MLA(multi-head latent attention) 모델에 data parallel attention을 도입했다.
Attention 부분만 GPU마다 다른 요청을 맡게 하면 GPU마다 자기 요청의 latent KV cache만 두므로, attention을 TP로 나눌 때 생기던 cache 복제가 사라지고 아낀 메모리만큼 batch를 키울 수 있다.[^sglang-v04]

### 3-2. 설정과 튜닝

SGLang의 설정도 같은 개념에 대응한다.[^sglang-args]
Weight와 KV cache pool에 줄 GPU 메모리 비율은 `--mem-fraction-static`, chunked prefill의 조각 크기는 `--chunked-prefill-size`,
동시 요청 수의 상한은 `--max-running-requests`, 요청의 실행 순서는 `--schedule-policy`로 정한다.
실행 순서의 기본값은 도착한 순서대로인 `fcfs`(first come, first served)이고,
`lpm`(longest prefix match)을 고르면 cache-aware scheduling처럼 cache와 일치하는 prefix가 긴 요청부터 처리한다.
다만 대기 요청이 128개를 넘으면 정렬 비용을 아끼려고 `fcfs`로 돌아간다.[^sglang-policy]
개념은 대응해도 정의가 vLLM과 꼭 같지는 않다.
`--chunked-prefill-size`는 prefill 조각의 크기이고 vLLM의 `--max-num-batched-tokens`는 decode 토큰까지 포함한 스텝당 예산이다.
그래서 두 엔진에 같은 숫자를 넣어도 같은 조건이 되지는 않는다.

SGLang의 튜닝 문서는 offline batch inference, 곧 지연 목표 없이 모아 둔 요청을 한꺼번에 처리하는 경우에 처리량을 높이려면 **batch를 크게 만드는 것이 가장 중요하다**고 요약한다.[^sglang-tune]
작은 batch에서는 weight 읽기가 병목이라는 roofline 분석과 같은 결론이다.
Batch가 커질수록 요청들의 KV cache가 메모리를 더 차지하므로, KV cache 사용률은 batch를 충분히 키웠는지 보는 단서가 된다.
다만 사용률은 문맥 길이와 남겨 둔 prefix cache에도 달려 있으므로 대기 요청 수와 함께 본다.
문서는 서버 로그의 KV cache 사용률이 0.9를 넘으면 메모리를 잘 쓰고 있다고 보고,
대기 요청이 쌓였는데도 0.9 아래에 머물면 서버가 새 요청을 너무 보수적으로 받아들이는 것이라고 본다.
메모리가 모자라면 prefill에서는 조각 크기를, decode에서는 동시 요청 수를 줄이라고 권한다.

## 4. 다른 엔진

vLLM과 SGLang 말고도 목적이 다른 엔진이 여럿 있다.[^survey]
NVIDIA의 TensorRT-LLM은 NVIDIA GPU에 맞춘 attention·행렬곱·MoE(mixture of experts) kernel과 prefill/decode 분리,
큰 규모의 expert parallelism, speculative decoding을 갖춘 라이브러리다.[^trtllm]
llama.cpp는 의존성 없는 C/C++ 구현으로,
개인용 컴퓨터와 다양한 하드웨어에서 양자화된 모델을 돌리는 데 널리 쓰인다.[^llamacpp]
LMDeploy는 TurboMind라는 자체 엔진으로 압축과 서빙을 함께 제공한다.[^lmdeploy]
한때 널리 쓰인 Hugging Face의 TGI(Text Generation Inference)는 현재 유지보수 모드이며,
저장소 스스로 vLLM, SGLang, llama.cpp 등을 권한다.[^tgi]
엔진을 고를 때는 지원하는 모델과 하드웨어, 필요한 기능(양자화 형식, speculative decoding, 구조화된 출력)을 먼저 확인하고, 그 조건에서 직접 재 본다.

## 5. 성능 측정

### 5-1. 측정 조건

엔진이나 설정을 비교할 때는 결과에 영향을 주는 조건을 모두 고정한다.
모델과 그 버전, GPU의 종류와 수, weight와 KV cache의 정밀도, 입력과 출력 길이의 분포,
sampling 설정이 같아야 한다.
출력 길이를 고정하려면 종료 토큰을 무시하고 정해진 길이까지 생성하게 한다.[^nvidia-bench]
엔진과 설정에 따라 첫 요청 무렵에는 CUDA graph capture·컴파일·메모리 할당 같은 한 번뿐인 작업이 섞일 수 있으므로,
본 측정 전에 측정할 부하와 비슷한 warmup 요청을 충분히 보내 이런 작업이 측정에 섞이지 않게 한다.
Prefix caching이 있는 엔진에서는 cache가 비어 있는 상태와 채워진 상태를 구분한다.
vLLM과 SGLang 모두 측정 사이에 prefix cache를 비우는 방법을 제공한다.[^sglang-bench]
같은 데이터라도 도구마다 지표의 정의가 조금씩 다르므로,
지표 이름보다 정의를 확인한다.
NVIDIA의 측정 안내는 ITL을 TPOT(time per output token)와 같은 값으로 정의하지만,
vLLM은 ITL을 출력 묶음 사이의 간격으로, TPOT를 첫 출력 뒤의 시간을 나머지 출력 토큰 수로 나눈 값으로 따로 보고한다.[^nvidia-bench][^vllm-bench]
그래서 speculative decoding처럼 토큰이 묶여 나오면 두 값이 달라진다.

### 5-2. 부하와 성능 곡선

서빙 성능은 숫자 하나가 아니라 **부하에 따른 곡선**이다.
요청을 적게 보내면 지연(latency)은 짧고 처리량은 낮으며,
많이 보낼수록 처리량은 오르다가 batch 상한이나 메모리·연산의 한계에 닿으면 포화하고 지연만 계속 늘어난다.
부하를 거는 방법은 두 가지다.
초당 요청 수를 정해 Poisson 과정으로 보내는 request rate 방식과,
응답을 기다리는 요청 수를 정해 두고 요청 하나가 끝날 때마다 새 요청 하나를 보내는 concurrency 방식이다.
Poisson 과정에서는 요청이 서로 독립적으로, 평균 간격 1/요청률로 무작위하게 도착한다(초당 2건이면 평균 0.5초 간격).
vLLM의 `vllm bench serve`는 둘 다 지원하고,
`--burstiness`로 요청이 몰려 오는 정도도 바꿀 수 있다.
기본값 1이면 Poisson 과정이고, 1보다 작을수록 요청이 한꺼번에 몰려 온다.[^vllm-bench]
NVIDIA의 안내는 요청률을 고정하면 처리하지 못한 요청이 끝없이 쌓일 수 있다며 concurrency 방식을 권하고,
1부터 엔진의 최대 batch를 조금 넘는 값까지 바꿔 가며 재라고 한다.[^nvidia-bench]

두 방식은 답하는 질문이 다르다.
Concurrency를 고정하면 응답이 느려질 때 새 요청도 늦게 들어가므로 서버가 감당할 수 있는 만큼만 부하가 걸린다.
그래서 동시 요청 수에 따른 처리량과 지연의 곡선, 곧 시스템의 용량을 보기에 좋다.
요청률을 고정하면 서버가 느려져도 요청이 계속 들어와 대기열이 쌓이므로,
실제 사용자가 일정한 속도로 몰려올 때 SLO(service-level objective)를 지키는지 보기에 좋다.

Goodput을 잴 때도 정의를 구분한다.
DistServe의 goodput은 요청 중 정해진 비율 이상이 SLO를 지키는 최대 요청률을 GPU 한 대당 값으로 나타낸 것이다.[^distserve]
반면 `vllm bench serve`의 `--goodput` 옵션에 TTFT와 TPOT의 목표치를 밀리초로 주면,
주어진 부하 하나에서 목표를 모두 지킨 요청 수를 측정 시간으로 나눈 값을 보고한다.[^vllm-bench-src]
그래서 DistServe의 goodput을 얻으려면 요청률을 바꿔 가며 여러 번 재고,
목표를 지킨 요청의 비율이 기준 이상인 최대 요청률을 찾고, GPU가 여러 대면 GPU 수로 나누어야 한다.

<Callout type="example">
기말 프로젝트에서 Llama 3.1 8B를 H100 한 대로 서빙하며 BF16(bfloat16)과 FP8(8-bit floating point)을 비교한다고 하자.
서버를 두 번 띄우되 정밀도만 다르게 하고, 엔진 버전과 KV cache 정밀도, batch 관련 설정은 같게 둔다.
앞선 측정의 prefix cache가 결과에 섞이지 않게 두 서버 모두 `--no-enable-prefix-caching`으로 prefix caching을 끈다.
FP8 서버는 미리 FP8로 양자화한 checkpoint를 불러오거나(이때는 아래 `--model`도 그 이름으로 바꾼다),
BF16 checkpoint를 불러오면서 `--quantization fp8_per_tensor`로 양자화하는 online 모드를 쓴다.
어느 방식인지와 엔진 버전, 설정을 결과와 함께 적는다.
예를 들어 vLLM 0.31.0에서 같은 H100 한 대로 차례로 잰다면, 먼저 BF16 서버를 다음처럼 띄운다.
이 모델은 접근 권한이 필요한 Hugging Face 모델이므로, 실행 환경에서 해당 모델의 이용 조건을 확인하고 접근 권한과 인증을 갖춰야 한다.

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 --kv-cache-dtype auto --no-enable-prefix-caching \
  --max-num-seqs 256 --max-num-batched-tokens 8192
```

서버가 준비되면 다른 터미널에서 아래 측정을 실행한다.
측정이 끝나면 첫 서버를 종료하고, 같은 GPU에서 FP8 서버를 띄워 같은 측정을 반복한다.

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 --kv-cache-dtype auto --no-enable-prefix-caching \
  --max-num-seqs 256 --max-num-batched-tokens 8192 \
  --quantization fp8_per_tensor
```

이 설정의 `--kv-cache-dtype auto`는 모델 dtype을 따르므로 두 서버 모두 KV cache는 BF16이다.
시작 로그와 실제 사용한 설정을 확인해 양자화 방식과 KV cache dtype, batch 관련 값이 의도한 대로 적용되었는지도 기록한다.
여기서는 두 batch 상한을 명시해 서버마다 기본값이 달라지는 일을 막는다.
두 서버를 동시에 올리는 것이 아니라 하나씩 띄워 GPU 메모리를 온전히 사용한다.
기본 주소는 `http://localhost:8000`이고, `--served-model-name`을 따로 정하지 않았으므로 측정 명령의 `--model`은 서버가 불러온 모델 이름과 같다.[^vllm-bench][^vllm-fp8w8a8]
두 서버에 각각 다음처럼 부하를 건다.

```bash
vllm bench serve --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --ignore-eos \
  --num-prompts 1000 --max-concurrency 64 --num-warmups 10 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:1000 tpot:50
```

`--ignore-eos`는 두 서버의 출력 길이를 맞추고,
`--num-warmups`는 측정 전에 warmup 요청을 보낸다(기본값 0).
`--request-rate`의 기본값 inf는 요청 사이에 도착 간격을 두지 않는다는 뜻이다.
여기에 `--max-concurrency 64`만 주면 응답을 기다리는 요청이 최대 64개로 제한되고, 남은 요청은 자리가 날 때마다 보내지므로 concurrency 방식의 측정이 된다.[^vllm-bench-src]
`e2el`은 요청 하나의 전체 지연(end-to-end latency)이다.
이 random 입력은 길이를 통제한 비교용이다.
Prefix 재사용이나 draft 수락처럼 입력 내용에 좌우되는 효과는, 그 기능을 켜고 대표 프롬프트와 실제 입출력 길이 분포로 따로 잰다.
`--max-concurrency`를 1, 4, 16, 64, 256으로 바꿔 가며 반복하고,
가로축에 사용자당 처리량(tokens/s/user), 곧 output token throughput을 설정한 동시 요청 수 상한으로 나눈 값을,
세로축에 GPU 한 대의 output token throughput을 두어 두 정밀도의 곡선을 겹쳐 그린다.
동시 요청 상한 64에서 초당 6,400토큰이 나왔다면 그 점은 (100, 6,400)이다(가상의 수치).
이 가로축은 측정 시간 대부분 동안 동시 요청 수가 상한에 가깝게 유지될 때 요청 하나가 받는 평균 속도의 근사값이다.
요청 수가 상한에 비해 적으면 시작과 끝 구간의 영향이 커지므로, 요청 수를 늘려 다시 잰다.
TTFT와 대기 시간이 섞여 있어 1/TPOT와 다르므로, decode 중에 사용자가 느끼는 속도는 TPOT로 따로 본다.
</Callout>

앞의 예시를 roofline으로 보면, 동시 요청이 적고 weight 읽기가 주된 병목이라면 FP8이 TPOT를 줄일 것으로 기대할 수 있다.
다만 vLLM의 FP8 문서가 설명하는 online 모드(`fp8_per_tensor`)는 매 forward마다 activation의 scale을 새로 구하는 비용이 들어,
문서도 이 모드의 지연 개선이 제한된다고 적는다.[^vllm-fp8w8a8]
동시 요청이 많아 행렬곱 연산이 병목이 되면 FP8 Tensor Core로 처리량이 높아질 수 있다.
결과가 예측과 다르면 동시 요청 1의 TPOT로 MBU(model bandwidth utilization)를 계산해 대역폭 지붕에서 얼마나 떨어져 있는지 본다.
이때 읽어야 할 bytes는 그 서버의 실제 저장 정밀도로 센다(FP8 서버라면 FP8 weight 기준).
클라이언트에서 잰 TPOT에는 전송과 서버의 다른 작업도 포함되므로, 이 값은 GPU의 실제 HBM 사용률이 아니라 서비스 지연을 포함한 추정치다.
GPU 실행 구간의 MBU나 하드웨어 counter를 함께 보면 네트워크·스케줄링 비용과 구분하는 데 도움이 된다.
그래도 원인이 보이지 않으면 엔진의 profiler로 실행 기록(trace)을 떠서 kernel 사이에 GPU가 노는 구간과 attention·행렬곱의 비중을 확인한다.[^vllm-profile]
예를 들어 vLLM 0.31.0의 진단용 서버 명령에 `--profiler-config '{"profiler":"torch","torch_profiler_dir":"./vllm_profile"}'`를 더하고,
측정 명령에는 `--backend vllm --profile`을 더해 소수의 요청만 보내면 실행 기록이 해당 디렉터리에 저장된다.
기존 서버를 종료한 뒤 진단용 서버를 같은 GPU에 다시 띄운다.
기록을 Perfetto에서 열어 GPU timeline의 kernel 이름과 시간을 엔진의 backend 설정·로그와 함께 확인한다.
Kernel 이름과 기록 범위는 버전과 GPU, CUDA graph 사용 여부에 따라 달라질 수 있으므로 이름 하나만으로 원하는 구현이라고 단정하지 않는다.
Profiler는 실행을 느리게 만들 수 있어, 지연과 처리량의 본 측정은 profiler를 끈 상태에서 따로 한다.[^vllm-profile]

양자화와 speculative decoding처럼 여러 기법을 함께 켤 때는 개별 이득을 단순히 곱해 예측할 수 없으므로,
둘 다 끈 기준, 하나씩만 켠 경우, 둘 다 켠 경우를 같은 조건에서 따로 잰다.
정확도는 같은 프롬프트에 대한 task 점수로 따로 확인한다.

vLLM은 이렇게 설정과 부하를 바꿔 가며 재는 일을 자동화하는 `vllm bench sweep`도 제공한다.
서버 설정의 조합마다 측정을 돌리고, 부하 수준을 바꿔 지연과 처리량의 맞교환을 찾으며,
위와 같은 정의의 사용자당 처리량과 GPU당 처리량으로 Pareto 곡선을 그린다.[^vllm-sweep]
Pareto 곡선은 두 축 모두 자신보다 나쁘지 않으면서 적어도 한 축은 더 나은 점이 없는 점들을 이은 경계다.
결과를 보고할 때는 곡선과 함께 측정 조건 전체를 적어,
다른 사람이 같은 조건에서 다시 잴 수 있게 한다.
