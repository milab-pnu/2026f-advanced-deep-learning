Inference 최적화 기법은 따로따로 쓰이는 일이 드물다.
요청 하나가 서버에 들어오면 scheduler가 그 요청을 batch에 넣는다.
KV(key-value) cache manager는 블록을 내주고 재사용할 prefix cache를 찾는다.
Kernel은 필요하면 양자화(quantization)한 weight로 계산하고, 경우에 따라 draft가 다음 토큰을 추측한다.
이 모두를 한 프로그램 안에서 맞물려 돌리는 것이 **inference engine**이다.
Park 등은 오픈소스와 상용 엔진 25개를 살펴보고, 엔진들이 쓰는 최적화를 batching, 병렬화, 압축, caching, attention 등으로 분류했다.[^survey]
이 노트는 그 가운데 대표적인 공개 엔진인 vLLM과 SGLang이 이 기법들을 어떻게 묶는지 보고,
엔진의 성능을 재는 절차를 정리한다.

## 1. 엔진의 구성

### 1-1. 요청의 처리 경로

요청 하나가 엔진 안에서 거치는 길은 엔진마다 이름이 달라도 대체로 같다.

1. <strong>API(application programming interface) 서버</strong>가 HTTP(hypertext transfer protocol) 요청을 받아 프롬프트를 토큰으로 바꾸고,
   생성된 토큰을 다시 텍스트로 되돌려(detokenize) 스트리밍한다.
2. **Scheduler**가 대기열의 요청 가운데 이번 스텝에 넣을 것과 각 요청에서 처리할 토큰 수를 정하고,
   블록이 모자라면 실행 중인 요청 하나를 골라 선점(preemption)해 블록을 비운다.
3. **KV cache manager**가 요청에 블록을 배정·해제하고, 일치하는 prefix의 블록을 찾아 재사용한다.
4. **Model runner**가 batch의 입력 텐서를 준비하고,
   attention·선형층 kernel을 실행해 모델의 출력을 구한다.
   지원하는 설정에서는 CUDA graph로 여러 kernel의 실행을 묶을 수도 있다.
5. **Sampler**가 일반 decode에서는 마지막 위치의 logits로 다음 토큰을 고르고,
   speculative decoding에서는 추측한 토큰 위치들의 logits로 각 토큰의 수락 여부를 정한다.

예를 들어 새 요청 A의 프롬프트가 4토큰이고, 생성 중인 요청 B는 직전에 출력한 토큰 하나를 입력으로 이어 간다고 하자.
Scheduler는 이번 스텝에 A의 프롬프트 4토큰과 B의 입력 1토큰을 넣고, KV cache manager는 A에 블록을 배정한다.
Model runner가 다섯 토큰을 한 번에 처리하면, sampler는 A의 마지막 프롬프트 위치에서 A의 첫 출력 토큰을, B의 위치에서 B의 다음 토큰을 고른다.
두 토큰은 다음 스텝의 입력이 된다.

### 1-2. CPU overhead

모델이 작으면 GPU(graphics processing unit)는 decode 스텝 하나를 매우 짧은 시간에 끝내기도 한다.[^vllm-v1]
그래서 kernel launch뿐 아니라 다음 스텝의 scheduling과 입력 텐서 준비 같은 CPU(central processing unit) 쪽 작업이 늦어져도 GPU에 빈 구간이 생긴다.
SGLang 팀은 최적화하지 않은 엔진이 시간의 상당 부분을 이런 CPU 작업에 쓸 수 있다고 보았다.[^sglang-v04]

해법은 두 갈래로 나뉜다.
하나는 CPU가 할 일을 줄이거나, 서로 다른 CPU 작업을 동시에 실행하는 것이다.
입력 텐서를 스텝마다 새로 만들지 않고 바뀐 부분만 고치거나, API 서버의 일과 scheduling을 서로 다른 프로세스에서 실행하는 식이다.
다른 하나는 남은 CPU 작업을 GPU 실행과 겹치는 것이다.
GPU가 스텝 N을 실행하는 동안 CPU가 스텝 N+1의 scheduling과 입력 준비를 미리 해 둔다.
SGLang은 v0.4에서 이런 scheduler를 도입했다.
다음 스텝에 입력할 토큰은 GPU가 아직 계산 중이므로, CPU는 그 토큰이 들어갈 자리만 비워 둔 채 나머지 입력을 준비한다.
현재 스텝의 출력이 나오면 그 자리에 토큰을 넣고 바로 다음 스텝을 실행한다.[^sglang-v04]
vLLM은 같은 방식을 async scheduling이라 부르며,[^vllm-mrv2]
v0.31.0에서는 호환되지 않는 설정이 아니면 기본으로 켠다.[^vllm-config]

## 2. vLLM

vLLM은 PagedAttention 논문과 함께 공개된 엔진이다.
2025년의 V1 구조 개편은 코드 단순화, 최적화 통합과 함께 **CPU overhead를 거의 없애는 것**을 주요 목표로 삼았다.[^vllm-v1]

V1의 주요 설계는 다음과 같다.[^vllm-v1][^vllm-arch]

- **프로세스 분리.** Scheduler와 KV cache manager를 담은 Engine Core는 별도 프로세스에서 반복 실행되며,
  scheduling과 KV cache 관리, GPU worker의 모델 실행 조율을 맡는다.
  토큰화·detokenize·스트리밍은 API 서버 프로세스가 맡아 Engine Core와 동시에 실행한다.
  Model runner와 sampler는 GPU worker에서 실행된다.
- **단계 구분이 없는 scheduler.** Scheduler의 결정은 "요청마다 이번에 처리할 토큰 수"라는 하나의 표에 담기고,
  그 합이 스텝당 토큰 예산을 넘지 않게 정해진다.
  앞의 예시라면 이 표에 A는 4, B는 1이 적힌다.
  새 요청의 prefill 조각도, 기존 요청의 decode 한 토큰도,
  speculative decoding으로 검증할 토큰 여러 개도 모두 같은 형식이다.
  그래서 chunked prefill도 별도 단계 없이 이 형식 안에서 처리된다.
- **부담이 거의 없는 prefix caching.** Hash 기반 prefix caching을 다시 구현해,
  vLLM 팀의 측정에서 cache가 전혀 적중하지 않아도 처리량(throughput)이 거의 줄지 않았고, 그래서 기본으로 켰다.
- **Persistent batch.** 이어지는 두 스텝의 batch는 요청 몇 개가 들어오거나 끝나는 것 말고는 거의 같다.
  그래서 block table처럼 큰 입력 텐서를 스텝마다 새로 만들지 않고, 이전 스텝의 텐서를 그대로 둔 채 바뀐 부분만 고쳐 CPU 시간을 줄인다.[^vllm-mrv2]

## 3. SGLang

SGLang은 LLM(large language model)을 여러 번 부르는 프로그램,
곧 생성·분기·도구 호출이 섞인 구조화된 생성을 빠르게 실행하려는 목표에서 출발했다.[^sglang]
그래서 생성 과정을 짜는 작은 프론트엔드 언어와, 그것을 실행하는 런타임을 함께 설계했다.
런타임의 핵심은 RadixAttention이다.
같은 프로그램 안에서 여러 호출이 공통 prefix를 공유하는 일이 잦기 때문이다.

엔진을 여러 인스턴스로 띄우면, 요청을 어느 인스턴스로 보내느냐도 prefix 재사용에 영향을 준다.
SGLang v0.4는 요청을 prefix가 맞을 인스턴스로 보내는 cache-aware load balancer를 넣었다.
엔진 인스턴스마다 radix tree가 따로 있으므로, 요청을 돌아가며 나누면 같은 prefix를 가진 요청이 여러 인스턴스에 흩어져 cache 적중률이 떨어진다.
이 load balancer는 각 인스턴스의 cache에 어떤 prefix가 있을지를 근사하는 radix tree를 따로 유지한다.
Prefix가 많이 맞을 인스턴스를 고르되, 부하가 한쪽에 몰리지 않게 요청을 보낸다.
SGLang 팀은 그룹마다 긴 공통 prefix를 공유하는 요청들로 workload를 만들어 그 효과를 쟀다.
이 측정에서 이 방식은 v0.3보다 cache 적중률을 크게 높였고, 그에 따라 처리량도 늘었다.[^sglang-v04]
실제 이득은 요청의 공통 부분과 부하에 따라 달라진다.

## 4. 성능 측정

### 4-1. 측정 조건

엔진이나 설정을 비교할 때는 비교하려는 항목을 제외하고 결과에 영향을 주는 주요 조건을 맞춘다.
모델과 그 버전, GPU의 종류와 수, weight와 KV cache의 정밀도, 입력과 출력 길이의 분포,
sampling 설정 등이 그 대상이다.
출력 길이를 고정하려면 종료 토큰을 무시하고 정해진 길이까지 생성하게 한다.[^nvidia-bench]
엔진과 설정에 따라 첫 요청 무렵에는 CUDA graph capture·컴파일·메모리 할당 같은 한 번뿐인 작업이 섞일 수 있으므로,
본 측정 전에 측정할 부하와 비슷한 warmup 요청을 충분히 보내 이런 작업이 측정에 섞이지 않게 한다.
Prefix caching이 있는 엔진에서는 cache가 비어 있는 상태와 채워진 상태를 구분한다.
vLLM과 SGLang 모두 측정 사이에 prefix cache를 비우는 방법을 제공한다.[^sglang-bench]
같은 데이터라도 도구마다 지표의 정의가 조금씩 다르므로,
지표 이름보다 정의를 확인한다.
예를 들어 NVIDIA의 측정 안내는 ITL(inter-token latency)을 TPOT(time per output token)와 같은 값으로 정의하지만, vLLM은 둘을 따로 보고해 토큰이 묶여 나오면 두 값이 달라진다.[^nvidia-bench][^vllm-bench]

### 4-2. 부하 방식

서빙 성능은 숫자 하나가 아니라 **부하에 따른 곡선**이다.
요청을 적게 보내면 지연은 짧고 처리량은 낮으며,
많이 보낼수록 처리량은 대체로 오르다가 batch 상한이나 메모리·연산의 한계에 닿으면 포화한다.
그 이후에도 요청이 계속 들어오면 대기열이 쌓여 지연이 늘어나고, 과부하로 처리량이 떨어질 수도 있다.
부하를 거는 방법은 두 가지다.
초당 요청 수를 정해 Poisson 과정으로 보내는 request rate 방식과,
응답을 기다리는 요청 수를 정해 두고 요청 하나가 끝날 때마다 새 요청 하나를 보내는 concurrency 방식이다.
Poisson 과정에서는 요청이 서로 독립적으로, 평균 간격 1/요청률로 무작위하게 도착한다(초당 2건이면 평균 0.5초 간격).
vLLM의 `vllm bench serve`는 둘 다 지원하고,
`--burstiness`로 요청이 몰려 오는 정도도 바꿀 수 있다.
기본값 1이면 Poisson 과정이고, 1보다 작을수록 요청이 한꺼번에 몰려 온다.[^vllm-bench]

두 방식은 알려 주는 것이 다르다.
Concurrency를 고정하면 응답이 느려질 때 새 요청도 늦게 들어가므로 미완료 요청 수가 정한 상한을 넘지 않는다.
그래서 동시 요청 수에 따른 처리량과 지연의 곡선, 곧 시스템의 용량을 보기에 좋다.
다만 상한이 서버에서 동시에 실행할 수 있는 요청 수보다 크면, 그 상한 안에서도 대기열이 생길 수 있다.
요청률을 고정하면 서버가 느려져도 요청이 계속 들어와 대기열이 쌓이므로,
실제 사용자가 일정한 속도로 몰려올 때 SLO(service-level objective)를 지키는지 보기에 좋다.
NVIDIA의 안내는 엔진의 용량을 잴 때 concurrency 방식을 권하고,
1부터 엔진의 최대 batch를 조금 넘는 값까지 바꿔 가며 재라고 한다.[^nvidia-bench]

Goodput을 잴 때도 정의를 구분한다.
DistServe의 goodput은 요청 중 정해진 비율 이상이 SLO를 지키는 최대 요청률(GPU 한 대당)이지만,[^distserve]
`vllm bench serve`의 `--goodput` 옵션은 주어진 부하 하나에서 TTFT(time to first token)와 TPOT 목표를 모두 지킨 요청 수를 측정 시간으로 나눈 값을 보고한다.[^vllm-bench-src]
DistServe의 goodput을 얻으려면 요청률을 바꿔 가며 이 측정을 되풀이한다.
이때 두 지표의 p90이 각각 목표 이내여도 전체 요청의 90%가 두 목표를 모두 지켰다는 뜻은 아니다.
TTFT 목표를 넘긴 요청과 TPOT 목표를 넘긴 요청이 서로 다를 수 있으므로, 요청별로 두 조건을 함께 확인한다.

### 4-3. 성능 곡선

Llama 3.1 8B를 같은 H100에서 BF16(bfloat16)과 FP8(8-bit floating point)으로 서빙해 비교한다고 하자.
모델 정밀도 외의 설정과 요청 분포를 맞추고, 동시 요청 수를 바꾸어 가며 TPOT와 처리량을 잰다.

<Details summary="BF16과 FP8 서버 측정 예시">
<Callout type="example">
기말 프로젝트에서 이 비교를 한다면, 서버를 두 번 띄우되 정밀도만 다르게 하고 엔진 버전, KV cache 정밀도, batch 상한은 같게 둔다.
vLLM 0.31.0에서 같은 H100 한 대로 차례로 잰다면, 먼저 BF16 서버를 다음처럼 띄운다(이 모델은 Hugging Face에서 접근 승인을 받아야 내려받을 수 있다).

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 --kv-cache-dtype auto --no-enable-prefix-caching \
  --max-num-seqs 256 --max-num-batched-tokens 8192
```

`--no-enable-prefix-caching`은 앞선 측정의 prefix cache가 결과에 섞이지 않게 하고, 두 batch 상한을 명시하면 서버마다 기본값이 달라지는 일을 막는다.
`--kv-cache-dtype auto`는 모델 dtype을 따르므로 KV cache는 BF16이다.
측정이 끝나면 첫 서버를 종료하고, 같은 명령에 `--quantization fp8_per_tensor`를 더해 FP8 서버를 띄운다.
이 online 모드는 BF16 checkpoint를 불러오면서 마지막 `lm_head`를 제외한 선형층 weight를 FP8로 저장하고, 실행할 때 activation도 FP8로 양자화한다.[^vllm-fp8w8a8]
두 서버에 각각 다음처럼 부하를 건다.

```bash
vllm bench serve --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --ignore-eos \
  --num-prompts 1000 --max-concurrency 64 --num-warmups 64 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:1000 tpot:50 --save-result --save-detailed
```

`--ignore-eos`는 두 서버의 출력 길이를 맞추고, `--num-warmups`는 측정 전에 warmup 요청을 보낸다.
`e2el`은 요청 하나의 전체 지연(end-to-end latency)이고, `--goodput`의 목표값은 ms 단위로 여기서는 TTFT 1초와 TPOT 50 ms다.
`--request-rate` 없이 `--max-concurrency 64`만 주면 응답을 기다리는 요청이 최대 64개로 유지되는 concurrency 방식의 측정이 되고,[^vllm-bench-src]
`--save-result --save-detailed`는 결과와 요청별 지연을 JSON(JavaScript Object Notation) 파일에 저장한다.[^vllm-bench]
`--max-concurrency`를 1, 4, 16, 64, 256으로 바꿔 가며 반복하고, warmup 요청 수와 `--num-prompts`도 상한에 맞춰 늘린다.
이 random 입력은 길이를 통제한 비교용이므로, prefix 재사용이나 draft 수락처럼 입력 내용에 좌우되는 효과는 대표 프롬프트로 따로 잰다.
</Callout>
</Details>

다음은 동시 요청 상한을 1, 4, 16, 64, 256으로 바꿔 가며 잰 곡선의 예다(설명을 위한 가상의 값).
가로축의 사용자당 처리량은 전체 output token throughput을 동시 요청 수 상한으로 나눈 값으로, 요청 하나가 받는 평균 속도를 근사한다.
TTFT와 대기 시간도 들어 있어 1/TPOT와는 다르다.
동시 요청을 늘리면 사용자당 속도는 낮아지고 GPU당 처리량은 높아져, 점이 왼쪽 위로 옮겨 간다.
측정한 점 가운데 두 축 모두에서 자신보다 나은 다른 점이 없는 점들을 이은 선을 Pareto 경계라 한다.

사용자당 100 tokens/s 이상이 조건이라면 FP8의 동시 요청 64(약 106 tokens/s/user에 6,800 tokens/s)를 고르고, BF16으로는 동시 요청 16(약 119에 1,900)까지만 조건을 만족한다.

vLLM의 `vllm bench sweep`은 설정과 부하를 바꿔 가며 재고 이런 Pareto 곡선을 그리는 일을 자동화한다.[^vllm-sweep]
다만 Pareto 경계는 시험한 설정 가운데의 선택지를 보여 줄 뿐, 시험하지 않은 설정까지 포함한 최적을 보장하지는 않는다.

### 4-4. 결과의 진단

BF16과 FP8의 비교를 roofline으로 보면, 동시 요청이 적고 weight 읽기가 주된 병목이라면 FP8이 TPOT를 줄일 것으로 기대할 수 있다.
다만 서버가 BF16 checkpoint를 불러오며 직접 양자화하는 online 모드는 forward마다 activation의 scale을 새로 구한다.
vLLM의 FP8 문서도 이 비용 때문에 지연 개선이 제한된다고 적는다.[^vllm-fp8w8a8]
동시 요청이 많아 행렬곱 연산이 병목이 되면 FP8 Tensor Core로 처리량이 높아질 수 있다.
결과가 예측과 다르면 동시 요청 1의 TPOT로 MBU(model bandwidth utilization)를 계산해 대역폭 지붕에서 얼마나 떨어져 있는지 본다.
이때 읽어야 할 bytes는 그 서버가 실제로 쓰는 저장 정밀도로 센다(online 모드는 출력층 `lm_head`를 양자화하지 않고, KV cache도 BF16으로 남는다).
그래도 원인이 보이지 않으면 엔진의 profiler로 실행 기록(trace)을 떠서 kernel 사이에 GPU가 노는 구간과 attention·행렬곱의 비중을 확인한다.[^vllm-profile]
Profiler는 실행을 느리게 만들 수 있어, 지연과 처리량의 본 측정은 profiler를 끈 상태에서 따로 한다.[^vllm-profile]

양자화와 speculative decoding처럼 여러 기법을 함께 켜면 한 기법이 다른 기법의 병목을 바꿀 수 있어 개별 이득을 곱해 예측할 수 없다.
그래서
둘 다 끈 기준, 하나씩만 켠 경우, 둘 다 켠 경우를 같은 조건에서 따로 잰다.
정확도는 같은 프롬프트에 대한 task 점수로 따로 확인한다.

결과를 보고할 때는 곡선과 함께 측정 조건 전체를 적어,
다른 사람이 같은 조건에서 다시 잴 수 있게 한다.
