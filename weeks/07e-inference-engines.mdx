6·7주차에 본 기법은 따로따로 쓰이는 일이 드물다. 요청 하나가 서버에 들어오면 [06d](/lecture/2026f-advanced-deep-learning/06d-batching-scheduling/)의 scheduler가 batch에 넣고, [06c](/lecture/2026f-advanced-deep-learning/06c-kv-cache-management/)의 KV cache 관리자가 블록을 내주고 prefix cache를 찾고, [07d](/lecture/2026f-advanced-deep-learning/07d-kernel-optimization/)의 kernel이 [07a](/lecture/2026f-advanced-deep-learning/07a-quantization/)의 양자화된 가중치로 계산하고, 경우에 따라 [07c](/lecture/2026f-advanced-deep-learning/07c-speculative-decoding/)의 draft가 다음 토큰을 추측한다. 이 모두를 한 프로그램 안에서 맞물려 돌리는 것이 **inference engine**이다. 이 노트는 대표적인 공개 엔진인 vLLM과 SGLang이 앞의 기법들을 어떻게 묶는지 보고, 엔진의 성능을 재는 절차로 6·7주차를 마무리한다.

전체 지도는 Park 등의 inference engine 서베이[^survey]로 잡는다. 이 서베이는 공개 엔진 25개를 하나씩 살펴보고(서베이 §4), 엔진들이 쓰는 최적화를 batching, 병렬화, 압축, caching, attention 등으로 분류한다(서베이 §5). 절 번호는 arXiv v2 기준이다. 이 노트의 §2–3은 서베이 §4 가운데 vLLM과 SGLang 절에, 그 밖의 엔진을 다루는 §4는 §4의 나머지 절에 대응하고, §5의 측정 절차는 엔진의 공식 문서를 따른다.

## 1. 엔진의 구성

요청 하나가 엔진 안에서 거치는 길은 엔진마다 이름이 달라도 대체로 같다.

1. **API 서버**가 HTTP 요청을 받아 프롬프트를 토큰으로 바꾸고, 생성된 토큰을 다시 글자로 바꿔 스트리밍한다.
2. **Scheduler**가 대기열의 요청 가운데 이번 반복에 넣을 것과 각 요청에서 처리할 토큰 수를 정한다(06d).
3. **KV cache 관리자**가 요청에 블록을 배정하고, 일치하는 prefix의 블록을 찾아 재사용하고, 공간이 모자라면 선점한다(06c).
4. **Model runner**가 batch의 입력 텐서를 준비하고, attention·선형층 kernel과 CUDA graph로 모델을 한 번 실행한다(07d).
5. **Sampler**가 마지막 위치의 logits로 다음 토큰을 고르고, speculative decoding이라면 추측을 검증한다(07c).

[06b §4-1](/lecture/2026f-advanced-deep-learning/06b-roofline/#4-1-batch-크기에-따른-decode-스텝)에서 Llama 3 8B의 decode 한 스텝의 하한이 H100에서 약 5 ms라고 계산했다. 이 짧은 시간 안에 1–3의 작업과 입력 텐서 준비 같은 CPU 쪽 작업까지 끝내야 GPU가 놀지 않는다. 최근 엔진 설계의 상당 부분이 이 CPU 쪽 시간을 GPU 실행 뒤에 숨기는 데 쓰이는 이유다.

## 2. vLLM

### 2-1. V1 구조

vLLM은 [06c §2](/lecture/2026f-advanced-deep-learning/06c-kv-cache-management/#2-pagedattention)의 PagedAttention 논문과 함께 공개된 엔진이다. 2025년의 V1 구조 개편은 기능보다 **CPU 비용**을 겨냥했다.[^vllm-v1] vLLM 팀은 개편의 동기로 H100에서 Llama 8B의 GPU 실행 시간이 스텝당 약 5 ms까지 짧아진 점을 들었다.

V1의 주요 설계는 다음과 같다.[^vllm-v1][^vllm-arch]

- **프로세스 분리.** Scheduler와 모델 실행만 맡는 Engine Core를 별도 프로세스의 반복문으로 두고, 토큰화·글자 변환·스트리밍은 API 서버 프로세스가 맡아 겹쳐 실행한다. `vllm serve -tp=4`라면 API 서버 하나, Engine Core 하나, GPU worker 넷의 프로세스 여섯 개가 뜬다.
- **단계 구분이 없는 scheduler.** Scheduler의 결정은 "요청마다 이번에 처리할 토큰 수"라는 하나의 표에 담기고, 그 합이 반복당 토큰 예산을 넘지 않게 정해진다. 새 요청의 prefill 조각도, 기존 요청의 decode 한 토큰도, speculative decoding으로 검증할 토큰 여러 개도 모두 같은 형식이다. 06d §2-2의 chunked prefill이 따로 켜는 기능이 아니라 scheduler의 기본 동작이 된다.
- **비용 없는 prefix caching.** 06c §3-2의 hash 기반 prefix caching을 다시 구현해, cache 적중률이 0%여도 처리량 손실이 1% 미만이 되게 했고, 그래서 기본으로 켰다.
- **Persistent batch와 CUDA graph.** 스텝마다 입력 텐서를 새로 만들지 않고 바뀐 부분만 고친다. 07d §4의 `torch.compile`과 구간별 CUDA graph를 쓴다.

vLLM 팀은 V1이 V0보다 처리량이 최대 1.7배 높다고 보고하면서, 두 버전이 쓰는 kernel은 거의 같다고 밝혔다.[^vllm-v1] 이득의 대부분이 kernel이 아니라 kernel 바깥의 시간을 줄인 데서 나왔다는 뜻이다.

### 2-2. 주요 설정

vLLM의 설정 손잡이는 앞 노트의 개념과 거의 일대일로 대응한다.[^vllm-args][^vllm-opt]

| 인자 | 기본값 | 무엇을 정하나 | 관련 노트 |
|---|---|---|---|
| `--gpu-memory-utilization` | 0.92 | 엔진이 쓸 GPU 메모리 비율. 가중치와 작업 공간을 뺀 나머지가 KV cache | 06a §4-3 |
| `--max-num-seqs` | GPU에 따라 다름 | 동시에 실행할 요청 수의 상한 | 06b §4, 06d §3 |
| `--max-num-batched-tokens` | GPU와 사용 방식에 따라 다름 | 반복당 토큰 예산. 작으면 ITL, 크면 TTFT와 처리량에 유리 | 06d §2-2 |
| `--enable-prefix-caching` | 지원하는 모델에서 켜짐 | 06c의 prefix 재사용 | 06c §3 |
| `--tensor-parallel-size` | 1 | TP로 나눌 GPU 수 | 06d §4-1 |
| `--kv-cache-dtype` | auto | KV cache의 정밀도(fp8 등) | 06c §4-1 |
| `--quantization` | 모델 설정을 따름 | 가중치 양자화 방식 | 07a |
| `--speculative-config` | 없음 | Draft 방식(EAGLE, n-gram, MTP 등)과 추측 길이 | 07c |
| `--enforce-eager` | False | `torch.compile`과 CUDA graph를 끄고 실행 | 07d §4 |

`--max-num-seqs`와 `--max-num-batched-tokens`의 기본값은 GPU의 메모리 크기와, 서버로 띄우는지 Python에서 직접 부르는지에 따라 달라진다. 실험 결과를 보고할 때는 기본값에 기대지 말고 실제 값을 함께 적는다.

## 3. SGLang

### 3-1. 설계

SGLang은 LLM을 여러 번 부르는 프로그램, 곧 생성·분기·도구 호출이 섞인 구조화된 생성을 빠르게 실행하려는 목표에서 출발했다.[^sglang] 그래서 생성 과정을 짜는 작은 프론트엔드 언어와, 그것을 실행하는 런타임을 함께 설계했다. 런타임의 핵심은 [06c §3-3](/lecture/2026f-advanced-deep-learning/06c-kv-cache-management/#3-3-radixattention)의 RadixAttention이다. 같은 프로그램 안에서 여러 호출이 공통 prefix를 공유하는 일이 잦기 때문이다.

정해진 형식으로 출력을 내게 하는 constrained decoding도 런타임이 맡는다. 출력이 JSON 스키마를 따라야 한다면, 생성 도중 스키마가 허용하는 토큰만 고르도록 매 스텝 마스크를 씌운다. SGLang은 스키마를 유한 상태 기계(FSM)로 바꾼 뒤, 다음에 올 수 있는 문자열이 하나뿐인 구간을 한 단계로 압축했다.[^sglang] 예를 들어 `{"name": "` 같은 고정된 부분은 토큰을 하나씩 decode하지 않고 한 번에 붙이고, 사람 이름처럼 모델이 정해야 하는 부분에서만 decode한다. 06a의 decode 스텝 수가 그만큼 줄어든다.

이후 버전은 vLLM V1과 같은 문제를 다른 방식으로 풀었다. SGLang 팀은 최적화하지 않은 엔진이 시간의 절반까지를 CPU 작업에 쓸 수 있다고 보고, scheduler가 **한 batch 앞서** 다음 batch의 준비를 하게 해 CPU 작업을 GPU 실행과 겹쳤다.[^sglang-v04] 여러 엔진 인스턴스 앞에서 요청을 나눌 때 각 인스턴스의 radix tree를 고려해 prefix가 맞는 곳으로 보내는 cache-aware load balancer, DeepSeek 계열의 MLA를 위한 data parallel attention도 더했다. 같은 글은 load balancer가 cache 적중률을 3.8배 높여 처리량을 최대 1.9배 늘렸다고 보고했다.

### 3-2. 설정과 튜닝

SGLang의 설정도 같은 개념에 대응한다.[^sglang-args] `--mem-fraction-static`은 가중치와 KV cache pool에 줄 GPU 메모리 비율, `--chunked-prefill-size`는 06d §2-2의 prefill 조각 크기(-1이면 끔), `--max-running-requests`는 동시 요청 수의 상한, `--schedule-policy`는 06d §3-1의 실행 순서(기본 `fcfs`, prefix가 긴 순서인 `lpm` 등), `--tp-size`는 TP의 GPU 수, `--attention-backend`는 07d의 attention kernel(FlashInfer, FlashAttention, Triton 등), `--speculative-algorithm`은 07c의 draft 방식이다.

SGLang의 튜닝 문서는 처리량을 높이려면 **batch를 크게 만드는 것이 가장 중요하다**고 요약한다.[^sglang-tune] 06b의 roofline이 말하는 것과 같다. 문서는 서버 로그에서 KV cache 사용률이 0.9를 넘고 대기 요청이 쌓여 있으면 batch가 충분히 큰 상태라고 보고, 메모리가 모자라면 prefill에서는 조각 크기를, decode에서는 동시 요청 수를 줄이라고 권한다. `lpm` 정책은 cache 적중을 늘리는 대신 scheduling 비용이 더 든다는 점도 적는다.

## 4. 다른 엔진

vLLM과 SGLang 말고도 목적이 다른 엔진이 여럿 있다.[^survey] NVIDIA의 TensorRT-LLM은 NVIDIA GPU에 맞춘 attention·행렬곱·MoE kernel과 prefill/decode 분리, 큰 규모의 expert parallelism, speculative decoding을 갖춘 라이브러리다.[^trtllm] llama.cpp는 의존성 없는 C/C++ 구현으로, 개인용 컴퓨터와 다양한 하드웨어에서 양자화된 모델을 돌리는 데 널리 쓰인다.[^llamacpp] LMDeploy는 TurboMind라는 자체 엔진으로 압축과 서빙을 함께 제공한다.[^lmdeploy] 한때 널리 쓰인 Hugging Face의 TGI는 현재 유지보수 모드이며, 저장소 스스로 vLLM, SGLang, llama.cpp 등을 권한다.[^tgi] 엔진을 고를 때는 지원하는 모델과 하드웨어, 필요한 기능(양자화 형식, speculative decoding, 구조화된 출력)을 먼저 확인하고, 그 조건에서 §5의 방법으로 직접 재 본다.

## 5. 성능 측정

### 5-1. 측정 조건

엔진이나 설정을 비교할 때는 결과에 영향을 주는 조건을 모두 고정한다. 모델과 그 버전, GPU의 종류와 수, 가중치와 KV cache의 정밀도, 입력과 출력 길이의 분포, sampling 설정이 같아야 한다. 출력 길이를 고정하려면 종료 토큰을 무시하고 정해진 길이까지 생성하게 한다.[^nvidia-bench] 첫 측정은 warmup으로 버리고, prefix caching이 있는 엔진에서는 cache가 비어 있는 상태와 채워진 상태를 구분한다. vLLM과 SGLang 모두 측정 사이에 prefix cache를 비우는 방법을 제공한다.[^sglang-bench] 같은 데이터라도 [06a §3-1](/lecture/2026f-advanced-deep-learning/06a-llm-inference/#3-1-요청-하나의-지연)에서 보았듯 도구마다 지표의 정의가 조금씩 다르므로, 지표 이름보다 정의를 확인한다. NVIDIA의 측정 안내는 ITL을 TPOT와 같은 값으로 정의하지만, vLLM은 둘을 따로 보고한다.[^nvidia-bench][^vllm-bench]

### 5-2. 부하를 걸고 곡선 그리기

서빙 성능은 숫자 하나가 아니라 **부하에 따른 곡선**이다. 요청을 적게 보내면 지연은 짧고 처리량은 낮으며, 많이 보낼수록 처리량은 오르다가 batch가 상한에 닿으면 포화하고 지연만 계속 늘어난다. 부하를 거는 방법은 두 가지다. 초당 요청 수를 정해 Poisson 과정으로 보내는 request rate 방식과, 동시에 처리 중인 요청 수를 고정하는 concurrency 방식이다. vLLM의 `vllm bench serve`는 둘 다 지원하고, `--burstiness`로 요청이 몰려 오는 정도도 바꿀 수 있다.[^vllm-bench] NVIDIA의 안내는 요청률을 고정하면 처리하지 못한 요청이 끝없이 쌓일 수 있다며 concurrency 방식을 권하고, 1부터 엔진의 최대 batch를 조금 넘는 값까지 바꿔 가며 재라고 한다.[^nvidia-bench]

[06a §3-3](/lecture/2026f-advanced-deep-learning/06a-llm-inference/#3-3-slo와-goodput)의 goodput도 직접 잴 수 있다. `vllm bench serve`의 `--goodput` 옵션에 TTFT와 TPOT의 목표치를 밀리초로 주면, 목표를 지킨 요청만 센 처리량을 함께 보고한다.[^vllm-bench]

<Callout type="example">
기말 프로젝트에서 Llama 3.1 8B를 H100 한 대로 서빙한다고 하자. BF16과 FP8 가중치 가운데 무엇이 나은지 알고 싶다면, 같은 엔진 버전과 설정으로 서버를 두 번 띄우고 각각 다음처럼 잰다.

```bash
vllm bench serve --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --num-prompts 1000 --max-concurrency 64 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:1000 tpot:50
```

`--max-concurrency`를 1, 4, 16, 64, 256으로 바꿔 가며 반복하면 동시 요청 수에 따른 곡선이 나온다. 가로축에 사용자 한 명이 받는 초당 토큰 수(1/TPOT), 세로축에 GPU 한 대의 output token throughput을 두고 두 정밀도의 곡선을 겹쳐 그린다. 06b에 따르면 동시 요청이 적을 때는 가중치 읽기가 병목이므로 FP8의 이득이 TPOT에서 크게 보이고, 동시 요청이 많을 때는 FP8 Tensor Core의 연산 속도와 줄어든 메모리로 커진 batch가 처리량을 올릴 것이다. 측정이 이 예측과 다르다면 MBU와 MFU를 계산해 어느 쪽 지붕 아래에서 멀어져 있는지부터 본다. 정확도는 같은 프롬프트에 대한 과제 점수로 따로 확인한다.
</Callout>

vLLM은 이런 반복을 자동화하는 `vllm bench sweep`도 제공한다. 서버 설정의 조합마다 측정을 돌리고, 부하 수준을 바꿔 지연과 처리량의 맞교환을 찾으며, 사용자당 처리량과 GPU당 처리량으로 Pareto 곡선을 그린다.[^vllm-sweep] 결과를 보고할 때는 곡선과 함께 측정 조건 전체를 적어, 다른 사람이 같은 조건에서 다시 잴 수 있게 한다.

## 6. 6·7주차 정리

두 주의 내용을 한 표로 모으면 다음과 같다. 각 기법은 06b의 roofline에서 한 스텝의 bytes, FLOPs, 순차 스텝 수, 실행 효율 가운데 무엇을 줄이느냐로 자리가 정해지고, 엔진에서는 대개 설정 하나로 켜고 끈다.

| 기법 | 줄이는 비용 | 노트 | vLLM에서 |
|---|---|---|---|
| KV head 공유(GQA·MLA) | KV cache bytes, decode attention의 읽기 | 3주차 03b, 06b §3-2 | 모델 구조 |
| Continuous batching, chunked prefill | 대기 시간, 가중치 읽기의 반복 | 06d | 기본 동작, `--max-num-batched-tokens` |
| PagedAttention | KV cache 공간의 낭비 | 06c §2 | 기본 동작 |
| Prefix caching | 반복되는 prefill 계산과 저장 | 06c §3 | `--enable-prefix-caching` |
| KV cache 양자화 | KV cache bytes | 06c §4-1 | `--kv-cache-dtype` |
| Prefill/decode 분리 | 두 단계의 간섭 | 06d §2-3 | disaggregated prefill(실험 기능) |
| 가중치 양자화 | 가중치 bytes, 저정밀 연산 | 07a | `--quantization` |
| Pruning, distillation | 파라미터 수 | 07b | 압축된 모델을 불러옴 |
| Speculative decoding | 순차 decode 스텝 수 | 07c | `--speculative-config` |
| Kernel, CUDA graph | 같은 계산의 실행 시간 | 07d | attention backend, `--enforce-eager` |

Inference는 학습이 끝난 뒤 모델을 쓰는 단계이지만, 06a §1에서 보았듯 그 비용이 모델의 크기와 학습 방식까지 거꾸로 정하기 시작했다. 어떤 기법이 효과가 있는지는 배포 환경의 메모리, batch 크기, 문맥 길이, 지연 목표에 따라 달라진다. 그래서 두 주 동안 반복한 순서, 곧 roofline으로 병목을 계산하고, 그 병목을 줄이는 기법을 고르고, 같은 조건에서 곡선으로 재는 순서가 이 주제의 핵심이다.
