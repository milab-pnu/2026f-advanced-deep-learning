앞 주차와 이번 주에 본 기법은 따로따로 쓰이는 일이 드물다.
요청 하나가 서버에 들어오면 scheduler가 batch에 넣고,
KV(key-value) cache 관리자가 블록을 내주고 prefix cache를 찾고,
kernel이 필요하면 양자화(quantization)한 가중치로 계산하고, 경우에 따라 draft가 다음 토큰을 추측한다.
이 모두를 한 프로그램 안에서 맞물려 돌리는 것이 **inference engine**이다.
이 노트는 대표적인 공개 엔진인 vLLM과 SGLang이 앞의 기법들을 어떻게 묶는지 보고,
엔진의 성능을 재는 절차로 inference 주제를 마무리한다.

Park 등은 오픈소스와 상용 엔진 25개를 살펴보고, 엔진들이 쓰는 최적화를 batching, 병렬화, 압축, caching, attention 등으로 분류했다.[^survey]

## 1. 엔진의 구성

요청 하나가 엔진 안에서 거치는 길은 엔진마다 이름이 달라도 대체로 같다.

1. <strong>API(application programming interface) 서버</strong>가 HTTP(hypertext transfer protocol) 요청을 받아 프롬프트를 토큰으로 바꾸고,
   생성된 토큰을 다시 글자로 바꿔 스트리밍한다.
2. **Scheduler**가 대기열의 요청 가운데 이번 반복에 넣을 것과 각 요청에서 처리할 토큰 수를 정하고,
   블록이 모자라면 실행 중인 요청 하나를 골라 선점(preemption)해 블록을 비운다.
3. **KV cache 관리자**가 요청에 블록을 배정·해제하고, 일치하는 prefix의 블록을 찾아 재사용한다.
4. **Model runner**가 batch의 입력 텐서를 준비하고,
   attention·선형층 kernel과 CUDA graph로 모델을 한 번 실행한다.
5. **Sampler**가 일반 decode에서는 마지막 위치의 logits로 다음 토큰을 고르고,
   speculative decoding에서는 추측한 토큰 위치들의 logits로 각 토큰의 수락 여부를 정한다.

앞 주차 roofline의 단순화한 모형에서 Llama 3 8B의 decode 한 스텝 하한은 BF16(bfloat16) 가중치와 KV cache, H100 SXM, batch 1, 문맥 2,048토큰에서 약 4.9 ms였다.
실제 GPU(graphics processing unit) 실행도 이렇게 수 ms에 끝나므로,
다음 스텝의 scheduling과 입력 텐서 준비 같은 CPU(central processing unit) 쪽 작업이 늦어지면 GPU에 빈 구간이 생긴다.
최근 엔진 설계의 상당 부분이 이 CPU 쪽 시간을 GPU 실행과 겹치는 데 쓰이는 이유다.

## 2. vLLM

### 2-1. V1 구조

vLLM은 PagedAttention 논문과 함께 공개된 엔진이다.
2025년의 V1 구조 개편은 코드 단순화, 최적화 통합과 함께 **CPU overhead를 거의 없애는 것**을 주요 목표로 삼았다.
GPU 실행 시간이 스텝당 수 ms로 짧아지자 그 사이의 CPU 작업이 드러났기 때문이다.[^vllm-v1]

<Figure src="https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/docs/assets/design/arch_overview/v1_process_architecture_tp4.png" alt="vLLM V1의 프로세스 구조(GPU 4대, TP=4). 왼쪽의 API Server가 HTTP 요청을 받아 입력 처리, 토큰화, 스트리밍을 맡고, ZMQ로 가운데의 Engine Core와 양방향으로 통신한다. Engine Core는 scheduler와 KV cache 관리자를 맡는다. Engine Core에서 오른쪽의 GPU Worker 0–3 네 개로 화살표가 나가며, 각 worker는 GPU 하나에서 모델 실행(forward)을 맡는다. 아래에 프로세스가 모두 6개(API Server 1, Engine Core 1, GPU Worker 4)라고 적혀 있다." caption="vLLM V1의 프로세스 구조. 토큰화와 스트리밍(API Server), scheduling과 KV cache 관리(Engine Core), 모델 실행(GPU Worker)이 서로 다른 프로세스에서 돈다." source="vLLM Project (v0.30.0), Architecture Overview 문서 · Apache-2.0" />

V1의 주요 설계는 다음과 같다.[^vllm-v1][^vllm-arch]

- **프로세스 분리.** Scheduling과 GPU worker의 모델 실행 조율만 맡는 Engine Core를 별도 프로세스의 반복문으로 두고,
  토큰화·글자 변환·스트리밍은 API 서버 프로세스가 맡아 겹쳐 실행한다.
  GPU 네 대에 TP(tensor parallelism)로 나눠 `vllm serve -tp=4`로 띄우면 API 서버 하나, Engine Core 하나, GPU worker 넷의 프로세스 여섯 개가 뜬다.
- **단계 구분이 없는 scheduler.** Scheduler의 결정은 "요청마다 이번에 처리할 토큰 수"라는 하나의 표에 담기고,
  그 합이 반복당 토큰 예산을 넘지 않게 정해진다.
  새 요청의 prefill 조각도, 기존 요청의 decode 한 토큰도,
  speculative decoding으로 검증할 토큰 여러 개도 모두 같은 형식이다.
  Chunked prefill이 따로 켜는 기능이 아니라 scheduler의 기본 동작이 된다.
- **부담이 거의 없는 prefix caching.** Hash 기반 prefix caching을 다시 구현해,
  vLLM 팀의 측정에서 cache 적중률이 0%여도 처리량(throughput) 감소가 1% 미만이었고, 그래서 기본으로 켰다.
- **Persistent batch와 CUDA graph.** 스텝마다 입력 텐서를 새로 만들지 않고 바뀐 부분만 고친다.
  `torch.compile`과 구간별 CUDA graph를 쓴다.

vLLM 팀은 V1이 여러 스텝을 한 번에 scheduling하는 multi-step scheduling을 끈 V0보다 처리량이 최대 1.7배 높다고 보고하면서,
두 버전이 쓰는 kernel은 거의 같다고 밝혔다.[^vllm-v1]
이득의 대부분이 kernel이 아니라 kernel 바깥의 시간을 줄인 데서 나왔다는 뜻이다.

### 2-2. 주요 설정

vLLM의 설정 인자는 지금까지 본 개념과 거의 일대일로 대응한다.[^vllm-args][^vllm-opt]

| 인자 | 기본값 | 무엇을 정하나 |
|---|---|---|
| `--gpu-memory-utilization` | 0.92 | 엔진이 쓸 GPU 메모리 비율. 가중치와 작업 공간을 뺀 나머지가 KV cache |
| `--max-num-seqs` | GPU에 따라 다름 | 동시에 실행할 요청 수의 상한 |
| `--max-num-batched-tokens` | GPU와 사용 방식에 따라 다름 | 반복당 토큰 예산. 작으면 ITL(inter-token latency), 크면 TTFT(time to first token)와 처리량에 유리 |
| `--enable-prefix-caching` | 지원하는 모델에서 켜짐 | Prefix 재사용 |
| `--tensor-parallel-size` | 1 | TP로 나눌 GPU 수 |
| `--kv-cache-dtype` | auto | KV cache의 정밀도(`fp8` 등) |
| `--quantization` | 모델 설정을 따름 | 양자화 방식(가중치, 방식에 따라 activation도) |
| `--speculative-config` | 없음 | Draft 방식(EAGLE, n-gram, MTP(multi-token prediction) 등)과 추측 길이 |
| `--enforce-eager` | False | `torch.compile`과 CUDA graph를 끄고 실행 |

`--max-num-seqs`의 기본값은 GPU의 종류와 메모리 크기, `--performance-mode`에 따라,
`--max-num-batched-tokens`의 기본값은 그에 더해 서버로 띄우는지 Python에서 직접 부르는지에 따라 달라진다.
실험 결과를 보고할 때는 기본값에 기대지 말고 실제 값을 함께 적는다.

설정을 바꾼 효과는 서버가 내보내는 지표로 확인한다.
앞 주차에 본 서버 내부 지표는 vLLM에서 Prometheus 형식으로 나온다.[^vllm-metrics]
KV cache 사용률은 `vllm:kv_cache_usage_perc`, prefix cache 적중률은 조회한 토큰 수와 적중한 토큰 수(`vllm:prefix_cache_queries`, `vllm:prefix_cache_hits`),
실행·대기 요청 수는 `vllm:num_requests_running`, `vllm:num_requests_waiting`으로 본다.

## 3. SGLang

### 3-1. 설계

SGLang은 LLM(large language model)을 여러 번 부르는 프로그램,
곧 생성·분기·도구 호출이 섞인 구조화된 생성을 빠르게 실행하려는 목표에서 출발했다.[^sglang]
그래서 생성 과정을 짜는 작은 프론트엔드 언어와, 그것을 실행하는 런타임을 함께 설계했다.
런타임의 핵심은 RadixAttention이다.
같은 프로그램 안에서 여러 호출이 공통 prefix를 공유하는 일이 잦기 때문이다.

정해진 형식으로 출력을 내게 하는 constrained decoding도 런타임이 맡는다.
출력이 JSON(JavaScript Object Notation) 스키마를 따라야 한다면,
생성 도중 스키마가 허용하는 토큰만 고르도록 매 스텝 마스크를 씌운다.
SGLang 논문은 스키마 같은 형식을 정규식(regular expression)으로 나타내고 이를 유한 상태 기계(finite state machine, FSM)로 바꾼 뒤,
다음에 올 수 있는 문자열이 하나뿐인 구간을 한 단계로 압축했다.[^sglang]
예를 들어 `{"name": "` 같은 고정된 부분은 토큰을 하나씩 decode하지 않고 forward 한 번에 여러 토큰을 함께 처리하고,
사람 이름처럼 모델이 정해야 하는 부분에서만 한 토큰씩 decode한다.
고정된 부분도 KV cache는 계산해야 하지만 순차 decode 스텝 수가 그만큼 줄어든다.

이후 v0.4는 vLLM V1과 같은 문제를 다른 방식으로 풀었다.
SGLang 팀은 최적화하지 않은 엔진이 시간의 절반까지를 CPU 작업에 쓸 수 있다고 보고,
scheduler가 **한 batch 앞서** 다음 batch의 준비를 하게 해 CPU 작업을 GPU 실행과 겹쳤다.[^sglang-v04]
다음 batch에 들어갈 토큰은 아직 GPU에서 계산 중이므로,
그 자리를 미리 표시해 둔 future token으로 준비를 진행하고 CUDA event로 실행 순서를 맞춘다.

같은 버전은 엔진을 여러 개 띄울 때 앞에서 본 cache-aware routing을 cache-aware load balancer로 구현했다.
엔진 인스턴스마다 radix tree가 따로 있으므로, 요청을 돌아가며 나누면 같은 prefix를 가진 요청이 여러 인스턴스에 흩어져 cache 적중률이 떨어진다.
이 load balancer는 각 인스턴스의 radix tree를 근사한 나무를 유지하며 prefix가 가장 많이 맞을 인스턴스로 요청을 보낸다.
같은 크기의 긴 공통 prefix 그룹이 여럿인 workload에서 이 방식은 v0.3보다 cache 적중률을 3.8배 높여 처리량을 최대 1.9배 늘렸다.[^sglang-v04]
앞에서 본 것처럼 DeepSeek 계열의 MLA(multi-head latent attention)는 attention을 TP로 나누면 latent KV cache가 GPU마다 복제된다.
Data parallel attention은 attention 부분만 GPU마다 다른 요청을 맡는 data parallelism으로 돌려 이 복제를 없애고, 그만큼 batch를 키운다.

### 3-2. 설정과 튜닝

SGLang의 설정도 같은 개념에 대응한다.[^sglang-args]
`--mem-fraction-static`은 가중치와 KV cache pool에 줄 GPU 메모리 비율,
`--chunked-prefill-size`는 chunked prefill의 조각 크기(-1이면 끔),
`--max-running-requests`는 동시 요청 수의 상한,
`--schedule-policy`는 요청의 실행 순서,
`--tp-size`는 TP의 GPU 수,
`--attention-backend`는 attention kernel(FlashInfer, FlashAttention, Triton 등),
`--speculative-algorithm`은 speculative decoding의 draft 방식이다.
실행 순서의 기본값은 도착한 순서대로인 `fcfs`(first come, first served)이고,
`lpm`(longest prefix match)을 고르면 앞에서 본 cache-aware scheduling처럼 cache와 일치하는 prefix가 긴 요청부터 처리한다.
다만 대기 요청이 128개를 넘으면 prefix 비교와 정렬 비용을 아끼려고 `fcfs`로 돌아가고, prefix cache를 끈 경우에도 `fcfs`를 쓴다.[^sglang-policy]

SGLang의 튜닝 문서는 offline batch inference에서 처리량을 높이려면 **batch를 크게 만드는 것이 가장 중요하다**고 요약한다.[^sglang-tune]
작은 batch에서는 가중치 읽기가 병목이라는 앞 주차 roofline 분석과 같은 결론이다.
문서는 서버 로그의 KV cache 사용률이 0.9를 넘으면 메모리를 잘 쓰고 있다고 보고,
대기 요청이 쌓였는데도 0.9 아래에 머물면 서버가 새 요청을 너무 보수적으로 받아들이는 것이라고 본다.
메모리가 모자라면 prefill에서는 조각 크기를, decode에서는 동시 요청 수를 줄이라고 권한다.

## 4. 다른 엔진

vLLM과 SGLang 말고도 목적이 다른 엔진이 여럿 있다.[^survey]
NVIDIA의 TensorRT-LLM은 NVIDIA GPU에 맞춘 attention·행렬곱·MoE(mixture of experts) kernel과 prefill/decode 분리,
큰 규모의 expert parallelism, speculative decoding을 갖춘 라이브러리다.[^trtllm]
llama.cpp는 의존성 없는 C/C++ 구현으로,
개인용 컴퓨터와 다양한 하드웨어에서 양자화된 모델을 돌리는 데 널리 쓰인다.[^llamacpp]
LMDeploy는 TurboMind라는 자체 엔진으로 압축과 서빙을 함께 제공한다.[^lmdeploy]
한때 널리 쓰인 Hugging Face의 TGI(Text Generation Inference)는 현재 유지보수 모드이며,
저장소 스스로 vLLM, SGLang, llama.cpp 등을 권한다.[^tgi]
엔진을 고를 때는 지원하는 모델과 하드웨어, 필요한 기능(양자화 형식, speculative decoding, 구조화된 출력)을 먼저 확인하고, 그 조건에서 직접 재 본다.

## 5. 성능 측정

### 5-1. 측정 조건

엔진이나 설정을 비교할 때는 결과에 영향을 주는 조건을 모두 고정한다.
모델과 그 버전, GPU의 종류와 수, 가중치와 KV cache의 정밀도, 입력과 출력 길이의 분포,
sampling 설정이 같아야 한다.
출력 길이를 고정하려면 종료 토큰을 무시하고 정해진 길이까지 생성하게 한다.[^nvidia-bench]
첫 측정은 warmup으로 버리고,
prefix caching이 있는 엔진에서는 cache가 비어 있는 상태와 채워진 상태를 구분한다.
vLLM과 SGLang 모두 측정 사이에 prefix cache를 비우는 방법을 제공한다.[^sglang-bench]
같은 데이터라도 도구마다 지표의 정의가 조금씩 다르므로,
지표 이름보다 정의를 확인한다.
NVIDIA의 측정 안내는 ITL을 TPOT(time per output token)와 같은 값으로 정의하지만,
vLLM은 둘을 따로 보고한다.[^nvidia-bench][^vllm-bench]

### 5-2. 부하와 성능 곡선

서빙 성능은 숫자 하나가 아니라 **부하에 따른 곡선**이다.
요청을 적게 보내면 지연(latency)은 짧고 처리량은 낮으며,
많이 보낼수록 처리량은 오르다가 batch 상한이나 메모리·연산의 한계에 닿으면 포화하고 지연만 계속 늘어난다.
부하를 거는 방법은 두 가지다.
초당 요청 수를 정해 Poisson 과정으로 보내는 request rate 방식과,
동시에 처리 중인 요청 수를 고정하는 concurrency 방식이다.
vLLM의 `vllm bench serve`는 둘 다 지원하고,
`--burstiness`로 요청이 몰려 오는 정도도 바꿀 수 있다.[^vllm-bench]
NVIDIA의 안내는 요청률을 고정하면 처리하지 못한 요청이 끝없이 쌓일 수 있다며 concurrency 방식을 권하고,
1부터 엔진의 최대 batch를 조금 넘는 값까지 바꿔 가며 재라고 한다.[^nvidia-bench]

두 방식은 답하는 질문이 다르다.
Concurrency를 고정하면 응답이 느려질 때 새 요청도 늦게 들어가므로 서버가 감당할 수 있는 만큼만 부하가 걸린다.
그래서 동시 요청 수에 따른 처리량과 지연의 곡선, 곧 시스템의 용량을 보기에 좋다.
요청률을 고정하면 서버가 느려져도 요청이 계속 들어와 대기열이 쌓이므로,
실제 사용자가 일정한 속도로 몰려올 때 SLO(service-level objective)를 지키는지 보기에 좋다.

Goodput을 잴 때도 정의를 구분한다.
`vllm bench serve`의 `--goodput` 옵션에 TTFT와 TPOT의 목표치를 밀리초로 주면,
그 부하에서 목표를 모두 지킨 요청 수를 측정 시간으로 나눈 값을 보고한다.[^vllm-bench-src]
앞에서 본 DistServe의 goodput은 SLO 달성률 목표(예: 90%)를 지키면서 GPU 한 대가 감당할 수 있는 **최대 요청률**이었다.
이 값을 얻으려면 요청률을 바꿔 가며 여러 번 재고, 달성률이 목표 아래로 떨어지기 직전의 요청률을 찾아야 한다.

<Callout type="example">
기말 프로젝트에서 Llama 3.1 8B를 H100 한 대로 서빙하며 BF16과 FP8(8-bit floating point)을 비교한다고 하자.
같은 엔진 버전과 설정으로 서버를 두 번 띄우되,
앞선 측정의 prefix cache가 결과에 섞이지 않게 두 서버 모두 `--no-enable-prefix-caching`으로 시작한다.
FP8 서버는 미리 FP8로 양자화한 checkpoint를 불러오거나,
BF16 checkpoint를 불러오면서 양자화한다(vLLM v0.31에서는 `--quantization fp8_per_tensor`).
어느 방식인지와 엔진 버전, KV cache 정밀도와 batch 관련 설정을 결과와 함께 적고,
미리 양자화한 checkpoint라면 아래 `--model`도 그 이름으로 바꾼다.
두 서버에 각각 다음처럼 부하를 건다.

```bash
vllm bench serve --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --ignore-eos \
  --num-prompts 1000 --max-concurrency 64 --num-warmups 10 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:1000 tpot:50
```

`--ignore-eos`는 종료 토큰(EOS, end of sequence)이 나와도 정해진 길이까지 생성하게 해 두 서버의 출력 길이를 맞추고,
`--num-warmups`는 측정 전에 warmup 요청을 보낸다(기본값 0).
`e2el`은 요청 하나의 전체 지연(end-to-end latency)이다.
이 random 입력은 길이를 통제한 비교용이므로,
prefix 재사용이나 draft 수락처럼 내용에 좌우되는 효과는 대표 프롬프트와 실제 입출력 길이 분포로 다시 잰다.
`--max-concurrency`를 1, 4, 16, 64, 256으로 바꿔 가며 반복하고,
가로축에 동시 요청 수로 나눈 처리량(output token throughput ÷ 동시 요청 수),
세로축에 GPU 한 대의 output token throughput을 두어 두 정밀도의 곡선을 겹쳐 그린다.
동시 요청 64에서 초당 6,400토큰이 나왔다면 그 점은 (100, 6,400)이다(교육용 수치).
가로축 값에는 TTFT와 대기 시간이 섞여 있어 1/TPOT와 다르므로, decode 중에 사용자가 느끼는 속도는 TPOT로 따로 본다.

Roofline으로 보면 동시 요청이 적을 때는 가중치 읽기가 병목이라 FP8이 TPOT를 줄일 것으로 기대한다.
다만 불러오면서 양자화하는 방식은 activation의 scale을 매 forward마다 구하므로 지연 개선이 제한된다.[^vllm-fp8w8a8]
동시 요청이 많아 행렬곱 연산이 병목이 되면 FP8 Tensor Core로 처리량이 높아질 수 있다.
결과가 예측과 다르면 동시 요청 1의 TPOT로 MBU(model bandwidth utilization)를 계산해 대역폭 지붕에서 얼마나 떨어져 있는지 보고,
그래도 원인이 보이지 않으면 엔진의 profiler로 실행 기록(trace)을 떠서 kernel 사이에 GPU가 노는 구간과 attention·행렬곱의 비중을 확인한다.[^vllm-profile]
양자화와 speculative decoding처럼 여러 기법을 함께 켤 때는 개별 이득을 단순히 곱해 예측할 수 없으므로,
각각 켠 경우와 함께 켠 경우를 같은 조건에서 따로 잰다.
정확도는 같은 프롬프트에 대한 task 점수로 따로 확인한다.
</Callout>

vLLM은 이런 반복을 자동화하는 `vllm bench sweep`도 제공한다.
서버 설정의 조합마다 측정을 돌리고, 부하 수준을 바꿔 지연과 처리량의 맞교환을 찾으며,
위와 같은 정의의 동시 요청당 처리량과 GPU당 처리량으로 Pareto 곡선을 그린다.[^vllm-sweep]
결과를 보고할 때는 곡선과 함께 측정 조건 전체를 적어,
다른 사람이 같은 조건에서 다시 잴 수 있게 한다.
