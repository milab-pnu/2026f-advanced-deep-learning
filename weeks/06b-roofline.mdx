H100에서 Llama 3 8B의 decode 한 스텝은 가중치를 읽는 데 약 4.8 ms, 계산하는 데 약 0.016 ms가 든다.
같은 가중치로 토큰 약 300개를 함께 처리해야 두 시간이 같아진다.
이런 어림을 모든 연산에 쓸 수 있게 일반화한 것이 **roofline model**이다.
연산 하나가 GPU(graphics processing unit)의 연산 속도와 메모리 대역폭 가운데 어느 쪽에 막히는지를 그림 한 장으로 보여 준다.

Yuan 등의 서베이는 LLM(large language model) inference의 기법들을 이 모형 위에서 분석해 정리했다.[^survey]
이 노트는 같은 분석을 Llama 3 8B와 H100 SXM으로 해 보고,
prefill과 decode의 두 병목을 TTFT(time to first token)와 TPOT(time per output token)의 하한, 처리량(throughput)의 상한이라는 숫자로 바꾼다.

## 1. 연산과 데이터 이동

### 1-1. 연산 속도와 메모리 대역폭

GPU 메모리는 두 층으로 나눌 수 있다.
칩 바깥의 크고 느린 HBM(high-bandwidth memory)과,
연산 장치 곁의 작고 빠른 SRAM(static random-access memory)이다.
가중치와 KV(key-value) cache는 HBM에 있고, 계산하려면 연산 장치 쪽으로 읽어 와야 한다.
그래서 GPU가 낼 수 있는 속도에는 두 가지 상한이 있다.

- **최대 연산 속도**(peak FLOP/s): 초당 할 수 있는 부동소수점 연산(floating-point operation, FLOP) 수의 상한이다.
  곱셈과 덧셈을 각각 1 FLOP으로 센다.
  H100 SXM의 BF16(bfloat16) Tensor Core는 dense 연산 기준 약 989 TFLOP/s다.[^h100]<Sidenote>NVIDIA의 사양표가 적는 1,979 TFLOP/s는 structured sparsity(2:4처럼 정해진 비율로 0을 두는 sparsity)를 썼을 때의 값이다. NVIDIA가 Hopper 구조를 소개한 글은 dense 값과 sparsity 값을 1:2로 함께 적으므로, dense 연산은 그 절반으로 계산한다.[^hopper]</Sidenote>
- **메모리 대역폭**(memory bandwidth): 초당 HBM에서 읽고 쓸 수 있는 bytes의 상한이다.
  H100 SXM은 3.35 TB/s다.[^h100]

두 숫자의 비는 $989\times10^{12}/(3.35\times10^{12})\approx295$다.
HBM에서 1 byte를 읽어 오는 동안 연산 장치는 약 295 FLOP을 할 수 있다는 뜻이다.
읽어 온 1 byte당 계산이 이보다 적으면 대역폭을 다 써도 연산 장치가 데이터를 기다리는 시간이 생겨 peak FLOP/s를 다 쓰지 못한다.

### 1-2. Arithmetic intensity

연산이 이 두 한계 가운데 어디에 걸리는지는 그 연산의 **arithmetic intensity**로 정해진다.
수행한 FLOPs를 HBM과 주고받은 bytes로 나눈 값이다.[^survey][^roofline]

$$
I=\frac{\text{FLOPs}}{\text{HBM과 주고받은 bytes}}\quad[\text{FLOP/byte}]
$$

두 가지 극단을 보자.
BF16 벡터 두 개를 더하는 $z=x+y$는 원소 하나마다 덧셈 한 번을 하는 동안 6 bytes(입력 2 bytes씩 두 개, 출력 2 bytes)를 옮긴다.
$I=1/6\approx0.17$이다.
반대로 $m\times m$ 행렬 두 개의 곱은 $2m^3$ FLOPs다.
입력 두 개와 출력 하나를 한 번씩만 옮긴다면 bytes는 $3\cdot2m^2$이므로 $I=m/3$이고, $m=4096$이면 1,365다.
같은 데이터를 여러 번 재사용하는 연산일수록 intensity를 높일 여지가 크다.
다만 그 재사용이 칩 안의 SRAM 같은 곳에서 일어나 HBM을 다시 읽지 않아야 intensity가 실제로 높아진다.

## 2. Roofline model

### 2-1. 두 지붕과 ridge point

Williams 등은 어떤 연산이 낼 수 있는 성능의 상한을 다음처럼 썼다.[^roofline]

$$
\text{달성 가능한 FLOP/s}=\min\bigl(\text{peak FLOP/s},\ \text{대역폭}\times I\bigr)
$$

Intensity가 낮으면 대역폭이 데이터를 대 주는 속도만큼만 계산할 수 있어 성능의 상한이 $I$에 비례하고,
intensity가 높으면 peak FLOP/s가 상한이 된다.
가로축과 세로축을 모두 로그로 그리면 비스듬한 지붕과 평평한 지붕이 만나는 모양이 된다.
Roofline이라는 이름이 여기서 왔다.
두 지붕이 만나는 점이 **ridge point**이고, 그 intensity가 앞에서 구한 비 295 FLOP/byte다.
Ridge point보다 왼쪽에 있는 연산은 **memory-bound**, 오른쪽에 있는 연산은 **compute-bound**다.

### 2-2. 시간의 하한

Roofline을 시간으로 바꾸면 계산이 더 쉬워진다.
연산 하나의 계산량이 $F$ FLOPs, 데이터 이동량이 $B$ bytes라면,
계산에는 적어도 $F/\text{peak}$, 데이터 이동에는 적어도 $B/\text{대역폭}$이 걸린다.
앞의 것은 computational cost를, 뒤의 것은 memory access cost를 시간으로 나타낸 값이다.
둘이 완전히 겹쳐도 전체 시간은 둘 중 큰 쪽보다 짧을 수 없다.

$$
t\ \ge\ \max\!\left(\frac{F}{\text{peak FLOP/s}},\ \frac{B}{\text{대역폭}}\right)
$$

모델의 한 스텝에서는 선형층과 attention 같은 연산이 차례로 실행된다.
그래서 연산마다 이 하한을 구해 더한 $\sum_i\max(F_i/\text{peak},\,B_i/\text{대역폭})$를 스텝 시간의 하한으로 쓴다.

실제 시간은 이 하한보다 길다.
GPU에서 연산 하나를 실행하는 프로그램을 kernel이라 한다.
Kernel은 한 연산 안에서도 계산과 데이터 이동을 완전히 겹치기 어렵고, 실제로 내는 대역폭과 FLOP/s도 사양값에 못 미친다.
CPU(central processing unit)에서 kernel을 띄우는 비용과 여러 GPU 사이의 통신도 이 식에는 없다.
그러므로 이 노트가 사양값 3.35 TB/s와 989 TFLOP/s로 구하는 시간은 이상적인 하한이고, 처리량은 이상적인 상한이다.

그래도 두 항 가운데 어느 쪽이 큰지가 하한을 낮추려면 무엇을 줄여야 하는지 알려 준다.
계산 항이 크면 FLOPs를 줄이거나 더 빠른 연산 형식을 쓰고,
데이터 항이 크면 한 번 읽은 데이터를 더 많이 재사용하는 식으로 옮기는 bytes를 줄인다.

## 3. Roofline 위의 Transformer 연산

이제 그림에 찍은 Llama 3 8B의 점들이 어디서 왔는지 계산해 보자.
이 모델은 32층이고, 모델 차원 $d=4096$, FFN(feed-forward network) 폭 14,336, 어휘(vocabulary) 약 128K, query head 32개, KV head 8개, head 차원 128이다.[^llama3]
모든 수치는 BF16(원소당 2 bytes)을 가정하고 1 GB는 $10^9$ bytes로 쓴다.
Bytes는 각 입력을 한 번 읽고 출력을 한 번 쓰는 최소량으로 센다.
계산을 단순하게 하려고 파라미터 $N\approx8.03\times10^9$개가 모두 행렬곱에 쓰이고 매 스텝 읽힌다고 본다.

### 3-1. 선형층

문맥이 아주 길지 않으면 Transformer의 계산 대부분은 attention의 Q·K·V·출력 투영과 FFN 같은 선형층이다.
한 번에 처리하는 토큰이 $b$개이고 가중치가 $d_{\text{in}}\times d_{\text{out}}$ 행렬(입력 $d_{\text{in}}$차원, 출력 $d_{\text{out}}$차원)이라 하자.
계산은 $2bd_{\text{in}}d_{\text{out}}$ FLOPs이고, 옮길 데이터는 가중치 $2d_{\text{in}}d_{\text{out}}$ bytes와 입력·출력 activation $2b(d_{\text{in}}+d_{\text{out}})$ bytes다.
$d_{\text{in}}=d_{\text{out}}=d=4096$인 투영이라면

$$
I=\frac{2b\,d^2}{2d^2+4bd}=\frac{b\,d}{d+2b}\approx b\qquad(b\ll d)
$$

이다.
토큰 수가 $d$보다 훨씬 적으면 **intensity가 함께 처리하는 토큰 수와 거의 같다.**
가중치를 한 번 읽어 토큰 $b$개에 쓰기 때문이다.
$b=1$이면 약 1, $b=16$이면 약 16, $b=256$이면 약 228이고,
$b=2048$이면 1,024로 ridge point를 크게 넘는다.

Decode 한 스텝은 요청마다 토큰 하나만 넣으므로, batch에 요청이 $b$개 있으면 선형층의 토큰 수도 $b$다.
요청이 하나면 선형층의 intensity는 약 1이다.
요청을 묶어도 $b$가 ridge point 약 295에 못 미치는 동안은 선형층이 memory-bound로 남는다.
Prefill은 프롬프트 길이 $n$만큼의 토큰을 한 번에 넣으므로, $n$이 수백을 넘으면 선형층의 intensity가 ridge point에 가까워지거나 넘어선다.

### 3-2. Decode의 attention

Attention은 사정이 다르다.
선형층의 가중치는 batch 안의 모든 요청이 공유하지만, KV cache는 요청마다 따로 있다.
요청들이 공통 prefix를 공유하지 않는 한 각 요청의 새 query는 **자기 KV cache만** 읽으므로,
batch를 키워도 attention의 intensity는 오르지 않는다.

요청 하나, 층 하나에서 문맥 길이가 $s$일 때를 계산해 보자.
Head 차원을 $d_h$라 하면, query head 하나는 key $s$개와 내적하고($2sd_h$ FLOPs) value $s$개를 가중합한다($2sd_h$ FLOPs).
GQA(grouped-query attention)에서는 query head $n_h$개를 KV head $n_{kv}$개에 나누어, query head $g=n_h/n_{kv}$개(그룹 크기)가 KV head 하나를 함께 쓴다.[^gqa]
그래서 KV head 하나를 읽는 동안 $4gsd_h$ FLOPs를 한다.
읽는 데이터는 그 KV head의 key와 value, $2\cdot s\cdot d_h\cdot2$ bytes다.
Query와 출력은 각각 $g\,d_h$ 크기라 문맥 $s$개분의 key·value에 비해 작으므로 뺐다.

$$
I_{\text{attn}}=\frac{4g\,s\,d_h}{4\,s\,d_h}=g
$$

문맥 길이는 약분되고 batch는 처음부터 식에 없으므로 **query head와 KV head의 비만 남는다.**
Llama 3 8B는 $g=32/8=4$이므로 decode attention의 intensity는 4이고, 그림의 속이 빈 점이다.

Query head마다 KV head를 따로 두는 MHA(multi-head attention)는 $g=1$이라 intensity가 1이고,
모든 query head가 KV head 하나를 함께 쓰는 MQA(multi-query attention)는 $g=n_h$다.
Head를 공유하면 KV cache가 줄 뿐 아니라,
한 번 읽은 key·value를 여러 query head가 재사용해 decode attention의 intensity가 올라간다.

KV head 하나에 연결된 선이 많을수록 한 번 읽은 key·value를 더 많은 query head가 재사용한다." source="Ainslie et al. (2023), Figure 2 · CC BY 4.0" />

MLA(multi-head latent attention)에서는 이 효과가 훨씬 크다.
MLA는 토큰마다 모든 head가 함께 쓰는 압축된 벡터 하나만 cache한다.[^dsv2]
Head별 key·value를 복원하지 않고 이 벡터를 바로 쓰는 weight absorption 방식으로 계산하면, query head 전부가 한 번 읽은 cache를 재사용한다.
DeepSeek-V3에서는 decode attention의 intensity가 200을 넘어 ridge point 가까이 오른다.

<Details summary="DeepSeek-V3로 계산한 MLA의 intensity">

MLA는 층마다 토큰 하나에 512차원 latent 벡터 $c$를 cache하고, head별 key와 value는 $c$에 행렬을 곱해 만든다.
Head 하나의 key를 $W^{UK}c$라 하면 점수는 다음처럼 바꿔 쓸 수 있다.

$$
q\cdot\left(W^{UK}c\right)=\left(W^{UK\top}q\right)\cdot c
$$

그래서 query에 $W^{UK\top}$를 먼저 곱해 두면 key를 복원하지 않고 $c$와 바로 내적할 수 있다.
Value 쪽도 마찬가지로 $c$를 먼저 가중합하고 head별 행렬은 나중에 곱한다.
이렇게 복원 행렬을 query와 출력 쪽 계산에 합쳐 두는 방법을 weight absorption이라 한다.

위치 정보는 이렇게 합칠 수 없다.
RoPE(rotary position embedding)는 key에 그 위치에 따라 다른 회전을 곱하므로, query에 미리 곱해 둘 행렬이 key 위치마다 달라져 하나로 합칠 수 없다.
그래서 MLA는 RoPE를 적용한 64차원 key를 따로 만들어 함께 cache한다.

결국 층마다 cache된 토큰 하나는 latent 512차원과 RoPE key 64차원을 합한 576개 원소로, BF16이면 1,152 bytes다.
Inference 코드의 weight absorption 경로에서는 query head 128개가 이 576개 원소를 함께 읽어, head마다 576차원으로 점수를 계산하고 512차원 latent로 가중합을 한다.[^dsv3][^dsv3-code]
그러면 cache된 토큰 하나를 읽을 때 $2\cdot128\cdot(576+512)\approx2.8\times10^5$ FLOPs를 하므로,
intensity는 $2.8\times10^5/1152\approx240$이고 ridge point에 가깝다.
Key·value를 복원해 head별로 cache하는 방식보다 head당 계산은 늘지만,
memory-bound인 decode에서는 그 늘어난 계산이 놀던 연산 장치를 채우는 셈이다.

</Details>

### 3-3. Prefill

Prefill에서는 선형층이 토큰 $n$개를 한꺼번에 처리하고, attention도 query $n$개가 같은 key·value를 재사용한다.
다만 $n\times n$ 점수 행렬을 HBM에 썼다가 다시 읽으면 그 이동 때문에 attention의 intensity가 낮아진다.
FlashAttention은 이 행렬을 SRAM 안에서 처리해 그 이동을 없앤다.[^flash]

<Callout type="example">
2,048토큰 프롬프트 하나를 prefill한다고 하자.
점수 행렬은 FlashAttention처럼 SRAM 안에서 처리한다고 본다.

**계산.** 선형층은 $2N\cdot n=2\times8.03\times10^9\times2048\approx32.9$ TFLOP이다.
Attention의 점수 계산과 가중합은 query head 하나에 $4n^2d_h$ FLOPs인데, causal mask로 앞쪽 토큰만 보므로 그 절반인 약 $2n^2d_h$ FLOPs다.
Head 32개와 층 32개를 곱하면 약 1.1 TFLOP이다.
합하면 약 34 TFLOP이고, 989 TFLOP/s로 나누면 약 34 ms다.

**데이터 이동.** 가중치 16.1 GB를 한 번 읽는다.
여기에 각 층이 2,048토큰의 activation을 읽고 쓰는 양이 약 12.6 GB 더해져 모두 약 28.7 GB이고,
3.35 TB/s로 약 8.6 ms가 걸린다.

계산 시간이 네 배쯤 길어(intensity 약 1,200) compute-bound다.
그래서 TTFT의 하한은 계산 시간인 **약 34 ms**다.
실제 kernel이 peak의 50%를 낸다면 약 69 ms가 된다.
</Callout>

## 4. Batching과 그 한계

### 4-1. Batch 크기에 따른 decode 스텝

요청을 묶으면 처리량이 오르고 TPOT가 늘어난다는 관계를 시간의 하한으로 계산해 보자.
모든 요청의 문맥이 2,048토큰이라고 가정한다.
토큰당 KV cache는 $2\,(\text{K와 V})\times32\,\text{층}\times8\ \text{KV head}\times128\,\text{차원}\times2\ \text{bytes}=131{,}072\ \text{bytes}\approx131\ \text{KB}$다.
그러면 요청 하나의 KV cache는 $2048\times131{,}072\ \text{bytes}\approx0.27$ GB다.

한 스텝에 읽는 데이터는 가중치 16.06 GB에 요청당 KV cache 0.27 GB를 더한 양이고,
계산은 요청마다 선형층 $2N\approx16.1$ GFLOP과 attention 약 1.1 GFLOP($4sd_h$에 query head 32개와 층 32개를 곱한 값)이다.
Activation 이동은 작아서 뺐다.

| batch $b$ | 읽는 데이터 | 읽기 시간 | 계산 시간 | 전체 intensity | 스텝 시간(TPOT 하한) | 처리량 상한 |
|---|---|---|---|---|---|---|
| 1 | 16.3 GB | 4.9 ms | 0.02 ms | 1.0 | 4.9 ms | 205 토큰/s |
| 16 | 20.4 GB | 6.1 ms | 0.28 ms | 13.5 | 6.1 ms | 2,630 토큰/s |
| 64 | 33.2 GB | 9.9 ms | 1.1 ms | 33 | 9.9 ms | 6,450 토큰/s |
| 192 | 67.6 GB | 20.2 ms | 3.3 ms | 49 | 20.2 ms | 9,520 토큰/s |

Batch를 1에서 192로 늘리면 스텝 시간은 약 4배가 되지만 처리량은 약 46배가 된다.
가중치 16 GB를 한 번 읽어 192개 요청에 나누어 쓰기 때문이다.

표의 모든 행에서 스텝 시간은 읽기 시간과 같다.
이 batch 범위에서는 선형층의 intensity가 약 192 이하이고 attention은 4라서, 두 연산 모두 ridge point 295보다 아래에 있기 때문이다.
연산마다 하한이 읽기 시간으로 정해지므로, 그 하한을 더한 스텝 시간도 전체 읽기 시간과 같아진다.

Batch 192에서도 전체 intensity는 49로 ridge point 295에 한참 못 미친다.
Activation을 빼고 선형층만 보면 intensity는 약 192인데도 전체가 49에 머무는 것은 KV cache를 읽는 데이터가 batch에 비례해 함께 늘기 때문이다.
Batch 192에서 읽는 67.6 GB 가운데 51.5 GB가 KV cache다.
Batch를 키울수록 읽는 데이터에서 KV cache의 비중이 커지고, 앞에서 본 것처럼 그 부분의 intensity는 4에 묶여 있다.
Batch를 한없이 키우면 가중치의 몫은 무시할 만큼 작아지고, 전체 intensity는 요청당 계산 17.1 GFLOP(선형층과 attention의 합)을 요청당 KV cache 0.27 GB로 나눈 약 64에 수렴한다.
메모리가 아무리 넉넉해도 batch만으로는 ridge point 295에 닿을 수 없다는 뜻이다.

### 4-2. KV cache 용량의 벽

표를 batch 192에서 멈춘 것은 KV cache 공간 때문이다.
H100 한 대(80 GB)에서 서빙 엔진이 쓰는 메모리 가운데 가중치와 activation·workspace를 빼고 KV cache에 남는 공간은 약 53.5 GB로 어림된다.
요청당 0.27 GB이면 약 199개가 상한이다.
선형층의 intensity는 묶은 요청 수와 거의 같으므로, 선형층만이라도 ridge point에 닿으려면 요청 300개 이상을 묶어야 한다.
그 전에 메모리가 바닥난다.

문맥이 길수록 벽은 더 가깝다.
같은 공간에서 문맥이 8,192토큰이면 batch는 49개에서 멈추고, 32,768토큰이면 12개다.
그때 스텝마다 읽는 데이터의 대부분은 KV cache다.
그래서 긴 문맥의 decode에서는 가중치 bytes보다 KV cache bytes를 줄이는 기법이 처리량을 더 직접 늘린다.
이 계산이 KV cache 관리의 동기이고, GQA·MLA가 서빙에서 중요한 이유다.

<Callout type="intuition">
식당 주방으로 비유해 보자.
요리사(연산 장치)는 아주 빠르고, 냉장고(HBM)에서 재료를 나르는 통로(대역폭)는 좁다.
공용 재료(가중치)는 한 번 꺼내 오면 여러 접시에 쓸 수 있으니 주문을 많이 받을수록 이득이다.
한편 손님마다 따로 보관하는 재료(KV cache)도 있다.
주문이 늘면 그 재료를 나르는 일도 같이 늘고, 냉장고 칸이 다 차면 주문을 더 받을 수 없다.
비유가 놓치는 점도 있다.
실제 GPU는 재료를 나르는 일과 요리를 겹쳐서 할 수 있어서,
roofline 모형은 전체 시간을 둘을 더한 값이 아니라 둘 중 오래 걸리는 쪽으로 잡는다.
</Callout>

## 5. 하드웨어 효율 지표

시간의 하한은 이상적인 값이다.
실제 시스템이 그 하한에 얼마나 가까운지를 재는 지표가 MFU(model FLOPs utilization)와 MBU(model bandwidth utilization)다.

### 5-1. MFU

**MFU**는 원래 학습 효율을 재는 지표다.[^palm]
초당 처리한 토큰 수에 토큰당 이론 FLOPs를 곱한 값, 곧 모델이 실제로 낸 FLOP/s를 peak FLOP/s로 나눈다.
학습에서는 토큰당 $6N$을 쓰지만 inference는 forward만 하므로 토큰당 $2N$이다.

$$
\text{MFU}=\frac{\text{처리한 토큰/s}\times2N}{\text{peak FLOP/s}}
$$

Compute-bound인 prefill의 효율은 MFU로 본다.
앞의 prefill 예처럼 2,048토큰 프롬프트를 69 ms에 prefill했다면 처리량은 초당 약 29,700토큰이고 MFU는 $\frac{29700\times2\times8.03\times10^9}{989\times10^{12}}\approx48\%$다.

### 5-2. MBU

Batch가 작은 decode는 memory-bound라 MFU가 낮다.
앞의 batch 표에서 batch 1이면 하한을 그대로 달성해도 MFU가 0.3%다.
이때 효율은 대역폭을 얼마나 썼는지로 보아야 한다.
Databricks의 Agarwal 등은 이를 **MBU**로 정의했다.[^mbu]

$$
\text{MBU}=\frac{(\text{가중치 bytes}+\text{KV cache bytes})\,/\,\text{TPOT}}{\text{peak 대역폭}}
$$

분자는 한 스텝에 읽어야 하는 데이터를 실제 스텝 시간으로 나눈 달성 대역폭이다.
Batch가 크면 KV cache bytes에는 batch 안 모든 요청의 몫을 더한다.
같은 글이 그래프로 보고한 측정에서는 Llama 2 70B를 FP16(16-bit floating point)으로 H100 두 대에 나누어 올리고 입력 512토큰, batch 1로 돌렸을 때 MBU가 약 60%였다.[^mbu]

<Callout type="example">
Llama 3 8B를 H100 한 대에서 batch 1, 문맥 2,048토큰으로 돌렸더니 TPOT가 8.0 ms였다고 하자.
한 스텝에 읽어야 하는 데이터는 16.33 GB이므로 달성 대역폭은 $16.33\ \text{GB}/8.0\ \text{ms}\approx2.04$ TB/s, MBU는 $2.04/3.35\approx61\%$다.
Batch 1의 하한 4.9 ms에 비해 약 1.6배 느리다.
나머지 39%는 kernel이 대역폭을 다 채우지 못하는 것, 작은 kernel을 여러 번 띄우는 비용 등에서 새어 나간다.
</Callout>

정리하면 compute-bound인 스텝은 MFU로, memory-bound인 스텝은 MBU로 효율을 본다.

## 6. Roofline 위의 최적화 기법

Roofline으로 보면 inference 최적화 기법들이 각각 무엇을 바꾸는지 한 표로 정리할 수 있다.
FLOPs나 bytes를 줄이거나, 같은 bytes로 더 많은 일을 해 점을 오른쪽으로 옮기거나, 지붕 자체를 높이거나, 실제 성능을 지붕에 가깝게 올리는 것이다.

| 기법 | Roofline에서의 효과 |
|---|---|
| GQA·MLA | 여러 query head가 같은 KV를 함께 읽어 decode attention의 intensity를 GQA는 $g$로, MLA는 weight absorption을 쓰면 ridge point 가까이 올린다 |
| 양자화(quantization) | 가중치와 KV cache를 낮은 비트로 저장해 읽는 bytes를 줄이므로 memory-bound 스텝의 하한이 낮아진다. Activation까지 하드웨어가 지원하는 저정밀 형식으로 계산하면 peak도 높아진다 |
| Pruning·low-rank·distillation | 가중치를 없애거나 작은 행렬의 곱으로 근사하거나 작은 모델에 옮겨 담아, FLOPs와 bytes를 함께 줄인다. 다만 unstructured pruning은 희소 형식에 맞는 kernel이 있어야 bytes가 준다 |
| KV cache 관리 | cache 공간을 필요한 만큼씩 나누어 주고 prefix를 공유해 같은 메모리에 더 큰 batch를 넣는다. 과거 토큰의 KV를 지우는 eviction은 읽는 KV cache bytes도 줄인다 |
| Batching | 가중치 bytes를 여러 요청에 나누어 선형층의 점을 오른쪽으로 옮긴다 |
| Speculative decoding | 작은 모델이 제안한 토큰 여러 개를 가중치 한 번 읽기로 함께 검증해 decode의 점을 오른쪽으로 옮긴다 |
| Kernel fusion·tiling | 연산을 kernel 하나로 합치거나 SRAM에 들어가는 블록(tile)으로 나누어, 중간값의 HBM 왕복과 재읽기를 줄이고 점을 오른쪽으로 옮긴다 |
| 작업 분배·실행 중첩 같은 그 밖의 kernel 최적화 | FLOPs와 bytes는 거의 그대로라 점은 제자리에 가깝고, 실제 성능을 지붕에 가깝게 올린다 |

같은 기법도 스텝이 어느 지붕 아래 있느냐에 따라 효과가 다르다.
예를 들어 계산은 BF16으로 두고 가중치만 INT4(4-bit 정수)로 저장하면 batch 1 스텝에서 읽을 가중치가 16 GB에서 약 4 GB로 줄어든다.
KV cache 0.27 GB를 더해도 하한은 약 1.3 ms로, BF16의 4.9 ms의 4분의 1쯤이다(scale 같은 부가 정보와 복원 계산은 뺀 값).
계산량은 그대로이므로 compute-bound인 prefill에는 효과가 작다.
