Batching은 한 번 읽은 weight를 여러 요청의 토큰에 나눠 써서 처리량을 높이고,
speculative decoding은 한 번의 검증으로 출력 토큰 여러 개를 얻어 요청 하나의 토큰당 지연을 줄이려 한다.[^survey]
두 경우 모두 roofline으로 구한 시간은 정한 계산량과 데이터 이동량을 최대 속도로 처리할 때의 이상적인 값이다.
실제 실행은 보통 그보다 오래 걸린다.
Llama 3.1 8B를 H100 한 대에서 batch 1로, speculative decoding 없이 돌린다.
문맥이 약 2,048토큰인 구간의 TPOT(time per output token), 곧 첫 토큰 이후 출력 토큰 하나에 걸린 평균 시간이 8.0 ms라고 하자(설명을 위한 값).
그러면 TPOT는 weight와 KV(key-value) cache를 BF16(bfloat16)으로 한 번씩 읽는다고 단순화한 4.9 ms의 약 1.6배다.
모델 weight와 KV cache의 크기를 TPOT로 나눈 값이 최대 대역폭의 몇 %인지를 MBU(model bandwidth utilization)라 한다.[^mbu]
4.9 ms가 그 bytes를 최대 대역폭으로 나눈 값이므로, 여기서는 $4.9/8.0\approx61\%$다.
MBU가 61%라는 사실만으로는 대역폭을 다 쓰지 못한 원인이 어디에 있는지 나눌 수 없다.
이 값은 모델의 weight와 KV cache를 한 번 읽는다고 가정한 추정치다.
실제 HBM에서 오간 모든 bytes를 하드웨어 counter로 잰 대역폭 사용률과는 다르다.
대역폭 사용률을 비교할 때는 분자에 실제 전송량을 쓰는지 모델이 읽어야 할 양을 추정해 쓰는지 먼저 확인해야 한다.
또 TPOT에 서버 대기나 네트워크 시간이 들어가면 GPU(graphics processing unit) 실행 시간만으로 구한 값과 비교할 수 없다.

연산 쪽에는 MFU(model FLOPs utilization)가 있다.
모델이 필요로 하는 FLOPs를 실제 경과 시간과 해당 정밀도의 이론상 peak FLOP/s의 곱으로 나눈 값이다.[^palm]
예를 들어 같은 스텝에 모델 계산 약 17 GFLOPs와 GPU 실행 시간 8.0 ms를 가정하면, H100 BF16 peak 989 TFLOP/s 대비 MFU는 약 0.21%다.
이 값은 모델의 필요한 계산량을 세므로 재계산이나 padding 등 실제 수행한 모든 연산을 포함하는 하드웨어 연산 사용률과 같지 않다.
Decode처럼 메모리 이동이 병목인 경우 MFU가 낮다고 해서 그것만으로 kernel이 잘못되었다고 결론 내릴 수 없다.
이상적인 계산에서 정한 데이터의 양에 비해 실행이 느린 이유를 찾으려면 **그 계산을 GPU에서 실행하는 방식**을 살펴야 한다.
Kernel 최적화는 두 가지 일을 한다.
하나는 kernel fusion처럼 중간값의 HBM(high-bandwidth memory) 왕복을 없애 실제로 옮기는 bytes를 줄이는 것이다.
같은 계산에 bytes가 줄면 intensity가 올라 roofline 위의 점이 오른쪽으로 옮겨 간다.
다른 하나는 일을 GPU의 연산 단위에 고르게 나누거나 kernel 사이의 빈 시간을 없애는 것이다.
이때는 intensity가 그대로인 채 실제 속도가 올라, 점이 같은 가로축 위치에서 위로 움직여 지붕에 가까워진다.

다만 kernel 하나의 배율이 곧 서비스의 배율은 아니다.
문맥이 길어 attention이 스텝 시간의 4분의 1을 차지한다고 해도,
attention kernel을 두 배 빠르게 하면 스텝은 8분의 7로 줄어 약 1.14배 빨라질 뿐이다(Amdahl의 법칙).
그래서 스텝 시간을 연산별로 나누어 보고, 시간을 많이 차지하는 부분부터 손댄다.

Pan과 Li의 inference 시스템 서베이는 attention kernel이 작업을 GPU의 연산 단위에 나누어 주는 방식이 어떻게 바뀌어 왔는지를 계보로 정리한다.[^survey]
이 노트는 kernel이 GPU에서 실행되는 방식과 kernel의 시간을 재는 도구를 먼저 보고,
그 계보를 따라 decode를 중심으로 attention kernel, 선형층과 MoE(mixture of experts)의 kernel,
그리고 kernel 바깥에서 새는 시간을 차례로 본다.

## 1. GPU에서 kernel이 실행되는 방식

Kernel은 GPU가 많은 데이터를 병렬로 처리하도록 실행하는 프로그램이다.
PyTorch처럼 연산을 하나씩 실행하면 행렬곱, 덧셈 같은 연산마다 kernel이 실행되고,
각 kernel은 입력을 GPU 메모리에서 읽어 결과를 다시 GPU 메모리에 쓴다.
데이터가 칩 안의 cache에 남아 있으면 HBM까지 가지 않아도 되지만, 없으면 HBM을 오간다.
Kernel fusion은 이어지는 연산을 한 kernel로 묶어 중간값의 HBM 왕복을 줄이는 방법이다.
예를 들어 원소마다 $y=\max(2x+1,0)$을 계산하며 곱셈, 덧셈, 최댓값을 따로 실행하면, 중간값 $2x$와 $2x+1$이 cache에 남지 않는 한 HBM에 썼다가 다시 읽어야 하지만,
한 kernel로 묶으면 $x$를 한 번 읽고 $y$를 한 번 쓰는 것으로 끝난다.

GPU는 수많은 연산 장치를 SM(streaming multiprocessor)이라는 단위로 묶어 둔다.
Kernel은 계산을 작은 실행 단위인 thread들에 나누고, thread들을 thread block으로 묶어 SM들에 나누어 준다.
Thread block 하나는 한 SM에서 실행되며, 그 안의 thread는 32개씩 warp로 묶여 같은 명령을 함께 실행한다.
H100 SXM에는 SM이 132개 있고, SM마다 thread들이 함께 쓰는 shared memory가 최대 228 KB까지 있다.[^hopper]
칩 안의 작고 빠른 메모리를 통틀어 SRAM(static random-access memory)이라 하며, register, shared memory, L2 cache가 여기에 든다.
FlashAttention 논문이 SRAM이라 부르며 블록을 올려 두는 곳은 그중 SM마다 있는 shared memory다.

이 구조에서 kernel이 하드웨어를 다 쓰려면 두 가지가 필요하다.
첫째, **모든 SM에 일이 돌아가야** 한다.
일이 thread block 40개로만 나뉘면 SM 132개 가운데 적어도 92개가 논다.
그래서 보통은 thread block을 SM 수보다 많이 만들어, 한 block이 끝나면 기다리던 block이 이어 실행되게 한다.
Persistent kernel을 쓰기도 하는데, 적은 수의 thread block(예: SM마다 하나)만 띄우고 각 block이 작업 하나를 마쳐도 끝나지 않고 다음 작업 조각을 가져와 처리하게 하는 방식이다.
둘째, 각 thread block이 HBM에서 데이터를 읽는 동안에도 연산 장치가 놀지 않도록 읽기와 계산을 겹쳐야 한다.
Decode에서는 특히 첫째 조건이 어렵다.
처리할 query가 적어 query 방향으로 SM 전체에 나눌 일을 만들기 어렵다.
한 스텝이 수 ms로 짧아 작은 비효율도 크게 드러난다.

## 2. Kernel 시간의 측정

스텝 시간을 연산별로 나누려면 실제 실행을 기록해 봐야 한다.
엔진에 들어 있는 PyTorch profiler로도 kernel별 시간을 볼 수 있고, NVIDIA는 쓰임새가 다른 profiler 두 가지를 따로 제공한다.
**Nsight Systems**는 스텝 전체의 시간이 어디에 쓰이는지를 타임라인으로 보여 주고,
**Nsight Compute**는 kernel 하나가 GPU의 연산 장치와 메모리 대역폭을 얼마나 쓰는지 분석한다.
보통은 Nsight Systems로 시간을 많이 쓰는 kernel과 빈 구간을 찾은 뒤, 그 kernel만 Nsight Compute로 들여다본다.

### 2-1. Nsight Systems

Nsight Systems(`nsys`)는 CPU thread, CUDA API 호출, GPU에서 실행된 kernel과 메모리 복사를 한 시간축 위에 그린다.[^nsys]
`nsys profile -o report <실행 명령>`으로 실행하면 기록이 `report.nsys-rep` 파일에 저장되고, GUI에서 열면 타임라인이 보인다.
이 타임라인에서 볼 것은 두 가지다.

첫째는 kernel별 시간의 합이다.
`nsys stats` 명령이 만드는 `cuda_gpu_kern_sum` 보고서는 kernel 이름마다 실행 횟수와 총 시간, 전체에서 차지하는 비율을 모아 준다.[^nsys]
이 비율은 보고서에 포함된 kernel 실행 시간의 합을 분모로 쓰므로, GPU가 빈 시간이나 메모리 복사까지 포함한 스텝 전체 시간의 비율은 아니다.[^nsys-analysis]
또 여러 stream의 kernel이 겹쳐 실행되면 각 실행 시간의 합이 실제 경과 시간보다 클 수 있다.
Amdahl의 법칙에 쓸 몫은 관심 있는 스텝의 타임라인에서 겹침과 빈 구간을 함께 살펴 추정한다.
도입의 예처럼 attention이 4분의 1이라면 attention kernel을 아무리 빠르게 해도 스텝은 4분의 3 아래로 줄지 않는다.

둘째는 GPU 줄의 빈 구간이다.
Kernel과 kernel 사이가 비어 있으면 GPU가 그 구간에서 일을 하지 못한 이유를 살펴본다.
CPU의 제출이 늦었을 수도 있지만, 데이터 복사나 다른 작업의 완료를 기다렸을 수도 있다.
같은 시각의 CPU와 메모리 복사 줄, 작업 사이의 의존성을 함께 보면 원인을 좁힐 수 있다.
코드에 NVTX(NVIDIA Tools Extension) 범위 표시를 넣으면 "decode 스텝", "12번째 층" 같은 구간 이름이 타임라인에 함께 나타나, 어느 구간의 kernel인지 찾기 쉽다.

vLLM 문서는 Nsight Systems로 vLLM을 잴 때 `--trace-fork-before-exec=true`와 `--cuda-graph-trace=node`를 붙이라고 권한다.[^vllm-profile]
앞의 옵션은 vLLM이 띄우는 worker 프로세스까지 기록하게 한다.
뒤의 옵션은 여러 kernel을 묶어 한 번에 재생하는 CUDA graph 안의 kernel도 하나하나 기록하게 한다.
CUDA driver가 11.7 이상이면 Nsight Systems는 기본적으로 CUDA graph를 통째로 한 구간으로 기록하므로, 이 옵션이 없으면 그래프 안의 kernel별 시간을 볼 수 없다.[^nsys]
대신 kernel 단위로 기록하는 만큼 측정 부담이 커지므로, 지연 자체는 profiler 없이 따로 잰다.

### 2-2. Nsight Compute

Nsight Compute(`ncu`)는 kernel 하나를 대상으로 GPU의 하드웨어 counter를 모아 분석한다.[^ncu]
필요한 지표를 한 번에 모을 수 없을 때는 같은 kernel을 여러 번 다시 실행한다(kernel replay).
기본 설정에서는 측정값의 변동을 줄이려고 kernel들을 차례로 실행하고 각 replay pass 전에 GPU cache를 비운다.[^ncu]
그래서 Nsight Compute가 보여 주는 실행 시간은 실제 서빙 중의 시간과 다를 수 있고, 엔진 전체에 걸면 매우 느려진다.
Nsight Systems로 고른 kernel의 이름 일부를 `-k regex:` 옵션으로, 잴 실행 횟수를 `-c` 옵션으로 정해 대상을 좁힌다.[^ncu-cli]
예를 들어 `ncu --set full -k regex:flash -c 1 -o attn <실행 명령>`은 이름에 flash가 들어간 kernel의 첫 실행 하나를 `full` section set의 지표로 재서 attn이라는 이름의 보고서로 저장한다.
`full`은 제공되는 모든 개별 지표를 뜻하는 것이 아니라 여러 분석 section을 묶은 설정이다.

보고서에서 먼저 볼 것은 Speed Of Light 절이다.
연산 장치와 메모리 각각의 처리량을 이론 최댓값에 대한 비율로 보여 주므로,[^ncu]
도입에서 스텝 전체로 계산한 MBU와 비슷한 지표를 kernel 하나 단위로 보는 셈이다.
다만 이 보고서는 실제 하드웨어 자원의 활동을 세며, 메모리 항목에는 HBM뿐 아니라 cache 등 여러 하위 자원이 포함된다.
모델 크기로 추정한 MBU와 같은 값으로 해석하지 않는다.
Roofline 차트는 그 kernel의 arithmetic intensity와 달성한 성능을 점 하나로 찍어 roofline의 지붕과 함께 보여 준다.[^ncu]
해당 intensity에서 대역폭 지붕이 연산 지붕보다 낮으면 roofline의 이론적 한계는 메모리 대역폭이 정한다.
실측 점이 그 지붕에서 멀다면 대역폭을 충분히 활용하지 못하거나 다른 비용이 있을 수 있으므로, 그 위치만으로 실제 병목을 확정하지 않는다.
일을 SM에 고르게 나누거나 읽기와 계산을 겹치는 최적화는 이 점을 위로 올리고, 중간값의 HBM 왕복을 없애는 fusion은 intensity를 높여 점을 오른쪽으로 옮긴다.

## 3. Attention kernel

### 3-1. FlashAttention의 병렬화

FlashAttention은 query와 key·value를 각각 작은 블록으로 나눈다.
Kernel은 query 블록 하나와 key 블록 하나로 작은 점수 타일을 계산하고, 이 타일을 하나씩 SM 안의 빠른 메모리(shared memory와 register)에서 처리한다(tiling).
그래서 시퀀스 길이 $n$에 대한 $n\times n$ 점수 행렬 전체를 HBM에 쓰지 않는다.[^fa1]
그런데 softmax의 분모는 한 query의 모든 점수를 보아야 정해지고, 블록을 하나씩 순회하면 점수가 일부만 보인다.
한 query와 위치 $j$의 key가 만든 점수를 $x_j$, 그 위치의 value를 $v_j$라 하자.
Kernel은 지금까지 처리한 위치들에 대해 점수의 최댓값 $m$, 지수 합 $\ell=\sum_j e^{x_j-m}$, value의 가중합 $a=\sum_j e^{x_j-m}v_j$를 들고 다닌다.
최댓값을 빼는 것은 지수가 너무 커지지 않게 하려는 것이다.
새 블록에서 더 큰 점수가 나와 최댓값이 바뀌면, 앞의 $\ell$과 $a$에 $e^{m_{\text{old}}-m_{\text{new}}}$를 곱해 새 기준에 맞춘 뒤 새 블록의 항을 더한다.
$e^{x_j-m_{\text{old}}}\,e^{m_{\text{old}}-m_{\text{new}}}=e^{x_j-m_{\text{new}}}$이기 때문이다.
마지막 블록까지 처리한 뒤 $a/\ell$이 출력이고, 이는 점수 전체로 한 번에 계산한 출력과 같다.
이 방식을 online softmax라 부른다.[^online-softmax]

예를 들어 첫 위치의 점수가 1이고 value가 10이면 $m=1$, $\ell=1$, $a=10$이다.
다음 위치의 점수가 2, value가 20이면 새 최댓값은 2가 된다.
기존 합을 $e^{1-2}\approx0.368$배로 바꾼 뒤 새 위치를 더해 $\ell\approx0.368+1=1.368$, $a\approx3.68+20=23.68$을 얻는다.
두 위치만 처리한 출력은 $a/\ell\approx17.31$이고, 아직 더 처리할 위치가 있다면 이 값들을 들고 이어 간다.

FlashAttention 1은 key·value 블록 하나를 불러 여러 query 블록에 차례로 적용한 뒤 다음 key·value 블록으로 넘어갔다.
이 순서는 key·value 블록을 여러 query 블록에 재사용하는 데 맞춘 것이다.
일을 SM에 나누는 단위는 batch와 attention head였다.
FlashAttention-2는 반복 순서를 바꿔, query 블록 하나가 모든 key·value 블록을 차례로 도는 구조로 만들었다.
그러면 query 블록끼리는 서로 기다릴 일이 없으므로, **query의 시퀀스 길이** 방향으로도 나누어 query 블록마다 thread block을 둘 수 있다.[^fa2]
학습과 긴 prompt의 prefill에서는 query가 많아 thread block이 넉넉하다.<Sidenote>Prefill 쪽에서는 FlashAttention-2가 H100 peak의 35%에 머물렀고, FlashAttention-3가 데이터 이동과 softmax를 행렬곱과 겹쳐 FP16(16-bit floating point)에서 peak의 75%까지 올렸다.[^fa3] Tensor Core가 지수 계산이나 shared memory 대역폭보다 훨씬 빨라진 Blackwell GPU에서는 FlashAttention-4가 softmax의 지수 계산 일부를 소프트웨어로 근사하는 등 행렬곱이 아닌 일을 줄이도록 kernel을 다시 설계했다.[^fa4]</Sidenote>

보통의 decode에서는 요청마다 query가 하나뿐이다.
Query 방향으로 나눌 것이 없으므로 병렬성은 batch × head만 남는다.
Dao 등은 이렇게 생기는 thread block이 SM 수보다 적으면 이 연산이 GPU의 작은 일부만 쓴다고 지적했다.[^flashdecoding]

<Callout type="example">
Llama 3.1 8B를 batch 1로 decode한다고 하자.
KV cache를 시퀀스 방향으로 더 나누지 않고 query head마다 thread block 하나를 두면, thread block은 32개뿐이고 H100의 SM 132개 가운데 100개가 논다.
문맥이 32,768토큰이고 head 차원이 128이라면, 한 층에서 KV head 하나의 key와 value(×2)는 원소당 2 bytes인 BF16으로 $32768\times128\times2\times2\ \text{bytes}\approx16.8$ MB다.
각 thread block이 자기 KV head의 16.8 MB를 처음부터 끝까지 차례로 읽어야 하므로,
SM 하나가 낼 수 있는 대역폭에 묶이기 쉽다.
SM 132개가 함께 쓰도록 설계된 3.35 TB/s를 SM 32개만으로 끌어 쓰려는 셈이라 다 쓰기 어렵다.
</Callout>

### 3-2. Flash-Decoding

Dao 등의 Flash-Decoding은 나눌 방향을 하나 더 만들었다.
**Key·value의 시퀀스 길이**다.[^flashdecoding]
긴 KV cache를 여러 조각(split)으로 나누고, 조각마다 thread block을 하나씩 두어 동시에 계산한다.
각 thread block은 자기 조각의 점수만으로 softmax를 계산한 부분 출력을 만들고,
그 조각의 softmax 분모(지수 합)에 로그를 씌운 스칼라 하나(LSE, log-sum-exp)를 함께 남긴다.
마지막에 짧은 reduce kernel이 LSE의 차이로 조각별 지수 합의 상대적인 크기를 구하고, 그 비중으로 부분 출력을 합친다.

<Callout type="example">
Query 하나의 점수 $x_j$가 $[1,2,3,0]$이고, 각 위치의 value $v_j$가 스칼라 $[10,20,30,40]$이라고 하자.
한 번에 계산한 정답 출력은 $\sum_j e^{x_j}v_j/\sum_j e^{x_j}\approx26.21$이다.
FlashAttention이라면 thread block 하나가 두 블록 $[1,2]$와 $[3,0]$을 차례로 처리하며 online softmax로 $m$과 $\ell$을 고쳐 나간다.
Flash-Decoding은 두 블록을 조각 두 개로 보고 동시에 계산한다.
조각 1($[1,2]$)은 부분 출력 약 17.31과 $\text{LSE}_1=\log(e^{1}+e^{2})\approx2.313$을,
조각 2($[3,0]$)는 부분 출력 약 30.47과 $\text{LSE}_2=\log(e^{3}+e^{0})\approx3.049$를 각자 낸다.
LSE는 online softmax에서 들고 다닌 최댓값 $m$과 지수 합 $\ell$을 한 값으로 접은 것으로, $m+\log\ell$과 같다(조각 1이면 $m=2$, $\ell=e^{-1}+e^{0}\approx1.368$이므로 $2+\log1.368$).
Reduce는 각 조각의 비중을 $e^{\text{LSE}_i}$에 비례하게 잡는다.
조각의 부분 출력은 자기 조각의 지수 합으로 이미 나눈 값이라, 그 지수 합 $e^{\text{LSE}_i}$를 다시 곱해 분자로 되돌리고 전체 지수 합으로 나누는 것이다.
지수가 너무 커지지 않게 두 LSE에서 같은 기준값 3을 빼고 $e^{2.313-3}\approx0.503$과 $e^{3.049-3}\approx1.050$을 비중으로 쓰면 $(0.503\times17.31+1.050\times30.47)/1.553\approx26.21$로,
정답과 같다.
순서대로 갱신하든 따로 계산해 합치든 수학적으로 결과가 같으므로, 조각을 나누어 병렬로 계산할 수 있다.
</Callout>

Flash-Decoding은 CodeLlama-34B에서 아주 긴 시퀀스의 decode를 최대 8배 빠르게 했고,
A100에서 batch 1, query head 16개로 잰 미시 벤치마크에서는 attention 자체가 FlashAttention보다 최대 50배 빨랐다.
시퀀스 길이 32K까지는 attention 시간이 거의 일정했다.[^flashdecoding]
KV를 여러 조각으로 나누어 여러 SM이 함께 읽으면서 GPU를 충분히 쓰게 되었기 때문이다.

조각을 나누는 데도 대가가 있다.
부분 결과를 HBM에 썼다가 reduce kernel이 다시 읽어야 하고, kernel이 하나 늘어난다.
Batch × head만으로 이미 SM이 꽉 찬다면 더 쪼개도 얻는 것이 적다.
vLLM v0.10.1의 PagedAttention kernel이 이 선택을 보여 준다.
시퀀스를 512토큰 조각으로 나누어 계산하고 reduce kernel로 합치는 v2와 나누지 않는 v1이 있었고,
최대 길이가 8,192토큰 이하이면서 시퀀스가 짧거나 batch × head만으로 thread block이 이미 충분하면 v1을 골랐다.[^vllm-pa]

### 3-3. 흩어진 KV cache와 FlashInfer

PagedAttention은 요청 하나의 KV cache를 GPU 메모리 곳곳의 블록에 흩어 두므로,
attention kernel은 block table을 따라 흩어진 블록을 찾아 읽는 비용을 치른다.
게다가 실제 서빙의 batch에는 prefill 조각과 decode가 섞이고, 요청마다 길이가 다르며,
prefix caching으로 여러 요청이 일부 블록을 공유한다.

Ye 등의 FlashInfer는 이런 경우를 하나의 틀로 다룬다.[^flashinfer]
먼저 어떤 query가 어떤 KV 블록을 읽는지를 **block-sparse 행렬**로 나타낸다(block table을 FlashInfer는 page table이라 부른다).
행은 query, 열은 KV cache의 블록이고, query가 그 블록을 읽어야 하는 자리만 0이 아니다.
PagedAttention의 흩어진 블록,
여러 요청이 공유하는 prefix, 요청마다 다른 길이가 모두 이 형식 하나로 표현된다.
Kernel은 흩어진 블록을 타일 단위로 GPU 메모리에서 shared memory의 연속된 공간에 모은 뒤,
거기서 dense한 연산을 하고 다음 타일로 넘어간다.
Query tile이 충분히 크면 Tensor Core를 쓰고, tile 크기가 1이면 CUDA Core를 쓴다.<Sidenote>CUDA Core는 원소 하나씩 덧셈과 곱셈을 하는 범용 연산 장치이고, Tensor Core는 작은 행렬 블록의 곱셈과 누산을 한 번에 처리하는 행렬곱 전용 장치다. Query 하나만 따로 처리하면 Tensor Core가 요구하는 행렬 타일을 채우기 어렵다. 다만 GQA에서 같은 KV를 쓰는 여러 query head를 묶거나 빈 행을 채워 Tensor Core를 쓰는 구현도 있으므로, query 길이 하나만으로 실행 장치를 단정할 수는 없다. 두 장치의 차이를 입문 수준에서 정리한 글로 GPU Mart의 [CUDA Cores vs Tensor Cores](https://www.gpu-mart.com/blog/cuda-cores-vs-tensor-cores)가 있다. 다만 이 글은 Tensor Core의 정밀도별 차이를 다루지 않고, core 수를 세대가 다른 GPU의 성능 지표처럼 설명한다.</Sidenote>
공유 prefix를 읽는 query들은 이 행렬에서 여러 행을 한 블록으로 묶어 함께 계산해, shared memory에 한 번 복사한 KV를 여러 query가 재사용하게 한다.
이를 위해 GPU 메모리에 저장된 KV cache를 재배치하지는 않고, 접근 관계를 나타내는 색인만 새로 만든다.
예를 들어 두 요청의 KV 블록이 $[A,B,C]$와 $[A,B,D]$라면,
두 query가 함께 읽는 $A,B$ 부분과 각자 읽는 $C$, $D$ 부분으로 나누어 계산하고,
$A,B$는 shared memory에 한 번만 올린다.

FlashInfer는 Flash-Decoding의 부분 결과 합치기도 일반화했다.
Query 하나에 대한 (부분 출력, log-sum-exp) 쌍을 attention state라 부르고,
두 state는 Flash-Decoding의 reduce처럼 지수 합을 비중으로 삼아 하나로 합칠 수 있다.
이 합치기는 덧셈처럼 결합법칙과 교환법칙을 만족하므로, KV를 어떻게 나누어 계산하고 어떤 순서로 합쳐도 수학적으로 결과가 같다.[^flashinfer]
State를 합칠 수 있으니 긴 KV를 여러 작업으로 나눠도 출력을 되살릴 수 있다.
그래서 요청마다 다른 KV 길이를 SM들에 고르게 나누는 계획을 CPU(central processing unit)에서 미리 세우고(plan),
GPU kernel은 그 계획대로 실행한다(run).
요청별 query와 KV 길이 등 계획의 조건이 같은 층들은 스텝마다 세운 계획을 함께 재사용할 수 있다.
Full attention과 sliding window가 섞여 층마다 읽을 KV 범위가 다르면 같은 계획을 그대로 재사용한다고 단정할 수 없으므로, 각 층의 조건과 구현을 확인해야 한다.
요청마다 query tile이 하나인 decode로 단순화하면,
계획은 전체 KV 길이를 thread block 수로 나눈 값을 조각의 최대 길이로 삼아 긴 KV를 자르고,
긴 조각부터 지금까지 맡은 일이 가장 적은 thread block에 하나씩 배정한다.[^flashinfer]

<Callout type="example">
Decode 요청 네 개의 KV 길이가 8K, 2K, 1K, 1K이고, 설명을 위해 thread block 네 개가 SM 네 개에서 동시에 돈다고 하자.
시간은 각 block이 읽는 KV 길이에 비례한다고 근사한다.
요청마다 thread block 하나를 두면 8K를 맡은 block이 끝날 때까지 나머지 셋은 2K, 1K, 1K만 처리하고 논다.
걸리는 시간은 KV 8K를 읽는 시간이다.
FlashInfer의 계획은 전체 12K를 4로 나눈 3K를 조각의 최대 길이로 잡아 8K를 3K, 3K, 2K로 자른다.
조각 3K, 3K, 2K, 2K, 1K, 1K를 긴 것부터 일이 가장 적은 block에 주면 배정은 $[3K]$, $[3K]$, $[2K,1K]$, $[2K,1K]$가 된다.
네 block이 모두 3K씩 맡으므로, 걸리는 시간은 3K를 읽는 시간으로 준다.
대가는 8K 요청의 세 부분 결과를 합치는 짧은 단계 하나다.

SGLang에 붙여 비교한 실험에서 FlashInfer는 Triton 언어로 작성한 attention backend보다 ITL(inter-token latency)을 29–69% 줄였다(Llama 3.1 8B는 H100 한 대, 70B는 네 대).[^flashinfer]
지금은 vLLM과 SGLang 모두 FlashInfer를 attention backend의 하나로 쓴다.
다만 엔진이 FlashInfer를 지원한다는 사실만으로 모든 설정에서 그것이 선택되는 것은 아니다.
실제 측정에서는 엔진이 보고한 backend와 profiler 실행 기록을 확인해 어떤 attention kernel과 행렬곱 kernel이 시간을 쓰는지 본다.
Attention 비중이 작다면 attention kernel만 바꾼 효과가 전체 지연에서는 작을 수 있다.

## 4. 선형층과 MoE의 kernel

### 4-1. 작은 batch의 행렬곱

Decode의 선형층은 batch가 작으면 행렬과 벡터의 곱에 가깝다.
Weight가 16-bit라면 이런 연산의 intensity는 토큰 수와 거의 같다.
이때 kernel의 주된 목표는 **weight를 메모리 대역폭에 최대한 가까운 속도로 읽는 것**이다.
큰 행렬곱에 맞춰 조율한 kernel을 그대로 쓰면,
한쪽 차원이 아주 작은 이 납작한 행렬곱에서는 대역폭을 다 쓰지 못한다.
Hong 등의 FlashDecoding++는 Flash-Decoding과 이름만 비슷한 별개의 연구로,
이 납작한 행렬곱(flat GEMM, GEMM은 general matrix multiplication)을 따로 다뤘다.[^fdpp]
원논문이 비교한 NVIDIA 행렬곱 라이브러리 cuBLAS·CUTLASS처럼 batch 쪽 차원을 64행 타일로 처리하면, batch가 8일 때 타일의 87.5%를 0으로 채운 채 계산한다.
FlashDecoding++는 batch 쪽 타일을 Tensor Core가 한 번에 처리하는 8행으로 줄여, batch가 8보다 작으면 8행이 될 때까지만 0으로 채운다.
일은 출력 차원 방향으로 thread block들에 나누고,
출력 차원이 크면 weight 읽기가 병목이 되므로, shared memory 버퍼 두 개를 번갈아 써서 다음 weight 타일을 읽는 동안 현재 타일을 계산한다(double buffering).

### 4-2. 양자화 weight의 kernel

Weight-only 양자화(quantization)에서 낮은 정밀도로 저장한 weight를 더 높은 정밀도의 activation과 곱하려면,
이 kernel처럼 곱셈에 맞는 정밀도로 weight를 변환할 수 있다(dequantize).
Frantar 등의 Marlin은 4-bit weight와 FP16 activation의 행렬곱을 위한 kernel이다.[^marlin]
다음 4-bit weight를 HBM에서 읽어 shared memory를 거쳐 레지스터로 가져오는 동안 이미 가져온 weight로 계산하고,
레지스터 안에서 FP16으로 되돌려 Tensor Core에 넣는다.
Weight는 kernel이 읽고 변환하는 순서에 맞게 미리 재배치해 저장해 둔다.

작은 batch에서는 일을 SM에 고르게 나누는 것도 문제다.
출력 타일 수가 SM 수로 나누어떨어지지 않으면 마지막 차례에서 일부 SM이 논다.
출력의 열 타일 하나를 만들려면, 그 열에 해당하는 weight 타일들을 입력의 대응하는 부분과 각각 곱해 모두 더해야 한다.
Marlin은 전체 weight 타일 수를 SM 수로 나눈 값을 올림해 SM당 몫으로 정하고, 한 SM의 몫이 한 출력 열의 타일을 다 맡고도 남으면 다음 출력 열의 위에서 이어 받게 배정한다(striped partitioning).
그러면 SM마다 일이 거의 같아지고, 부분합을 더하는 일은 한 출력 열을 나누어 맡은 SM들 사이에서만 생긴다.[^marlin]

Scale 저장과 activation 이동을 무시한 이상적인 roofline 계산으로 보면, 4-bit weight 하나는 0.5 byte인데 토큰 하나가 weight 하나마다 2 FLOPs(floating-point operations)를 쓰므로 batch $b$에서 intensity는 약 $4b$ FLOP/byte다.
H100에서는 이 값이 ridge point 295에 닿는 $b\approx74$까지 4-bit 쪽도 memory-bound라, 읽는 bytes가 FP16의 4분의 1인 만큼 이상적으로 4배 빠르다.
계산량은 그대로라 batch가 더 커지면 4-bit 쪽부터 compute-bound에 가까워지고,
이득은 약 $295/b$배로 줄다가 intensity가 $b$인 FP16 쪽도 compute-bound가 되는 $b\approx295$에서 사라진다.[^marlin]
vLLM에 넣은 end-to-end 측정에서는 RTX A6000으로 Llama-2-7B를 서빙할 때 TPOT가 FP16 대비 약 2.8배 짧아졌다.[^marlin]
이 비교는 요청률을 바꿔 가며 잰 서빙 결과라, 응답 속도에 따라 실제 batch 크기도 달라질 수 있다.
따라서 고정 batch의 선형층 kernel만 잰 배율과 구분해서 읽는다.

### 4-3. MoE의 grouped GEMM

MoE 층에서는 router가 토큰마다 expert 몇 개를 고르므로, batch의 토큰들이 서로 다른 expert로 흩어지고 expert마다 받는 토큰 수가 다르다.
각 expert는 자기에게 온 토큰들에만 FFN(feed-forward network) 행렬곱을 하므로, expert마다 행렬곱의 크기가 달라진다.
모든 expert에 같은 수의 토큰을 맞춰 하나의 batched 행렬곱으로 계산하는 단순한 구현은,
넘치는 토큰을 버리거나 모자란 자리를 0으로 채워야 했다.
크기가 다른 여러 행렬곱을 묶어 한 번에 실행하는 방식을 grouped GEMM이라 부른다.
Gale 등의 MegaBlocks는 토큰을 expert별로 묶어 행에, expert들의 weight를 열에 놓는다.
각 토큰 묶음은 자기 expert의 weight와만 곱하므로, 첫 선형층의 결과는 대각선 위의 블록에만 생기는 행렬(block-diagonal)이 되고 MegaBlocks는 이 블록들만 block-sparse 행렬곱으로 계산했다.
Expert마다 대각 블록의 행 수는 그 expert가 받은 토큰 수만큼이고, 실제 계산은 이를 고정 크기의 작은 블록 여러 개로 나누어 한다.
그래서 expert마다 토큰 수를 맞추거나 넘치는 토큰을 버릴 필요가 없다.[^megablocks]
이 결과에 활성화를 적용한 뒤, 이 희소한 행렬을 입력으로 받는 둘째 선형층의 행렬곱도 block-sparse 연산으로 계산한다.
Inference 엔진도 토큰 수가 다른 여러 expert의 행렬곱을 한꺼번에 처리한다.
vLLM v0.31.0의 fused MoE kernel은 한 경로에서 토큰을 expert 순서로 정렬한 뒤,
블록마다 어떤 expert의 weight를 쓸지를 표시해 같은 선형층에 속한 모든 expert의 행렬곱을 kernel 하나로 처리한다.[^vllm-fusedmoe]
토큰과 expert의 배정 수가 전체 expert 수에 비해 매우 적은 일부 설정에서는 정렬을 건너뛰고,
토큰과 expert의 배정 하나씩 블록에 넣는 경로도 쓴다.
첫 선형층, 활성화, 둘째 선형층까지 한 kernel로 합치지는 않고 따로 호출한다.

## 5. Kernel 바깥의 시간

### 5-1. Kernel launch와 CUDA graph

Kernel 자체가 빨라도 그 사이가 빈다면 GPU는 논다.
CPU는 kernel을 하나씩 GPU에 제출하는데, 제출마다 마이크로초 단위의 비용이 든다.
같은 stream에 제출한 kernel은 순서대로 실행되므로, kernel 하나의 실행이 제출 비용보다 짧으면 대기열이 비어 GPU가 다음 제출을 기다릴 수 있다.
NVIDIA의 측정에서 V100에서 실행 시간 2.9 μs짜리 kernel을 제출할 때마다 끝나기를 기다리면, kernel당 9.6 μs가 걸렸다.[^cudagraph-nv]
Decode 한 스텝은 층마다 정규화, 투영,
attention, 활성화 같은 kernel 여러 개를 수십 층에 걸쳐 실행하므로, fusion 정도에 따라 kernel이 수백 개에 이를 수 있다.
그 가운데 정규화·원소별 연산 kernel은 수 μs면 끝나 대기열이 비기 쉽다.
vLLM 팀도 H100에서 Llama 8B의 GPU 실행 시간이 스텝당 약 5 ms에 불과해,
CPU 쪽의 비용이 무시할 수 없게 된다고 밝혔다.[^vllm-v1]

**CUDA graph**는 이 비용을 줄인다.
한 스텝에서 실행할 kernel들의 순서와 인자를 한 번 기록(capture)해 두고,
이후에는 기록한 그래프 전체를 한 번에 재생(replay)한다.
NVIDIA의 같은 측정에서 동기화 없이 이어 제출하면 kernel당 3.8 μs, CUDA graph로 재생하면 3.4 μs였다.
이 단순한 예에서는 차이가 작지만, CPU의 kernel 제출 비용이 병목인 모델에서는 이득이 커질 수 있다.
예를 들어 PyTorch 팀은 MLPerf 학습 벤치마크의 Mask R-CNN에서 GPU당 batch 1일 때 backbone 구간이 31 ms에서 6 ms로 줄었다고 보고했다.[^cudagraph-pt]
대신 재생은 같은 kernel을 같은 메모리 주소로 실행한다.
입력값은 기록할 때 쓴 고정 버퍼에 새로 복사해 넣으면 바꿀 수 있지만, 버퍼의 모양은 바꿀 수 없다.[^cudagraph-pt]
그런데 서빙에서는 batch 크기가 스텝마다 바뀐다.
그래서 vLLM은 처리할 토큰 수 1, 2, 4, 8, 16, 24, …에 맞춘 그래프를 미리 기록해 두고,
실제 토큰 수를 그 수 이상인 가장 작은 기록 크기로 채워(padding) 재생한다.
요청마다 query가 하나인 보통의 decode에서는 이 토큰 수가 곧 batch 크기다.
Attention은 요청마다 KV 길이가 달라 실행할 일이 스텝마다 바뀌므로 고정된 그래프에 담기 어렵다.
이를 지원하는 attention backend는 바뀌는 길이와 작업 계획을 고정 주소의 버퍼에 넣어, 같은 그래프를 재생하면서도 다른 입력을 처리한다.
vLLM V1의 기본 설정은 모델을 attention을 경계로 나누어 컴파일한다(piecewise compilation).
이때 attention backend가 지원하면 요청마다 query 길이가 같은 decode batch는 전체를 그래프 하나로 기록하고,
나머지는 attention 사이의 구간만 그래프로 기록한다.[^vllm-cg]

### 5-2. 컴파일러

Kernel을 하나하나 손으로 쓰지 않고 컴파일러에 맡기는 길도 있다.
Tillet 등의 Triton은 GPU의 thread 대신 데이터 타일 단위로 연산을 쓰게 하는 언어이자 컴파일러로,
당시 GTX 1070 실험에서 행렬곱이 cuBLAS에 비견하는 성능을 냈다.[^triton]
PyTorch 2의 `torch.compile`에서는 TorchDynamo가 Python 프로그램의 연산을 실행 중에 그래프로 잡고,
TorchInductor가 그 그래프로 GPU용 Triton kernel을 생성하거나 일부 연산은 라이브러리 kernel을 호출한다.
A100에서 180개 넘는 모델의 inference를 기하평균 2.27배 빠르게 했다.[^pt2]
Kernel fusion을 사람이 일일이 하지 않아도 컴파일러가 찾아 준다.
Fusion은 HBM 왕복과 함께 제출할 kernel 수도 줄이므로, 컴파일러는 kernel 안과 바깥의 시간을 함께 줄인다.

Inference 엔진은 둘을 섞어 쓴다.
vLLM은 attention 사이의 토큰별 연산을 `torch.compile`로 묶어 fusion하고,
attention은 FlashAttention이나 FlashInfer처럼 직접 최적화한 kernel을 쓴다.
FlashInfer 논문도 Triton이 아직 여러 경우에 CUDA·CUTLASS로 쓴 kernel만큼 빠르지 않아 CUDA 코드를 생성한다고 밝힌다.[^flashinfer]
성능이 가장 중요한 몇 개의 kernel은 손으로, 나머지는 컴파일러로 처리하는 분업이다.
