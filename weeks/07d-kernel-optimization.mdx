Batching은 한 번 읽은 weight를 여러 요청의 토큰에 나눠 써서 처리량을 높이고,
speculative decoding은 한 번의 검증으로 출력 토큰 여러 개를 얻어 요청 하나의 토큰당 지연을 줄이려 한다.[^survey]
두 경우 모두 roofline으로 구한 시간은 정한 연산량과 데이터 이동량을 최대 속도로 처리할 때의 이상적인 값이다.
실제 실행은 보통 그보다 오래 걸린다.
예를 들어 Llama 3.1 8B를 H100 한 대에서 batch 1로 돌려, 문맥이 약 2,048토큰인 구간의 TPOT(time per output token)가 8.0 ms였다고 하자(설명을 위한 값).
BF16(bfloat16) weight 약 16 GB와 KV(key-value) cache 약 0.27 GB를 최대 대역폭 3.35 TB/s로 한 번씩 읽는 데는 약 4.9 ms가 걸린다.
두 시간의 비인 MBU(model bandwidth utilization)는 $4.9/8.0\approx61\%$다.[^mbu]
MBU가 61%라는 사실만으로는 대역폭을 다 쓰지 못한 원인이 어디에 있는지 알 수 없다.
그 원인을 찾으려면 **그 계산을 GPU(graphics processing unit)에서 실행하는 방식**을 살펴야 한다.

Kernel, 곧 GPU에서 연산을 실행하는 프로그램을 최적화하는 일은 두 갈래다.
하나는 이어지는 연산을 한 kernel로 묶어 중간값의 HBM(high-bandwidth memory) 왕복을 없애, 실제로 옮기는 bytes를 줄이는 것이다.
다른 하나는 일을 GPU의 연산 단위에 고르게 나누거나 kernel 사이의 빈 시간을 없애, 같은 bytes를 더 빨리 처리하는 것이다.

다만 kernel 하나를 두 배 빠르게 해도 서비스 전체가 두 배 빨라지지는 않는다.
문맥이 길어 attention이 스텝 시간의 4분의 1을 차지한다고 해도,
attention kernel을 두 배 빠르게 하면 스텝은 8분의 7로 줄어 약 1.14배 빨라질 뿐이다(Amdahl의 법칙).
그래서 스텝 시간을 연산별로 나누어 보고, 시간을 많이 차지하는 부분부터 손댄다.

## 1. GPU에서 kernel이 실행되는 방식

Kernel은 GPU가 많은 데이터를 병렬로 처리하도록 실행하는 프로그램이다.
PyTorch처럼 연산을 하나씩 실행하면 행렬곱, 덧셈 같은 연산마다 kernel이 실행되고,
각 kernel은 입력을 GPU 메모리에서 읽어 결과를 다시 GPU 메모리에 쓴다.
데이터가 칩 안의 cache에 남아 있으면 HBM까지 가지 않아도 되지만, 없으면 HBM을 오간다.
Kernel fusion은 이어지는 연산을 한 kernel로 묶어 중간값의 HBM 왕복을 줄이는 방법이다.
예를 들어 원소마다 $y=\max(2x+1,0)$을 계산하며 곱셈, 덧셈, 최댓값을 따로 실행하면, 중간값 $2x$와 $2x+1$이 cache에 남지 않는 한 HBM에 썼다가 다시 읽어야 하지만,
한 kernel로 묶으면 $x$를 한 번 읽고 $y$를 한 번 쓰는 것으로 끝난다.

GPU는 수많은 연산 장치를 SM(streaming multiprocessor)이라는 단위로 묶어 둔다.
Kernel은 계산을 작은 실행 단위인 thread들에 나누고, thread들을 thread block으로 묶어 SM들에 나누어 준다.
Thread block 하나는 한 SM에서 실행되며, 그 안의 thread는 32개씩 warp로 묶여 같은 명령을 함께 실행한다.
H100 SXM에는 SM이 132개 있고, SM마다 thread들이 함께 쓰는 shared memory가 최대 228 KB까지 있다.[^hopper]
SM의 연산 장치는 원소 하나씩 더하고 곱하는 CUDA core와, 작은 행렬 블록의 곱을 한 번에 계산하는 행렬곱 전용 Tensor Core로 나뉜다.

이 구조에서 kernel이 하드웨어를 다 쓰려면 두 가지가 필요하다.
첫째, **모든 SM에 일이 돌아가야** 한다.
일이 thread block 40개로만 나뉘면 SM 132개 가운데 적어도 92개가 논다.
그래서 보통은 thread block을 SM 수보다 많이 만들어, 한 block이 끝나면 기다리던 block이 이어 실행되게 한다.
둘째, HBM에서 데이터를 읽는 지연을 숨길 만큼 다른 일을 준비해야 한다.
한 warp가 데이터를 기다리는 동안 같은 SM의 다른 준비된 warp가 실행될 수 있다.
Kernel 안에서 다음 데이터의 읽기와 현재 데이터의 계산을 겹치는 방법도 있다.
Decode에서는 특히 첫째 조건이 어렵다.
처리할 query가 적어 query 방향으로 SM 전체에 나눌 일을 만들기 어렵다.
한 스텝이 수 ms로 짧아 작은 비효율도 크게 드러난다.

## 2. Kernel 시간의 측정

스텝 시간을 연산별로 나누려면 실제 실행을 기록해 봐야 한다.
NVIDIA는 쓰임새가 다른 profiler 두 가지를 제공한다.
**Nsight Systems**는 스텝 전체의 시간이 어디에 쓰이는지를 타임라인으로 보여 주고,
**Nsight Compute**는 kernel 하나가 GPU의 연산 장치와 메모리 대역폭을 얼마나 쓰는지 분석한다.
보통은 Nsight Systems로 시간을 많이 쓰는 kernel과 빈 구간을 찾은 뒤, 그 kernel만 Nsight Compute로 들여다본다.

Nsight Systems는 CPU(central processing unit) thread, CUDA API 호출, GPU에서 실행된 kernel과 메모리 복사를 한 시간축 위에 그린다.[^nsys]
이 타임라인에서 볼 것은 두 가지다.

첫째는 kernel별 시간의 합이다.
Kernel 이름마다 총 시간과 전체에서 차지하는 비율을 모아 보면 어느 연산부터 손댈지 정할 수 있다.[^nsys-analysis]
이 비율의 분모는 kernel 실행 시간의 합이므로, GPU 줄에 빈 구간이 많으면 스텝 시간에서 차지하는 몫은 이보다 작다.
둘째는 GPU 줄의 빈 구간이다.
Kernel과 kernel 사이가 비어 있으면 CPU의 제출이 늦었는지, 데이터 복사나 다른 작업의 완료를 기다렸는지를 같은 시각의 CPU 줄과 메모리 복사 줄을 함께 보며 좁힌다.
코드에 NVTX(NVIDIA Tools Extension) 범위 표시를 넣으면 "decode 스텝", "12번째 층" 같은 구간 이름이 타임라인에 함께 나타나, 어느 구간의 kernel인지 찾기 쉽다.

Nsight Compute는 필요한 지표를 모으려고 같은 kernel을 여러 번 다시 실행하므로, 엔진 전체가 아니라 Nsight Systems로 고른 kernel만 지정해 잰다.[^ncu]
보고서의 Speed Of Light 절은 연산 장치와 메모리 각각의 처리량을 이론 최댓값에 대한 비율로 보여 주어, 도입의 MBU와 비슷한 지표를 kernel 하나 단위로 보는 셈이다.
다만 메모리 항목에는 HBM뿐 아니라 cache 등 여러 하위 자원이 포함되므로, 모델 크기로 추정한 MBU와 같은 값으로 읽으면 안 된다.
Roofline 차트는 그 kernel의 arithmetic intensity와 달성한 성능을 점 하나로 찍어 roofline의 지붕과 함께 보여 준다.[^ncu]
일을 SM에 고르게 나누거나 읽기와 계산을 겹치는 최적화는 이 점을 위로 올리고, 중간값의 HBM 왕복을 없애는 fusion은 intensity를 높여 점을 오른쪽으로 옮긴다.

## 3. Attention kernel

### 3-1. FlashAttention의 병렬화

FlashAttention은 query와 key·value를 각각 작은 블록으로 나눈다.
Kernel은 query 블록 하나와 key 블록 하나로 작은 점수 타일을 계산하고, 이 타일을 하나씩 SM 안의 빠른 메모리(shared memory와 register)에서 처리한다(tiling).
그래서 시퀀스 길이 $n$에 대한 $n\times n$ 점수 행렬 전체를 HBM에 쓰지 않는다.[^fa1]
그런데 softmax의 분모는 한 query의 모든 점수를 보아야 정해지고, 블록을 하나씩 순회하면 점수가 일부만 보인다.
한 query와 위치 $j$의 key가 만든 점수를 $x_j$, 그 위치의 value를 $v_j$라 하자.
Kernel은 지금까지 처리한 위치들에 대해 점수의 최댓값 $m$, 지수 합 $\ell=\sum_j e^{x_j-m}$, value의 가중합 $a=\sum_j e^{x_j-m}v_j$를 들고 다닌다.
최댓값을 빼는 것은 지수가 너무 커지지 않게 하려는 것이다.
새 블록에서 더 큰 점수가 나와 최댓값이 바뀌면, 앞의 $\ell$과 $a$에 $e^{m_{\text{old}}-m_{\text{new}}}$를 곱해 새 기준에 맞춘 뒤 새 블록의 항을 더한다.
$e^{x_j-m_{\text{old}}}\,e^{m_{\text{old}}-m_{\text{new}}}=e^{x_j-m_{\text{new}}}$이기 때문이다.
마지막 블록까지 처리한 뒤 $a/\ell$이 출력이고, 이는 점수 전체로 한 번에 계산한 출력과 같다.
이 방식을 online softmax라 부른다.[^online-softmax]

<Details summary="Online softmax 계산 예">
예를 들어 첫 위치의 점수가 1이고 value가 10이면 $m=1$, $\ell=1$, $a=10$이다.
다음 위치의 점수가 2, value가 20이면 새 최댓값은 2가 된다.
기존 합을 $e^{1-2}\approx0.368$배로 바꾼 뒤 새 위치를 더해 $\ell\approx0.368+1=1.368$, $a\approx3.68+20=23.68$을 얻는다.
두 위치만 처리한 출력은 $a/\ell\approx17.31$이고, 아직 더 처리할 위치가 있다면 이 값들을 들고 이어 간다.
</Details>

FlashAttention 1은 key·value 블록 하나를 불러 여러 query 블록에 차례로 적용한 뒤 다음 key·value 블록으로 넘어갔다.
일을 SM에 나누는 단위는 batch와 attention head였다.
FlashAttention-2는 반복 순서를 바꿔, query 블록 하나가 모든 key·value 블록을 차례로 도는 구조로 만들었다.
그러면 query 블록 하나의 계산이 다른 query 블록과 무관하게 처음부터 끝까지 이어지므로, **query의 시퀀스 길이** 방향으로도 나누어 query 블록마다 thread block을 둘 수 있다.[^fa2]
학습과 긴 prompt의 prefill에서는 query가 많아 thread block이 넉넉하다.<Sidenote>Prefill 쪽에서는 FlashAttention-2의 연산 속도가 H100의 최대 연산 성능에 한참 못 미쳤고, FlashAttention-3가 데이터 이동과 softmax를 행렬곱과 겹쳐 FP16(16-bit floating point)에서 최대 성능에 훨씬 가깝게 올렸다.[^fa3] Tensor Core가 지수 계산이나 shared memory 대역폭보다 훨씬 빨라진 Blackwell GPU에서는 FlashAttention-4가 softmax의 지수 계산 일부를 소프트웨어로 근사하는 등 행렬곱이 아닌 일을 줄이도록 kernel을 다시 설계했다.[^fa4]</Sidenote>

보통의 decode에서는 요청마다 query가 하나뿐이다.
Query 방향으로 나눌 것이 없으므로 병렬성은 batch × head만 남는다.[^fa2]
Dao 등은 이때 batch 크기가 SM 수보다 작으면 이 연산이 GPU의 작은 일부만 쓴다고 지적했다.[^flashdecoding]

<Callout type="example">
Llama 3.1 8B를 batch 1로 decode한다고 하자.
이 모델은 query head 32개가 네 개씩 KV head 8개를 나누어 쓰는 GQA(grouped-query attention) 구조다.
KV cache를 시퀀스 방향으로 더 나누지 않고 query head마다 thread block 하나를 두면, thread block은 32개뿐이고 H100의 SM 132개 가운데 100개가 논다.
문맥이 32,768토큰이고 head 차원이 128이라면, 한 층에서 KV head 하나의 key와 value(×2)는 원소당 2 bytes인 BF16으로 $32768\times128\times2\times2\ \text{bytes}\approx16.8$ MB다.
각 thread block이 자기 KV head의 16.8 MB를 처음부터 끝까지 차례로 읽어야 하므로,
SM 하나가 낼 수 있는 대역폭에 묶이기 쉽다.
SM 132개가 함께 쓰도록 설계된 3.35 TB/s를 SM 32개만으로 끌어 쓰려는 셈이라 다 쓰기 어렵다.
</Callout>

### 3-2. Flash-Decoding

Dao 등의 Flash-Decoding은 나눌 방향을 하나 더 만들었다.
**Key·value의 시퀀스 길이** 방향이다.[^flashdecoding]
긴 KV cache를 여러 조각(split)으로 나누고, 조각마다 thread block을 하나씩 두어 동시에 계산한다.
각 thread block은 자기 조각의 점수만으로 softmax를 계산한 부분 출력 $o_i$를 만들고,
그 조각 점수들의 log-sum-exp인 스칼라 $\text{LSE}=\log\sum_j e^{x_j}$ 하나를 함께 남긴다.
마지막에 짧은 reduce kernel이 LSE의 차이로 조각별 지수 합의 상대적인 크기를 구하고, 그 비중으로 부분 출력을 합친다.
조각마다 지수 합이 다르므로 부분 출력을 똑같이 평균하면 안 되고, 지수 합에 비례한 비중으로 합쳐야 한다.

<Callout type="example">
Query 하나의 점수 $x_j$가 $[1,2,3,0]$이고, 각 위치의 value $v_j$가 스칼라 $[10,20,30,40]$이라고 하자.
한 번에 계산한 정답 출력은 $\sum_j e^{x_j}v_j/\sum_j e^{x_j}\approx26.21$이다.
FlashAttention이라면 thread block 하나가 두 블록 $[1,2]$와 $[3,0]$을 차례로 처리하며 online softmax로 $m$과 $\ell$을 고쳐 나간다.
Flash-Decoding은 두 블록을 조각 두 개로 보고 동시에 계산한다.
조각 1($[1,2]$)은 부분 출력 약 17.31과 $\text{LSE}_1=\log(e^{1}+e^{2})\approx2.313$을,
조각 2($[3,0]$)는 부분 출력 약 30.47과 $\text{LSE}_2=\log(e^{3}+e^{0})\approx3.049$를 각자 낸다.
Reduce는 각 조각의 비중을 $e^{\text{LSE}_i}$에 비례하게 잡는다.
조각의 부분 출력은 자기 조각의 지수 합으로 이미 나눈 값이라, 그 지수 합 $e^{\text{LSE}_i}$를 다시 곱해 분자로 되돌리고 전체 지수 합으로 나누는 것이다.
지수가 너무 커지지 않게 두 LSE에서 같은 기준값 3을 빼고 $e^{2.313-3}\approx0.503$과 $e^{3.049-3}\approx1.050$을 비중으로 쓰면 $(0.503\times17.31+1.050\times30.47)/1.553\approx26.21$로,
정답과 같다.
순서대로 갱신하든 따로 계산해 합치든 수학적으로 결과가 같으므로, 조각을 나누어 병렬로 계산할 수 있다.
</Callout>

Flash-Decoding은 아주 긴 시퀀스에서 FlashAttention을 쓸 때보다 생성 속도를 크게 높였고, attention만 따로 재면 시퀀스가 꽤 길어질 때까지 attention 시간이 거의 일정했다.[^flashdecoding]
KV를 여러 조각으로 나누어 여러 SM이 함께 읽으면서 GPU를 충분히 쓰게 되었기 때문이다.

조각을 나누는 데도 대가가 있다.
부분 결과를 HBM에 썼다가 reduce kernel이 다시 읽어야 하고, kernel이 하나 늘어난다.
Batch × head만으로 이미 SM이 꽉 찬다면 더 쪼개도 얻는 것이 적다.

### 3-3. 흩어진 KV cache와 FlashInfer

PagedAttention은 요청 하나의 KV cache를 GPU 메모리 곳곳의 블록에 흩어 두므로,
attention kernel은 block table을 따라 흩어진 블록을 찾아 읽는 비용을 치른다.
게다가 실제 서빙의 batch에는 prefill 조각과 decode가 섞이고, 요청마다 길이가 다르며,
prefix caching으로 여러 요청이 일부 블록을 공유한다.

Ye 등의 FlashInfer는 이런 경우를 하나의 틀로 다룬다.[^flashinfer]
먼저 어떤 query가 어떤 KV 블록을 읽는지를 **block-sparse 행렬**로 나타낸다(block table을 FlashInfer는 page table이라 부른다).
행은 query, 열은 KV cache의 블록이고, query가 그 블록을 읽어야 하는 자리만 0이 아니다.
PagedAttention의 흩어진 블록,
여러 요청이 공유하는 prefix, 요청마다 다른 길이가 모두 이 형식 하나로 표현된다.
Kernel은 흩어진 블록을 타일 단위로 GPU 메모리에서 shared memory의 연속된 공간에 모은 뒤,
거기서 dense한 연산을 하고 다음 타일로 넘어간다.
Query tile이 충분히 크면 Tensor Core를 쓰고, tile 크기가 1이면 CUDA core를 쓴다.<Sidenote>Query 하나만 따로 처리하면 Tensor Core가 요구하는 행렬 타일을 채우기 어렵다. 다만 GQA에서 같은 KV를 쓰는 여러 query head를 묶거나 빈 행을 채워 Tensor Core를 쓰는 구현도 있으므로, query 길이 하나만으로 실행 장치를 단정할 수는 없다.</Sidenote>
공유 prefix를 읽는 query들은 이 행렬에서 여러 행을 한 블록으로 묶어 함께 계산해, shared memory에 한 번 복사한 KV를 여러 query가 재사용하게 한다.
이를 위해 GPU 메모리에 저장된 KV cache를 재배치하지는 않고, 접근 관계를 나타내는 색인만 새로 만든다.
예를 들어 두 요청의 KV 블록이 $[A,B,C]$와 $[A,B,D]$라면,
두 query가 함께 읽는 $A,B$ 부분과 각자 읽는 $C$, $D$ 부분으로 나누어 계산하고,
$A,B$는 shared memory에 한 번만 올린다.

FlashInfer는 Flash-Decoding의 부분 결과 합치기도 일반화했다.
Query 하나에 대한 (부분 출력, log-sum-exp) 쌍을 attention state라 부르고,
두 state는 Flash-Decoding의 reduce처럼 지수 합을 비중으로 삼아 하나로 합칠 수 있다.
이 합치기는 덧셈처럼 결합법칙과 교환법칙을 만족하므로, KV를 어떻게 나누어 계산하고 어떤 순서로 합쳐도 수학적으로 결과가 같다.[^flashinfer]
부분 state들을 합쳐 전체 출력을 구할 수 있으므로, 긴 KV를 여러 작업으로 나누어 계산해도 된다.
그래서 요청마다 다른 KV 길이를 SM들에 고르게 나누는 계획을 CPU에서 미리 세우고(plan),
GPU kernel은 그 계획대로 실행한다(run).
요청마다 query tile이 하나인 decode로 단순화하면,
계획은 전체 KV 길이를 thread block 수로 나눈 값을 조각의 최대 길이로 삼아 긴 KV를 자르고,
긴 조각부터 지금까지 맡은 예상 비용이 가장 적은 thread block에 하나씩 배정한다.[^flashinfer]

<Callout type="example">
Decode 요청 네 개의 KV 길이가 8K, 2K, 1K, 1K이고, 설명을 위해 thread block 네 개가 SM 네 개에서 동시에 돈다고 하자.
시간은 각 block이 읽는 KV 길이에 비례한다고 근사한다.
요청마다 thread block 하나를 두면 8K를 맡은 block이 끝날 때까지 나머지 셋은 2K, 1K, 1K만 처리하고 논다.
걸리는 시간은 KV 8K를 읽는 시간이다.
FlashInfer의 계획은 전체 12K를 4로 나눈 3K를 조각의 최대 길이로 잡아 8K를 3K, 3K, 2K로 자른다.
조각 3K, 3K, 2K, 2K, 1K, 1K를 긴 것부터 일이 가장 적은 block에 주면 배정은 $[3K]$, $[3K]$, $[2K,1K]$, $[2K,1K]$가 된다.
네 block이 모두 3K씩 맡으므로, 걸리는 시간은 3K를 읽는 시간으로 준다.
대가는 8K 요청의 세 부분 결과를 합치는 짧은 단계 하나다.
요청마다 같은 수로 자르는 방식과 달리, 짧은 요청은 자르지 않고 긴 요청만 필요한 만큼 자른다.
</Callout>

SGLang에 붙여 비교한 실험에서 FlashInfer는 GPU kernel용 언어 Triton으로 작성한 기존 attention backend보다 ITL(inter-token latency)을 뚜렷하게 줄였다.[^flashinfer]
지금은 vLLM과 SGLang 모두 FlashInfer를 attention backend의 하나로 쓴다.

## 4. 작은 batch의 행렬곱

Decode의 선형층은 batch가 작으면 행렬과 벡터의 곱에 가깝다.
Weight 하나(16-bit, 2 bytes)에 토큰마다 2 FLOPs(floating-point operations)를 쓰므로 intensity는 토큰 수와 거의 같고,
H100의 ridge point 295보다 훨씬 작아 memory-bound다.
이때 kernel의 주된 목표는 **weight를 메모리 대역폭에 최대한 가까운 속도로 읽는 것**이다.
큰 행렬곱에 맞춰 조율한 kernel을 그대로 쓰면,
한쪽 차원이 아주 작은 이 납작한 행렬곱에서는 대역폭을 다 쓰지 못한다.
Hong 등의 FlashDecoding++는 Flash-Decoding과 이름만 비슷한 별개의 연구로,
이 납작한 행렬곱(flat GEMM)을 따로 다뤘다.[^fdpp]
원논문이 비교한 NVIDIA 행렬곱 라이브러리 cuBLAS·CUTLASS처럼 batch 쪽 차원을 64행 타일로 처리하면, batch가 8일 때 타일의 87.5%를 0으로 채운 채 계산한다.
FlashDecoding++는 batch 쪽 타일을 Tensor Core가 한 번에 처리하는 8행으로 줄여, batch가 8보다 작으면 8행이 될 때까지만 0으로 채운다.
일은 출력 차원 방향으로 thread block들에 나누고,
출력 차원이 크면 weight 읽기가 병목이 되므로, shared memory 버퍼 두 개를 번갈아 써서 다음 weight 타일을 읽는 동안 현재 타일을 계산한다(double buffering).

## 5. Kernel launch와 CUDA graph

Kernel 자체가 빨라도 그 사이가 빈다면 GPU는 논다.
CPU는 kernel을 하나씩 GPU에 제출하는데, 제출마다 마이크로초 단위의 비용이 든다.
CPU가 제출한 kernel은 대기열(stream)에서 순서대로 실행되므로, kernel 하나의 실행이 제출 비용보다 짧으면 대기열이 비어 GPU가 다음 제출을 기다릴 수 있다.
NVIDIA가 잰 예에서는, 실행 시간이 아주 짧은 kernel을 제출하고 매번 끝나기를 기다리면 kernel당 걸린 시간이 실행 시간의 몇 배였다.[^cudagraph-nv]
Decode 한 스텝은 층마다 정규화, 투영,
attention, 활성화 같은 kernel 여러 개를 수십 층에 걸쳐 실행하므로, fusion 정도에 따라 kernel이 수백 개에 이를 수 있다.
그 가운데 정규화·원소별 연산 kernel은 실행 시간이 수 μs 수준으로 짧을 수 있어 대기열이 비기 쉽다.

**CUDA graph**는 이 비용을 줄인다.
한 스텝에서 실행할 kernel들의 순서와 인자를 한 번 기록(capture)해 두고,
이후에는 기록한 그래프 전체를 제출 한 번으로 재생(replay)하므로, kernel마다 치르던 제출 비용이 사라진다.
대신 재생은 같은 kernel을 같은 메모리 주소로 실행한다.
입력값은 기록할 때 쓴 고정 버퍼에 새로 복사해 넣으면 바꿀 수 있지만, 버퍼의 모양은 바꿀 수 없다.[^cudagraph-pt]
그런데 서빙에서는 batch 크기가 스텝마다 바뀐다.
요청마다 query가 하나인 보통의 decode에서는 한 스텝에 처리할 토큰 수가 곧 batch 크기다.
그래서 vLLM은 예를 들어 처리할 토큰 수 1, 2, 4, 8, 16, 24, …에 맞춘 그래프를 미리 기록해 두고,
실제 토큰 수 이상인 기록 크기 가운데 가장 작은 것을 골라, 입력을 그 크기에 맞게 채운(padding) 뒤 그 그래프를 재생한다.
기록할 크기는 설정에 따라 달라지며, 기록 범위를 넘거나 맞는 그래프가 없으면 그래프를 재생하지 않고 실행한다.
Attention은 요청마다 KV 길이가 달라 실행할 일이 스텝마다 바뀌므로 고정된 그래프에 담기 어렵다.
이를 지원하는 attention backend는 바뀌는 길이와 작업 계획을 고정 주소의 버퍼에 넣어, 같은 그래프를 재생하면서도 다른 입력을 처리한다.
vLLM V1의 기본 설정은 모델을 attention을 경계로 여러 구간으로 나눈다.
이때 attention backend가 지원하면 요청마다 query 길이가 같은 decode batch는 전체를 그래프 하나로 기록하고,
나머지는 attention 사이의 구간만 그래프로 기록한다.[^vllm-cg]

## 6. Inference engine

지금까지 본 기법들을 한 프로그램 안에서 맞물려 돌리는 것이 **inference engine**이다.
vLLM과 SGLang이 대표적인 공개 엔진이고, 요청 하나가 엔진 안에서 거치는 길은 대체로 같다.

1. <strong>API(application programming interface) 서버</strong>가 요청을 받아 프롬프트를 토큰으로 바꾸고, 생성된 토큰을 다시 텍스트로 되돌려 스트리밍한다.
2. **Scheduler**가 대기열의 요청 가운데 이번 스텝에 넣을 것과 각 요청에서 처리할 토큰 수를 정하고, 블록이 모자라면 실행 중인 요청을 선점한다.
3. **KV cache manager**가 요청에 블록을 배정·해제하고, 일치하는 prefix의 블록을 찾아 재사용한다.
4. **Model runner**가 batch의 입력 텐서를 준비하고 attention·선형층 kernel을 실행하며, 지원하는 설정에서는 CUDA graph로 여러 kernel의 실행을 묶는다.
5. **Sampler**가 각 요청의 logits로 다음 토큰을 고른다.

Scheduler의 결정은 "요청마다 이번 스텝에 처리할 토큰 수"라는 하나의 표에 담긴다.
새 요청의 prefill 조각도 기존 요청의 decode 한 토큰도 같은 형식이라, chunked prefill도 별도 단계 없이 처리된다.[^vllm-v1]
