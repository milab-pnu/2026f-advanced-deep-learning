앞 주차의 예시에서 Llama 3 8B를 H100 한 대에서 batch 1, 문맥 2,048토큰으로 돌릴 때 TPOT(time per output token)가 8.0 ms라면,
가중치와 KV(key-value) cache를 BF16(bfloat16)으로 한 번씩 읽는 하한 4.9 ms의 약 1.6배이고,
MBU(model bandwidth utilization)는 61%라고 했다.
MBU만으로는 남은 39%가 어디서 새는지 나눌 수 없다.
읽어야 할 데이터의 양은 하한에 이미 들어 있으므로, 먼저 의심할 곳은 **그 계산을 GPU(graphics processing unit)에서 실행하는 방식**이다.
Kernel 최적화는 두 가지 일을 한다.
Kernel fusion처럼 중간값의 HBM(high-bandwidth memory) 왕복을 없애 실제로 옮기는 bytes를 줄이면 roofline 위의 점이 오른쪽으로 옮겨 가고,
일을 GPU의 연산 단위에 고르게 나누거나 kernel 사이의 빈 시간을 없애면 같은 위치의 점이 지붕에 가까워진다.

전체 지도는 Pan과 Li의 inference 시스템 서베이[^survey]로 잡는다.
§3.1이 kernel을 다루며,
그 가운데 §3.1.1은 attention kernel의 계보를 작업을 GPU 연산 단위에 나누어 주는 방식으로 정리한다.
FlashAttention은 작업 조각을 연산 단위에 돌아가며 배정하고(round-robin),
Flash-Decoding은 KV cache를 정해진 수로 쪼개 배정하며(fixed-split),
FlashInfer 등은 길이가 다른 작업을 이어 붙여 고르게 흘려 보낸다(streaming)는 것이다.
이 노트는 그 계보를 따라 decode를 중심으로 attention kernel, 선형층과 MoE(mixture of experts)의 kernel,
그리고 kernel 바깥에서 새는 시간을 차례로 본다.

## 1. GPU에서 kernel이 실행되는 방식

학습 엔지니어링을 다룰 때 kernel을 GPU가 많은 데이터를 병렬로 처리하도록 실행하는 프로그램으로,
kernel fusion을 이어지는 연산을 한 kernel에 묶어 중간값의 HBM 왕복을 줄이는 방법으로 보았다.
여기에 한 가지를 더한다.
GPU는 수많은 연산 장치를 SM(streaming multiprocessor)이라는 단위로 묶어 두고,
kernel은 일을 thread block 단위로 쪼개 SM들에 나누어 준다.
Thread block 하나는 한 SM에서 실행되며, 그 안의 thread는 32개씩 warp로 묶여 같은 명령을 함께 실행한다.
H100 SXM에는 SM이 132개 있고, SM마다 최대 228 KB의 shared memory가 있다.[^hopper]
앞서 SRAM(static random-access memory)이라 부른 칩 안의 작고 빠른 메모리가 이것이다.

이 구조에서 kernel이 하드웨어를 다 쓰려면 두 가지가 필요하다.
첫째, **모든 SM에 일이 돌아가야** 한다.
일이 thread block 40개로만 나뉘면 SM 132개 가운데 적어도 92개가 논다.
그래서 보통은 thread block을 SM 수보다 많이 만들고,
SM마다 block 하나만 띄워 두고 작업 조각을 차례로 넘기는 persistent kernel을 쓰기도 한다.
둘째,
각 thread block이 HBM에서 데이터를 읽는 동안에도 연산 장치가 놀지 않도록 읽기와 계산을 겹쳐야 한다.
Decode는 두 조건을 모두 어렵게 만든다.
처리할 토큰이 적어 일이 잘게 나뉘지 않고, 한 스텝이 수 ms로 짧아 작은 비효율도 크게 드러난다.

## 2. Attention kernel

### 2-1. FlashAttention의 병렬화

앞서 본 FlashAttention 1은 key·value 블록을 바깥 반복에 두고 여러 query 블록에 재사용하며,
online softmax로 결과를 갱신했다.
일을 SM에 나누는 단위는 batch와 attention head였다.
FlashAttention-2는 반복 순서를 바꿔 query 블록을 바깥에 두고,
**query의 시퀀스 길이** 방향으로도 나누어 query 행 블록마다 thread block을 두었다(원논문 §3.2).[^fa2]
학습과 긴 prompt의 prefill에서는 query가 많아 thread block이 넉넉하다.

Prefill 쪽의 발전은 새 GPU의 연산 장치를 쉬지 않게 하는 방향으로 이어졌다.
FlashAttention-2는 H100에서 peak의 35%밖에 쓰지 못했는데,
Shah 등의 FlashAttention-3는 데이터를 옮기는 warp와 계산하는 warp를 나누어 둘을 겹치고,
한 warp 묶음이 softmax를 계산하는 동안 다른 묶음은 행렬곱을 하도록 둘을 겹쳐 FP16(16-bit floating point)에서 peak의 75%까지 올렸다.[^fa3]
이 수치는 arXiv판 기준이고, NeurIPS 게재판 초록은 BF16에서 85%를 보고한다.
이와 별도로 FP8(8-bit floating point) 연산도 지원한다.
Blackwell GPU에서는 Tensor Core가 지수 함수 계산이나 shared memory 대역폭보다 훨씬 빨라져,
FlashAttention-4는 softmax의 지수 계산 일부를 소프트웨어로 근사하는 등 행렬곱이 아닌 일을 줄이는 쪽으로 다시 설계했다.[^fa4]
같은 알고리즘이라도 하드웨어 세대마다 병목이 옮겨 가 kernel을 다시 짜야 한다는 뜻이다.

보통의 decode에서는 요청마다 query가 하나뿐이다.
Query 방향으로 나눌 것이 없으므로 병렬성은 batch × head만 남는다.
Dao 등은 이렇게 생기는 thread block이 SM 수보다 적으면 이 연산이 GPU의 작은 일부만 쓴다고 지적했다.[^flashdecoding]

<Callout type="example">
Llama 3 8B를 batch 1로 decode한다고 하자.
KV split 없이 query head마다 thread block 하나를 두면 thread block은 32개뿐이고, H100의 SM 132개 가운데 100개가 논다.
문맥이 32,768토큰이라면 KV head 하나의 key·value는 BF16으로 $32768\times128\times2\times2\ \text{bytes}\approx16.8$ MB다.
Thread block 하나가 이 16.8 MB를 처음부터 끝까지 혼자 읽어야 하므로,
SM 하나가 낼 수 있는 대역폭이 그 시간을 정한다.
SM 132개가 함께 쓰도록 설계된 3.35 TB/s를 SM 32개만으로 끌어 쓰려는 셈이라 다 쓰기 어렵다.
</Callout>

### 2-2. Flash-Decoding

Dao 등의 Flash-Decoding은 나눌 방향을 하나 더 만들었다.
**Key·value의 시퀀스 길이**다.[^flashdecoding]
긴 KV cache를 여러 조각(split)으로 나누고, 조각마다 thread block을 하나씩 두어 동시에 계산한다.
각 thread block은 자기 조각에 대한 부분 출력과 함께,
그 조각의 softmax 분모에 로그를 씌운 스칼라 하나(LSE, log-sum-exp)를 남긴다.
마지막에 짧은 reduce kernel이 이 값들로 부분 출력의 비중을 맞춰 합친다.

<Callout type="example">
FlashAttention의 online softmax 예시를 다시 쓰자.
Query 하나의 점수가 $[1,2,3,0]$, value가 $[10,20,30,40]$이고 정답 출력은 약 26.21이었다.
그때는 thread block 하나가 두 블록을 차례로 처리하며 통계를 고쳐 나갔다.
Flash-Decoding은 두 조각을 동시에 계산한다.
조각 1($[1,2]$)은 부분 출력 약 17.31과 $\text{LSE}_1=\log(e^{1}+e^{2})\approx2.313$을,
조각 2($[3,0]$)는 부분 출력 약 30.47과 $\text{LSE}_2=\log(e^{3}+e^{0})\approx3.049$를 각자 낸다.
LSE는 앞에서 들고 다닌 최댓값 $m$과 지수 합 $\ell$을 한 값으로 접은 것으로, $m+\log\ell$과 같다(조각 1이면 $2+\log1.368$).
Reduce는 각 조각의 비중을 $e^{\text{LSE}_i}$에 비례하게 잡는다.
공통 기준 3을 빼 $e^{2.313-3}\approx0.503$과 $e^{3.049-3}\approx1.050$을 비중으로 쓰면 $(0.503\times17.31+1.050\times30.47)/1.553\approx26.21$로,
정답과 같다.
순서대로 갱신하든 따로 계산해 합치든 수학적으로 결과가 같으므로, 조각을 나누어 병렬로 계산할 수 있다.
</Callout>

Flash-Decoding은 CodeLlama-34B에서 아주 긴 시퀀스의 decode를 최대 8배 빠르게 했고,
A100에서 batch 1, query head 16개로 잰 미시 벤치마크에서는 attention 자체가 FlashAttention보다 최대 50배 빨랐다.
시퀀스 길이 32K까지는 attention 시간이 거의 일정했다.[^flashdecoding]
긴 KV cache를 읽는 일이 이제 SM 전체로 퍼졌기 때문이다.

조각을 나누는 데도 대가가 있다.
부분 결과를 HBM에 썼다가 reduce kernel이 다시 읽어야 하고, kernel이 하나 늘어난다.
Batch × head만으로 이미 SM이 꽉 찬다면 더 쪼개도 얻는 것이 적다.
vLLM의 초기 PagedAttention kernel이 이 선택을 그대로 보여 준다.
시퀀스를 512토큰 단위로 나누어 계산하고 reduce kernel로 합치는 V2와 나누지 않는 V1이 있었는데,
최대 길이가 8,192토큰 이하이면서 시퀀스가 512토큰 조각 하나에 들어가거나 `num_seqs × num_heads`가 512를 넘어 thread block이 이미 충분할 때는 V1을 골랐다.[^vllm-pa]

### 2-3. 흩어진 KV cache와 FlashInfer

PagedAttention은 요청 하나의 KV cache를 GPU 메모리 곳곳의 블록에 흩어 둔다.
Attention kernel은 block table을 따라 그 블록들을 찾아 읽어야 하고,
앞 주차에서 보았듯 vLLM 원논문의 kernel은 이 때문에 연속 메모리를 쓰는 FasterTransformer의 kernel보다 지연이 20–26% 길었다(원논문 §7.1, Fig. 18a).[^vllm]
게다가 실제 서빙의 batch에는 prefill 조각과 decode가 섞이고, 요청마다 길이가 다르며,
prefix caching으로 여러 요청이 일부 블록을 공유한다.

Ye 등의 FlashInfer는 이런 경우를 하나의 틀로 다룬다.[^flashinfer]
먼저 page table을 **block-sparse 행렬**로 본다.
행은 query, 열은 KV cache의 블록이고, 어떤 query가 어떤 블록을 읽는지가 0이 아닌 칸이다.
PagedAttention의 흩어진 블록,
여러 요청이 공유하는 prefix, 요청마다 다른 길이가 모두 이 형식 하나로 표현된다.
Kernel은 흩어진 블록을 GPU 메모리에서 shared memory의 연속된 공간으로 모은 뒤,
거기서 dense한 Tensor Core 연산을 한다(query가 하나뿐인 tile은 CUDA core 경로를 쓴다).
공유 prefix를 읽는 query들은 행 수가 많은 블록 하나로 묶어, 여러 query가 shared memory에 올린 같은 KV를 재사용하게 한다.
KV cache 자체를 옮기지 않고 색인만 새로 만든다.
예를 들어 두 요청의 KV 블록이 $[A,B,C]$와 $[A,B,D]$라면,
두 query가 함께 읽는 $A,B$ 부분과 각자 읽는 $C$, $D$ 부분으로 나누어 계산하고,
$A,B$는 shared memory에 한 번만 올린다.

FlashInfer는 Flash-Decoding의 부분 결과 합치기도 일반화했다.
Query 하나에 대한 (부분 출력, log-sum-exp) 쌍을 attention state라 부르고,
실수 연산에서 두 state를 합치는 연산이 결합법칙과 교환법칙을 만족하므로 행렬곱의 덧셈처럼 어떤 순서로든 나누어 계산하고 합칠 수 있다고 정리한다.[^flashinfer]
그 위에서 요청마다 다른 KV 길이를 SM들에 고르게 나누는 계획을 CPU(central processing unit)에서 미리 세우고(plan),
GPU kernel은 그 계획대로 실행한다(run).
같은 계획을 모든 층에서 재사용하고,
kernel의 thread block 수를 고정해 CUDA graph와도 함께 쓸 수 있게 했다.
합치는 순서를 원자적 연산에 맡기지 않아, 요청들의 길이 정보가 같으면 늘 같은 순서로 합친다(원논문 §3.3.1).
Batch 구성이 바뀌면 순서도 바뀌어 부동소수점 결과의 마지막 자리가 달라질 수 있다.

SGLang에 붙여 비교한 실험에서 FlashInfer는 Triton으로 작성한 attention backend보다 ITL(inter-token latency)을 29–69% 줄였다(원논문 Fig. 7, H100에서 Llama 3.1 8B·70B).[^flashinfer]
지금은 vLLM과 SGLang 모두 FlashInfer를 attention backend의 하나로 쓴다.

## 3. 선형층과 MoE의 kernel

### 3-1. 작은 batch의 행렬곱

Decode의 선형층은 batch가 작으면 행렬과 벡터의 곱에 가깝다.
가중치가 16-bit라면 이런 연산의 intensity는 토큰 수와 거의 같다.
이때 kernel의 주된 목표는 **가중치를 대역폭의 한계 속도로 흘려 읽는 것**이다.
큰 행렬곱에 맞춰 조율한 kernel을 그대로 쓰면,
한쪽 차원이 아주 작은 이 납작한 행렬곱에서는 대역폭을 다 쓰지 못한다.
Hong 등의 FlashDecoding++는 이 납작한 행렬곱(flat GEMM, GEMM은 general matrix multiplication)을 따로 다뤘다.[^fdpp]
원논문이 비교한 cuBLAS·CUTLASS 구현처럼 batch 쪽 차원을 64행 타일로 처리하면, batch가 8일 때 타일의 87.5%를 0으로 채운 채 계산한다.
FlashDecoding++는 batch 축을 8행까지만 채우고 그 축은 더 나누지 않으며, 일은 출력 차원 방향으로 thread block들에 나눈다.
출력 차원이 크면 shared memory 버퍼 두 개를 번갈아 써서 다음 타일을 읽는 동안 현재 타일을 계산한다(double buffering, 원논문 §4, Fig. 8).

### 3-2. 양자화 가중치의 kernel

Weight-only 양자화(quantization)는 kernel 안에서 가중치를 되돌려야 한다.
Frantar 등의 Marlin은 4-bit 가중치와 FP16 activation의 행렬곱을 위한 kernel이다.[^marlin]
4-bit 가중치를 HBM에서 읽어 shared memory를 거쳐 레지스터로 가져오는 동안 앞선 데이터의 계산을 겹치고,
레지스터 안에서 FP16으로 되돌려 Tensor Core에 넣는다.

원논문은 이 kernel이 언제까지 이득을 내는지 roofline으로 설명한다.
토큰 하나는 가중치 하나마다 2 FLOP(floating-point operation)을 쓰는데, 4-bit 가중치 하나는 0.5 byte이므로,
A10 GPU에서는 batch가 약 50보다 작은 동안 가중치 읽기가 시간을 지배한다(원논문 §3.1).
같은 계산을 H100에 대입하면 batch $b$에서 intensity는 약 $2b/0.5=4b$이므로,
$4b$가 ridge point 295에 닿는 $b\approx74$까지는 가중치를 읽는 시간이 행렬곱을 지배한다.
그동안은 읽는 bytes가 4분의 1로 줄어든 만큼 이상적으로 4배 빨라진다.
그 뒤로는 4-bit 쪽은 계산이 시간을 정하지만, intensity가 $b$인 FP16 쪽은 $b\approx295$까지 아직 읽기가 시간을 정한다.
그래서 이득은 한 번에 사라지지 않고 약 $295/b$배로 줄어(batch 128이면 약 2.3배) $b\approx295$에서 없어진다.
Scale을 읽는 비용 같은 부가 비용은 뺀 근사다.
Marlin의 실측은 A10에서 72k×18k 행렬로 쟀다.
Batch 16–32까지는 scale 저장분을 감안한 이상값 3.87배에 가깝게 냈고,
batch 128에서는 1.5배 정도로 줄었다(원논문 §1, §5.1, Fig. 1).[^marlin]
vLLM에 넣은 end-to-end 측정에서는 RTX A6000의 Llama-2-7B serving에서 TPOT가 FP16 대비 약 2.8배 짧아졌다(원논문 §5.2, Fig. 15).

### 3-3. MoE의 grouped GEMM

MoE 층에서는 batch의 토큰들이 서로 다른 expert로 흩어지고, expert마다 받는 토큰 수가 다르다.
모든 expert에 같은 수의 토큰을 맞춰 하나의 batched 행렬곱으로 계산하는 단순한 구현은,
넘치는 토큰을 버리거나 모자란 자리를 0으로 채워야 했다.
크기가 다른 여러 행렬곱을 묶어 한 번에 실행하는 방식을 grouped GEMM이라 부른다.
Gale 등의 MegaBlocks는 이 계산을 크기가 다른 블록들로 이루어진 block-diagonal 행렬의 곱,
곧 block-sparse 행렬곱으로 바꿔 토큰을 버리지 않고 계산했다.[^megablocks]
Inference 엔진도 같은 생각을 쓴다.
vLLM의 fused MoE kernel은 토큰을 expert 순서로 정렬한 뒤,
블록마다 어떤 expert의 가중치를 쓸지를 표시해 같은 선형층에 속한 모든 expert의 행렬곱을 kernel 하나로 처리한다.[^vllm-fusedmoe]
첫 선형층, 활성화, 둘째 선형층은 따로 호출한다.
Expert parallelism에서 토큰을 GPU 사이로 보내고 받는 all-to-all도 전용 kernel이 맡는다.
DeepSeek가 공개한 DeepEP가 그 예다.[^deepep]

## 4. Kernel 바깥의 시간

### 4-1. Kernel launch와 CUDA graph

Kernel 자체가 빨라도 그 사이가 빈다면 GPU는 논다.
CPU는 kernel을 하나씩 GPU에 제출하는데, 제출마다 마이크로초 단위의 비용이 든다.
NVIDIA의 측정에서 V100에서 2.9 μs짜리 kernel을 하나씩 동기화하며 실행하면 kernel당 9.6 μs가 걸렸다.[^cudagraph-nv]
Decode 한 스텝은 층마다 정규화, 투영,
attention, 활성화 같은 kernel 여러 개를 수십 층에 걸쳐 실행하므로, fusion 정도에 따라 kernel이 수백 개에 이를 수 있다.
vLLM 팀도 H100에서 Llama 8B의 GPU 실행 시간이 스텝당 약 5 ms에 불과해,
CPU 쪽의 비용이 무시할 수 없게 된다고 밝혔다.[^vllm-v1]

**CUDA graph**는 이 비용을 줄인다.
한 스텝에서 실행할 kernel들의 순서와 인자를 한 번 기록(capture)해 두고,
이후에는 기록한 그래프 전체를 한 번에 재생(replay)한다.
NVIDIA의 같은 측정에서 동기화 없이 이어 제출하면 kernel당 3.8 μs, CUDA graph로 재생하면 3.4 μs였다.
이 단순한 예에서는 차이가 작지만, CPU가 kernel을 준비하는 일이 무거운 실제 모델에서는 차이가 커서,
PyTorch 팀은 MLPerf 학습 작업인 Mask R-CNN에서 GPU당 batch 1일 때 backbone 구간이 31 ms에서 6 ms로 줄었다고 보고했다(Fig. 3–4).[^cudagraph-pt]
대신 재생은 같은 kernel을 같은 인자,
같은 메모리 주소로 실행하므로 입력의 모양이 고정되어야 한다.[^cudagraph-pt]
Batch 크기가 스텝마다 바뀌는 서빙에서는 이것이 문제다.
vLLM은 기본 설정에서 처리할 토큰 수 1, 2, 4, 8, 16, 24, …에 맞춘 그래프를 미리 기록해 두고,
실제 토큰 수를 그 수 이상인 가장 작은 기록 크기로 채워(padding) 재생한다.
요청마다 query가 하나인 보통의 decode에서는 이 토큰 수가 곧 batch 크기다.
기록한 가장 큰 크기를 넘으면 그래프 없이 실행한다.
Attention은 요청마다 길이가 달라 그래프에 담기 어려우므로,
v0.31.0의 기본 모드(`FULL_AND_PIECEWISE`)는 attention backend가 지원하면 요청마다 query 길이가 같은 decode batch(uniform decode)는 전체를 그래프 하나로,
나머지는 attention 사이의 구간만 그래프로 기록한다.[^vllm-cg]

<Figure src="https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/docs/assets/design/cuda_graphs/current_design.png" alt="vLLM 문서의 CUDA graph 설계 그림. 위쪽에서 모델은 torch.compile로 attention 사이의 submodule들로 쪼개지고(piecewise compilation), submodule마다 CUDA graph wrapper가 붙는다. 실행 시 요청 batch의 종류와 크기에 따라 세 가지 방식 가운데 하나를 고른다. ### 4-2. 컴파일러

Kernel을 하나하나 손으로 쓰지 않고 컴파일러에 맡기는 길도 있다.
Tillet 등의 Triton은 GPU의 thread 대신 데이터 타일 단위로 연산을 쓰게 하는 언어이자 컴파일러로,
당시 GTX 1070 실험에서 행렬곱이 cuBLAS에 비견하는 성능을 냈다(원논문 §6).[^triton]
PyTorch 2의 `torch.compile`은 Python 프로그램을 실행 중에 그래프로 잡아(TorchDynamo),
GPU에서는 주로 Triton kernel을 생성하고 일부 연산은 라이브러리 kernel을 호출한다(TorchInductor).
A100에서 180개 넘는 모델의 inference를 기하평균 2.27배 빠르게 했다.[^pt2]
앞서 본 kernel fusion을 사람이 일일이 하지 않아도 컴파일러가 찾아 준다.
Fusion은 HBM 왕복과 함께 제출할 kernel 수도 줄이므로, 컴파일러는 kernel 안과 바깥의 시간을 함께 줄인다.

Inference 엔진은 둘을 섞어 쓴다.
vLLM은 attention 사이의 토큰별 연산을 `torch.compile`로 묶어 fusion하고 그 구간을 CUDA graph로 기록하며,[^vllm-cg] attention은 FlashAttention이나 FlashInfer처럼 직접 최적화한 kernel을 쓴다.
FlashInfer 논문도 Triton이 아직 여러 경우에 CUDA·CUTLASS로 쓴 kernel만큼 빠르지 않아 CUDA 코드를 생성한다고 밝힌다.[^flashinfer]
성능이 가장 중요한 몇 개의 kernel은 손으로, 나머지는 컴파일러로 처리하는 분업이다.

## 5. 정리

Decode에서 kernel이 하드웨어를 다 쓰지 못하는 까닭은 대개 일의 모양에 있다.
병목의 모양과 그에 맞춘 kernel을 묶으면 다음과 같다.

| 일의 모양 | 생기는 문제 | 대응 |
|---|---|---|
| 짧은 query, 긴 KV cache | batch × head만으로는 SM이 남는다 | Flash-Decoding의 KV split과 LSE 합치기 |
| 흩어진 블록, 다른 길이, 공유 prefix | 연속 메모리를 전제한 kernel이 맞지 않는다 | FlashInfer의 block-sparse 형식과 plan/run |
| 작은 batch의 선형층 | 큰 행렬곱용 타일이 0을 계산한다 | flat GEMM kernel |
| 작은 batch의 가중치 읽기 | 읽는 bytes가 시간을 정한다 | 4-bit 가중치를 레지스터에서 되돌리는 Marlin |
| expert마다 다른 토큰 수 | padding을 하거나 토큰을 버린다 | block-sparse 행렬곱, fused MoE kernel |
| 짧은 kernel의 연속 | 제출 비용 동안 GPU가 논다 | CUDA graph, `torch.compile`의 fusion |

어느 경우든 기준은 roofline이 정한 하한이다.
Memory-bound인 decode에서는 MBU로 대역폭을 얼마나 쓰는지 보고,
batch가 커져 compute-bound로 옮겨 가면 MFU(model FLOPs utilization)와 계산 시간의 하한을 함께 본다.
Marlin의 이득이 batch에 따라 줄어들듯, 같은 kernel이라도 어떤 batch에서 쓰는지가 효과를 정한다.

Kernel 하나의 배율이 곧 서비스의 배율도 아니다.
도입의 8 ms 스텝에서 attention이 2 ms를 차지한다고 가정하면,
attention kernel을 두 배 빠르게 해도 스텝은 7 ms가 되어 약 1.14배 빨라질 뿐이다(Amdahl의 법칙).
그래서 개선은 스텝 시간을 연산별로 나누어 보고 큰 몫부터 손댄다.
