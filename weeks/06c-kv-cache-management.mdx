앞의 두 노트는 같은 결론에 닿았다. [06a §4-3](/lecture/2026f-advanced-deep-learning/06a-llm-inference/#4-3-동시에-처리할-수-있는-요청-수)에서 H100 한 대에 Llama 3 8B를 올리면 KV cache에 약 53.5 GB가 남아 8,192토큰 요청이 49개까지 들어간다고 계산했고, [06b §4-2](/lecture/2026f-advanced-deep-learning/06b-roofline/#4-2-kv-cache-용량의-벽)에서 batch를 키워 처리량을 올리는 일이 이 공간에서 먼저 막힌다는 것을 보았다. 그런데 이 계산은 공간을 한 칸도 낭비하지 않는다고 가정했다. 실제 서빙 시스템은 이 공간을 얼마나 알뜰하게 쓰고 있을까? 그리고 여러 요청이 같은 문장을 따로따로 계산해 저장하고 있지는 않을까?

이 노트는 KV cache를 서빙 중에 관리하는 방법을 다룬다. 전체 지도는 Jiang 등의 서베이[^survey]로 잡는다. 이 서베이는 모델 가중치나 구조를 바꾸지 않고 서빙 단계에서 KV cache를 다루는 방법만 범위로 삼아, 실행 순서(temporal), 저장 위치(spatial), 표현과 보존(structural)의 세 축으로 나눈다. 이 노트의 §1–2(공간 할당)와 §3(prefix 재사용)은 서베이 §5.2.1에, §4의 양자화는 §5.1.1, eviction은 §5.2.2, offloading은 §4.1에 대응한다. 같은 서베이도 범위에서 뺀 구조 변경, 곧 GQA·MLA처럼 KV head나 표현 자체를 줄이는 방법은 [3주차 Attention heads and KV cache](/lecture/2026f-advanced-deep-learning/03b-kv-cache-attention/)에서, sliding window처럼 참조 위치를 줄이는 방법은 [3주차 Efficient attention](/lecture/2026f-advanced-deep-learning/03c-efficient-attention/)에서 다뤘다.

세 가지 문제를 차례로 본다. 공간을 미리 잡아 두는 방식의 낭비(§1–2), 같은 prefix를 요청마다 다시 계산하고 저장하는 중복(§3), 그리고 낭비와 중복을 없애도 남는 길이에 비례하는 크기(§4)다. 문제마다 동기가 달라 해법도 각각의 계보를 따른다.

## 1. 연속 공간 할당의 낭비

### 1-1. 최대 길이만큼 미리 잡기

KV cache는 생성이 진행되면서 토큰 하나에 한 칸씩 자란다. 문제는 요청이 들어올 때 그 요청이 몇 토큰을 생성할지 모른다는 점이다. Attention kernel은 한 요청의 key·value가 메모리에 연속으로 놓여 있다고 가정하는 경우가 많았기 때문에, 이전 서빙 시스템들은 요청마다 **최대 길이만큼의 연속 공간**을 미리 잡았다. Kwon 등은 이런 방식에서 생기는 낭비를 세 가지로 나누었다.[^vllm]

<Figure src="https://arxiv.org/html/2309.06180v1/baseline-memory-management.svg" alt="vLLM 논문의 Figure 3. 한 줄로 이어진 KV cache 공간에 요청 A와 요청 B가 나란히 놓여 있다. 요청 A는 프롬프트 'Four score and seven years ago our' 7칸, 지금까지 생성한 'fathers brought' 2칸, 앞으로 생성할 'forth'와 종료 토큰 2칸(reserved), 끝까지 쓰이지 않을 2,038칸(internal fragmentation)을 차지한다. 두 요청 사이의 빈칸은 external fragmentation이다. 요청 B도 프롬프트 'You only live' 3칸과 생성 중인 'once' 뒤로 남은 칸을 미리 잡고 있다." caption="최대 길이만큼 연속 공간을 미리 잡을 때의 세 가지 낭비. Reserved는 나중에 쓰이지만 지금은 다른 요청이 쓸 수 없는 칸, internal fragmentation은 끝까지 쓰이지 않는 칸, external fragmentation은 요청 사이에 남은 칸이다." source="Kwon et al. (2023), Efficient Memory Management for Large Language Model Serving with PagedAttention, Figure 3. CC BY 4.0. 원본 그대로 사용." hero />

- **Reserved**: 앞으로 생성할 토큰을 위해 잡아 둔 칸이다. 결국 쓰이지만, 쓰이기 전까지는 다른 요청이 쓸 수 없다.
- **Internal fragmentation**: 최대 길이를 넉넉히 잡은 탓에 끝까지 쓰이지 않는 칸이다. 그림의 요청 A는 최대 2,048칸을 잡았지만 12칸만 쓰고 끝나 2,038칸이 남는다.
- **External fragmentation**: 요청마다 크기가 다른 덩어리를 잡았다 놓기를 반복하면서 덩어리 사이에 생기는 빈틈이다. 합하면 넉넉해도 새 요청이 들어갈 만큼 이어진 공간이 없을 수 있다.

<Callout type="example">
Llama 3 8B로 최대 8,192토큰을 허용하는 서비스에서, 입력 100토큰에 출력 200토큰을 생성하고 끝나는 요청을 생각하자. 연속 할당은 요청이 들어오는 순간 8,192칸, 1 GiB를 잡는다. 실제로 쓰는 칸은 300칸, 37.5 MiB로 3.7%다. 06a의 53.5 GB를 이런 요청에 나누어 준다면 동시에 49개만 받을 수 있지만, 쓰는 만큼만 준다면 산술적으로 1,300개 넘게 받을 수 있다.
</Callout>

### 1-2. 측정된 낭비

Kwon 등은 이 낭비를 실제 서빙 실험에서 쟀다. Orca 방식으로 최대 길이만큼 미리 잡으면 KV cache 공간의 20.4%만 실제 토큰 상태를 담았다. 할당 크기를 2의 거듭제곱으로 맞추면 26.8%, 출력 길이를 미리 안다고 가정한 이상적인 경우(Oracle)에도 38.2%였다(원논문 Figure 2).[^vllm] Oracle에서도 internal fragmentation이 사라질 뿐 reserved와 external fragmentation이 남기 때문이다. 06b의 표에서 KV cache 공간이 batch 크기의 상한이었으니, 이 낭비는 곧 처리량의 손실이다.

## 2. PagedAttention

### 2-1. 블록과 block table

Kwon 등은 운영체제가 프로세스의 메모리를 관리하는 방식, 곧 **paging**을 가져왔다. 운영체제는 프로세스에게 연속된 가상 주소를 보여 주면서 실제 메모리는 고정 크기의 page 단위로 흩어 배치하고, page table로 둘을 잇는다. vLLM은 같은 생각으로 KV cache를 고정 크기 **블록**으로 나눈다. 원논문의 비유대로 블록은 page, 토큰은 byte, 요청은 process에 해당한다.[^vllm]

<Figure src="https://arxiv.org/html/2309.06180v1/logical-and-physical-block-table.svg" alt="vLLM 논문의 Figure 6. 요청 A의 프롬프트는 'Four score and seven years ago our', 출력은 'fathers', 'brought' 순이다. 왼쪽의 logical KV block은 블록마다 토큰 4칸이며 block 0에 Four score and seven, block 1에 years ago our fathers, block 2에 brought가 들어 있다. 가운데 block table은 logical block 0을 physical block 7에, block 1을 physical block 1에, block 2를 physical block 3에 대응시키고, 블록마다 채워진 칸 수(4, 3에서 4로, 1)를 기록한다. 오른쪽의 physical KV block은 GPU 메모리에서 7, 1, 3번 블록에 흩어져 있다. 동그라미 숫자 1, 2, 3은 prefill, 첫 decode, 둘째 decode 단계를 뜻한다." caption="Logical 블록과 physical 블록을 잇는 block table. 요청은 연속된 logical 블록을 보지만 실제 블록은 GPU 메모리 어디에나 놓일 수 있다. 동그라미 숫자는 블록이 채워진 단계다." source="Kwon et al. (2023), Efficient Memory Management for Large Language Model Serving with PagedAttention, Figure 6. CC BY 4.0. 원본 그대로 사용." hero />

요청마다 logical 블록이 순서대로 이어지고, block table은 logical 블록마다 그 내용을 담은 physical 블록 번호와 채워진 칸 수를 기록한다. 새 토큰이 생기면 마지막 블록의 빈칸에 쓰고, 블록이 다 차면 그때 빈 physical 블록 하나를 새로 받는다. 요청이 끝나면 블록을 모두 돌려준다. 이렇게 하면 미리 잡는 공간이 없어 reserved가 사라지고, 모든 블록의 크기가 같아 external fragmentation도 사라진다. 남는 낭비는 요청마다 마지막 블록의 빈칸뿐이라, 원논문의 표현대로 낭비가 요청당 블록 하나 안으로 제한된다(원논문 §4.3).[^vllm]

<Callout type="example">
vLLM의 기본 블록 크기는 16토큰이다(원논문 §7.2).[^vllm] Llama 3 8B에서 블록 하나는 $16\times128\ \text{KiB}=2\ \text{MiB}$다. §1-1의 요청이 300토큰까지 자라면 블록 19개(304칸)를 쓰고, 마지막 블록의 빈칸 4개, 0.5 MiB만 낭비한다. 연속 할당의 1 GiB 대신 38 MiB다. 블록이 너무 작으면 블록 table을 읽고 블록을 오가는 비용이 늘고, 너무 크면 마지막 블록의 빈칸이 커진다. 원논문은 ShareGPT 작업에서 16–128토큰 블록이 가장 좋았다고 보고했다.
</Callout>

이 방식에는 대가가 있다. 한 요청의 key·value가 메모리에 흩어져 있으므로, attention kernel이 block table을 보며 블록을 찾아 읽어야 한다. 원논문은 이 때문에 attention kernel 자체의 지연이 연속 메모리를 쓰는 FasterTransformer보다 20–26% 길었다고 밝혔다(원논문 §7.1).[^vllm] 그래도 batch를 훨씬 크게 키울 수 있어 전체 처리량은 크게 오른다. 흩어진 블록을 효율적으로 읽는 kernel은 7주차 kernel 노트에서 다룬다.

### 2-2. 블록 공유와 copy-on-write

블록 단위 관리는 공유도 쉽게 만든다. 같은 프롬프트로 응답 여러 개를 sampling하는 parallel sampling이나 beam search에서는 여러 시퀀스가 같은 prefix를 가진다. 연속 할당에서는 시퀀스마다 그 prefix의 KV cache를 복사해 두어야 했지만, block table을 쓰면 여러 시퀀스의 logical 블록이 같은 physical 블록을 가리키게 하면 된다. vLLM은 physical 블록마다 몇 개의 시퀀스가 가리키는지 reference count를 두고, 공유 중인 블록에 어느 한 시퀀스가 새 토큰을 써야 할 때만 그 블록을 복사한다. 운영체제의 **copy-on-write**와 같은 방식이다(원논문 §4.4).[^vllm]

공유로 줄어드는 메모리는 작업에 따라 다르다. OPT-13B 실험에서 parallel sampling은 6.1–9.8%(Alpaca)와 16.2–30.5%(ShareGPT), 가지가 더 많이 공유되는 beam search는 37.6–55.2%와 44.3–66.3%의 메모리를 아꼈다(원논문 Figure 15).[^vllm]

### 2-3. 결과와 선점

이 설계를 구현한 것이 vLLM이다. 원논문은 같은 지연 수준에서 FasterTransformer와 Orca보다 처리량이 2–4배 높았다고 보고했다.[^vllm] §1-2에서 20.4–38.2%였던 KV cache 공간의 실제 사용률은 96.3%로 올랐다(원논문 Figure 2).

공간을 쓰는 만큼만 주면 새로운 문제가 생긴다. 생성 도중 빈 블록이 바닥날 수 있다는 것이다. 그때는 실행 중인 요청 일부를 멈추고(preemption) 그 블록을 회수해야 한다. 원논문은 두 방법을 비교했다. 멈춘 요청의 블록을 CPU 메모리로 옮겨 두었다가 다시 가져오는 swapping과, 블록을 버리고 나중에 다시 prefill해 KV cache를 재계산하는 recomputation이다(원논문 §4.5). 재계산은 이미 생성한 토큰까지 프롬프트처럼 한 번에 처리하므로 원래의 decode보다 훨씬 빠르다. 현재 vLLM은 recomputation을 기본으로 쓴다.[^vllm-opt] 어떤 요청을 멈추고 어떤 요청을 먼저 실행할지는 다음 노트의 scheduling 문제다.

## 3. Prefix 재사용

### 3-1. 반복되는 prefix

§2의 공유는 한 요청 안에서 갈라진 시퀀스끼리의 이야기였다. 실제 서비스에서는 **서로 다른 요청**도 같은 시작 부분을 자주 가진다. 모든 요청 앞에 붙는 시스템 프롬프트, 같은 few-shot 예시, 대화가 이어질 때마다 다시 보내는 이전 대화, [06a §1-2](/lecture/2026f-advanced-deep-learning/06a-llm-inference/#1-2-늘어나는-생성-길이)의 agent가 도구 결과를 받을 때마다 다시 넣는 문맥이 그렇다. Causal attention에서 어떤 위치의 key·value는 그 위치까지의 토큰에만 달려 있으므로, 시작 토큰열이 같으면 그 부분의 KV cache도 같다.

<Callout type="example">
2,000토큰짜리 시스템 프롬프트를 모든 요청 앞에 붙이는 서비스를 생각하자. Llama 3 8B에서 이 부분의 prefill은 약 33 TFLOP이라 H100의 peak로도 약 33 ms, peak의 절반을 낸다면 약 67 ms다. KV cache로는 $2000\times128\ \text{KiB}\approx262$ MB다. 이 부분을 한 번만 계산해 두고 재사용하면, 요청마다 TTFT에서 수십 ms를 덜고 동시 요청마다 262 MB씩 중복 저장하던 공간을 하나로 줄인다.
</Callout>

이렇게 이미 계산한 prefix의 KV cache를 다른 요청에서 찾아 쓰는 것이 **prefix caching**이다. 찾는 방법에 따라 두 가지 설계가 있다.

### 3-2. Hash 기반 prefix caching

vLLM의 automatic prefix caching은 블록 단위로 찾는다.[^vllm-apc] 블록마다 hash를 계산하는데, 그 블록의 토큰만이 아니라 **부모 블록의 hash**를 함께 넣는다. 그래서 같은 hash는 그 블록까지의 prefix 전체가 같다는 뜻이 된다. LoRA adapter ID, 멀티모달 입력의 hash, 다른 사용자와 cache를 분리하기 위한 salt 같은 부가 정보도 hash에 들어간다. 새 요청이 오면 첫 블록부터 hash를 계산해 이미 있는 블록을 찾고, 처음으로 없는 블록부터 prefill한다.

꽉 찬 블록만 cache에 넣는다는 점에 주의한다. 문서의 예처럼 블록 크기가 4일 때 프롬프트 14토큰 가운데 앞 10토큰이 이전 요청과 같다면, 앞의 두 블록(8토큰)만 재사용된다. 셋째 블록은 4칸 가운데 2칸만 같기 때문이다.[^vllm-apc]

요청이 끝난 블록은 곧바로 지우지 않고 빈 블록 목록에 넣어 두되 cache에는 남겨 둔다. 새 요청이 같은 prefix를 찾으면 다시 꺼내 쓰고, 빈 블록이 필요하면 가장 오래 쓰이지 않은 블록부터 내보낸다(LRU, least recently used). 한 요청의 블록을 목록에 넣을 때는 뒤쪽 블록부터 넣는다. 뒤쪽 블록일수록 더 긴 prefix를 hash에 담아 다시 쓰일 가능성이 낮으므로 먼저 내보내기 위해서다.[^vllm-apc]

### 3-3. RadixAttention

SGLang의 RadixAttention은 cache를 **radix tree**로 관리한다.[^sglang] 나무의 각 간선은 토큰열을 나타내고, 뿌리에서 어떤 노드까지의 경로가 하나의 prefix다. 새 요청이 오면 나무에서 가장 길게 일치하는 경로를 찾아 그 KV cache를 재사용하고, 나머지 부분을 계산한 뒤 나무에 가지로 붙인다. 이 방식에서 page의 크기는 토큰 하나라서, vLLM과 달리 블록 경계와 상관없이 일치하는 토큰까지 재사용한다.

메모리가 모자라면 **가장 오래 쓰이지 않은 잎**부터 지운다. 잎부터 지우면 여러 요청이 공유하는 조상 노드는 남아 계속 재사용된다. 실행 중인 요청이 쓰고 있는 노드는 reference count가 0이 아니어서 지우지 않는다. 또 cache와 실행 중인 요청이 같은 메모리 공간을 나누어 쓰므로, cache를 위한 공간을 따로 떼어 둘 필요가 없다.[^sglang]

재사용을 늘리려면 요청의 처리 순서도 바꿔야 한다. 같은 prefix를 가진 요청들이 멀리 떨어져 처리되면 그 사이에 cache가 지워질 수 있다. SGLang은 대기 중인 요청을 cache와 일치하는 prefix가 긴 순서로 정렬해 먼저 처리하는 cache-aware scheduling을 제안했고, 이 순서가 나무를 깊이 우선으로 훑는 것과 같아 오프라인에서는 최적임을 보였다(원논문 Theorem 3.1). 다만 일치하는 prefix가 짧은 요청은 계속 밀려 굶을 수 있다.[^sglang] 현재 SGLang은 이 정책을 선택 사항으로 두고 기본값은 도착 순서(FCFS, first come first served)다.[^sglang-args]

SGLang 논문은 여러 작업에서 cache 적중률이 50–99%였고, 처리량이 최대 6.4배 높아졌다고 보고했다. Chatbot Arena에 배치했을 때 Vicuna-33B의 적중률은 74.1%였고 첫 토큰 지연은 평균 1.7배 줄었다(원논문 §6).[^sglang] [06a §3-4](/lecture/2026f-advanced-deep-learning/06a-llm-inference/#3-4-서버-내부-지표)의 prefix cache 적중률이 바로 이 값이다. 적중률이 높은 작업일수록 TTFT와 처리량이 함께 좋아진다.

<Callout type="note">
두 설계는 같은 문제를 다른 단위로 푼다. vLLM은 PagedAttention의 블록을 그대로 cache 단위로 써서 블록 경계까지만 재사용하고, hash 조회로 빠르게 찾는다. SGLang은 토큰 단위의 나무로 일치하는 토큰까지 모두 재사용하고, 나무 구조로 공유 관계를 드러내 eviction과 scheduling에 쓴다. 지금은 두 엔진 모두 상대의 장점을 상당 부분 받아들였으므로, 엔진을 고를 때는 설계 이름보다 작업에서 실제 적중률을 재 보는 편이 낫다.
</Callout>

## 4. 길이에 비례하는 크기 줄이기

§2–3으로 낭비와 중복을 없애도, 남은 KV cache는 여전히 토큰 하나에 128 KiB씩 문맥 길이에 비례해 자란다. 06b §4-2에서 보았듯 긴 문맥의 decode는 이 KV cache를 읽는 시간이 스텝을 지배한다. 서빙 단계에서 이 크기를 줄이는 방법은 세 갈래다. 토큰 하나를 적은 bytes로 저장하거나(양자화), 저장할 토큰 수를 줄이거나(eviction), GPU 밖의 더 큰 저장소로 옮기는 것(offloading)이다.

### 4-1. 양자화

가장 직접적인 방법은 KV cache의 원소당 bytes $p$를 줄이는 것이다. vLLM은 KV cache를 FP8로 저장하는 옵션을 제공한다. 텐서 전체 또는 attention head마다 scale을 두고, 보정 데이터로 scale을 정하는 것을 권장한다.[^vllm-fp8] Llama 3 8B라면 토큰당 128 KiB가 64 KiB로 줄어, 06a의 53.5 GB에 약 816,000토큰이 들어간다. 같은 메모리로 두 배의 batch를 받을 수 있고, 긴 문맥에서는 스텝마다 읽는 bytes도 거의 절반이 된다.

더 낮은 비트로 가면 어떤 축으로 묶어 scale을 둘지가 중요해진다. Liu 등의 KIVI는 key와 value의 분포가 다르다는 데서 출발했다.[^kivi] Key에는 값이 유독 큰 channel이 몇 개 고정되어 나타나므로, 같은 channel끼리 묶어(per-channel) scale을 두어야 그 큰 값이 다른 channel의 정밀도를 망치지 않는다. Value에는 그런 패턴이 없고, attention 출력은 토큰별 value의 가중합이므로 토큰끼리 묶는(per-token) 편이 오차가 작다.

<Figure src="https://arxiv.org/html/2402.02750v2/quant_scheme.svg" alt="KIVI 논문의 양자화 단위 그림. 왼쪽은 per-token 양자화로, 토큰 수만큼의 길이를 가진 scale과 zero-point 벡터가 행렬 X 옆에 세로로 붙고 빨간 점선이 한 행(토큰 하나)을 묶는다. 오른쪽은 per-channel 양자화로, 차원 d만큼의 길이를 가진 scale과 zero-point 벡터가 행렬 위에 가로로 놓이고 빨간 점선이 한 열(channel 하나)을 묶는다." caption="Per-token과 per-channel 양자화. 같은 scale과 zero-point를 공유하는 범위가 행(토큰)인지 열(channel)인지가 다르다. KIVI는 key를 per-channel로, value를 per-token으로 양자화한다." source="Liu et al. (2024), KIVI: A Tuning-Free Asymmetric 2bit Quantization for KV Cache, 원논문 그림. CC BY 4.0. 원본 그대로 사용." />

Key를 channel 단위로 묶으려면 여러 토큰이 모여야 하므로, KIVI는 가장 최근 토큰 128개까지는 원래 정밀도로 두고 32개씩 모일 때마다 2-bit로 양자화한다. 이렇게 2-bit KV cache로 모델 가중치를 포함한 최대 메모리를 2.6배 줄였고, batch를 최대 4배 키워 처리량을 2.35–3.47배 높였다(Llama-2-7B, A100 한 대).[^kivi] 서베이도 key는 channel 단위, value는 토큰 단위로 양자화하는 것이 흔한 관행이 되었다고 정리한다(서베이 §5.1.1).[^survey] 양자화 자체의 원리는 7주차 양자화 노트에서 가중치와 함께 다룬다.

### 4-2. Eviction

토큰을 덜 저장하는 방법도 있다. 생성 중에 모든 과거 토큰이 똑같이 중요하지는 않다는 관찰에서 출발한다. Zhang 등의 H2O는 OPT 모델의 attention 행렬이 거의 모든 층에서 95% 넘게 희소하고, 누적 attention 점수가 power law를 따라 소수의 토큰에 몰린다는 것을 관찰했다.[^h2o] 그런 토큰을 heavy hitter라 부르고, 최근 토큰과 heavy hitter만 KV cache에 남기고 나머지를 지운다. 20%의 heavy hitter만 남기고도 처리량이 기존 inference 시스템보다 최대 29배 높아졌다.

Li 등의 SnapKV는 지울 토큰을 정하는 시점을 prefill로 옮겼다.[^snapkv] 프롬프트의 마지막 부분(observation window)이 앞부분의 어느 위치에 attention하는지를 보면, 생성하는 동안 각 head가 주목할 위치를 미리 알 수 있다는 관찰이다. Head마다 그 위치들만 골라 KV cache를 압축하고, 고른 위치 주변을 pooling으로 함께 남겨 전화번호에서 국가 번호만 남는 식으로 정보가 끊기는 것을 막는다. 16K토큰 입력에서 생성 속도를 3.6배, 메모리 효율을 8.2배 높였고, A100 한 대에서 380K토큰 문맥을 처리했다.

<Callout type="warning">
Eviction은 손실이 있는 압축이다. 지운 토큰의 key·value는 나중에 그 토큰이 다시 중요해져도 되살릴 수 없다. [3주차 Normalization and attention sink §4-3](/lecture/2026f-advanced-deep-learning/03e-normalization/#4-3-대응)의 StreamingLLM도 같은 성격이어서, 생성이 무너지지 않게 할 뿐 밀려난 중간 토큰의 정보를 볼 수 있게 하지는 않는다. 긴 문서에서 특정 문장을 찾아야 하는 작업처럼 어떤 토큰이 나중에 필요할지 미리 알기 어려운 경우에는 품질을 꼭 확인한다. §2–3의 paging과 prefix caching은 결과를 바꾸지 않는다는 점에서 성격이 다르다.
</Callout>

### 4-3. Offloading과 계층 저장

마지막 갈래는 KV cache를 지우지 않고 GPU 밖으로 옮기는 것이다. GPU 메모리(HBM) 바깥에는 CPU 메모리(DRAM), SSD, 네트워크로 연결된 다른 서버의 메모리가 있다. 가까울수록 빠르고 작으며, 멀수록 느리고 크다. 서베이는 이런 계층 사이에서 KV cache를 배치하고 옮기는 방법을 §4.1에서 정리한다.[^survey]

이 방식이 특히 잘 맞는 곳이 §3의 prefix caching이다. GPU 메모리에서 밀려난 prefix를 지우는 대신 CPU 메모리에 두었다가, 같은 prefix의 요청이 오면 다시 가져온다. Liu 등의 LMCache는 vLLM·SGLang 같은 엔진이 만든 KV cache를 GPU 밖으로 꺼내 저장하고, 여러 요청과 여러 엔진 인스턴스가 공유하게 하는 계층이다.[^lmcache] Qin 등의 Mooncake는 GPU cluster의 CPU 메모리, DRAM, SSD를 묶어 하나의 분산 KV cache pool로 쓰고, 블록마다 자기 내용과 prefix로 hash를 만들어 중복을 없앤다. Moonshot AI의 Kimi 서비스가 이 구조로 운영된다.[^mooncake]

<Callout type="example">
§3-1의 2,000토큰 prefix를 CPU 메모리에서 가져온다고 하자. KV cache는 262 MB다. H100 사양표의 PCIe Gen5 대역폭 128 GB/s를 모두 쓴다면 약 2 ms, 그 절반만 쓴다고 해도 약 4 ms다.[^h100] 같은 부분을 다시 prefill하는 데는 peak로도 약 33 ms가 든다. 가져오는 쪽이 훨씬 싸다. 반대로 prefix가 짧거나 SSD나 네트워크처럼 더 느린 곳에 있다면 차이가 줄어, 재계산이 나을 수도 있다.
</Callout>

## 5. 정리

KV cache 공간은 06a·06b에서 batch 크기와 처리량의 상한이었다. 이 노트는 그 공간을 서빙 단계에서 관리하는 세 가지 문제와 해법을 보았다.

| 문제 | 해법 | 대가 |
|---|---|---|
| 최대 길이만큼 연속 공간을 미리 잡아 20–38%만 사용 | PagedAttention: 고정 크기 블록과 block table, 공유와 copy-on-write | 흩어진 블록을 읽는 kernel의 부담, 공간이 바닥날 때의 선점 |
| 같은 prefix를 요청마다 다시 계산하고 저장 | Prefix caching: 블록 hash(vLLM) 또는 radix tree(SGLang), LRU eviction | 적중률이 작업과 처리 순서에 달림 |
| 낭비가 없어도 문맥 길이에 비례하는 크기 | 양자화(FP8, KIVI), eviction(H2O, SnapKV), offloading(LMCache, Mooncake) | 양자화와 eviction은 품질 손실 가능, offloading은 전송 시간 |

앞의 두 문제의 해법은 계산 결과를 바꾸지 않고 공간과 계산의 낭비만 없앤다. 셋째 문제의 양자화와 eviction은 근사이므로 품질을 확인해야 하고, offloading은 결과를 바꾸지 않는 대신 전송 시간을 치른다. 모델 구조를 바꿔 KV cache 자체를 작게 만드는 GQA·MLA는 이 모든 방법과 함께 쓸 수 있다.

공간을 쓰는 만큼만 주고 prefix를 재사용하면, 이제 여러 요청을 어떤 순서로 묶어 실행할지가 성능을 좌우한다. 어떤 요청을 먼저 prefill하고, 공간이 모자랄 때 누구를 멈추고, prefill과 decode를 한 batch에 섞을지가 다음 노트의 주제다.
