다음 토큰의 정답은 문서 자체에서 얻을 수 있다. 그렇다면 문서를 많이 모으기만 하면 좋은 모델이 될까? Zhao 등의 LLM(large language model) 서베이가 구분하는 데이터 준비·목적함수·학습 설정[^survey]을 따라 이 질문을 살펴본다. 중심은 **어떤 텍스트를 어떤 비율로 어떤 학습 샘플에 담는가**다.

## 1. LLM 학습 과정

우리가 사용하는 대화 모델은 큰 텍스트 말뭉치로 학습한 직후의 모델과 구분할 필요가 있다. 대표적인 개발 흐름은 다음과 같다. 모든 모델이 같은 단계나 순서를 따르는 것은 아니며, 데이터를 보강하고 평가하면서 여러 번 반복하기도 한다.

| 구분 | 대표적인 데이터 | 학습에서 바꾸려는 것 |
|---|---|---|
| Pre-training | 문서·코드 등 대규모 말뭉치 | 다양한 문맥의 다음 토큰을 예측하는 기반 능력 |
| Post-training: SFT(supervised fine-tuning) | 지시와 응답, 대화 예시 | 원하는 입력 형식에서 적절한 응답을 생성하는 행동 |
| Post-training: 선호도 학습·RL(reinforcement learning) | 응답 선호도, 검증 가능한 보상, 상호작용 결과 | 여러 가능한 응답 중 목적에 더 맞는 행동을 강화 |

필요하면 base model에 특정 언어·도메인 데이터를 더 학습하는 **continued pre-training**을 수행한다. 모든 모델에 필수인 별도 단계는 아니다. Post-training 안에서도 SFT와 선호도 학습·RL을 어떤 순서와 조합으로 사용할지는 달라진다.

Pre-training을 마친 **base model**은 텍스트를 이어 쓰는 모델이다. 질문 뒤에 답변을 쓸 수도 있지만, 질문을 반복하거나 시험지의 다음 문제를 이어 쓸 수도 있다. SFT는 원하는 응답 예시를 학습에 사용한다. 둘 다 next-token loss를 사용할 수 있으나 데이터 분포와 loss를 적용하는 구간이 다르다.

Llama 3 보고서는 pre-training과 post-training을 각각 §3과 §4에서 다룬다. 이처럼 하나의 모델 보고서를 단계별로 읽으면 최종 성능의 변화가 어느 학습 단계에서 나온 것인지 구분하기 쉽다.[^llama]

## 2. 학습 목표

### 2-1. 세 구조의 사전학습

1주차에서 본 구조와 대표적인 학습 목표를 정리하면 다음과 같다. 구조와 목적함수는 설계상 별개이므로 아래 연결이 가능한 조합의 전부는 아니다.

| 구조 | 문맥을 읽는 방식 | 대표적인 사전학습 목표 |
|---|---|---|
| Encoder-only | 입력 내부에서 양방향으로 참조 | 가린 토큰 복원: BERT의 MLM(masked language modeling) |
| Decoder-only | 현재 위치와 이전 위치 참조 | 다음 토큰 예측: causal language modeling |
| Encoder–decoder | 입력을 양방향으로 읽고 출력은 순차 생성 | 손상된 입력에서 빠진 부분이나 원문 복원: T5 계열 |

### 2-2. NTP 목적함수

이제 decoder-only의 NTP(next-token prediction)에 집중한다. 데이터의 토큰열을 $t_1,\ldots,t_T$라고 하면 각 위치에서 앞선 토큰들을 조건으로 다음 토큰에 확률을 준다.

$$
p_\theta(t_{1:T})=\prod_{i=1}^{T}p_\theta(t_i\mid t_{<i})
$$

첫 토큰의 조건은 문서 시작 토큰 등으로 구현할 수 있다. 최대우도 학습은 관측된 토큰열에 높은 확률을 주는 방향으로 가중치 $\theta$를 바꾼다. 음의 로그를 취하면 곱이 합으로 바뀌어 각 위치를 따로 채점할 수 있다.

$$
\mathcal{L}=-\frac{1}{\sum_i m_i}\sum_i m_i\log p_\theta(t_i\mid t_{<i})
$$

$m_i$는 해당 정답 위치를 loss에 포함하면 1, 제외하면 0인 mask다. 유효한 정답이 적어도 하나 있다고 가정한다. 이 식은 데이터에 실제로 나타난 토큰에 낮은 확률을 줄수록 큰 벌점을 준다.

<Callout type="example">
두 위치의 정답 확률이 각각 0.5와 0.25라면 평균 loss는 $-(\log0.5+\log0.25)/2\approx1.040$이다. 두 번째 정답 확률을 0.5로 올리면 약 0.693으로 줄어든다. 여기서 로그는 자연로그이며 단위는 nat이다.
</Callout>

### 2-3. 입력과 정답

가상 토큰열 `[BOS, 부산, 항구, EOS]`를 보자. BOS(beginning of sequence)와 EOS(end of sequence)는 문서 시작·종료를 표시하는 special token이다. 입력을 한 칸 오른쪽의 정답과 짝지으면 다음과 같다.

| 위치 | 입력 토큰 | 참조 가능한 문맥 | 정답 |
|---|---|---|---|
| 0 | BOS | BOS | 부산 |
| 1 | 부산 | BOS, 부산 | 항구 |
| 2 | 항구 | BOS, 부산, 항구 | EOS |

실제 모델에는 문자열이 아닌 ID를 넣는다. 한 번의 causal forward로 세 위치의 logits를 얻고, 각 위치에서 정답 ID의 확률을 읽어 cross-entropy를 계산한다. **학습 중에는 정답을 채점하기 위해 토큰을 sampling할 필요가 없다.** 미분 가능한 loss에서 gradient를 구해 embedding·attention·FFN(feed-forward network) 등 연결된 가중치를 갱신한다. 이때 입력의 실제 앞선 토큰을 사용하는 방식이 teacher forcing이다.

NTP의 정답은 텍스트 자체에서 얻는다. 사람이 문장마다 별도 라벨을 붙일 필요가 적다는 점이 큰 말뭉치를 활용하는 데 유리하다. 동시에 데이터의 오류·반복·편향도 학습 신호가 될 수 있다. **정답을 자동으로 얻는 것과 데이터가 저절로 좋아지는 것은 다른 문제**다.

## 3. 학습 데이터

### 3-1. 데이터 구성과 분포

우리 연구실에서 한국어와 코드를 잘 다루는 모델을 학습한다고 가정하자. 웹 문서가 가장 많다는 이유로 모두 같은 확률로 읽히면, 목표 능력에 필요한 데이터는 드물게 나타날 수 있다. 먼저 모델의 사용 목적과 평가할 도메인을 정하고, 그에 맞춰 데이터의 구성을 살펴야 한다.

| 데이터 유형 | 얻을 수 있는 신호 | 살펴볼 문제 |
|---|---|---|
| 웹 문서 | 다양한 주제와 언어 표현 | 광고·탐색 메뉴·중복·기계 생성 텍스트 |
| 책·논문·교육 자료 | 긴 설명과 구조화된 지식 | 접근·이용 조건, 추출 품질, 도메인 편중 |
| 코드 | 문법과 구조, 문제 해결 패턴 | 생성 파일·복제 저장소·라이선스·비밀정보 |
| 다국어 문서 | 언어별 표현과 지식 | 언어 식별 오류, 언어별 양과 품질 격차 |
| 합성 데이터 | 부족한 유형의 예시 보강 | 생성 모델의 오류와 반복, 검증 가능성 |

이 표는 데이터셋의 성능 순위가 아니라, 수집할 때 던질 질문이다. 공개적으로 읽을 수 있는 문서와 학습·재배포 조건이 확인된 문서도 구분해야 한다. 데이터 출처, 수집 시점, 필터 설정을 기록하면 나중에 성능 변화의 원인을 추적할 수 있다.

### 3-2. 추출·필터링·중복 제거

다음은 교육용 데이터 처리 흐름이다. 실제 파이프라인에서는 순서를 바꾸거나 여러 단계를 반복한다.

```
수집과 출처 기록
  → 본문 추출·언어 식별
  → 품질·안전·민감정보 필터링
  → 중복 제거·평가 데이터 오염 점검
  → train/validation 분리
  → 데이터 혼합·tokenization·학습 샘플 구성
```

**본문 추출**은 HTML 태그를 지우는 것보다 어렵다. 메뉴와 본문을 구분하고, 표나 코드의 구조를 얼마나 보존할지 정해야 한다. 줄바꿈을 모두 없애면 일반 산문은 읽을 수 있어도 코드의 의미가 달라질 수 있다.

**품질 필터링**은 문서 길이, 반복 비율, 언어 판별 점수나 학습된 분류기 등을 사용할 수 있다. 기준을 강하게 하면 잡음을 줄일 수 있지만, 짧은 질의응답이나 소수 언어의 정상 문서를 제거할 수도 있다. 필터 통과율만 보지 말고 빠진 문서의 표본을 직접 읽어야 한다.

**중복 제거**는 같은 문서의 여러 URL, 조금씩 바뀐 복제 페이지, 문서 내부의 긴 반복 구간을 다룬다. 완전 일치와 근접 중복은 다른 문제다. Lee 등의 연구는 중복 제거를 암기된 텍스트 생성 및 train–test 중복과 연결해 분석한다.[^dedup]

**평가 데이터 오염**은 학습 데이터에 benchmark 문제나 해설이 들어 있는 경우다. 문자열 일치로 찾을 수 있는 중복도 있지만 번역·의역된 유출은 더 어렵다. “검사에서 발견하지 못했다”는 결과만으로 오염이 없다고 단정하지 않는다.

<Callout type="example">
같은 한국어 강의 안내문이 서로 다른 50개 사이트에 복제되어 있다고 하자. URL 단위로 train과 validation을 나누면 양쪽에 같은 본문이 들어갈 수 있다. 먼저 본문 유사성을 기준으로 묶고, 같은 묶음이 양쪽에 흩어지지 않도록 분리하는 방법을 생각할 수 있다. 단순 무작위 분할의 단위가 왜 중요한지 보여주는 예다.
</Callout>

FineWeb은 데이터 처리 선택을 바꾸어 같은 구조의 모델을 학습하고 성능을 비교한다.[^fineweb] 아래는 WARC(Web ARChive)에서 추출한 텍스트에 기본 필터를 적용한 경우와 적용하지 않은 경우의 비교다. 필터를 통과한 문서 수보다 **그 데이터로 학습한 모델의 평가 결과**를 본다는 점에 주목하자.

### 3-3. 데이터 혼합과 반복 노출

문서가 저장된 비율과 학습에서 선택하는 비율은 다를 수 있다. 말뭉치의 문서 수가 아니라 **모델이 소비하는 토큰의 비율**로 혼합을 설명하면 계산 예산과 연결하기 쉽다.

예를 들어 100M 토큰을 읽힐 때 일반 문서 60%, 코드 25%, 한국어 전문 자료 15%를 목표로 삼았다고 하자. 이는 교육용 설정이며 권장 비율이 아니다. 한국어 전문 자료가 5M 토큰뿐이라면 15M 토큰을 소비하기 위해 평균적으로 약 세 번 재사용해야 한다. 비율을 높이는 선택에는 반복 노출이 따라온다.

$$
\text{평균 노출 횟수}\approx
\frac{\text{해당 데이터에서 소비할 토큰 수}}{\text{해당 데이터의 고유 토큰 수}}
$$

따라서 데이터량을 보고할 때 **고유 데이터량과 학습 중 소비한 총 토큰 수**를 구분한다. 같은 1B 토큰이라는 표현도 새 텍스트 1B를 한 번 읽은 것과 100M을 열 번 읽은 것은 다르다.

혼합 비율은 학습 내내 고정할 수도 있고 후반에 바꿀 수도 있다. 어느 쪽이 나은지는 목표 도메인별 검증 결과를 보아야 한다. 평균 loss가 내려가도 작은 도메인의 성능은 나빠질 수 있으므로, 일반 문서·한국어·코드 평가를 따로 유지하는 것이 이 예제에 적합하다.

### 3-4. 학습 시퀀스와 문서 경계

문서의 길이는 제각각이지만 모델은 한 번에 처리할 수 있는 context 길이가 정해져 있다. 따라서 말뭉치의 문서와 학습에 넣는 시퀀스가 항상 일대일로 대응하지는 않는다. 긴 문서를 여러 구간으로 나누거나, 짧은 문서를 이어 붙여 일정 길이의 시퀀스를 만들 수 있다. Megatron 방식의 일반적인 pre-training은 문서들을 이어서 샘플을 구성한다.[^packing]

여기서 **배열에서 이웃한 두 문서를 서로의 문맥으로 사용할 것인지**는 별도로 정해야 한다. EOS는 문서 종료를 표시하는 토큰이지 attention을 자동으로 끄는 명령이 아니다.

| 문서 경계 처리 | 뒤 문서가 읽는 문맥 | 학습 데이터의 의미 |
|---|---|---|
| 이어진 causal stream | 현재 배열에 있는 앞 문서까지 참조 가능 | 문서 경계를 포함한 토큰 흐름을 이어 쓰기 |
| 문서별 attention 분리 | 자기 문서의 앞선 토큰만 참조 | 여러 문서를 같은 배열에 담아도 각 문서를 독립적으로 학습 |

독립적인 문서를 학습하려면 입력·정답도 문서별로 맞춘다. §2-3의 문서 A와, 한 토큰 더 긴 문서 B를 보자. 아래는 실제 tokenizer 출력이 아닌 교육용 토큰이다.

| 문서 | 입력 토큰 | 각 위치의 정답 |
|---|---|---|
| A | `[BOS, 부산, 항구]` | `[부산, 항구, EOS]` |
| B | `[BOS, 코드, 실행, 완료]` | `[코드, 실행, 완료, EOS]` |

A의 마지막 입력 `항구`는 EOS를 예측하고, B의 첫 입력 BOS는 `코드`를 예측한다. 두 입력 배열을 붙여 저장해도 A의 마지막 정답을 B의 BOS로 바꾸지 않는다. 문서별 attention을 분리하고 position ID를 문서마다 다시 시작하도록 정하면, 두 문서를 따로 읽혔을 때의 문맥을 보존할 수 있다. 여기서는 이 독립 문서 구성을 예제로 사용하며, 모든 pre-training이 같은 처리를 한다는 뜻은 아니다.

<Callout type="note">
Attention mask는 **어디를 볼 수 있는가**, loss mask는 **어디의 예측을 채점하는가**를 정한다. 어떤 위치를 loss에서 제외하는 것만으로 서로 다른 문서의 attention이 차단되지는 않는다.
</Callout>

## 4. 학습과 평가

### 4-1. 가중치 갱신

한 배치를 학습하는 순서는 다음과 같다.

```
입력·정답·mask 준비
  → forward로 위치별 logits 계산
  → 유효한 정답 위치의 cross-entropy 평균
  → backward로 gradient 계산
  → optimizer가 가중치 갱신
  → 다음 배치
```

Learning rate는 gradient를 따라 이동하는 크기를 조절한다. 대표적인 optimizer인 AdamW는 gradient의 이동평균과 제곱의 이동평균을 유지해 파라미터별 갱신 크기를 조절하고, weight decay를 gradient 기반 갱신과 분리해 적용한다. 이 두 평균을 저장하는 데도 메모리가 필요하다.[^adamw]

학습 초기에는 learning rate를 낮게 시작해 점차 높이는 **warmup**을 사용하기도 한다. 학습 후반의 **decay**는 갱신 폭을 줄인다. **Gradient clipping**은 gradient norm이 임계값을 넘으면 전체 크기를 줄여 한 번의 과도한 갱신을 제한한다. 세 방법은 역할이 다르므로 하나가 다른 하나를 대신하지 않는다. 실제 recipe를 읽을 때에는 learning rate뿐 아니라 전체 학습 길이, batch 크기, warmup 길이를 함께 확인한다.

### 4-2. 검증 지표

Training loss가 줄어드는 것만으로는 충분하지 않다. 적어도 서로 다른 질문을 나누어 본다.

| 관측 | 답하려는 질문 |
|---|---|
| Training loss | 학습 데이터의 정답 토큰을 더 잘 맞히는가? |
| Held-out loss | 학습에 넣지 않은 같은 종류의 텍스트에도 일반화하는가? |
| 도메인별 평가 | 한국어·코드 등 목표한 능력이 개선되는가? |
| 생성 결과 표본 | 반복·형식 오류·데이터 암기 같은 문제가 보이는가? |

Perplexity는 평균 NTP loss를 지수화한 값이다. 위의 loss 1.040 예제라면 $\exp(1.040)\approx2.83$이다. 낮을수록 정답에 더 높은 확률을 준다는 의미지만, **서로 다른 tokenizer의 토큰 단위 perplexity는 곧바로 비교하지 않는다**. 토큰 단위와 평가 텍스트, 문맥 길이, mask 조건을 맞춰야 한다.[^perplexity]

데이터 구성과 검증 방법을 정해도 모델 크기와 학습 기간은 아직 선택해야 한다. 같은 계산 예산으로 큰 모델을 짧게 학습할지, 작은 모델에 더 많은 토큰을 읽힐지가 scaling의 문제다.
