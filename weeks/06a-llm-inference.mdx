학습을 마친 LLM(large language model)을 실제로 써서 답을 생성하는 단계가 inference다.
Reasoning model의 긴 CoT(chain of thought)나 agent처럼 요청 하나가 처리하는 토큰이 늘면서,
inference 비용을 줄이는 일은 더 중요해졌다.

Inference 비용은 세 가지로 나누어 볼 수 있다.[^survey]

- **Computational cost**: 계산 자체의 양으로, FLOPs(floating-point operations)로 센다.
- **Memory access cost**: 가중치나 KV(key-value) cache 같은 데이터를 메모리에서 연산 장치로 읽어 오고 결과를 다시 쓰는 데 드는 비용이다.
- **Memory usage**: 가중치와 KV cache 등이 GPU(graphics processing unit) 메모리를 차지하는 양이다.

먼저 생성이 prefill과 decode 두 단계로 나뉘는 과정을 보고, 각 단계의 시간을 computational cost와 memory access cost 가운데 어느 쪽이 정하는지 따진다.
이어서 GPU 메모리에 가중치와 KV cache가 얼마나 들어가고, 그 공간이 동시에 처리할 수 있는 요청 수를 어떻게 정하는지 계산한다.
마지막으로 사용자가 겪는 지연과 서버 전체의 처리량을 어떤 지표로 재는지 정리한다.
기준 모델은 Llama 3 8B(층 수 $L=32$, query head 32개, KV head 8개, head 차원 $d_h=128$, 최대 문맥 128K 토큰)다.[^llama3]

## 1. Prefill과 decode

### 1-1. Autoregressive 생성

학습은 teacher forcing으로 정답 문장을 입력에 넣고 causal mask로 각 위치가 자기와 왼쪽만 보게 하므로,
길이 $n$인 시퀀스의 모든 위치를 한 번의 forward로 처리하고 각 위치의 loss를 병렬로 구한다.
생성은 정답 문장이 없으니 그럴 수 없다.
다음 토큰은 앞 토큰을 고른 뒤에야 입력할 수 있다.

$$
x_{n+1}\sim p_\theta(\cdot\mid x_{1:n}),\qquad
x_{n+2}\sim p_\theta(\cdot\mid x_{1:n+1}),\qquad\dots
$$

$p_\theta$는 파라미터가 $\theta$인 모델이 앞 토큰들을 보고 내놓는 다음 토큰 분포다.
이렇게 앞 토큰들을 조건으로 한 토큰씩 차례로 생성하는 방식을 autoregressive 생성이라 한다.
토큰을 하나씩 생성하므로 출력 토큰 $m$개를 만들려면 모델 전체를 $m$번 차례로 실행해야 한다.

### 1-2. KV cache

이 반복에서 매번 처음부터 다시 계산하지 않아도 되는 부분이 있다.
Attention 층 하나에서 head 하나만 보면, 위치 $t$의 출력은 그 위치의 query와 위치 1부터 $t$까지의 key·value로 계산한다.

$$
q_t=x_tW^Q,\qquad k_j=x_jW^K,\qquad v_j=x_jW^V
$$

$$
o_t=\sum_{j=1}^{t}\operatorname{softmax}_j\!\left(\frac{q_t\cdot k_j}{\sqrt{d_h}}\right)v_j
$$

$x_j$는 그 층에 들어오는 위치 $j$의 벡터다.
Causal mask 때문에 $x_j$는 위치 $j$까지의 토큰에만 달려 있으므로, 뒤에 새 토큰이 붙어도 과거 위치의 $k_j$와 $v_j$는 바뀌지 않는다.
그래서 한 번 계산한 key·value를 층마다 저장해 두고 다음 스텝에서 다시 쓴다.
이 저장소가 **KV cache**다.
Query는 저장하지 않는다.
다음 토큰을 고르는 데는 새 위치의 출력 $o_t$만 필요하고, 그 계산에는 새 query $q_t$ 하나만 쓰이기 때문이다.

정리하면 새 토큰 하나를 만들 때 층마다 새 토큰의 query·key·value만 계산하고,
새 key·value를 cache 뒤에 붙인 뒤, 새 query로 cache 전체를 읽어 attention을 계산한다.[^survey]

<Callout type="example">
입력 1,000토큰에 출력 200토큰인 요청을 forward에 넣는 토큰 수로 세어 보자.
Cache가 없으면 출력 토큰을 하나 만들 때마다 지금까지의 시퀀스 전체를 다시 넣어야 하므로,
1,000, 1,001, …, 1,199토큰을 차례로 넣어 모두 $200\times1{,}000+(0+1+\dots+199)=219{,}900$토큰을 처리한다.
Cache가 있으면 처음에 1,000토큰을 한 번 넣고 그 뒤로는 새 토큰 하나씩 199번 넣으므로 1,199토큰이면 된다.
약 180배 차이이고, 출력이 길어질수록 차이는 더 커진다.

KV cache를 쓰면 생성 요청은 성격이 다른 두 단계, prefill과 decode로 나뉜다.[^survey]

### 1-3. 두 단계의 역할

**Prefill.** 프롬프트의 토큰 $n$개를 한 번의 forward로 함께 처리해 모든 층의 key·value를 KV cache에 쓰고, 첫 출력 토큰을 고른다.
$n$개 토큰이 함께 계산되므로 학습의 forward처럼 큰 행렬곱이 된다.

**Decode.** 그다음부터는 직전에 고른 토큰 하나만 입력해 다음 토큰을 고른다.
스텝마다 새 토큰의 key·value를 cache 뒤에 붙이고, cache 전체를 읽어 attention을 계산한다.
이 과정을 종료 토큰이 나오거나 최대 길이에 이를 때까지 반복한다.

## 2. 단계마다 다른 병목

두 단계에서 forward 한 번에 담긴 일의 양이 다르다는 것이 실행 시간으로 어떻게 이어지는지 보려면, 먼저 GPU가 계산과 데이터를 어떻게 나누어 다루는지 알아야 한다.
GPU는 계산을 하는 연산 장치와 데이터를 담는 메모리로 이루어지고, 메모리는 크기와 속도가 다른 두 층으로 나뉜다.

| 구성 | 위치 | H100 SXM | 하는 일 |
|---|---|---|---|
| 연산 장치(SM의 Tensor Core 등) | GPU 칩 안 | SM 132개 | 행렬곱 같은 계산 |
| SRAM(register, shared memory, L2 cache 등) | GPU 칩 안, 연산 장치 곁 | 합산하면 약 120 MB | 지금 계산할 데이터를 잠시 둔다. 매우 빠르다 |
| HBM | GPU 칩 바로 옆, 같은 패키지 안 | 80 GB, 초당 3.35 TB | 가중치와 KV cache를 모두 담는다 |

SM(streaming multiprocessor)은 연산 장치를 묶은 단위이고, SRAM(static random-access memory)은 연산 장치 자체가 아니라 그 곁에 붙은 작고 빠른 메모리다.[^hopper]
흔히 "GPU 메모리 80 GB"나 VRAM(video RAM)이라 부르는 것이 HBM(high-bandwidth memory)이다.[^h100]
계산하려면 데이터를 HBM에서 SRAM을 거쳐 연산 장치로 읽어 와야 하는데,
SRAM은 다 합쳐도 약 120 MB라 16 GB인 8B 모델의 가중치를 담아 둘 수 없다.<Sidenote>약 120 MB는 사양표에 적힌 값이 아니라 직접 더한 값이다. H100 SXM의 SM 132개마다 register file 256 KB와 L1 cache·shared memory 256 KB가 있고 L2 cache가 50 MB이므로, 약 34 MB + 34 MB + 50 MB ≈ 118 MB다.[^h100]</Sidenote>
그래서 forward를 한 번 할 때마다 가중치 전체를 HBM에서 다시 읽어 온다.
GPU는 읽기와 계산을 겹쳐 진행하므로, forward 한 번의 시간은 대략 **읽는 시간**과 **계산하는 시간** 가운데 긴 쪽이 정한다.

Prefill은 한 번 읽은 가중치를 $n$개 토큰에 함께 쓴다.
프롬프트가 어느 정도 길면 계산하는 시간이 읽는 시간보다 길어진다.[^distserve]
이렇게 computational cost가 시간을 정하는 단계를 **compute-bound**라 부른다.
Decode는 같은 가중치를 다 읽어 와서 토큰 하나에만 쓴다.
계산은 금방 끝나고 시간 대부분이 가중치와 KV cache를 읽는 데, 곧 memory access cost에 든다.
이런 단계는 **memory-bound**다.

<Callout type="example">
Llama 3 8B의 BF16(bfloat16) 가중치는 약 16 GB다.
H100 SXM은 HBM에서 초당 3.35 TB를 읽고, BF16 행렬곱을 초당 약 $989\times10^{12}$ FLOPs(989 TFLOP/s, sparsity를 쓰지 않는 dense 연산 기준)까지 계산한다.[^h100][^hopper]
가중치를 한 번 읽는 데는 $16\ \text{GB}/3.35\ \text{TB/s}\approx4.8$ ms가 걸린다.
토큰 하나의 forward는 파라미터마다 곱셈과 덧셈을 한 번씩 하므로 계산량이 약 $2N\approx16$ GFLOPs(파라미터 수 $N\approx8.03\times10^9$)이고, 계산은 $16\ \text{GFLOPs}/989\ \text{TFLOP/s}\approx0.016$ ms면 끝난다.
Decode 한 스텝은 읽는 데 4.8 ms, 계산하는 데 0.016 ms라서 연산 장치는 시간의 99% 이상을 기다린다.
1,000토큰을 prefill하면 계산이 1,000배인 16 ms로 늘지만 가중치는 여전히 한 번만 읽으므로, 이번에는 계산이 더 오래 걸린다.
두 시간이 같아지는 것은 토큰 약 300개를 함께 처리할 때다.
여기서는 attention 계산과 KV cache 읽기를 빼고, 계산과 읽기가 사양값의 최대 속도로 완전히 겹친다고 단순화했다.
</Callout>

그래서 prefill에는 계산을 줄이거나 여러 GPU에 나누는 방법이,
decode에는 읽어 올 데이터를 줄이거나 한 번 읽은 가중치를 여러 토큰에 함께 쓰는 방법이 주로 효과를 낸다.

Decode에서 가중치를 여러 토큰에 함께 쓰는 대표적인 방법은 여러 요청의 decode 스텝을 한 forward로 묶는 **batching**이다.
가중치를 한 번 읽어 여러 요청의 토큰을 계산하므로 연산 장치가 기다리는 시간이 줄어든다.
다만 요청마다 KV cache는 따로 읽어야 하므로 묶은 수만큼 읽는 양도 함께 는다.

## 3. Memory usage

Batching으로 묶은 요청은 저마다 KV cache를 GPU 메모리에 두어야 한다.
그래서 얼마나 많이 묶을 수 있는지는 메모리가 정한다.
요청을 받아 batch로 묶고 모델을 실행하는 소프트웨어를 서빙 엔진이라 하며, 이 노트는 오픈소스 엔진 vLLM을 예로 든다.
KV cache에 쓸 수 있는 공간은 엔진이 쓰도록 잡아 둔 GPU 메모리에서 가중치, activation, workspace(계산 중에 잠시 쓰는 버퍼)를 빼고 남은 만큼이다.
Llama 3 8B를 GPU 한 대에 올려 그 숫자를 계산해 보자.

### 3-1. 가중치

가중치 메모리는 파라미터 수에 원소당 바이트 수를 곱한 값이다.
Embedding까지 포함한 Llama 3 8B의 파라미터는 약 8.03B개이고, BF16은 원소당 2 bytes이므로 가중치는 약 16.1 GB다.
학습과 달리 gradient나 optimizer 상태가 없으므로 이 값이 모델 상태의 전부이고, 요청 수나 문맥 길이와 상관없이 고정이다.

이 값을 줄이는 방향은 두 가지다.
하나는 원소당 바이트 수를 줄이는 양자화(quantization)다.
모든 가중치를 4-bit 정수(INT4)로 둔다고 단순화하면 약 4 GB가 된다.
다른 하나는 pruning, low-rank factorization, distillation처럼 파라미터 수 자체를 줄이는 압축이다.

### 3-2. KV cache

Head가 여러 개인 MHA(multi-head attention)는 head마다 key·value를 따로 만든다.
Llama 3 8B는 query head 네 개가 KV head 하나를 함께 쓰는 GQA(grouped-query attention)라서, query head는 32개지만 KV head는 8개다.
Cache에는 KV head의 key·value만 저장하므로 KV head 수가 cache 크기를 정한다.

Llama 3 8B처럼 모든 층이 전체 문맥에 attention하는 모델에서 KV cache는 층마다, KV head마다, 지금까지의 모든 토큰에 대해 key와 value 벡터를 하나씩 저장한다.
토큰 하나에 저장하는 원소 수에 원소당 바이트 수(BF16이면 2 bytes)를 곱하면 토큰당 크기가 나온다($n_{kv}$는 KV head 수).

$$
\frac{\text{KV cache}}{\text{토큰}}
=\underbrace{2}_{K,\,V}\cdot L\cdot n_{kv}\cdot d_h\cdot(\text{원소당 bytes})
=2\cdot32\cdot8\cdot128\cdot2\ \text{bytes}
=131{,}072\ \text{bytes}=128\ \text{KiB}
$$

KiB(kibibyte)는 $2^{10}$ bytes, GiB(gibibyte)는 $2^{30}$ bytes로, $10^{9}$ bytes인 GB와 다르다.

요청 하나의 KV cache는 이 값에 그 요청의 길이(입력과 지금까지의 출력 토큰 수의 합)를 곱한 만큼으로 잡는다.
요청끼리 공유하는 부분이 없다면 서버 전체의 KV cache는 동시에 처리 중인 요청 길이의 합에 비례한다.

| 상황 | KV cache | 가중치(BF16, 16.1 GB) 대비 |
|---|---|---|
| 8,192토큰 요청 1개 | 1 GiB (1.07 GB) | 약 0.07배 |
| 131,072토큰 요청 1개 | 16 GiB (17.2 GB) | 약 1.07배 |
| 8,192토큰 요청 32개 | 32 GiB (34.4 GB) | 약 2.1배 |

최대 문맥인 128K(131,072)토큰을 채운 요청 하나만으로도 KV cache가 가중치만큼 커지고,
요청을 많이 묶으면 가중치를 쉽게 넘어선다.
이것도 GQA로 줄인 값이다.
MHA처럼 query head마다 KV head를 따로 두었다면 토큰당 512 KiB로 이 표의 네 배였다.

### 3-3. 동시에 처리할 수 있는 요청 수

가중치와 KV cache 말고도 실행 중의 activation과 workspace가 필요하다.
학습과 달리 backward가 없어 층의 중간 결과를 다음 층으로 넘기면 버릴 수 있으므로 activation의 비중은 작다.
vLLM은 시작할 때 더미 입력으로 forward를 한 번 돌려(profile run) activation 메모리의 peak를 재고, 가중치와 그만큼을 뺀 나머지를 KV cache 공간으로 잡는다.[^vllm-worker]

<Callout type="example">
메모리 80 GB인 H100 SXM 한 대에 vLLM을 띄운다.
vLLM은 기본적으로 GPU 메모리의 92%를 쓰므로 사용할 수 있는 공간은 약 73.6 GB다.[^vllm-args]
여기서 가중치 16.1 GB와 실행 중의 activation과 workspace 약 4 GB를 뺀다고 가정하면 KV cache에 약 53.5 GB가 남는다.
토큰당 128 KiB이므로

$$
\frac{53.5\times10^{9}\ \text{bytes}}{131{,}072\ \text{bytes/토큰}}\approx408{,}000\ \text{토큰}
$$

이다.
요청마다 8,192토큰까지 자란다면 동시에 49개, 131,072토큰까지 자란다면 3개만 들어간다.
</Callout>

이 계산에서 세 가지를 읽을 수 있다.
첫째, 이 설정에서 GPU 한 대가 동시에 처리할 수 있는 요청 수의 상한은 **KV cache가 들어갈 공간**이 정한다.
연산이 포화되기 전까지는 요청을 많이 묶을수록 처리량이 오르므로, 처리량의 상한도 이 공간에 묶인다.
둘째, 요청이 최종적으로 몇 토큰까지 자랄지는 생성이 끝나기 전에는 알 수 없다.
요청마다 최대 길이만큼 공간을 미리 잡아 두면 실제로 짧게 끝나는 요청의 몫이 낭비되고,
너무 적게 잡으면 생성 도중 공간이 모자란다.
셋째, 같은 시스템 프롬프트로 시작하는 요청들은 프롬프트의 앞부분(prefix)이 같은데,
이 부분의 KV cache를 공유하지 않으면 요청마다 따로따로 저장하는 낭비도 생긴다.

## 4. 성능 지표

### 4-1. 요청 하나의 지연

사용자는 응답이 스트리밍될 때 두 가지를 체감한다.
첫 글자가 뜨기까지의 대기와, 그 뒤 글자가 흘러나오는 속도다.
생성한 토큰을 바로 스트리밍한다면 앞의 것은 주로 prefill이, 뒤의 것은 decode가 정한다.
이를 나누어 재는 지연(latency) 지표가 다음 네 가지다.
정의는 vLLM의 벤치마크 문서를 따른다.[^vllm-bench]

- <strong>TTFT(time to first token)</strong>는 요청을 보낸 시점부터 첫 출력 토큰을 받을 때까지의 시간이다.
  클라이언트 쪽에서 재므로 prefill 시간 말고도 요청이 서버 대기열에서 기다린 시간,
  토크나이즈 같은 전처리 시간, 네트워크 왕복 시간이 함께 들어간다.
- <strong>ITL(inter-token latency)</strong>는 이웃한 두 출력이 도착하는 간격이다.
  요청 하나에서 간격이 여러 개 나오므로 모든 간격을 모아 분포로 본다.
- <strong>E2E(end-to-end) latency</strong>는 요청을 보낸 시점부터 마지막 토큰까지의 시간이다.
- <strong>TPOT(time per output token)</strong>는 첫 토큰 뒤 출력 토큰 사이의 평균 간격으로, 요청마다 한 번 계산한다.
  출력 토큰이 $m$개($m>1$)일 때 $(\text{E2E}-\text{TTFT})/(m-1)$이므로, E2E latency는 $\text{TTFT}+(m-1)\cdot\text{TPOT}$와 같다.

<figcaption>요청 하나의 지연 지표. 0.25초에 첫 토큰, 6.22초에 200번째 토큰이 도착한 요청을 축척 없이 그렸다. 토큰 하나가 막대 하나이며, 가운데 토큰과 TTFT에 들어가는 대기·네트워크 시간은 생략했다. vLLM 벤치마크 문서의 정의를 바탕으로 직접 구성했다.[^vllm-bench]</figcaption>
</figure>

토큰이 하나씩 도착하면 한 요청의 TPOT는 그 요청 ITL들의 평균과 같다.
TPOT는 요청마다 평균 속도 하나를, ITL은 간격 하나하나의 분포를 보여 준다는 점이 다르다.

지연 지표는 평균만으로 보지 않는다.
같은 서버에서도 입력 길이, 도착 시점, 앞선 요청이 자원을 얼마나 오래 쓰는지에 따라 요청마다 지연이 크게 다르고, 부하가 높을수록 이 차이가 커진다.
그래서 중앙값(p50)과 함께 분포의 꼬리 쪽 백분위수(tail percentile)인 p90·p99를 본다.
p90·p99는 요청들을 지연이 짧은 순으로 늘어놓았을 때 각각 90번째, 99번째 백분위수다.
예를 들어 TTFT의 p99가 2초라면 요청 100개 가운데 99개는 2초 안에 첫 토큰을 받고, 나머지 1개 정도가 그보다 오래 기다린다.

### 4-2. 서버 전체의 처리량

서비스를 운영하는 쪽은 서버가 단위 시간에 얼마나 많은 일을 하는지, 곧 처리량(throughput)을 본다.
**Output token throughput**은 측정 시간 동안 생성한 출력 토큰 수를 시간으로 나눈 값이고,
**request throughput**은 같은 시간에 끝낸 요청 수를 시간으로 나눈 값이다.
입력 토큰까지 더한 total token throughput을 함께 보고하기도 한다.[^vllm-bench]

<Callout type="example">
60초 동안 요청 300개가 각각 200토큰을 생성했다면 output token throughput은 초당 1,000토큰이다.
이때 요청마다 TPOT가 앞 그림의 요청처럼 30 ms라면 사용자 한 명이 보는 속도는 초당 약 33토큰이다.
서버 처리량이 사용자 한 명이 보는 속도의 30배쯤인 이유는 여러 요청이 동시에 decode되기 때문이다.
같은 길이의 요청이 고르게 들어온다면 초당 5건이 도착하고, 각 요청은 약 6초($199\times30$ ms) 동안 decode된다.
초당 5건씩 들어와 6초씩 머무르므로 어느 순간에나 약 $5\times6=30$개 요청이 함께 decode되고 있다.
평균 동시 요청 수가 도착률과 머무는 시간의 곱이라는 이 관계를 Little's law라 한다.
</Callout>

처리량과 지연은 대체로 한쪽을 얻으면 다른 쪽을 내주는 관계다.
함께 decode하는 요청을 늘리면 처리량은 오르지만,
요청마다 KV cache를 따로 읽고 계산도 늘어 decode 한 스텝, 곧 요청 하나의 TPOT가 길어진다.

### 4-3. 서버 내부 지표

지연과 처리량이 결과라면, 그 원인을 보여 주는 서버 내부의 상태가 있다.
vLLM 같은 서빙 엔진은 다음 값을 지표나 로그로 보여 준다.[^vllm-metrics]

| 지표 | 읽는 법 |
|---|---|
| KV cache 사용률 | KV cache용으로 잡아 둔 공간 중 쓰고 있는 비율. 1에 가까우면 새 요청을 받을 자리가 거의 없다 |
| Prefix cache 적중률 | 새 요청의 프롬프트 토큰 가운데 다시 계산하지 않고 이전 요청의 KV cache를 재사용한 비율. 시스템 프롬프트처럼 prefix가 같은 요청이 많을수록 높고, 높을수록 prefill 계산이 준다 |
| 실행·대기 요청 수 | 대기 요청이 쌓이면 TTFT가 길어진다 |

예를 들어 TTFT의 p99가 길어졌는데 KV cache 사용률이 1 근처이고 대기 요청이 쌓여 있다면,
계산이 느려서라기보다 KV cache 공간이 모자라 새 요청이 들어가지 못하는 상황을 먼저 의심할 수 있다.
