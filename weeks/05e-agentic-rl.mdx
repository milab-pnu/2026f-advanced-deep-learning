지금까지의 RL(reinforcement learning)은 프롬프트 하나에 응답 하나를 내는 문제였다. [04b](/lecture/2026f-advanced-deep-learning/04b-rlhf/)의 PPO(proximal policy optimization)도, [05c](/lecture/2026f-advanced-deep-learning/05c-policy-optimization/)의 GRPO(group relative policy optimization)도 응답이 끝나면 에피소드가 끝나고 보상이 한 번 온다. 실제 과제의 많은 부분은 그렇지 않다. 검색해서 읽고 다시 검색하고, 코드를 실행해 오류를 보고 고치고, 사용자와 여러 턴을 주고받는다. 모델의 출력이 환경을 바꾸고 환경의 응답이 다음 입력이 되는 이 설정을 **agentic RL**이라고 부른다. 이 노트는 단일 응답 RL이 도구 호출과 다중 턴 궤적으로 확장될 때 무엇이 달라지는지를 따라간다. 데이터의 형태, 손실을 거는 위치, 보상이 오는 시점, 그리고 [05d](/lecture/2026f-advanced-deep-learning/05d-rl-systems/)의 생성 비용이 모두 바뀐다.

전체 지도는 Zhang 등이 2025년에 정리하고 2026년 TMLR에 실린 agentic RL 서베이[^survey]로 잡는다. §2가 단일 응답 RL과 agentic RL을 MDP(Markov decision process)의 형식으로 대비하고, §3이 능력별(계획, 도구 사용, 기억, 자기 개선, 추론, 지각) 분류를, §4가 과제별 분류를, §5가 환경과 프레임워크를 정리한다. 이 노트는 §2의 형식과 §3.2의 도구 사용에 집중한다.

## 1. 단일 응답에서 궤적으로

### 1-1. 형식의 차이

서베이 §2는 지금까지의 post-training RL을 **퇴화한 MDP**로 본다.[^survey] 상태는 프롬프트 하나이고, 행동은 응답 전체이며, 행동 뒤에 상태 전이가 없고, 보상은 한 번 온다. Agentic RL은 부분 관측 MDP(partially observable MDP, POMDP)다. 정책이 행동(텍스트, 도구 호출)을 내면 환경이 관측(검색 결과, 실행 출력, 사용자 답)을 돌려주고, 그것이 다음 상태의 일부가 되며, 보상은 여러 시점에 올 수 있고 최종 성공은 여러 턴 뒤에 정해진다.

| | 단일 응답 RL (04b–05c) | Agentic RL |
|---|---|---|
| 상태 | 프롬프트 | 프롬프트 + 지금까지의 행동과 관측 |
| 행동 | 응답 전체 (토큰열) | 한 턴의 텍스트 또는 도구 호출 |
| 전이 | 없음 (한 스텝에 종료) | 환경이 관측을 돌려줌 |
| 보상 | 응답 끝에 한 번 | 최종 결과, 또는 턴마다 |
| 궤적 길이 | 응답 하나 | 턴 여러 개, 수만 토큰 |

### 1-2. 학습에서 달라지는 세 가지

이 형식 변화가 04b–05c의 학습 절차에 미치는 영향은 셋이다.

**손실을 거는 위치.** 궤적에는 정책이 생성하지 않은 토큰이 섞여 있다. 검색 결과와 실행 출력은 환경이 넣은 것이므로, 정책의 log 확률을 올리거나 내리는 대상이 아니다. Search-R1은 검색으로 가져온 토큰을 손실에서 mask했고, 이 mask가 없으면 학습이 불안정했다고 보고했다.[^searchr1] [04a §2-3](/lecture/2026f-advanced-deep-learning/04a-sft/)의 loss mask가 지시 토큰을 제외한 것과 같은 논리이고, 대상이 관측 토큰으로 바뀐 것이다.

**보상의 귀속.** 최종 보상 하나를 여러 턴에 어떻게 나누는가가 credit assignment 문제다. 가장 단순한 방법은 04b §3-2의 return처럼 최종 보상을 모든 턴에 그대로 주는 것이고, 턴마다 별도 보상(도구 호출 형식, 중간 결과)을 더하면 [05a §2-4](/lecture/2026f-advanced-deep-learning/05a-rlvr/)의 process 보상이 된다.

**생성 비용.** 궤적 하나를 만들려면 정책 생성과 환경 실행이 번갈아야 한다. 도구 실행(검색, 코드 실행)의 지연이 생성에 더해지고, 궤적 길이의 분산이 커진다. 05d의 비동기 설계가 여기서 더 절실해지며, 실행 결과가 학습 신호를 주지 않는 궤적이 많다는 보고도 있다.[^liu2026]

<Callout type="example">
**두 턴 궤적의 return.** 정책이 (턴 1) 검색어를 내고, 환경이 문서를 돌려주고, (턴 2) 답을 쓴다고 하자. 최종 답이 맞아 보상 1을 받았고 중간 보상은 없다. 할인 없이 계산한 각 턴의 return은 둘 다 1이며, 두 턴의 정책 토큰이 모두 양의 신호를 받는다. 환경이 돌려준 문서의 토큰은 손실에서 빠진다. 여기에 "검색어가 형식을 지켰는가"에 대한 process 보상 0.1을 턴 1에 더하면 턴 1의 return은 1.1, 턴 2는 1이 된다. 최종 보상을 두 턴에 임의로 반씩 나누지는 않는다. 각 턴은 자기 뒤에 온 보상의 합을 받는다.
</Callout>

## 2. 도구 사용의 계보

### 2-1. 프롬프트로 유도하기: ReAct

도구 사용의 출발점은 학습이 아니라 프롬프트였다. Yao 등의 ReAct는 모델이 "생각(thought)"과 "행동(action)"을 번갈아 쓰고 행동의 결과인 "관측(observation)"을 받아 다음 생각을 잇게 하는 형식을 few-shot 예시로 유도했다.[^react] 질의응답과 사실 확인에서 위키백과 검색을, 상호작용 과제에서 환경 명령을 행동으로 썼다. 이 형식은 이후 거의 모든 agent의 뼈대가 되었지만, 매번 예시를 넣어야 하고 예시에 없는 상황에서 언제 도구를 부를지 모델이 알기 어렵다.

### 2-2. 언제 부를지 배우기: Toolformer

Schick 등의 Toolformer는 도구 호출을 모델에 **학습**시켰다.[^toolformer] 계산기, 검색, 번역 같은 API를 어디에 끼워 넣으면 다음 토큰 예측이 좋아지는지를 모델 자신이 표집·검증해 학습 데이터를 만들고, 그 데이터로 fine-tuning했다. 사람이 쓴 예시는 API마다 몇 개뿐이다. 이것은 [04a](/lecture/2026f-advanced-deep-learning/04a-sft/)의 SFT이며, 이후의 공개 recipe는 도구 호출이 포함된 대화 데이터를 SFT에 넣는다. Olmo 3 Instruct의 SFT 데이터에는 도구 사용 프롬프트가 약 23만 개 들어 있다(원논문 Table 30).[^olmo3] SFT의 한계는 04a §5와 같다. 시연에 없는 도구 조합이나 실패 뒤의 복구는 배우기 어렵다.

### 2-3. 결과에 보상 주기: Search-R1과 ToolRL

[05a](/lecture/2026f-advanced-deep-learning/05a-rlvr/)의 검증 가능한 보상이 여기서 다시 쓰인다. Jin 등의 Search-R1은 모델이 `<think>`, `<search>`, `<answer>` 태그로 추론·검색·답을 번갈아 내게 하고, 검색 엔진이 `<information>` 태그로 결과를 돌려주며, 보상은 최종 답의 정확 일치뿐이다. 언제 무엇을 검색할지는 가르치지 않았다. 일곱 개 질의응답 데이터셋 평균에서 Qwen2.5-7B의 정확 일치가 검색 증강 기준선의 0.304에서 0.431로(상대 41%), 3B는 0.270에서 0.303으로(20%) 올랐다.[^searchr1] Qian 등의 ToolRL은 보상 설계에 집중했다. 도구 호출의 형식 보상에 더해, 정답 호출과 비교해 도구 이름·인자 이름·인자 값이 각각 맞는지를 나누어 점수를 주는 세분화된 정확성 보상을 두었다. GRPO로 학습한 모델이 base model보다 약 17%, SFT 모델보다 약 15% 높았고, SFT로 초기화한 뒤 RL을 하는 것보다 base model에서 바로 RL을 시작하는 편이 나았으며, 긴 추론이 도구 호출 성능을 자동으로 높이지는 않았다.[^toolrl] 보상을 세분화하면 학습이 안정적이었다는 관찰은 [04d](/lecture/2026f-advanced-deep-learning/04d-reward-hacking/)의 "검증기가 무엇을 확인하는가"의 다른 면이다. 도구 호출에서는 무엇을 확인해야 하는지가 비교적 분명하다.

### 2-4. 도구 결과 뒤의 불확실성: ARPO

궤적 단위로 보상을 주는 GRPO를 그대로 쓰면 궤적 안의 어느 턴이 좋았는지 구분하지 못한다. Dong 등의 ARPO(agentic reinforced policy optimization)는 도구 결과가 돌아온 직후 10–50토큰에서 정책의 entropy가 급격히 오른다는 관측에서 출발했다.[^arpo] 새 정보를 받은 직후가 가장 불확실한 지점이라는 뜻이다. ARPO는 이 지점에서 궤적을 가지치기해 여러 후속을 뽑고(entropy 기반 적응 rollout), 공통 prefix에는 같은 advantage를, 갈라진 뒤에는 다른 advantage를 주어 어느 턴의 선택이 결과를 바꿨는지 학습하게 했다. 수학·지식 질의응답·심층 검색 13개 벤치마크에서 궤적 단위 알고리즘보다 높았고, 도구 호출 예산은 절반이었다.[^arpo] [05c §1-2](/lecture/2026f-advanced-deep-learning/05c-policy-optimization/)의 그룹이 "같은 프롬프트의 응답들"에서 "같은 prefix의 후속들"로 옮겨 간 것이다.

## 3. 환경과 데이터

### 3-1. 환경을 만드는 문제

단일 응답 RL의 데이터는 문제와 정답이었다. Agentic RL의 데이터는 **환경**이다. 도구가 실제로 실행되어야 하고, 과제마다 성공 조건이 있어야 하며, 궤적이 길어 사람이 만들기 어렵다. Kimi K2는 이 문제를 합성으로 풀었다. GitHub의 MCP(model context protocol) 도구 3천여 개에 합성 도구 2만여 개를 더해 도구 저장소를 만들고, 서로 다른 시스템 프롬프트와 도구 조합으로 수천 개의 agent를 정의한 뒤, 각 agent에 성공 기준(rubric)이 달린 과제를 주고, 사용자 역할의 LLM(large language model)과 상태를 유지하는 도구 시뮬레이터 사이에서 다중 턴 궤적을 생성해 LLM 판정자가 rubric으로 걸렀다.[^kimik2] 이 궤적은 SFT 데이터가 되고, 그 뒤의 RL은 검증 가능한 보상과 rubric 기반 자기 비평 보상을 함께 쓴다.[^kimik2] 시뮬레이터가 실제 환경과 다르면 시뮬레이터에 맞춘 행동을 배운다는 위험은 04d의 대리 지표 문제와 같다.

### 3-2. 평가의 민감성

Liu 등은 2026년에 도구 호출 agent의 평가가 무작위 시드와 시스템 프롬프트 같은 문서화되지 않은 작은 선택에 크게 좌우되며, RL 학습에서는 학습 신호를 주지 않는 rollout에 많은 계산이 낭비된다고 보고했다.[^liu2026] 단일 응답 벤치마크보다 환경이 개입하는 만큼 변동 요인이 많다. 05c의 dynamic sampling이 도구 호출 궤적에서는 더 중요한 이유이기도 하다.

## 4. 정리와 다음 노트

Agentic RL은 04b–05c의 틀을 버리지 않는다. 정책 갱신은 같은 policy gradient이고 보상은 05a의 검증기와 04b·04d의 판정자에서 온다. 바뀐 것은 궤적에 환경의 토큰이 섞이고, 보상이 여러 턴 뒤에 오며, 생성이 환경 실행과 얽힌다는 점이다. 그래서 손실 mask, credit assignment, 환경 합성, rollout 효율이 새 문제가 된다. 서베이 §3의 나머지 능력(계획, 기억, 자기 개선)과 §4의 과제(코드, GUI, 구현 agent)는 이 노트의 범위 밖이며, 14주차의 world model과 VLA(vision-language-action) 모델에서 다시 만난다.

5주차의 마지막 질문이 남는다. 이렇게 RL로 만든 큰 모델의 능력을 작은 모델에 어떻게 옮기는가. [05f](/lecture/2026f-advanced-deep-learning/05f-distillation/)가 그 답을 [04c §3-1](/lecture/2026f-advanced-deep-learning/04c-dpo/)의 on-policy 관점에서 찾는다.
