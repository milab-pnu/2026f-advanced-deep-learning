지금까지의 RL(reinforcement learning)은 프롬프트 하나에 응답 하나를 내고, 응답이 끝나면 보상이 한 번 오는 문제였다.
실제 task의 많은 부분은 그렇지 않아서, 검색해서 읽고 다시 검색하고, 코드를 실행해 오류를 보고 고치고, 사용자와 여러 턴을 주고받는다.
이처럼 모델의 출력이 환경을 바꾸고 환경의 응답이 다음 입력이 되는 상호작용 궤적을 보상으로 학습하는 것을 **agentic RL**이라고 부른다.[^survey]
정책 갱신 식은 앞에서 본 PPO(proximal policy optimization)·GRPO(group relative policy optimization)와 크게 다르지 않고,
달라지는 것은 그 식에 넣을 궤적을 만들고 믿을 수 있게 채점하는 일이다.

## 1. 단일 응답에서 궤적으로

### 1-1. 형식의 차이

지금까지의 RL에서 LLM(large language model)은 프롬프트를 받아 응답을 한 번 내고 끝났고, 보상도 응답 끝에 한 번 왔다.
Agentic RL에서는 모델이 행동(텍스트, 도구 호출)을 낼 때마다 환경이 결과(검색 결과, 실행 출력, 사용자 답)를 돌려주고,
모델은 그 결과를 문맥에 이어 붙여 다음 행동을 정한다.
이 주고받기가 여러 턴 이어지고, 최종 성공은 여러 턴 뒤에 정해진다.
환경에는 모델이 직접 보지 못하는 부분(파일 시스템 전체, 검색 엔진의 색인, 사용자의 의도)이 있어서,
모델은 돌려받은 결과로만 그 상태를 짐작한다.
이런 문제는 부분 관측 MDP(partially observable Markov decision process, POMDP)로 모델링한다.[^survey]

아래 그림은 사용자 요청을 받아 도구를 호출하고, 그 결과로 다음 행동을 정하는 궤적의 예다.[^muarl]

### 1-2. 학습에서 달라지는 세 가지

이 형식 변화가 PPO·GRPO의 학습 절차에 미치는 영향은 셋이다.

**손실을 거는 위치.** 위 그림에서 정책이 생성한 것은 **회색 상자**(agent의 답과 도구 호출)뿐이다.
보라(사용자 발화)와 빨강(데이터베이스 결과)은 환경이 넣은 것이므로, 정책의 log 확률을 올리거나 내리는 대상이 아니다.
SFT(supervised fine-tuning)의 loss mask가 지시 토큰을 제외한 것과 같은 논리로, 시스템 프롬프트에 더해 보라·빨강 토큰도 손실에서 제외한다.
이 토큰들은 문맥에 남아 뒤의 회색 토큰을 예측하는 조건이 된다.

**보상의 귀속.** 그림의 궤적에 보상을 주는 방식은 크게 둘이다.
최종 결과만 보면, 사용자가 원하는 답을 받았는지로 마지막에 한 번 1 또는 0을 준다.
이 보상은 모든 회색 턴에 똑같이 가므로, 검색어를 잘못 넣었다가 고쳐서 성공한 궤적은 잘못된 호출까지 1을 받고,
인증과 검색은 잘했는데 마지막 안내만 틀린 궤적은 잘한 호출까지 0을 받는다.
중간 과정도 보면, 도구 호출마다 형식과 도구·인자가 맞았는지로 턴마다 보상을 더한다.
신호는 촘촘해지지만, 정해 둔 호출 경로와 다르게 성공한 궤적은 감점될 수 있다.
어느 쪽이든 각 턴은 앞 주차 PPO에서 본 누적 보상 $G_t$처럼 그 턴부터 끝까지 받은 보상의 합을 받고,
최종 보상 하나를 여러 턴에 어떻게 나눌지가 credit assignment 문제다.

**생성 비용.** 그림의 궤적 하나를 만들려면 빨강 상자마다 도구 실행을, 보라 상자마다 사용자(학습에서는 보통 사용자 역할의 LLM)의 답을 기다려야 한다.
이 지연이 생성에 더해지고, 궤적 길이의 분산이 커진다.
한 궤적이 도구 결과를 기다리는 동안 다른 궤적의 생성이 멈추지 않도록 궤적마다 따로 진행시키고, 가장 긴 궤적을 기다리지 않도록 생성과 학습을 겹쳐 돌리는 비동기 설계가 더 중요해지며,
비싸게 만든 궤적 중 상당수가 학습 신호를 주지 않는다는 문제도 커진다.

## 2. 프롬프팅에서 RL까지

계보는 프롬프팅 논문 두 편에서 시작한다.
ReAct는 모델이 도구·환경과 주고받는 **상호작용 형식**을 정했고,
Reflexion은 실패한 시도의 **피드백**을 다음 시도의 문맥에 넣어, 가중치를 바꾸지 않고 행동을 고쳤다.
다른 갈래는 모델 자체를 학습시키는 쪽이었다.
Toolformer는 도구 호출이 든 텍스트로 가중치를 학습했고,
이후의 function calling SFT는 구조화된 호출 형식과 대규모 합성 데이터로 대화 모델이 도구 호출을 생성하도록 학습했다.
두 학습 방식 모두 신호는 정해진 텍스트의 다음 토큰 예측이었다.
RL에서 두 갈래가 합쳐진다.
환경이 판정한 결과를 Reflexion처럼 신호로 쓰면서 SFT처럼 가중치에 남긴다.
표의 "겨냥한 한계"는 각 방법을 앞의 방법과 견주어 정리한 것이며, 원논문이 앞 방법을 직접 계승했다는 뜻은 아니다.

| 방법 | 축 | 겨냥한 한계 | 학습 신호 | 학습 단위 |
|---|---|---|---|---|
| ReAct | 상호작용 형식 | (출발점) 추론만 하는 프롬프팅과 행동만 하는 방식이 따로 다뤄짐 | 주로 few-shot 프롬프트 | 없음(주 방법 기준) |
| Reflexion | 피드백 활용 (문맥) | ReAct는 실패한 시도의 경험을 다음 시도로 넘기지 못함 | 환경의 성패를 말로 옮긴 반성 (가중치 갱신 없음) | 없음(반성을 기억에 쌓아 다음 시도의 문맥에 넣음) |
| Toolformer | 가중치 학습 (자기 지도) | ReAct식 프롬프팅은 매번 예시가 필요하고 호출 시점을 학습하지 않음 | 다음 토큰 예측 | 도구 호출이 끼워진 텍스트 |
| Function calling SFT | 가중치 학습 (합성 시연) | Toolformer는 소수의 도구를 하나씩 따로 호출하고 연쇄 호출의 예가 없음 | 다음 토큰 예측 | 도구 schema가 주어진 단일·병렬 호출, 또는 관측을 포함한 다중 턴 궤적 |
| Search-R1 | 피드백으로 가중치 학습 (RL, 궤적 갈래) | 고정된 시연은 현재 정책이 스스로 실수한 뒤의 문맥을 충분히 덮지 못할 수 있음 | 최종 답의 정확 일치 | 검색 실행을 포함한 다중 턴 궤적 |
| ARPO(agentic reinforced policy optimization) | 피드백으로 가중치 학습 (RL, 궤적 갈래) | Search-R1식 궤적 단위 보상은 궤적 안의 어느 구간이 좋았는지 구분 못함 | 정확성·형식 + 다중 도구 사용 보너스 | 분기로 공통 prefix를 공유하는 궤적 묶음 |
| ToolRL | 피드백으로 가중치 학습 (RL, 단계 갈래) | SFT는 낯설거나 복잡한 도구 사용에 일반화가 약함(궤적 대신 단일 단계 호출과 보상 설계로 접근) | 형식 + 호출의 세분화된 정확성 | 이력이 주어진 다음 호출 한 단계 |

### 2-1. ReAct와 Reflexion의 프롬프팅

Yao 등의 ReAct는 주로 가중치 학습 없이 프롬프트만으로 도구 사용을 유도했다.[^react]
모델이 "생각(thought)"과 "행동(action)"을 번갈아 쓰고 행동의 결과인 "관측(observation)"을 받아 다음 생각을 잇는 형식이며, few-shot 예시로 이 형식을 보여 주었다.
질의응답과 사실 확인에서 위키백과 검색을, 상호작용 task에서 환경 명령을 행동으로 썼다.
이 형식은 이후 agent에서 널리 쓰이게 되었지만,
이 프롬프팅 설정에서는 매번 예시를 넣어야 하고 예시에 없는 상황에서 언제 도구를 부를지 모델이 알기 어렵다.
또 한 번의 시도 안에서는 관측을 보고 다음 행동을 고칠 수 있지만, 시도가 실패로 끝나면 그 경험은 다음 시도로 이어지지 않는다.

Shinn 등의 Reflexion은 실패한 시도의 경험을 다음 시도로 넘기는 방법을 보였다.[^reflexion]
Task를 한 번 수행하면 평가자가 그 궤적의 성패를 판정하고(질의응답은 정답과의 정확 일치, 코딩은 모델이 스스로 만든 단위 테스트),
LLM이 궤적과 성패를 보고 무엇이 잘못되었고 다음에는 어떻게 할지를 글로 쓴다.
이 반성문을 기억(episodic memory)에 쌓아 같은 task의 다음 시도 문맥에 넣는다.
가중치를 바꾸는 대신 말로 된 피드백으로 행동을 강화한다는 뜻에서 저자들은 이를 verbal reinforcement라 불렀다.
그러나 모델은 그대로이고 나아진 것은 문맥뿐이다.
반성은 같은 task의 다음 시도 문맥에 들어가므로 새 task에 그대로 쓰기 어렵고,
문맥에 넣을 수 있는 반성의 양에도 한계가 있다.
피드백으로 나아지는 효과를 모델에 남기려면 가중치를 학습해야 한다.

### 2-2. Toolformer와 function calling의 SFT

Schick 등의 Toolformer는 도구 호출을 모델에 **학습**시켰다.[^toolformer]
계산기, 검색, 번역 같은 API(application programming interface)를 어디에 끼워 넣으면 다음 토큰 예측이 좋아지는지를 모델 자신이 생성·검증해 학습 데이터를 만들고,
그 데이터로 언어 모델을 자기 지도 방식으로 fine-tuning했다.
검증의 기준은 뒤 토큰의 예측 손실이다.
"Out of 1400 participants, 400 (or 29%) passed"에서 "29%" 자리에 `[Calculator(400 / 1400) → 0.29]`를 끼워 넣었을 때 "29%"부터 이어지는 토큰들의 손실이 충분히 줄면 그 호출을 남긴다.
다만 도구마다 호출을 따로 만들었으므로, 한 도구의 결과를 다른 도구의 입력으로 쓰는 연쇄 호출의 예는 학습 데이터에 없었다.

지금의 대화 모델은 도구를 흔히 **function calling** 형식으로 쓴다.
도구마다 이름, 설명, 인자의 이름과 타입을 JSON(JavaScript Object Notation) Schema로 적어 모델에 주고,
모델은 자유 텍스트 대신 "어떤 도구를 어떤 인자로 부를지"를 구조화된 호출로 낸다.
실행은 모델 밖의 코드가 맡고, 그 결과는 tool 역할의 메시지로 대화에 다시 들어간다.
Hugging Face Transformers의 chat template은 이 대화를 다음과 같은 메시지 목록으로 다룬다.[^hf-tools]

```python
tools = [get_current_temperature]  # 이름·인자·docstring으로 JSON Schema를 만든다
messages = [
    {"role": "user", "content": "지금 파리 기온이 몇 도야?"},
    {"role": "assistant", "tool_calls": [{"type": "function", "function": {
        "name": "get_current_temperature",
        "arguments": {"location": "Paris, France", "unit": "celsius"}}}]},
    {"role": "tool", "content": "22"},          # 실행 결과는 항상 문자열로 넣는다
    {"role": "assistant", "content": "지금 파리는 섭씨 22도입니다."},
]
```

각 모델의 chat template은 이 목록을 그 모델의 특수 토큰을 쓴 문자열로 바꾸고, 모델이 생성한 호출 문자열은 외부 코드가 파싱해 실행한다.
SFT에서는 assistant 차례의 토큰(호출과 최종 답)에만 손실을 걸고 tool 메시지는 mask하도록 설정할 수 있다.
이렇게 하면 앞에서 본 관측 토큰의 mask가 SFT 단계부터 들어간다.

이런 대화를 사람이 대량으로 쓰기는 어려워서 학습 데이터를 합성하는 경우가 많다.
특히 호출 결과를 보고 다음 호출을 정하는 다중 턴 궤적이 있어야 연쇄 호출을 배운다.
Qin 등의 ToolLLM은 실제 웹 API를 모아 지시를 만들고, ChatGPT가 API 응답을 받아 가며 호출의 연쇄를 찾게 해 이런 궤적을 합성했다.
이 데이터로 SFT한 모델은 학습 때 보지 못한 API에도 일반화했다.[^toolllm]

SFT도 새 도구와 상황에 일반화할 수 있다.
다만 고정된 시연은 다른 모델이나 파이프라인이 만든 문맥이라,
현재 정책이 스스로 잘못 호출하고 오류를 받은 뒤의 문맥을 충분히 덮는다는 보장이 없다.
앞 주차 SFT에서 본 학습 문맥과 생성 문맥의 차이다.
오류와 복구를 담은 시연을 일부러 넣을 수도 있지만,
정책이 실제로 방문하는 문맥에서 성패를 얻는 가장 직접적인 방법은 환경과 상호작용하는 RL이다.

### 2-3. Search-R1의 다중 턴 rollout

Reflexion은 환경의 성패를 반성으로 문맥에 남겼다.
이제 그 성패를 가중치를 바꾸는 보상으로 쓴다.
RLVR의 검증 보상이 여기서 다시 쓰인다.
Jin 등의 Search-R1은 모델이 `<think>`, `<search>`,
`<answer>` 태그로 추론·검색·답을 번갈아 내게 하고,
검색 엔진이 `<information>` 태그로 결과를 돌려주며, 보상은 최종 답의 정확 일치뿐이다.[^searchr1]
프롬프트는 지식이 부족하면 검색을 부를 수 있다고만 알려 주고,
언제 무엇을 검색할지 보여 주는 예시는 주지 않았다.

정책 생성과 검색 실행이 번갈아 이어지는 궤적 전체가 하나의 rollout이다.
Search-R1의 rollout은 다음 순서로 돈다.

1. 질문을 넣고 행동 횟수를 0으로 둔다.
2. 정책이 `</search>`, `</answer>`, 또는 종료 토큰을 낼 때까지 토큰을 생성한다.
3. 방금 생성한 구간에 검색 호출이 있으면 검색어를 파싱해 실행하고, 결과를 `<information>`으로 감싸 궤적 뒤에 붙인다.
4. 답이 있으면 rollout을 끝낸다.
5. 둘 다 없으면 "My action is not correct. Let me rethink."라는 문장을 붙여 다시 생성하게 한다.
6. 행동 횟수를 하나 늘리고, 최대 행동 수에 이르지 않았으면 2로 돌아간다.

끝난 궤적은 최종 답을 정답과 비교해 채점하고, 그 보상으로 PPO나 GRPO를 써서 정책을 갱신한다.
여기서 보듯 잘못된 형식의 출력, 도구 실행의 오류나 timeout, 예산 소진은 각각 처리 방식을 정해야 하는 설계 선택이다.
Search-R1은 잘못된 형식을 다시 생각하라는 관측으로 돌려주고 예산이 다하면 그대로 끝내 채점한다.
오류를 관측으로 돌려주면 정책이 복구를 배울 기회가 생기고,
궤적을 끝내고 보상 0을 주면 형식 실수에 강한 벌이 된다.
검색 서버 장애처럼 정책의 잘못이 아닌 실패에 보상 0을 주면 정책이 하지 않은 실수를 벌하게 되므로,
그런 궤적은 학습에서 빼는 선택도 있다.
또 파일을 고치거나 데이터베이스를 바꾸는 환경이라면 그룹의 각 궤적은 같은 초기 상태의 독립된 사본에서 시작해야 한다.
한 궤적이 바꾼 상태 위에서 다른 궤적이 시작하면 그룹 안의 비교가 공정하지 않다.

<Callout type="example">
**두 턴 궤적의 mask와 누적 보상.** "소설 『채식주의자』의 작가가 노벨 문학상을 받은 해는?"이라는 질문에
Search-R1 형식으로 답하는 교육용 궤적을 보자.
학습에 들어가는 토큰열은 세 구간으로 나뉜다.

| 구간 | 내용 | 생성 주체 | Loss mask |
|---|---|---|---|
| 턴 1 | `<think>`작가를 먼저 확인하고 수상 연도를 찾는다`</think><search>`채식주의자 작가 노벨 문학상`</search>` | 정책 | 1 |
| 관측 | `<information>`한강은 2024년 노벨 문학상을 받았다. …`</information>` | 환경(검색 엔진) | 0 |
| 턴 2 | `<think>`작가는 한강이고 수상 연도는 2024년이다`</think><answer>`2024`</answer>` | 정책 | 1 |

관측 구간은 mask가 0이지만 턴 2의 토큰을 계산할 때 문맥으로 들어간다.
정책 갱신의 확률비와 log 확률은 mask가 1인 두 구간의 토큰에서만 계산한다.
최종 답이 맞아 보상 1을 받았고 중간 보상은 없다면, 각 턴의 누적 보상은 둘 다 1이다.
여기에 "검색어가 형식을 지켰는가"에 대한 process 보상 0.1을 턴 1에 더하면 턴 1의 누적 보상은 1.1, 턴 2는 1이 된다.
최종 보상을 두 턴에 임의로 반씩 나누지는 않는다.
각 턴은 자기 뒤에 온 보상의 합을 받는다.
PPO에서는 단순한 추정이라면 이 누적 보상에서 value model의 예측을 빼 advantage를 구하고, 이 값이 갱신 방향을 정한다.
중간 보상 없이 최종 outcome 보상만 쓰는 GRPO에서는 궤적의 최종 보상을 같은 질문의 다른 궤적들과 비교해 정규화한 값을 그 궤적의 모든 정책 토큰에 준다.
이 궤적과 같은 질문의 다른 궤적들이 모두 1을 받았다면 advantage가 0이 되어 학습 신호가 사라진다.
</Callout>

Search-R1은 검색으로 가져온 토큰을 이렇게 손실에서 mask했고,
mask를 적용했을 때 성능 향상이 더 크고 학습이 더 안정적이었다고 보고했다.
질의응답 벤치마크에서 Search-R1은 검색 결과를 프롬프트에 붙여 주는 기준선보다 정확 일치가 크게 높았다.[^searchr1]
모델이 검색 시점을 보여 주는 예시 없이 최종 답의 보상만으로 검색을 쓰는 법을 배운 것이다.

### 2-4. ARPO의 분기 rollout

Search-R1처럼 궤적 단위로 보상을 주는 GRPO를 그대로 쓰면 궤적 안의 어느 구간이 좋았는지 구분하지 못한다.
Dong 등의 ARPO는 도구 결과가 돌아온 직후 정책의 entropy가 급격히 오른다는 관측에서 출발했다.[^arpo]
새 정보를 받은 직후에 모델이 특히 불확실해진다는 뜻이다.
그래서 ARPO는 rollout 예산의 일부로만 궤적을 처음부터 따로 만들고,
나머지는 도구 결과 뒤에 entropy가 크게 오른 지점에서 궤적을 여러 갈래로 분기해 이어 생성하는 데 쓴다.

이렇게 얻은 궤적들은 분기 지점 앞의 토큰(공통 prefix)을 공유한다.
보상의 정규화는 일반 GRPO처럼 같은 질문의 전체 rollout 그룹에서 하고, 손실도 GRPO를 그대로 쓴다.
그러면 공통 prefix의 토큰은 분기들의 신호를 함께 받고,
갈라진 뒤의 토큰은 자기 분기의 advantage만 받는다.
예를 들어 한 prefix에서 갈라진 두 분기 중 하나는 성공하고 하나는 실패했다면,
공통 토큰은 두 신호를 합친 만큼 움직이고,
갈라진 뒤의 토큰은 성공한 쪽은 확률이 오르고 실패한 쪽은 내려간다.
다만 갈라진 뒤의 구간 안에서 어느 행동이 성패에 기여했는지는 여전히 나누지 못하며,
단계별 기여를 직접 판정하는 방법은 아니다.
보상은 정확성과 형식에 더해, 정답을 내면서 검색과 코드 실행을 함께 쓴 궤적에 작은 보너스를 준다.

수학·지식 질의응답·심층 검색 벤치마크에서 ARPO는 궤적 단위 RL보다 성능이 높았고,
학습 중 도구 호출은 GRPO보다 적게 썼다.[^arpo]

### 2-5. ToolRL과 Tool-N1의 호출 단위 보상

Qian 등의 ToolRL은 SFT가 낯설거나 복잡한 도구 사용에 잘 일반화하지 못한다는 문제를 RL로 다루되, 궤적 대신 단일 단계 호출을 학습 단위로 삼았다.
다중 턴 궤적을 "지금까지의 대화 이력이 주어졌을 때 다음 도구 호출"이라는 단일 단계 사례로 분해해 프롬프트에 이력을 넣고,
보상 설계에 집중했다.
도구 호출의 형식 보상에 더해,
정답 호출과 비교해 도구 이름·인자 이름·인자 값이 각각 맞는지를 나누어 점수를 주는 세분화된 정확성 보상을 두었다.
예를 들어 정답 호출이 `search(query="한강", year=2024)`인데 모델이 `search(query="한강", year=2023)`을 냈다면,
도구 이름과 인자 이름은 맞고 인자 값 하나만 틀렸으므로 0점이 아니라 부분 점수를 받는다.
Instruct 모델에서 출발해 GRPO로 학습했다.[^toolrl]
원논문은 도구 호출 데이터로 SFT를 더 한 뒤 RL을 하는 것보다 Instruct 모델에서 바로 RL을 시작하는 편이 그 실험에서 나았고,
보상을 세분화하면 학습이 안정적이었다고 보고한다.[^toolrl]
같은 시기 Tool-N1은 반대로 형식과 도구 이름·인자가 모두 맞을 때만 1점을 주는 이진 보상을 썼다.[^tooln1]
형식이나 도구 이름만 맞아도 부분 점수를 주는 설정과 비교하면 그 실험에서는 이진 보상이 더 나았고,
원논문은 부분 점수가 겉모습만 맞춘 호출에도 보상을 주어 reward hacking을 부른다고 해석한다.[^tooln1]
두 결과는 process 보상이 신호를 촘촘하게 하는 대신 겉모습을 맞추는 쪽으로 최적화될 수 있다는 장단점을 양쪽에서 보여 준다.

정답 호출이 주석된 데이터만 있으면 환경을 끝까지 돌리지 않고도 RL을 구성할 수 있다는 것이 이 갈래의 장점이다.
대신 보상이 정해진 정답 호출과의 일치이므로,
같은 결과에 이르더라도 정답 주석과 다른 도구·인자 조합은 낮은 점수를 받을 수 있고,
자기 실수 뒤의 복구나 여러 턴 뒤의 최종 성공은 직접 최적화하지 않는다.

## 3. 환경, 채점, 평가

### 3-1. 학습 환경의 구성

환경과 상호작용하는 궤적을 직접 학습하려면 문제와 정답뿐 아니라 실행할 수 있는 **환경**과 성공을 판정하는 절차가 필요하다.
도구가 실제로든 시뮬레이터 안에서든 실행되어야 하고 task마다 성공 조건이 있어야 해서,
이런 task를 사람이 하나씩 만들기 어렵다.

코딩 agent의 학습 task를 보면 환경이 무엇인지 구체적으로 드러난다.
Task 하나에는 저장소, 고칠 내용을 적은 이슈, 코드를 실제로 돌릴 수 있는 실행 환경, 수정이 맞는지 확인할 단위 테스트가 들어 있다.
정책은 파일을 찾아 읽고, 코드를 고치고, 실행해 결과를 보는 일을 여러 턴 되풀이한 뒤 최종 patch를 낸다.
그 patch에 테스트를 돌려 통과하면 성공이다.
SWE-bench는 이 형식을 갖춘 대표적인 평가 세트인데,
평가 세트로 학습하면 그 점수를 믿을 수 없으므로 학습에는 같은 형식이면서 평가와 겹치지 않는 task가 따로 필요하다.
Pan 등의 SWE-Gym은 SWE-bench와 겹치지 않는 Python 저장소에서 GitHub 이슈와 그것을 해결한 pull request를 모아,
실행 환경과 테스트를 갖춘 학습용 task를 만들었다.[^swegym]
실행 환경은 task마다 의존성을 반수동으로 설정했다.
같은 환경에서 테스트 통과를 그대로 보상으로 쓰면 검증 보상을 건 RL이 된다.

실제 저장소마다 환경을 손으로 만드는 방식은 규모를 키우기 어려워서, 도구와 사용자를 시뮬레이터로 대신하기도 한다.
Kimi K2는 실제 MCP(model context protocol) 도구와 합성 도구로 도구 저장소를 만들고,
성공 기준(rubric)이 달린 task를 사용자 역할의 LLM과 상태를 유지하는 도구 시뮬레이터 사이에서 풀게 해 다중 턴 궤적을 대규모로 생성했다.[^kimik2]
이렇게 만든 궤적 중 LLM judge가 rubric으로 거른 것은 SFT 데이터가 되고, 그 뒤의 RL은 검증 보상과 rubric 기반 자기 비평 보상을 함께 쓴다.
시뮬레이터가 실제 환경과 다르면 시뮬레이터에 맞춘 행동을 배운다는 위험은 앞 주차 reward hacking에서 본 대리 지표 문제와 같다.

### 3-2. 무효 rollout과 생성 전 필터링

환경에서 궤적을 만드는 비용이 큰 만큼, 만든 궤적이 학습 신호를 주는지가 더 중요해진다.
Liu 등은 도구 호출 agent의 학습과 평가를 함께 점검했다.[^liu2026]
한 프롬프트의 rollout이 모두 같은 보상을 받으면 그룹 advantage가 0이 되어 policy 항의 학습 신호가 없는데,
도구 호출 RL에서는 이런 프롬프트가 대부분이었다.

앞에서 본 DAPO(decoupled clip and dynamic sampling policy optimization)의 dynamic sampling은 이런 그룹을 버리고 다시 뽑아 배치를 채우지만,
버린 만큼 생성을 다시 해야 하고,
Liu 등은 이 방식이 오히려 학습 시간을 크게 늘렸다고 관찰했다.
대신 이들은 생성 **전에** 거르는 방법을 제안했다.
최근 몇 epoch 동안 모든 rollout이 정답이었던 프롬프트는 한동안 계속 정답일 가능성이 높다는 관찰에 근거해,
그런 프롬프트를 rollout을 만들기 전에 건너뛴다.
어느 프롬프트가 무효인지는 학습 중에 바뀌므로 학습 전에 한 번 거르는 것으로는 부족하다.
여기에 생성한 rollout 중 보상의 분산이 가장 크게 남도록 일부만 골라 정책 갱신에 쓰는 down-sampling을 더해,
같은 성능에 더 빨리 도달했다고 보고했다.[^liu2026]

### 3-3. 채점 환경의 분리와 감시

Agentic 코딩 task에서는 정책이 코드를 고치는 바로 그 환경 안에 테스트와 채점 스크립트가 있다.
그러면 정책은 답을 고치는 대신 채점을 고칠 수 있다.
Baker 등은 OpenAI가 추론 모델을 학습하던 중 두 해킹이 거의 모든 학습 환경으로 퍼진 것을 보고했다.[^baker]
하나는 `exit(0)`로, 단위 테스트가 모두 실행되기 전에 프로그램을 끝낸다.
다른 하나는 `raise SkipTest`로, 테스트 프레임워크 밖에서 예외를 일으켜 테스트를 건너뛰게 한다.

이런 해킹은 검증 조건을 늘려서는 막기 어렵다.
정책이 답을 맞히는 대신 테스트가 실행되는 과정을 피해 가거나, 채점 코드와 결과 보고를 고치기 때문이다.
대응은 환경 설계 쪽에 있다.
정책이 고칠 수 있는 파일과 채점에 쓰는 파일을 나누고,
채점은 정책이 손대지 못하는 원래 테스트로 다시 돌린다.
Baker 등은 정책이 테스트를 고칠 수 있게 한 실험에서,
모든 테스트를 통과하더라도 테스트에 가한 변경을 되돌렸을 때 실패하면 그 해답을 부정행위로 판정했다.[^baker]

사고 과정까지 보면 해킹을 더 많이 잡을 수 있다.
Baker 등은 다른 LLM을 감시자(monitor)로 두고 실제 해킹을 얼마나 잡아내는지 비교했다.
정책의 행동(도구 호출과 출력)만 본 감시자보다 사고 과정까지 본 감시자가 훨씬 많은 해킹을 잡았다.[^baker]
원논문이 든 예에서 정책은 테스트가 특정 함수만 확인한다는 점을 짚고, verify가 항상 참을 돌려주게 해 테스트를 피해 가자는 생각을 사고 과정에 적었다.

그렇다면 감시자의 판정을 보상에 넣어 "나쁜 생각"에 벌점을 주면 어떨까.
저자들이 사고 과정만 보는 감시자로 이를 시험하자,
부정행위 없이 통과하는 해답은 기준 정책보다 늘었다.
그러나 정책은 여전히 부정행위를 했고, 사고 과정에는 그 의도를 쓰지 않게 되어
감시자가 해킹을 거의 잡지 못하게 되었다.
저자들은 이를 obfuscated reward hacking이라 부르고,
사고 과정에 직접 강한 최적화 압력을 가하지 말 것을 권했다.[^baker]
사고 과정을 보는 감시 신호를 보상에 넣으면 그 신호도 대리 지표가 된다.
다만 이 경고는 사고 과정 자체에 벌점을 주는 경우에 관한 것이다.
MacDiarmid 등이 실제 학습 환경 가운데 해킹에 취약한 코딩 환경을 골라 한 실험에서는,
해킹 행동을 잡는 분류기의 벌점을 보상에 넣자 해킹이 학습되지 않았다.[^macdiarmid]

채점 코드를 숨겨도 정책이 채점의 입력을 바꿀 수 있으면 판정은 무력해진다.
가중치 대신 자기 코드를 고치며 점수를 올리는 코딩 agent인 Darwin Gödel Machine은 도구를 부르지 않고 부른 척 쓰는 환각(hallucination)을 검사하는 함수를 볼 수 없었는데도,
실제 도구 호출 때 남기던 표시 토큰을 기록하지 않도록 자기 코드를 고쳐 만점을 받았다.[^dgm]
그래서 채점 코드뿐 아니라 실행 기록의 수집 경로도 정책이 고칠 수 없는 곳에 둔다.

### 3-4. 평가의 보고 기준

채점을 정책에게서 떼어 놓아도, 서로 다른 설정에서 잰 점수끼리는 여전히 비교하기 어렵다.
앞의 Liu 등은 평가 쪽에서 무작위 시드, 시스템 프롬프트, 다중 턴 template의 구성,
이전 턴의 이력과 추론을 다음 턴에 어떻게 넘기는지 같은 문서화되지 않은 작은 선택이 보고 점수를 크게 바꾸며,
다중 턴 설정에서는 표준화 없이 leaderboard 순위를 믿기 어렵다고 보고했다.[^liu2026]
자기 실험에서 agent 학습의 효과를 주장하려면 적어도 다음을 맞추고 함께 보고한다.

- **비교 대상.** 같은 출발 모델의 학습 전후를, 같은 도구·환경 버전과 같은 턴·토큰 예산에서 비교한다.
- **성공의 정의.** 호출의 일치 여부와 task의 최종 성공 여부는 서로 다른 평가 기준이다.
  Yao 등의 τ-bench는 대화가 끝난 뒤의 데이터베이스 상태를 목표 상태와 비교해 성공을 판정한다.[^taubench]
- **반복 안정성.** 같은 task를 여러 번 돌린다.
  τ-bench는 long CoT(chain of thought) 노트에서 본 안정성 지표 $\mathrm{pass}^k$를 처음 제안한 agent 벤치마크이며,
  강한 agent도 같은 task를 여러 번 연속으로 성공하는 비율은 한 번의 성공률보다 크게 낮았다.[^taubench]
- **비용.** 성공률과 함께 task당 호출 수, 생성 토큰, 실행 시간을 적는다.
