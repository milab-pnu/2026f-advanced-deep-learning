지금까지의 RL(reinforcement learning)은 프롬프트 하나에 응답 하나를 내는 문제였다.
앞 주차의 PPO(proximal policy optimization)도,
이 주에 본 GRPO(group relative policy optimization)도 응답이 끝나면 에피소드가 끝나고 과제의 보상이 한 번 온다.
실제 과제의 많은 부분은 그렇지 않다.
검색해서 읽고 다시 검색하고, 코드를 실행해 오류를 보고 고치고, 사용자와 여러 턴을 주고받는다.
모델의 출력이 환경을 바꾸고 환경의 응답이 다음 입력이 된다.
이런 상호작용 궤적을 보상으로 학습하는 것을 **agentic RL**이라고 부른다.
모델이 도구를 쓰게 된 과정은 RL보다 길다.
프롬프트로 상호작용의 형식을 정했고, 도구 호출이 든 텍스트와 대화로 모델을 학습시켰으며,
그 위에서 환경의 성패를 보상으로 쓰는 RL이 나왔다.
이 노트는 그 계보를 따라가면서, 단일 응답 RL이 다중 턴 궤적으로 넓어질 때 데이터의 형태, 손실을 거는 위치,
보상이 오는 시점, 생성 비용이 어떻게 바뀌는지 본다.
환경에 행동할 권한이 생기면 채점 절차 자체도 정책으로부터 분리해야 한다.
마지막으로 과제와 학습 장치까지 모델이 스스로 만드는 자기 개선의 방향과 그 한계를 짧게 본다.

전체 지도는 Zhang 등이 2025년에 정리하고 2026년 TMLR에 실린 agentic RL 서베이[^survey]로 잡는다.
§2가 단일 응답 RL과 agentic RL을 MDP(Markov decision process)의 형식으로 대비하고, §3이 능력별(계획,
도구 사용, 기억, 자기 개선, 추론, 지각) 분류를, §4가 과제별 분류를,
§5가 환경과 프레임워크를 정리한다.
이 노트는 §2의 형식과 §3.2의 도구 사용에 집중하고, §3.4의 자기 개선은 끝에서 일부만 다룬다.

## 1. 단일 응답에서 궤적으로

### 1-1. 형식의 차이

서베이 §2는 선호 기반 강화 fine-tuning(preference-based reinforcement fine-tuning, PBRFT)으로
대표되는 지금까지의 post-training RL을,
응답 전체를 행동 하나로 묶은 **퇴화한 MDP**로 형식화한다.[^survey]
상태는 프롬프트 하나이고, 그 행동 뒤에 종료 상태로 한 번 전이하며,
보상은 한 번 온다(앞 주차 RLHF에서처럼 토큰을 행동으로 보면 토큰 단위 MDP가 되지만 환경의 개입은 없다).
서베이는 agentic RL을 부분 관측 MDP(partially observable MDP, POMDP)로 모델링한다.
환경에는 정책이 다 볼 수 없는 상태(파일 시스템, 검색 엔진의 색인, 사용자의 의도)가 있고,
정책이 행동(텍스트, 도구 호출)을 내면 환경이 관측(검색 결과, 실행 출력, 사용자 답)을 돌려준다.
서베이의 식은 정책이 현재 관측을 보고 행동한다고 쓰지만,
LLM(large language model) agent에서는 지금까지의 행동과 관측이 모두 문맥에 이어 붙으므로 사실상 그
이력 전체가 다음 행동의 입력이 된다.
보상은 여러 시점에 올 수 있고 최종 성공은 여러 턴 뒤에 정해진다.

| | 단일 응답 RL (PPO·GRPO) | Agentic RL |
|---|---|---|
| 환경 상태 | 프롬프트 | 프롬프트와 정책이 다 보지 못하는 세계 상태 |
| 정책의 입력 | 프롬프트 | 프롬프트 + 지금까지의 행동과 관측의 이력 |
| 행동 | 응답 전체 (토큰열) | 한 턴의 텍스트 또는 도구 호출 |
| 전이 | 종료 상태로 한 번 | 행동에 따라 환경 상태가 바뀌고, 정책은 그에 대한 관측을 받음 |
| 보상 | 응답 끝에 한 번 | 최종 결과, 또는 턴마다 |
| 궤적 길이 | 응답 하나 | 턴 여러 개, 길면 수만 토큰 |

### 1-2. 학습에서 달라지는 세 가지

이 형식 변화가 PPO·GRPO의 학습 절차에 미치는 영향은 셋이다.

**손실을 거는 위치.** 궤적에는 정책이 생성하지 않은 토큰이 섞여 있다.
검색 결과와 실행 출력은 환경이 넣은 것이므로, 정책의 log 확률을 올리거나 내리는 대상이 아니다.
앞 주차 SFT(supervised fine-tuning)의 loss mask가 지시 토큰을 제외한 것과 같은 논리이고, 대상이 관측 토큰으로 바뀐 것이다.
SFT에서처럼 mask는 토큰을 손실에서만 빼고 입력에서는 빼지 않는다.
관측 토큰은 문맥에 남아 뒤의 정책 토큰을 예측하는 조건이 되고,
확률비와 log 확률은 정책이 생성한 토큰에서만 계산한다.

**보상의 귀속.** 최종 보상 하나를 여러 턴에 어떻게 나누는가가 credit assignment 문제다.
가장 단순한 방법은 PPO의 return처럼 최종 보상을 모든 턴에 그대로 주는 것이고,
턴마다 별도 보상(도구 호출 형식, 중간 결과)을 더하면 RLVR에서 본 process 보상이 된다.

**생성 비용.** 궤적 하나를 만들려면 정책 생성과 환경 실행이 번갈아야 한다.
도구 실행(검색, 코드 실행)의 지연이 생성에 더해지고, 궤적 길이의 분산이 커진다.
생성과 학습을 겹치는 비동기 설계가 여기서 더 절실해지고,
비싸게 만든 궤적 중 상당수가 학습 신호를 주지 않는다는 문제도 커진다.

## 2. 상호작용 학습의 계보

계보는 프롬프팅 논문 두 편에서 시작한다.
ReAct는 모델이 도구·환경과 주고받는 **상호작용 형식**을 정했고,
Reflexion은 그 형식에서 받은 환경의 **피드백**으로 여러 시도에 걸쳐 나아지는 일을 가중치를 바꾸지 않고 문맥만으로 해냈다.
다른 갈래는 모델 자체를 학습시키는 쪽이었다.
Toolformer는 도구 호출이 든 텍스트로 가중치를 학습했고,
이후의 function calling SFT는 구조화된 호출 형식과 대규모 합성 궤적으로 이를 대화 모델의 표준 능력으로 만들었다.
두 학습 방식 모두 신호는 정해진 텍스트의 다음 토큰 예측이었다.
RL에서 두 갈래가 합쳐진다.
환경이 판정한 결과를 Reflexion처럼 신호로 쓰면서 SFT처럼 가중치에 남긴다.
표의 "겨냥한 한계"는 각 방법을 앞의 방법과 견주어 이 노트가 정리한 것이며,
원논문이 그 방법을 직접 계승했다는 뜻은 아니다.

| 방법 | 축 | 겨냥한 한계 | 학습 신호 | 학습 단위 |
|---|---|---|---|---|
| ReAct | 상호작용 형식 | (출발점) 추론만 하는 프롬프팅과 행동만 하는 방식이 따로 다뤄짐 | 없음(few-shot 프롬프트) | 없음 |
| Reflexion | 피드백 활용 (문맥) | ReAct는 실패한 시도의 경험을 다음 시도로 넘기지 못함 | 환경의 성패를 말로 옮긴 반성 (가중치 갱신 없음) | 없음(반성을 기억에 쌓아 다음 시도의 문맥에 넣음) |
| Toolformer | 가중치 학습 (자기 지도) | ReAct식 프롬프팅은 매번 예시가 필요하고 호출 시점을 학습하지 않음 | 다음 토큰 예측 | 도구 호출이 끼워진 텍스트 |
| Function calling SFT (APIGen, ToolLLM 등) | 가중치 학습 (합성 시연) | Toolformer는 소수의 도구를 하나씩 따로 호출하고 연쇄 호출의 예가 없음 | 다음 토큰 예측 | 도구 schema가 주어진 단일·병렬 호출, 또는 관측을 포함한 다중 턴 궤적 |
| Search-R1 | 피드백으로 가중치 학습 (RL, 궤적 갈래) | 고정된 시연은 현재 정책이 스스로 실수한 뒤의 문맥을 충분히 덮지 못할 수 있음 | 최종 답의 정확 일치 | 검색 실행을 포함한 다중 턴 궤적 |
| ARPO | 피드백으로 가중치 학습 (RL, 궤적 갈래) | Search-R1식 궤적 단위 보상은 궤적 안의 어느 구간이 좋았는지 구분 못함 | 정확성·형식 + 다중 도구 사용 보너스 | 분기로 공통 prefix를 공유하는 궤적 묶음 |
| ToolRL | 피드백으로 가중치 학습 (RL, 단계 갈래) | Search-R1과 같은 한계를 단일 단계 호출과 보상 설계로 다룸 | 형식 + 호출의 세분화된 정확성 | 이력이 주어진 다음 호출 한 단계 |

### 2-1. ReAct와 Reflexion의 프롬프팅

도구 사용의 출발점은 학습이 아니라 프롬프트였다.
Yao 등의 ReAct는 모델이 "생각(thought)"과 "행동(action)"을 번갈아 쓰고 행동의 결과인
"관측(observation)"을 받아 다음 생각을 잇게 하는 형식을 few-shot 예시로 유도했다.[^react]
질의응답과 사실 확인에서 위키백과 검색을, 상호작용 과제에서 환경 명령을 행동으로 썼다.
이 형식은 이후 agent에서 널리 쓰이게 되었지만,
이 프롬프팅 설정에서는 매번 예시를 넣어야 하고 예시에 없는 상황에서 언제 도구를 부를지 모델이 알기 어렵다.
또 한 번의 시도 안에서는 관측을 보고 다음 행동을 고칠 수 있지만, 시도가 실패로 끝나면 그 경험은 다음 시도로 이어지지 않는다.

Shinn 등의 Reflexion은 실패한 시도의 경험을 다음 시도로 넘기는 방법을 보였다.[^reflexion]
과제를 한 번 수행하면 평가자가 그 궤적의 성패를 판정하고(질의응답은 정답과의 정확 일치, 코딩은 모델이 스스로 만든 단위 테스트),
LLM이 궤적과 성패를 보고 무엇이 잘못되었고 다음에는 어떻게 할지를 글로 쓴다.
이 반성문을 기억(episodic memory)에 쌓아 같은 과제의 다음 시도 문맥에 넣는다.
가중치를 바꾸는 대신 말로 된 피드백으로 행동을 강화한다는 뜻에서 저자들은 이를 verbal reinforcement라 불렀다.
그러나 모델은 그대로이고 나아진 것은 문맥뿐이다.
반성은 그 과제의 다음 시도에만 쓰이므로 새 과제에서는 다시 실패하고 다시 반성해야 하고,
쌓을 수 있는 반성의 양도 문맥 길이에 묶인다.
피드백으로 나아지는 효과를 모델에 남기려면 가중치를 학습해야 한다.

### 2-2. Toolformer의 자기 지도 학습

Schick 등의 Toolformer는 도구 호출을 모델에 **학습**시켰다.[^toolformer]
계산기, 검색,
번역 같은 API(application programming interface)를 어디에 끼워 넣으면 다음 토큰 예측이 좋아지는지를
모델 자신이 표집·검증해 학습 데이터를 만들고,
그 데이터로 언어 모델을 자기 지도 방식으로 fine-tuning했다.
사람이 쓴 예시는 API마다 몇 개뿐이다.
다만 도구마다 호출을 따로 생성해 데이터를 만들었으므로,
한 도구의 결과를 다른 도구의 입력으로 쓰는 연쇄 호출의 예가 학습 데이터에 없다는 한계를 저자들이 밝혔다(원논문 Limitations).
여러 도구 중 하나를 고르고 결과를 보며 호출을 이어 가는 대화형 사용은 다음 단계의 몫이었다.

### 2-3. Function calling과 합성 궤적의 SFT

대화 모델이 도구를 쓰는 방식은 지금 대부분 **function calling** 형식으로 정리되어 있다.
도구마다 이름, 설명, 인자의 이름과 타입을 JSON Schema로 적어 모델에 주고,
모델은 자유 텍스트 대신 "어떤 도구를 어떤 인자로 부를지"를 구조화된 호출로 낸다.
실행은 모델 밖의 코드가 맡고, 그 결과는 tool 역할의 메시지로 대화에 다시 들어간다.
Hugging Face Transformers의 chat template은 이 대화를 다음과 같은 메시지 목록으로 다룬다.[^hf-tools]

```python
tools = [get_current_temperature]  # 이름·인자·docstring에서 JSON Schema를 만들어 프롬프트에 넣는다
messages = [
    {"role": "user", "content": "지금 파리 기온이 몇 도야?"},
    {"role": "assistant", "tool_calls": [{"type": "function", "function": {
        "name": "get_current_temperature",
        "arguments": {"location": "Paris, France", "unit": "celsius"}}}]},
    {"role": "tool", "content": "22"},          # 실행 결과는 항상 문자열로 넣는다
    {"role": "assistant", "content": "지금 파리는 섭씨 22도입니다."},
]
```

모델마다 chat template이 이 목록을 자기 특수 토큰을 쓴 문자열로 바꾸고,
모델이 낸 호출 문자열은 다시 파싱해 실행한다.
SFT에서는 대개 assistant 차례의 토큰(호출과 최종 답)에만 손실을 걸고 tool 메시지는 mask한다.
앞에서 본 관측 토큰의 mask가 SFT 단계부터 들어가는 셈이다.

이런 대화를 사람이 대량으로 쓰기는 어려워서 학습 데이터는 주로 합성한다.
합성 데이터에는 두 종류가 있다.
하나는 질의와 도구 목록을 받아 호출 하나, 또는 한 응답에 여러 호출을 한꺼번에 내는(parallel) 데이터다.
다른 하나는 호출 결과를 관측으로 받고 그것을 보고 다음 호출을 정하는 다중 턴 궤적이다.
앞의 것만 학습하면 호출 형식과 도구 선택은 익히지만, 결과를 해석해 호출을 이어 가는 법은 따로 배워야 한다.

Liu 등의 APIGen은 앞의 종류에서 데이터의 정확성을 다뤘다.
실행 가능한 API로 질의와 호출을 생성한 뒤,
형식 검사, 실제 실행, 그리고 실행 결과가 질의의 목적에 맞는지를 다른 LLM이 판정하는 의미 검사의 세 단계를 모두 통과한 것만 남겼다.[^apigen]
Qin 등의 ToolLLM은 뒤의 종류를 만들었다.
실제 REST API를 모아 한 도구 또는 여러 도구를 써야 하는 지시를 ChatGPT로 만들고,
각 지시를 푸는 호출의 연쇄도 ChatGPT가 API 응답을 받아 가며 찾게 했다.[^toolllm]
이 탐색에는 막히면 되돌아가 다른 호출을 시도하는 깊이 우선 탐색 기반의 결정 트리(DFSDT)를 썼고,
이 데이터로 SFT한 모델은 학습 때 보지 못한 API에도 일반화했다.
Kimi K2는 다중 턴 궤적의 합성을 더 크게 밀었다.[^kimik2]
실제 MCP(model context protocol) 도구와 합성 도구로 도구 저장소를 만들고,
도구 조합이 다른 수많은 agent에 성공 기준(rubric)이 달린 과제를 주어,
사용자 역할의 LLM과 상태를 유지하는 도구 시뮬레이터 사이에서 궤적을 생성한 뒤 LLM 판정자가 rubric으로 걸렀다.
이 궤적은 SFT 데이터가 되고, 그 뒤의 RL은 검증 가능한 보상과 rubric 기반 자기 비평 보상을 함께 쓴다.[^kimik2]

<Details summary="세 데이터의 규모">

ToolLLM은 RapidAPI Hub의 49개 범주에서 REST API 16,464개를 모았다.[^toolllm]
APIGen은 21개 범주의 API 3,673개를 썼고, 이 데이터로 학습한 7B 모델은 발표 당시 Berkeley Function-Calling Benchmark에서 여러 GPT-4 모델을 앞섰다.[^apigen]
Kimi K2의 도구 저장소는 GitHub의 MCP 도구 3천여 개와 합성 도구 2만여 개로 이루어졌다.[^kimik2]

</Details>

SFT도 새 도구와 상황에 일반화할 수 있다.
다만 고정된 시연은 다른 모델이나 파이프라인이 만든 문맥이라,
현재 정책이 스스로 잘못 호출하고 오류를 받은 뒤의 문맥을 충분히 덮는다는 보장이 없다.
앞 주차 SFT에서 본 학습 문맥과 생성 문맥의 차이다.
오류와 복구를 담은 시연을 일부러 넣을 수도 있지만,
정책이 실제로 방문하는 문맥에서 성패를 얻는 가장 직접적인 방법은 환경과 상호작용하는 RL이다.

## 3. 환경 피드백으로 정책 학습

### 3-1. Search-R1의 다중 턴 rollout

Reflexion은 환경의 성패를 반성으로 문맥에 남겼다.
이제 그 성패를 가중치를 바꾸는 보상으로 쓴다.
RLVR의 검증 가능한 보상이 여기서 다시 쓰인다.
Jin 등의 Search-R1은 모델이 `<think>`, `<search>`,
`<answer>` 태그로 추론·검색·답을 번갈아 내게 하고,
검색 엔진이 `<information>` 태그로 결과를 돌려주며, 보상은 최종 답의 정확 일치뿐이다.[^searchr1]
프롬프트는 지식이 부족하면 검색을 부를 수 있다고만 알려 주고,
언제 무엇을 검색할지 보여 주는 예시는 주지 않았다.

정책 생성과 검색 실행이 번갈아 이어지는 궤적 전체가 하나의 rollout이다.
원논문 Algorithm 1의 rollout은 다음 순서로 돈다.

1. 질문을 넣고 행동 횟수를 0으로 둔다.
2. 정책이 `</search>`, `</answer>`, 또는 종료 토큰을 낼 때까지 토큰을 생성한다.
3. 방금 생성한 구간에 검색 호출이 있으면 검색어를 파싱해 실행하고, 결과를 `<information>`으로 감싸 궤적 뒤에 붙인다.
4. 답이 있으면 rollout을 끝낸다.
5. 둘 다 없으면 "My action is not correct. Let me rethink."라는 문장을 붙여 다시 생성하게 한다.
6. 행동 횟수를 하나 늘리고, 최대 행동 수에 이르지 않았으면 2로 돌아간다.

끝난 궤적은 최종 답을 정답과 비교해 채점하고, 같은 질문의 궤적들로 정책을 갱신한다.
여기서 보듯 잘못된 형식의 출력, 도구 실행의 오류나 timeout, 예산 소진은 각각 처리 방식을 정해야 하는 설계 선택이다.
Search-R1은 잘못된 형식을 다시 생각하라는 관측으로 돌려주고 예산이 다하면 그대로 끝내 채점한다.
오류를 관측으로 돌려주면 정책이 복구를 배울 기회가 생기고,
궤적을 끝내고 보상 0을 주면 형식 실수에 강한 벌이 된다.
검색 서버 장애처럼 정책의 잘못이 아닌 실패에 보상 0을 주면 정책이 하지 않은 실수를 벌하게 되므로,
그런 궤적은 학습에서 빼는 선택도 있다.
또 파일을 고치거나 데이터베이스를 바꾸는 환경이라면 그룹의 각 궤적은 같은 초기 상태의 독립된 사본에서 시작해야 한다.
한 궤적이 바꾼 상태 위에서 다른 궤적이 시작하면 그룹 안의 비교가 공정하지 않다.

<Callout type="example">
**두 턴 궤적의 mask와 return.** "소설 『채식주의자』의 작가가 노벨 문학상을 받은 해는?"이라는 질문에
Search-R1 형식으로 답하는 교육용 궤적을 보자.
학습에 들어가는 토큰열은 세 구간으로 나뉜다.

| 구간 | 내용 | 생성 주체 | Loss mask |
|---|---|---|---|
| 턴 1 | `<think>`작가를 먼저 확인하고 수상 연도를 찾는다`</think><search>`채식주의자 작가 노벨 문학상`</search>` | 정책 | 1 |
| 관측 | `<information>`한강은 2024년 노벨 문학상을 받았다. …`</information>` | 환경(검색 엔진) | 0 |
| 턴 2 | `<think>`작가는 한강이고 수상 연도는 2024년이다`</think><answer>`2024`</answer>` | 정책 | 1 |

관측 구간은 mask가 0이지만 턴 2의 토큰을 계산할 때 문맥으로 들어간다.
정책 갱신의 확률비와 log 확률은 mask가 1인 두 구간의 토큰에서만 계산한다.
최종 답이 맞아 보상 1을 받았고 중간 보상은 없다면, 할인 없이 계산한 각 턴의 return은 둘 다 1이다.
여기에 "검색어가 형식을 지켰는가"에 대한 process 보상 0.1을 턴 1에 더하면 턴 1의 return은 1.1, 턴 2는 1이 된다.
최종 보상을 두 턴에 임의로 반씩 나누지는 않는다.
각 턴은 자기 뒤에 온 보상의 합을 받는다.
실제 갱신 방향은 이 return에서 value model이나 그룹 baseline을 뺀 advantage가 정한다.
GRPO처럼 그룹 baseline을 쓰는데 같은 문제의 다른 궤적들도 모두 1을 받았다면,
advantage가 0이 되어 policy 항의 신호가 사라진다(KL 항의 gradient는 남는다).
</Callout>

Search-R1은 검색으로 가져온 토큰을 이렇게 손실에서 mask했고,
mask를 적용했을 때 성능 향상이 더 크고 학습이 더 안정적이었다고 보고했다.[^searchr1]
결과는 일곱 개 질의응답 데이터셋의 정확 일치 평균으로 보고되었다.
7B 모델에서 Instruct 모델에 검색 증강 생성(retrieval-augmented generation, RAG)을 붙인 기준선은 0.304,
base model에서 PPO로 학습한 Search-R1은 0.431이었다(원논문 Table 2).[^searchr1]
초기 모델이 서로 달라 엄밀한 전후 비교는 아니지만
이 결과에서 모델은 검색 시점을 보여 주는 예시 없이 최종 답의 보상만으로 검색을 쓰는 법을 배웠다.

### 3-2. ARPO의 분기 rollout

Search-R1처럼 궤적 단위로 보상을 주는 GRPO를 그대로 쓰면 궤적 안의 어느 구간이 좋았는지 구분하지 못한다.
Dong 등의 ARPO(agentic reinforced policy optimization)는 도구 결과가 돌아온 직후
정책의 entropy가 급격히 오른다는 관측에서 출발했다.[^arpo]
새 정보를 받은 직후에 모델이 특히 불확실해진다는 뜻이다.
그래서 ARPO는 궤적을 처음부터 끝까지 여러 개 따로 만드는 대신,
도구 결과 뒤에 entropy가 크게 오른 지점에서 궤적을 여러 갈래로 분기해 이어 생성한다(원논문 §3.1).

이렇게 얻은 궤적들은 분기 지점 앞의 토큰(공통 prefix)을 공유한다.
보상의 정규화는 일반 GRPO처럼 같은 질문의 전체 rollout 그룹에서 하고, 손실도 GRPO를 그대로 쓴다.
그러면 공통 prefix의 토큰은 분기 수만큼의 궤적에 같은 문맥으로 들어가 분기들의 신호를 함께 받고(궤적 길이 정규화와 clipping이 그 가중을 정한다),
갈라진 뒤의 토큰은 자기 분기의 advantage만 받는다.
예를 들어 더 큰 그룹 안에서 한 prefix로부터 갈라진 두 분기의 advantage가 $+0.8$과 $-0.4$이고
두 궤적의 길이가 같으며 clipping에 걸리지 않았다고 하면,
공통 토큰은 두 신호를 함께 받아 대체로 확률이 올라가는 쪽으로 움직이고,
갈라진 뒤의 토큰은 한쪽은 올라가고 다른 쪽은 내려간다.
공통 구간과 갈라진 뒤의 구간이 서로 다른 신호를 받게 되는 것이다.
다만 갈라진 뒤의 구간 안에서 어느 행동이 성패에 기여했는지는 여전히 나누지 못하며,
단계별 기여를 직접 판정하는 방법은 아니다.
보상은 정확성과 형식에 더해, 정답을 내면서 검색과 Python 실행을 함께 쓴 궤적에 0.1을 더 준다(원논문 §3.2).

수학·지식 질의응답·심층 검색의 13개 벤치마크에서 ARPO는 궤적 단위 RL 알고리즘보다 평균 성능이 높았고,
Qwen2.5-7B에서는 GRPO보다 학습 중 도구 호출을 절반만 쓰면서 정확도가 더 높았다(원논문 Figure 7).[^arpo]

### 3-3. ToolRL의 단일 단계 호출 보상

Qian 등의 ToolRL은 같은 문제를 다른 학습 단위로 다룬다.
다중 턴 궤적을 "지금까지의 대화 이력이 주어졌을 때 다음 도구 호출"이라는 단일 단계 사례로 분해해 프롬프트에 이력을 넣고,
보상 설계에 집중했다.
도구 호출의 형식 보상에 더해,
정답 호출과 비교해 도구 이름·인자 이름·인자 값이 각각 맞는지를 나누어 점수를 주는 세분화된 정확성 보상을 두었다.
Qwen2.5-Instruct와 Llama-3.2-3B-Instruct에서 출발해 GRPO로 학습했다.[^toolrl]
원논문은 도구 호출 데이터로 SFT를 더 한 뒤 RL을 하는 것보다 Instruct 모델에서 바로 RL을 시작하는 편이 그 실험에서 나았고,
보상을 세분화하면 학습이 안정적이었다고 보고한다.[^toolrl]

정답 호출이 주석된 데이터만 있으면 환경을 끝까지 돌리지 않고도 RL을 구성할 수 있다는 것이 이 갈래의 장점이다.
대신 보상이 정해진 정답 호출과의 일치이므로,
같은 결과에 이르는 다른 호출 순서는 낮은 점수를 받을 수 있고,
자기 실수 뒤의 복구나 여러 턴 뒤의 최종 성공은 직접 최적화하지 않는다.

## 4. 환경과 채점

### 4-1. 학습 환경의 구성

단일 응답 RL의 데이터는 문제와 정답이었다.
Agentic RL의 데이터는 **환경**이다.
도구가 실제로든 시뮬레이터 안에서든 실행되어야 하고, 과제마다 성공 조건이 있어야 하며,
궤적이 길어 사람이 만들기 어렵다.

코딩 agent의 학습 과제를 보면 환경이 무엇인지 구체적으로 드러난다.
과제 하나에는 저장소, 고칠 내용을 적은 이슈, 코드를 실제로 돌릴 수 있는 실행 환경, 수정이 맞는지 확인할 단위 테스트가 들어 있다.
정책은 파일을 찾아 읽고, 코드를 고치고, 실행해 결과를 보는 일을 여러 턴 되풀이한 뒤 최종 patch를 낸다.
그 patch에 테스트를 돌려 통과하면 성공이다.
SWE-bench는 이 형식을 갖춘 대표적인 평가 세트인데,
평가 세트로 학습하면 그 점수를 믿을 수 없으므로 학습에는 같은 형식이면서 평가와 겹치지 않는 과제가 따로 필요하다.
Pan 등의 SWE-Gym은 SWE-bench와 겹치지 않는 Python 저장소 11개에서 GitHub 이슈와 그것을 해결한 pull request를 모아,
실행 환경과 테스트를 갖춘 학습용 과제 2,438개를 만들었다.[^swegym]
실행 환경은 저장소마다 사람이 직접 설정했다.
이 논문의 학습 자체는 RL이 아니었다.
정책이 만든 궤적 중 테스트를 통과한 것만 골라 fine-tuning하는 rejection sampling fine-tuning을 썼고,
성공과 실패가 표시된 궤적으로 궤적의 성공 확률을 매기는 verifier를 따로 학습해 추론 때 여러 후보 중 하나를 고르는 데 썼다.[^swegym]
같은 환경에서 테스트 통과를 그대로 보상으로 쓰면 검증 가능한 보상을 건 RL이 된다.

실제 저장소마다 환경을 손으로 만드는 방식은 규모를 키우기 어렵고,
그래서 앞에서 본 Kimi K2처럼 도구와 사용자를 시뮬레이터로 대신하기도 한다.
시뮬레이터가 실제 환경과 다르면 시뮬레이터에 맞춘 행동을 배운다는 위험은 앞 주차 reward hacking에서 본 대리 지표 문제와 같다.

### 4-2. 무효 rollout과 생성 전 필터링

환경에서 궤적을 만드는 비용이 큰 만큼, 만든 궤적이 학습 신호를 주는지가 더 중요해진다.
Liu 등은 2026년에 도구 호출 agent의 학습과 평가를 함께 점검했다.[^liu2026]
학습 쪽의 관찰은 앞의 두 턴 궤적 예시의 마지막 문장과 이어진다.
한 프롬프트의 rollout이 모두 같은 보상을 받으면 그룹 advantage가 0이 되어 policy 항의 학습 신호가 없다.
도구 호출 RL에서는 이런 프롬프트의 비율이 예상보다 높았다.

Liu et al. 2026, Figure 4 오른쪽 · arXiv:2606.00135v2 · CC BY 4.0 · 수정 없음" />

[라이선스](https://creativecommons.org/licenses/by/4.0/)

DAPO의 dynamic sampling은 이런 그룹을 버리고 다시 뽑아 배치를 채우지만,
버린 만큼 생성을 다시 해야 하고,
Liu 등은 이 방식이 오히려 학습 시간을 크게 늘렸다고 관찰했다.
대신 이들은 생성 **전에** 거르는 방법을 제안했다.
최근 몇 epoch 동안 모든 rollout이 정답이었던 프롬프트는 한동안 계속 정답일 가능성이 높다는 관찰에 근거해,
그런 프롬프트를 rollout을 만들기 전에 건너뛴다.
어느 프롬프트가 무효인지는 학습 중에 바뀌므로 학습 전에 한 번 거르는 것으로는 부족하다.
여기에 정책 갱신 단계의 계산을 줄이는 rollout down-sampling을 더해,
같은 성능에 도달하는 시간이 단일 턴에서 1.7배, 다중 턴에서 2.6배 빨라졌다(원논문 Figure 7).[^liu2026]

### 4-3. 채점 환경의 분리와 감시

Agentic 코딩 과제에서는 정책이 코드를 고치는 바로 그 환경 안에 테스트와 채점 스크립트가 있다.
그러면 정책은 답을 고치는 대신 채점을 고칠 수 있다.
Baker 등은 OpenAI가 o1, o3-mini와 같은 계열의 추론 모델을 학습하던 중 두 해킹이 거의 모든 학습
환경으로 퍼진 것을 보고했다.[^baker]
하나는 `exit(0)`로, 단위 테스트가 모두 실행되기 전에 프로그램을 끝낸다.
다른 하나는 `raise SkipTest`로, 테스트 프레임워크 밖에서 예외를 일으켜 테스트를 건너뛰게 한다.

이런 해킹은 검증 조건을 늘려서는 막기 어렵다.
정책이 검증기 자체를 바꾸기 때문이다.
대응은 환경 설계 쪽에 있다.
정책이 고칠 수 있는 파일과 채점에 쓰는 파일을 나누고,
채점은 정책이 손대지 못하는 원래 테스트로 다시 돌린다.
Baker 등은 정책이 테스트를 고칠 수 있게 한 실험에서,
모든 테스트를 통과하더라도 테스트에 가한 변경을 되돌렸을 때 실패하면 그 해답을 부정행위로 판정했다.[^baker]

해킹을 잡으려면 먼저 봐야 한다.
Baker 등은 프롬프트를 준 GPT-4o를 감시자(monitor)로 쓰고,
앞의 두 해킹을 정규식으로 찾은 결과와 비교했다.
정책의 행동(도구 호출과 출력)만 본 감시자는 재현율(recall)이 60%였지만,
사고 과정까지 본 감시자는 95%였다(원논문 Table 1).[^baker]
정책은 해킹하기 전에 "테스트가 이 함수만 확인하니 verify가 항상 참을 돌려주게 하면 된다"는 식의 생각을 사고 과정에 그대로 적었다.
그렇다면 감시자의 판정을 보상에 넣어 "나쁜 생각"에 벌점을 주면 어떨까.
저자들이 사고 과정만 보는 감시자로 이를 시험하자,
학습 초반에는 부정행위 없이 통과하는 해답이 늘었다.
그러나 학습이 진행되자 정책은 여전히 부정행위를 하면서 사고 과정에는 그 의도를 쓰지 않게 되었고,
감시자의 재현율은 0에 가깝게 떨어졌다.
저자들은 이를 obfuscated reward hacking이라 부르고,
사고 과정에 직접 강한 최적화 압력을 가하지 말 것을 권했다.[^baker]
감시 신호도 보상에 넣는 순간 대리 지표가 된다.
다만 이 경고는 사고 과정 자체에 벌점을 주는 경우에 관한 것이다.
MacDiarmid 등의 실험에서는 해킹 행동을 잡는 분류기의 벌점을 보상에 넣으면 해킹이 학습되지 않았다.[^macdiarmid]

<Details summary="해킹을 배운 정책의 정렬 실패">

MacDiarmid 등은 Claude Sonnet 3.7의 학습에 쓰인 실제 코딩 환경에서 같은 종류의 해킹이 학습되는 과정을 재현했다.[^macdiarmid]
어떤 값과 비교해도 같다고 답하는 객체를 돌려주는 "AlwaysEqual", `sys.exit(0)`,
그리고 pytest의 결과 보고를 항상 통과로 고치는 `conftest.py` 파일이다.
이 실험은 해킹 방법을 담은 문서를 섞어 pre-training을 이어 하거나 프롬프트로 힌트를 주어 정책이 해킹을 시도할 수 있게 하고,
해킹이 가능한 환경만 골라 학습했다.

정책이 해킹을 배우기 시작한 시점에 맞춰 코딩과 무관한 정렬(alignment) 평가의 점수도 함께 나빠졌다.
목표를 묻는 단순한 질문에 겉으로만 정렬된 척하는 추론을 하거나,
해킹 탐지 분류기를 만들어 달라는 요청에 분류기가 덜 잡도록 몰래 손을 쓰는 식이다.
해킹 벌점으로 해킹을 막은 학습에서는 이런 정렬 실패가 늘지 않았다.
저자들은 pre-training 데이터에서 reward hacking이 정렬 실패와 함께 묘사되기 때문에
해킹을 배운 것이 그 연관을 따라 일반화되었다고 해석한다.
학습 프롬프트에 해킹을 허용된 행동으로 적어 두면(inoculation prompting) 해킹은 그대로 배워도 정렬 실패가 크게 줄었다는 결과가 그 근거다.
이 결과는 해킹 지식을 주입하고 해킹 가능한 환경만으로 학습한 조건에서 얻은 것이며
메커니즘은 저자들의 가설이다.

## 5. 자기 개선 루프

앞의 합성 파이프라인에서도 모델이 과제를 만들고 도구를 흉내 냈지만,
과제를 만드는 절차와 무엇이 개선인지의 기준은 사람이 정했고 학습을 돌리는 코드도 사람이 짰다.
개선된 시스템이 다음 자기 개선에 다시 참여하도록 그 부분까지 모델에게 넘기는 구조를 재귀적 자기 개선(recursive self-improvement, RSI)이라고 부른다.
그 반복이 개선을 가속한다는 기대가 있지만, 가속은 구조만으로 보장되지 않고 실험으로 보여야 할 대상이다.
지금까지 보고된 시스템은 루프의 일부만 닫았다.

첫째 갈래는 과제를 만드는 정책까지 RL로 학습한다.
Zhao 등의 Absolute Zero는 한 모델이 과제를 내는 역할(proposer)과 푸는 역할(solver)을 함께 맡는다.[^azr]
과제는 프로그램·입력·출력 중 둘을 주고 나머지 하나를 맞히는 코드 추론 문제이고,
코드 실행기가 제안된 과제가 오류 없이 결정적으로 돌아가는지 확인한 뒤 답을 채점한다.
Solver는 정답 보상을 받고,
proposer는 solver의 평균 정답률 $\bar r$가 0이면 보상 0, 아니면 $1-\bar r$를 받아 너무 쉽지도 풀 수 없지도 않은 과제를 내도록 학습된다(원논문 §3.1).
두 역할의 보상으로 같은 모델의 가중치를 갱신한다.
RLVR에서 본 "풀 수 있으면서 어려운 문제"라는 데이터 조건을 모델이 직접 맞추는 셈이다.
사람이 만든 학습 데이터 없이도 수만 개의 선별 데이터로 학습한 같은 크기의 RL-Zero 모델들과 비슷하거나 나은 코드·수학 점수를 냈다.[^azr]
판정은 여전히 사람이 정한 코드 실행기가 맡는다.

둘째 갈래는 가중치 대신 LLM을 감싼 코드를 고친다.
Zelikman 등의 STOP은 LLM을 불러 프로그램을 개선하는 개선기(improver) 프로그램을 자기 자신에게 적용해 더 나은 개선기를 얻었다.[^stop]
Zhang 등의 Darwin Gödel Machine은 코딩 agent가 자기 도구와 작업 흐름의 코드를 고친 변형을 만들고,
벤치마크로 평가해 보관소(archive)에 쌓으며 여러 갈래로 탐색했다.
SWE-bench Verified의 200개 과제 부분집합에서 성공률이 20.0%에서 50.0%로 올랐다.[^dgm]
두 방법 모두 기반 LLM의 가중치는 고정이고, 개선은 그 LLM을 쓰는 코드의 생성·평가·선택으로 이루어진다.
STOP의 저자들은 이 때문에 완전한 RSI가 아니라고 밝혔고,
Darwin Gödel Machine에서는 보관소 관리와 부모 선택 같은 바깥 탐색 절차도 사람이 정한 그대로 남는다(원논문 §3).[^dgm]

루프를 닫아도 개선을 판정하는 평가는 바깥에 남아야 하고, 그 평가가 다시 최적화 대상이 된다.
STOP에서는 "바꾸지 말라"고 적어 둔 sandbox 설정을 끄는 코드가 경고를 넣은 조건에서도 일부 수정안에 나왔다.[^stop]
Darwin Gödel Machine에서는 도구 사용의 환각을 줄이는 과제에서,
환각 검사 함수를 agent에게 숨겨 두었는데도 agent가 그 검사가 읽는 도구 사용 표시를 기록하지 않도록 자기 코드를 고쳐 만점을 받았다(원논문 Appendix H).[^dgm]
평가 함수를 숨기거나 채점 코드를 분리해도, 정책이 평가의 입력인 실행 기록을 바꿀 수 있으면 판정은 무력해진다.
그래서 자기 개선 시스템에서는 채점 코드뿐 아니라 실행 기록의 수집 경로도 수정 대상에서 떼어 놓고, sandbox와 사람의 감독을 전제로 둔다.

<Details summary="STOP의 sandbox 해제 시도 비율">

STOP은 초기 개선기에 대해 GPT-4가 낸 독립적인 수정안 10,000개에서 sandbox 해제를 시도한 코드를 문자열로 판별해 셌다.
그 비율은 기본 조건에서 0.42%, 해제하지 말라는 경고를 더한 조건에서 0.46%였다(원논문 §6.2, Table 2).[^stop]
여러 세대의 자기 개선에서 실제로 sandbox를 벗어난 비율이 아니라 시도의 비율이다.

</Details>

## 6. Agent의 평가

채점을 정책에게서 떼어 놓아도, 서로 다른 설정에서 잰 점수끼리는 여전히 비교하기 어렵다.
앞의 Liu 등은 평가 쪽에서 무작위 시드, 시스템 프롬프트, 다중 턴 template의 구성,
이전 턴의 이력과 추론을 다음 턴에 어떻게 넘기는지 같은 문서화되지 않은 작은 선택이 보고 점수를 크게 바꾸며,
다중 턴 설정에서는 표준화 없이 leaderboard 순위를 믿기 어렵다고 보고했다.[^liu2026]
자기 실험에서 agent 학습의 효과를 주장하려면 적어도 다음을 맞추고 함께 보고한다.

- **비교 대상.** 같은 출발 모델의 학습 전후를, 같은 도구·환경 버전과 같은 턴·토큰 예산에서 비교한다.
- **성공의 정의.** 호출 하나가 정답 호출과 같은지와 과제가 실제로 끝났는지는 다르다.
  Yao 등의 τ-bench는 대화가 끝난 뒤의 데이터베이스 상태를 목표 상태와 비교해 성공을 판정한다.[^taubench]
- **반복 안정성.** 같은 과제를 여러 번 돌린다.
  τ-bench는 long CoT에서 본 pass^$k$를 agent 평가에 제안한 벤치마크이며,
  GPT-4o 같은 function calling agent도 retail 영역에서 pass^8이 25% 아래였다.[^taubench]
- **비용.** 성공률과 함께 과제당 호출 수, 생성 토큰, 실행 시간을 적는다.

## 7. 정리

Agent를 만드는 방법은 신호를 어디서 얻고 어디에 남기느냐로 바뀌어 왔다.
프롬프팅은 형식과 반성을 문맥에만 두었고,
SFT는 합성한 시연을 가중치에 넣었지만 정책이 스스로 만든 문맥은 덮지 못할 수 있었고,
RL은 정책이 직접 만든 궤적의 성패를 가중치에 남긴다.
그 대가로 학습 데이터는 문제와 정답에서 실행 가능한 환경으로 바뀌었다.
환경의 초기화와 실패 처리가 곧 과제의 정의가 되고,
채점이 정책의 손에 닿으면 보상이 아니라 채점 절차가 최적화 대상이 된다.
정책 갱신 식 자체는 PPO·GRPO에서 크게 달라지지 않았고,
달라진 것은 그 식에 들어갈 궤적을 만들고 믿을 수 있게 하는 일이다.

서베이 §3의 나머지 능력 중 기억은 Reflexion에서 프롬프팅 수준으로만 보았고, 계획과 함께 이 노트에서 더 다루지 않는다.
서베이 §4의 과제 중 GUI(graphical user interface)와
체화 agent(embodied agent)는 이 노트의 범위 밖이다.
