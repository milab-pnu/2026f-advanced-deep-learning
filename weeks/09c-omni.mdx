영상에서 누군가 주전자 옆에 서 있고, 끓는 소리가 들린다고 하자.
화면만 보면 물이 끓는지 확실하지 않을 수 있다.
소리만 들으면 무엇이 소리를 내는지 알기 어렵다.
모델이 두 신호를 함께 보고 “주전자의 물이 끓고 있다”고 답하려면, 이미지나 audio를 각각 설명할 때보다 한 단계를 더 가야 한다.
영상과 소리가 같은 사건의 어느 순간에 해당하는지도 알아야 하기 때문이다.

Omni-modal large language model(Omni-MLLM)은 여러 종류의 입력을 함께 해석하는 모델이다.[^survey]
모델에 따라서는 텍스트 외의 형태로도 출력한다.
다만 Omni라는 이름만으로는 지원 범위를 알 수 없다.
모델마다 이미지·audio·비디오·텍스트 가운데 무엇을 입력으로 받고, 텍스트·음성·이미지 가운데 무엇을 출력하는지 따로 확인해야 한다.
이 노트는 서로 다른 입력을 LLM(large language model)에 연결하는 방법에서 출발한다.
이어서 시간에 따라 함께 흐르는 영상과 소리를 다루는 방법과, 음성으로 응답하는 구조를 살펴본다.

## 1. 여러 modality의 결합

### 1-1. 공통 표현 공간

이미지와 텍스트를 맞추는 CLIP과 audio와 텍스트를 맞추는 CLAP은 입력마다 encoder로 표현 벡터를 만들고, 서로 대응하는 입력의 표현이 가까워지도록 학습한다.
이 원리를 더 많은 modality로 넓히면서 모든 쌍을 직접 정렬하려 하면, modality 쌍마다 대응 자료가 필요하다.
ImageBind는 이미지를 공통 연결점으로 삼아 이 문제를 푼다.[^imagebind]
ImageBind는 이미지와 텍스트가 이미 정렬된 공간에서 출발해, audio·깊이·열영상 같은 다른 modality의 encoder를 각각 대응 이미지의 표현과 가까워지도록 학습한다.
그러면 짖는 소리와 “개가 짖는다”라는 텍스트의 쌍을 직접 보지 않았더라도, 두 표현이 개 사진을 거쳐 가까워질 수 있다.
ImageBind 원논문은 이처럼 직접 학습하지 않은 조합에서 나타나는 정렬을 emergent alignment라 부른다.

<Callout type="warning">
공통 공간은 각 표현의 **유사도를 비교할 수 있는 공간**이다.
표현을 같은 공간에 놓았다는 사실만으로 시간 관계를 추론하거나 문장으로 답하는 기능까지 생기는 것은 아니다.
</Callout>

### 1-2. 표현 공간에서 LLM 입력으로

질문에 답하려면 표현을 비교하는 데서 그치지 않고, LLM(large language model)이 그 표현을 읽어야 한다.
그래서 projector가 modality마다 encoder의 표현을 LLM의 입력 표현으로 바꾸고, 모델은 이 입력을 조건으로 다음 token을 예측하도록 학습한다.
초기 audio-visual 모델인 Video-LLaMA는 영상과 audio에 서로 다른 경로를 두고, 경로마다 학습 가능한 query로 frame이나 소리 구간의 정보를 정해진 수의 벡터로 요약해 LLM에 넣는다.[^videollama]

<Figure src="https://arxiv.org/html/2306.02858v4/video_llama_architecture_v7.png" alt="Video-LLaMA 구조. 왼쪽 vision-language branch에서는 고정된 visual encoder가 비디오 frame마다 feature를 내고, 시간 위치 embedding을 더한 뒤 Video Q-Former와 선형층을 거쳐 LLM으로 들어간다. 오른쪽 audio-language branch에서는 고정된 audio encoder가 소리 구간마다 feature를 내고, 시간 위치를 더한 뒤 Audio Q-Former와 선형층을 거친다. 맨 위의 LLM은 고정되어 있고 두 branch의 출력과 텍스트 지시를 받아 설명을 생성한다." caption="Video-LLaMA의 두 경로. 눈꽃 표시는 고정된 모델, 불꽃 표시는 학습하는 모듈이다. 영상과 audio가 각각 Q-Former로 요약되어 LLM에 들어가며, 두 경로는 LLM 안에서 처음 만난다." source="Zhang et al. (2023), Figure 1 · CC BY 4.0" />

Video-LLaMA는 audio–텍스트 자료가 부족해 audio 경로를 시각–텍스트 자료로 학습했는데도, 추론할 때 audio를 이해하는 능력을 보였다고 보고한다.
ImageBind의 공통 공간에서 이미지와 audio의 표현이 가깝기 때문이다.
다만 영상과 audio를 각각 고정 개수의 벡터로 요약하므로, 두 신호 사이의 세밀한 시간 관계는 LLM에 충분히 전달되지 않을 수 있다.

### 1-3. 입력과 출력의 표현

다른 modality를 LLM에 넣는 방법은 encoder의 연속 벡터를 그대로 넣는 continuous representation과, codebook으로 만든 이산 ID를 어휘에 추가하는 discrete token의 두 가지다.
어려움은 출력에서 생긴다.
LLM의 출력층은 어휘에 대한 확률을 계산해 discrete token ID를 고르므로, 이 출력층만으로는 연속 벡터를 내보내지 못한다.
그래서 이미지나 음성을 출력하는 길도 둘이다.
첫째, 이미지·음성의 codebook ID를 어휘에 추가해 LLM이 고르게 하고, decoder가 ID를 픽셀이나 파형으로 되돌린다.
둘째, LLM의 hidden state를 별도의 생성기에 연속 조건으로 넘겨, 생성기가 이미지나 음성을 만든다.
그래서 Omni 모델에서는 입력을 continuous representation으로 받고 음성 출력은 discrete token으로 내는 비대칭 구성이 자주 보인다.

```text
입력: [텍스트 embedding] [이미지 연속 벡터 × 64] [음성 연속 벡터 × 125]
출력: LLM 또는 별도 음성 생성기 → [음성 codec ID] … → codec decoder → 파형
```

한 modality에 두 표현을 함께 쓰기도 한다.
HyperCLOVA X 8B Omni는 이미지와 음성을 연속 encoder와 이산 tokenizer 양쪽으로 언어 모델에 연결하고, 생성한 이산 token은 modality별 decoder가 이미지와 음성으로 바꾼다.[^naver-omni-report]
연속 feature는 입력을 세밀하게 이해하는 데, discrete token은 입력과 출력 양쪽에 쓰인다.

<Figure src="https://arxiv.org/html/2601.01792v1/Overview_model_main.png" alt="HyperCLOVA X 8B Omni의 전체 구조. 가운데의 단일 언어 모델 아래쪽에 입력 경로가 있다. 이미지는 continuous representation을 내는 vision encoder와 discrete token을 내는 vision tokenizer를 모두 거치고, 음성도 연속 audio encoder와 이산 audio tokenizer를 모두 거친다. 위쪽에는 출력 경로가 있어, 생성된 vision token은 diffusion 기반 vision decoder로, audio token은 화자 embedding과 함께 audio decoder로 들어간다." caption="HyperCLOVA X 8B Omni의 입력과 출력. 아래쪽 입력에서는 vision과 audio 각각에 연속 encoder와 discrete tokenizer를 함께 쓰고, 위쪽 출력에서는 모델이 생성한 discrete token을 modality별 decoder가 이미지와 음성으로 바꾼다." source="NAVER Cloud HyperCLOVA X Team (2026), Figure 2 · CC BY 4.0" wide />

지원하는 입출력도 모델마다 다르다.
같은 Omni 모델이라도 비디오를 입력으로만 받고 생성하지 않거나, 음성으로는 답하지 않고 텍스트로만 답하기도 한다.[^naver-omni-card][^gemini4argon]
그래서 Omni라는 이름만으로는 지원 범위를 알 수 없다.

### 1-4. 여러 형태의 출력

같은 요청 “고양이 그림을 그려 줘”에 대해, 앞의 두 출력 경로는 다음처럼 다르다.

| 접근 | 언어 모델에서 나온 표현 | 이미지 생성 경로 |
| --- | --- | --- |
| hidden state를 조건으로 넘기기 | 이미지를 알리는 특수 token 위치의 hidden state | 출력 projection → 기존 이미지 생성기의 조건 → 이미지 |
| 이미지 ID를 직접 생성하기 | 이미지 code ID sequence, 예를 들어 `[12, 8, 31, …]` | 코드 → 이미지 decoder → 이미지 |

NExT-GPT는 첫째 방식으로, 기존 생성기를 그대로 쓸 수 있지만 LLM의 출력을 각 생성기의 조건에 맞추는 학습이 필요하다.[^nextgpt]
AnyGPT는 둘째 방식으로, 이미지·음성·음악을 모두 discrete token으로 바꾸어 텍스트 token과 하나의 sequence로 모델링한다.[^anygpt]

## 2. 데이터와 학습

### 2-1. 정렬과 instruction tuning

서로 다른 encoder를 LLM에 붙였다고 해서, 모델이 곧바로 모든 입력 조합에 답하지는 못한다.
보통 먼저 이미지–텍스트나 audio–텍스트처럼 대응 관계가 있는 자료로 projector를 학습해 각 입력 경로를 LLM에 맞추고, 이후 사용자 지시와 원하는 응답을 갖춘 자료로 instruction tuning을 한다.[^survey]
이때 단일 modality 데이터 여러 종류를 섞는 것과, 한 예제에서 여러 modality를 **함께 사용하도록 요구하는 것**은 구별해야 한다.
모델이 이미지 질문과 audio 질문을 각각 잘 푼다고 해서, 화면의 특정 인물과 동시에 들리는 목소리를 연결할 수 있다고 결론 낼 수는 없다.

여러 입력을 함께 쓰는 자료는 드물어서 만들어 쓰기도 한다.
카카오는 Kanana-o를 개발하면서, 이미지–텍스트 자료의 질문이나 답변을 음성으로 합성해 이미지·음성·텍스트가 함께 쓰이는 학습 예시를 만들었다.[^kanana-o]
예를 들어 같은 이미지에 대한 질문을 음성으로 주고 텍스트로 답하게 하거나, 텍스트 질문에 음성으로 답하게 할 수 있다.
합성 음성은 자료를 쉽게 늘려 주지만, 합성만으로 실제 환경의 잡음과 말투를 모두 담기는 어렵다.

### 2-2. Interleaved sequence

이미지와 텍스트가 교차하는 interleaved sequence는 여러 이미지와 문맥의 관계를 표현한다.[^flamingo]
같은 구성을 audio와 비디오까지 넓히면, 시간 관계를 어떻게 표현할지가 문제가 된다.

```text
[영상: 0–2초] [audio: 0–2초] [영상: 2–4초] [audio: 2–4초]
[질문: 박수는 언제 들렸는가?] [답변]
```

각 구간의 영상과 audio를 가까이 배치해도, 구간 안에서 사건이 일어난 시각은 따로 나타내야 한다.
문서 속 이미지의 순서는 서술 순서일 수 있지만, 비디오와 audio에서는 각 조각이 실제로 언제 일어났는지가 중요하다.

### 2-3. 영상과 소리의 시간 관계

두 사람이 차례로 말하는 영상에서 “누가 박수가 들릴 때 말했는가?”를 묻는다고 하자.
모델은 박수 소리 주변의 frame에서 입의 움직임을 보고 음성과 대조해야 하고, 그러려면 사건의 순서와 동시성에 관한 정보가 필요하다.
그런데 모델은 보통 원본 영상의 모든 frame을 넣지 않는다.
예를 들어 0초와 1초에 영상 frame을 뽑고 audio를 0.5초 구간으로 나누면, 0.7초의 박수는 두 번째 audio 구간에 들어가지만 그 순간의 화면은 입력에 없다.

영상 frame과 audio 구간을 촘촘히 나누면 빠른 사건을 포착하기 쉽지만, 입력 길이와 계산량이 늘어난다.
반대로 강하게 압축하면 입력은 짧아지지만, 입 모양과 음절이 맞는지 같은 세부 관계가 사라질 수 있다.

## 3. 시간 동기화

### 3-1. 위치와 실제 시간

텍스트의 위치는 token sequence 안의 순서로 나타낸다.
그런데 audio encoder는 영상 encoder와 다른 속도로 표현을 만들므로, 입력에 순번만 매기면 서로 다른 modality의 표현이 실제 시간에서 얼마나 떨어져 있는지 알 수 없다.
Qwen2.5-Omni의 TMRoPE(time-aligned multimodal rotary position embedding)는 위치 번호를 시간·높이·너비 세 성분으로 나누고, 시간 성분을 실제 시간에 맞춘다.[^qwen25]
영상은 frame마다 시간 성분이 달라지고, audio는 공간 위치가 없으므로 세 성분에 같은 시간 번호를 쓴다.

<Figure src="https://arxiv.org/html/2503.20215v1/figures/ATMRoPE.png" alt="TMRoPE의 위치 부여. 영상 frame의 patch마다 (시간, 높이, 너비) 세 숫자가 붙어 있다. 첫 frame의 patch는 (0, 0, 0)부터 (0, 2, 2)까지이고 다음 frame은 시간 성분이 25, 그다음은 50, 75로 늘어난다. 아래의 audio 파형에는 (0, 0, 0), (25, 25, 25), (50, 50, 50)처럼 세 성분이 같은 값으로 붙고, 2초마다 구간이 나뉜다." caption="TMRoPE의 위치 ID (시간, 높이, 너비). 한 frame의 patch는 시간 ID를 공유하고 높이·너비가 다르며, audio는 세 성분이 같은 시간 ID로 함께 늘어난다. 시간 ID 25칸이 1초이므로, 같은 순간의 영상 patch와 audio 표현은 시간 ID가 같다." source="Xu et al. (2025), Figure 3 · CC BY 4.0" wide />

그래서 같은 순간의 영상과 audio는 sequence 안에서 멀리 떨어져 있어도 같은 시간 번호를 받는다.
다만 위치 정보는 단서일 뿐이고, 모델이 그 관계를 실제로 쓰는지는 시간 관계가 필요한 질문으로 평가해야 한다.

### 3-2. Chunk와 동기화의 단위

영상과 audio를 실제 시간 기준의 짧은 구간(chunk)으로 나누고, 구간마다 영상 표현 다음에 audio 표현을 두는 방식도 있다.[^qwen25]
이 순서는 처리 단위를 시간에 가깝게 묶어 주지만, 구간 안의 실제 시간 차이는 각 표현의 위치 번호가 나타낸다.
후속 모델은 고정된 chunk 대신 실제 timestamp에 맞춘 위치 번호로 영상과 audio를 정렬하면서도, streaming을 위해 입력을 조각으로 나눠 앞부분부터 처리하는 방식은 유지한다.[^qwen3]

긴 비디오에서는 audio 표현의 수도 문제가 된다.
그래서 비디오의 audio feature를 초당 1개 수준까지 압축해 더 긴 영상을 넣기도 한다.[^naver-omni-report]
다만 여러 시점을 하나로 요약하므로, 압축된 표현이 구간 안의 순서와 짧은 사건을 얼마나 보존하는지 확인해야 한다.

## 4. 통합 입력과 출력

### 4-1. Cascade와 native multimodal

음성 인식기가 질문을 텍스트로 바꾸고, 이미지 모델이 설명을 생성한 다음, 텍스트 LLM이 두 결과를 보고 답하게 만들 수도 있다.
이런 cascade는 각 부품을 따로 바꾸기 쉽지만, 앞 단계가 버린 정보는 다음 단계가 복구할 수 없다.
예를 들어 “정말 잘했어”라는 문장만 전달되면, LLM은 칭찬인지 비꼬는 말인지 가를 억양을 알 수 없다.
Audio와 이미지 표현을 모델에 직접 전달하고, 텍스트로 확정하는 단계 없이 입력부터 출력까지 이어 학습한 구성을 end-to-end라 부른다.
OpenAI는 GPT-4o를 이렇게 학습해, 텍스트·audio·이미지·비디오 입력과 텍스트·audio·이미지 출력을 같은 신경망이 처리한다고 소개한다.[^gpt4o]

End-to-end로 학습하는 모델도 대개 사전학습된 부품에서 출발해 단계적으로 연결한다.[^qwen25]
카카오의 Kanana-o는 이를 다른 방식으로 풀었다.[^kanana-o]
같은 언어 모델에서 출발해 각각 시각과 음성을 학습한 Kanana-v와 Kanana-a를 model merging으로 합친 뒤, 추가로 학습했다.
두 모델이 같은 언어 모델에서 갈라져 나왔기에 parameter를 결합할 수 있었다.

### 4-2. Thinker와 Talker

입력을 이해하고 답의 내용을 정하는 일과, 발음·길이·억양을 담은 음성을 만드는 일은 계산의 성격이 다르다.
그래서 두 역할을 나누는 설계가 있다.
Qwen2.5-Omni의 Thinker는 텍스트와 영상·audio 입력을 받아 응답 텍스트와 내부 표현을 만들고, Talker는 그 내부 표현과 텍스트를 조건으로 음성 token을 생성한다.[^qwen25]

<Figure src="https://arxiv.org/html/2503.20215v1/figures/overview.png" alt="Qwen2.5-Omni 구조. 아래쪽에서 시간 순서로 놓인 영상 frame과 audio 파형이 vision encoder와 audio encoder를 거쳐 텍스트 token과 함께 Thinker에 들어간다. Thinker는 응답 텍스트 token을 차례로 sample하고, 그 위의 Talker는 Thinker의 hidden 표현과 sample된 텍스트 token을 받아 codec token을 생성한다. 맨 위의 streaming codec decoder가 codec token을 파형으로 바꾼다." caption="Qwen2.5-Omni의 Thinker–Talker 구조. Thinker가 입력을 이해해 텍스트를 생성하고, Talker는 Thinker의 hidden 표현과 생성된 텍스트를 받아 codec token을 낸다. 맨 위의 decoder가 이를 파형으로 바꾼다." source="Xu et al. (2025), Figure 2 · CC BY 4.0" />

후속 모델은 음성 출력을 여러 codebook의 token으로 구성하고, 한 frame의 나머지 codebook은 작은 예측 모듈에 맡긴다.[^qwen3]
한 frame의 여러 codebook을 작은 모듈에 맡긴다는 점에서 Moshi의 Depth Transformer와 같은 문제를 푸는 설계다.[^moshi]
또 앞선 문맥만 쓰는 causal decoder로 파형을 만들어, 첫 음성 frame부터 streaming할 수 있게 했다.
Thinker와 Talker가 나뉘어 있으므로, 텍스트만 필요하면 Thinker만 쓸 수도 있다.

### 4-3. 음성 token 생성과 발화 제어

Kanana-o도 답의 내용을 만드는 언어 모델과 음성 token을 만드는 Voice Token LM을 나누고, 음성 tokenizer로 의미·음향 token을 함께 쓰는 LM-SPT를 적용했다.[^kanana-o-speech]
한 frame에 여러 codebook이 있으므로, Voice Token LM은 각 codebook의 출력을 한 단계씩 늦춰 생성한다.
그러면 뒤쪽 codebook은 같은 frame의 앞쪽 결과를 참고하면서도, 여러 시간 위치의 token을 병렬로 생성할 수 있다.

| 생성 단계 | 의미 token | 음향 token |
| --- | --- | --- |
| 1 | S1 | 대기 |
| 2 | S2 | A1 |
| 3 | 종료 후 대기 | A2 |

두 번째 단계에서는 다음 frame의 `S2`와 첫 frame의 `A1`을 함께 예측하고, `A1`은 이미 생성한 `S1`을 참고한다.
생성이 끝나면 `S1`과 `A1`, `S2`와 `A2`를 각각 같은 frame으로 다시 묶는다.

음성 token을 생성할 수 있다는 것과 “아주 빠르게 말해 줘”라는 지시를 정확히 따르는 것은 별개다.
카카오는 같은 문장에서 발화 속도 등만 바꾼 음성들로 선호 쌍을 만들어 보상 모델을 학습하고, 이 보상으로 online RL(reinforcement learning)을 적용했다.
발화 지시 점수만 높이면 빠르게 말하는 대신 단어를 빠뜨리는 문제가 생길 수 있어, 발화 오류율·화자 유사도·음질도 함께 보상에 반영했다.

### 4-4. 실시간 상호작용

음성으로 답하는 모델은 출력을 작은 조각으로 나누어 앞부분부터 내보내는 streaming을 쓴다.
하지만 첫 조각을 빨리 내는 것과, 사용자가 말하는 동안에도 듣고 말하는 full duplex는 다른 문제다.
한 가지 방법은 동시에 흐르는 입력과 출력을 짧은 시간 구간별로 묶어 하나의 sequence에 번갈아 넣는 것이다.[^minicpmo45]
그러면 모델은 사용자의 영상과 음성을 받아들이는 동안에도 음성으로 응답할 수 있다.

## 5. Omni 모델의 평가

입력 modality별 점수와 modality를 함께 써야 하는 문제의 점수는 서로 다른 능력을 측정한다.
그래서 Omni 모델은 여러 입력을 함께 써야만 풀리는 벤치마크로 평가한다.

| 영역 | 묻는 능력 | 대표 벤치마크 |
| --- | --- | --- |
| 이미지·audio·텍스트 통합 | 세 입력을 함께 이해하고 추론하기 | OmniBench[^omnibench] |
| Audio-visual 비디오 이해 | 영상과 소리가 함께 담긴 실제 비디오에 대해 답하기 | WorldSense[^worldsense] |
| 소리 자체의 지각 | 영상과 함께 주어진 소리의 크기, 높낮이 같은 속성을 구별하기 | AV-Odyssey[^avodyssey] |

OmniBench는 정답을 맞히려면 이미지, 소리, 텍스트를 모두 이해해야 하도록 사람이 문제를 만들었고, 대부분의 모델이 50%에 못 미쳤다.
WorldSense는 영상과 소리가 맞물린 비디오 1,662개에 26가지 task의 객관식 질문 3,172개를 붙였고, 발표 당시 가장 높은 정확도는 65.1%였다.
AV-Odyssey 원논문은 두 소리 가운데 어느 쪽이 더 크거나 높은지 같은, 사람에게는 쉬운 문제에서도 모델들이 자주 틀린다고 보고한다.

한 modality만 보고도 맞힐 수 있는 지름길도 확인해야 한다.
예를 들어 같은 영상에서 A가 먼저 말하고 B가 나중에 말할 때, 박수를 A의 발화 구간에서 B의 발화 구간으로 옮기면 정답도 A에서 B로 바뀌어야 한다.
모델이 두 경우에 같은 답을 낸다면, 박수와 발화의 시간 관계를 쓰지 못한 것이다.
실시간 시스템은 정답 외에도 첫 응답까지의 지연과 입력이 겹쳤을 때의 행동을 함께 살펴야 하며, 지연 수치는 하드웨어와 측정 조건에 따라 달라진다.
