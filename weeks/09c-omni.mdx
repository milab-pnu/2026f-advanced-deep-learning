영상에서 누군가 주전자 옆에 서 있고, 끓는 소리가 들린다고 하자.
화면만 보면 물이 끓는지 확실하지 않을 수 있고, 소리만 들으면 무엇이 소리를 내는지 알기 어려울 수 있다.
두 신호를 함께 보고 “주전자의 물이 끓고 있다”고 답하는 일은 이미지나 오디오를 각각 설명하는 것보다 한 단계 더 나아간다.
영상과 소리가 같은 사건의 어느 순간에 해당하는지도 알아야 하기 때문이다.

Omni-modal large language model(Omni-MLLM)은 여러 종류의 입력을 받아 함께 해석하고, 모델에 따라 여러 형태의 출력을 만들도록 설계한 모델이다.[^survey]
이름만으로 모든 modality의 입출력을 지원한다고 가정할 수는 없다.
모델마다 이미지·오디오·비디오·텍스트 가운데 무엇을 입력으로 받고, 텍스트·음성·이미지 중 무엇을 출력할 수 있는지 따로 확인해야 한다.
이 노트는 서로 다른 입력을 LLM(large language model)에 연결하는 방법에서 출발해, 시간에 따라 결합된 영상과 소리를 다루고 음성으로 응답하는 구조까지 살펴본다.

## 1. 여러 modality의 결합

### 1-1. 공통 표현 공간

이미지와 텍스트를 맞추는 CLIP이나 오디오와 텍스트를 맞추는 CLAP에서는 입력마다 encoder로 표현 벡터를 만들고, 대응하는 입력의 표현이 가까워지도록 학습한다.
이 원리를 더 많은 modality로 확장할 때 모든 종류의 쌍을 직접 수집해야 한다면 데이터 요구량이 빠르게 늘어난다.
오디오와 텍스트, 오디오와 깊이 영상, 깊이 영상과 텍스트 등 가능한 조합마다 대응 자료가 필요하기 때문이다.

ImageBind는 이미지를 공통 연결점으로 삼아 이 문제를 다룬다.[^imagebind]
텍스트와 이미지를 연결한 표현 공간을 사용하고, 오디오·깊이·열영상·관성 측정 정보도 각각 대응 이미지와 가깝도록 학습한다.
예를 들어 개 사진과 그 사진에 대응하는 짖는 소리의 표현이 가까워지고, 개 사진과 “개가 짖는다”라는 텍스트 표현도 가까워진다면, 직접 짝지어진 소리–텍스트를 보지 않았더라도 두 표현이 가까워질 가능성이 있다.
이처럼 직접 학습하지 않은 조합에 나타나는 정렬을 논문은 emergent alignment라고 부른다.

<Callout type="warning">
공통 공간은 각 표현의 **유사도를 비교할 수 있는 공간**이다.
서로 가까운 표현이 생겼다고 해서 모델이 시간 관계를 정확하게 추론하거나 자유로운 문장으로 답변하는 능력까지 자동으로 얻는 것은 아니다.
공통 공간을 만든 ImageBind와 이를 활용하는 생성형 모델은 역할이 다르다.
</Callout>

### 1-2. 표현 공간에서 LLM 입력으로

생성형 모델은 표현을 비교하는 데서 더 나아가 사용자의 질문에 답해야 한다.
이미지와 audio encoder가 만든 벡터가 LLM의 입력과 차원이 같아도, 그 자체로 LLM이 해당 벡터의 의미를 해석할 수 있는 것은 아니다.
별도의 connector를 학습해 modality 표현을 LLM이 처리할 수 있는 입력 표현으로 바꾸고, 그 입력에 조건을 건 다음 token을 예측하도록 학습한다.

초기 audio-visual 모델인 Video-LLaMA는 영상 frame과 오디오에 서로 다른 경로를 둔다.[^videollama]
이미지 encoder로 frame마다 feature를 추출하고 시간 위치를 더한 후, 학습 가능한 query로 frame 정보를 모아 LLM 입력으로 변환한다.
오디오 경로는 짧게 나눈 소리를 ImageBind의 사전학습된 audio encoder로 표현하고, 각 구간에 시간 위치를 더한 뒤 query 기반 연결부에 전달한다.
두 경로 모두 query 기반 연결부의 출력은 선형 변환을 거쳐 LLM의 입력 차원에 맞춰진다.
이 연결부는 BLIP-2의 Q-Former처럼 학습 가능한 query 벡터가 입력 feature에 cross-attention을 적용해 정해진 수의 표현을 뽑는다.
앞서 본 공통 표현 공간이 여기서는 생성형 모델의 입력을 만드는 데 쓰인다.
LLM은 두 입력을 텍스트 지시와 함께 받아 답변을 생성한다.

| 입력 | 표현 경로 | LLM에 전달되는 정보 |
| --- | --- | --- |
| 영상 | frame별 이미지 encoder → 시간 위치 → Video Q-Former | 시간 순서가 반영된 영상 표현 |
| 오디오 | 구간별 ImageBind audio encoder → 시간 위치 → Audio Q-Former | 시간 순서가 반영된 오디오 표현 |

두 경로의 상세 구조는 [Video-LLaMA 원논문](https://arxiv.org/html/2306.02858v4)에서 확인할 수 있다.

frame 하나를 이미지처럼 처리하는 것만으로는 움직임의 방향을 알기 어렵다.
예를 들어 공이 왼쪽에 있는 frame과 오른쪽에 있는 frame이 있더라도 순서를 잃으면 어느 쪽으로 움직였는지 구분할 수 없다.
Video-LLaMA는 frame에 시간 위치를 부여한 다음 이를 모으는 방법으로 순서 정보를 전달한다.
다만 오디오와 영상을 각각 요약해 넣는 구조가 모든 세밀한 시간 관계를 보존한다는 보장은 없다.

### 1-3. 연속 표현과 이산 token

Video-LLaMA는 영상과 오디오를 encoder의 연속 벡터로 LLM에 넣었다.
텍스트만 다루던 LLM에 이런 벡터를 넣을 수 있는 것은 LLM도 안에서는 벡터를 다루기 때문이다.
텍스트 LLM은 token ID를 embedding table에서 벡터로 바꾸어 Transformer에 넣고, 출력에서는 마지막 hidden state를 어휘의 ID마다 하나씩인 점수(logit)로 바꾸고 softmax로 다음 ID를 고른다.
Transformer 층이 받는 것은 ID가 아니라 벡터의 sequence다.

그래서 입력 쪽에서는 이미지·오디오·비디오를 두 방식 중 하나로 텍스트와 같은 sequence에 넣을 수 있다.
하나는 encoder와 connector가 만든 연속 벡터를 embedding 자리에 바로 넣는 것이다.
다른 하나는 codebook(학습된 대표 벡터의 목록)으로 입력을 이산 ID로 바꾸고, 그 ID를 어휘에 추가해 텍스트처럼 embedding table에서 꺼내는 것이다.
Omni 모델은 이 선택을 modality마다 따로 할 수 있다.
연속 벡터는 codebook 근사로 잃는 정보가 없어 이해에 유리하므로, 입력은 연속 표현으로 받는 경우가 많다.

어려움은 출력에서 생긴다.
LLM의 출력층은 어휘 위의 softmax이므로 그대로는 ID만 고를 수 있다.
이미지나 음성을 출력하려면 크게 두 길이 있다.
첫째, 이미지·음성의 codebook ID를 어휘에 추가해 텍스트와 같은 softmax로 고르고, 해당 decoder가 ID를 픽셀이나 파형으로 되돌린다.
둘째, LLM이 만든 hidden state를 연속 조건으로 별도의 생성기에 넘기고, 생성기가 결과를 만든다.
입력은 정보 손실이 적은 연속 표현으로 받고, 출력은 softmax로 고를 수 있는 이산 token으로 내는 비대칭 구성이 Omni 모델에서 흔한 이유가 여기에 있다.

사진을 보여 주며 음성으로 질문하고 음성으로 답을 듣는 대화를 개념적으로 쓰면 다음과 같다.
대괄호는 데이터의 종류를 나타낸 표시이며 개수는 가상의 값이다.

```text
입력: [텍스트 embedding] [이미지 연속 벡터 × 64] [음성 연속 벡터 × 125]
출력: [음성 codec ID] [음성 codec ID] … → codec decoder → 파형
```

입력의 세 조각은 모두 같은 차원의 벡터라 한 sequence로 이어지지만, 출력은 softmax로 고른 ID이고 파형으로 바꾸는 decoder가 따로 있다.

### 1-4. 여러 형태의 출력

Video-LLaMA가 다루는 출력은 텍스트다.
사용자가 설명을 읽는 대신 이미지나 소리 자체를 만들어 달라고 하면 앞에서 본 두 출력 경로 중 하나가 필요하다.
NExT-GPT는 둘째 길을, AnyGPT는 첫째 길을 택한 대표 사례다.

NExT-GPT는 사전학습된 입력 encoder(ImageBind)의 연속 표현을 LLM에 넣고, LLM 뒤에 이미지·오디오·비디오용 생성 decoder를 연결한다.[^nextgpt]
예를 들어 이미지 생성을 요청하면 LLM의 출력 표현을 이미지 decoder가 활용할 조건으로 변환하고, decoder가 이미지를 만든다.
NExT-GPT는 LLM 어휘에 이미지·오디오·비디오를 알리는 특수 token(modality signal token)을 추가한다.
LLM이 이 token을 출력하면 그 위치의 hidden representation을 출력 projection이 생성기의 조건으로 바꾼다.
기존 생성기를 활용할 수 있지만, 각 decoder가 이해하는 조건과 LLM의 출력을 맞추는 학습이 필요하다.

AnyGPT는 이미지·음성·음악을 각각 이산 token으로 바꾸어 텍스트 token과 함께 sequence로 모델링하므로, 입력과 출력이 모두 이산 token이다.[^anygpt]
음성에는 SpeechTokenizer의 내용 중심 token을 사용하고, 이미지에는 이미지 표현을 quantization하여 얻은 token을 사용한다.
Quantization은 연속적인 표현을 codebook의 유한한 선택지 중 하나로 바꾸는 과정이다.
음성 출력에서는 내용 중심 token 외의 음향 정보를 voice cloning 모델로 보완한다.
LLM이 생성한 modality별 token은 해당 decoder를 거쳐 이미지나 소리로 바뀐다.
예를 들어 텍스트 다음에 이미지 token을 생성하면 이를 이미지 decoder에 전달한다.
AnyGPT도 생성한 이미지 코드를 곧바로 픽셀로 읽는 것은 아니다.
코드를 생성용 표현으로 바꾼 뒤 diffusion 기반 이미지 decoder를 사용한다.
따라서 두 방식의 차이는 diffusion을 쓰는지보다, LLM이 생성하는 것이 이미지 코드인지 생성기를 조건화할 signal 위치의 표현인지에 있다.

같은 요청 “고양이 그림을 그려 줘”에 대한 두 경로를 비교하면 중간 표현의 역할이 드러난다.

| 접근 | 언어 모델에서 나온 표현 | 이미지 생성 경로 |
| --- | --- | --- |
| NExT-GPT | 이미지 signal token 위치의 hidden representation | 출력 projection → 이미지 생성기의 조건 → 이미지 |
| AnyGPT | 이미지 code ID sequence, 예를 들어 `[12, 8, 31, …]` | 코드 → 생성용 표현 → diffusion 이미지 decoder → 이미지 |

ID 숫자는 설명을 위한 가상 값이다.
두 모델이 같은 그림을 만든다고 가정한 것이 아니라, 하나는 생성기의 조건을 만들고 다른 하나는 이미지 코드 자체를 생성한다는 차이를 보여 준다.

## 2. 데이터와 학습

### 2-1. 정렬과 instruction tuning

서로 다른 encoder와 LLM을 붙인 구조가 만들어졌다고 곧바로 모든 입력 조합에 답할 수 있는 것은 아니다.
학습 데이터와 목적함수가 각 입력을 어떻게 사용할지 가르쳐야 한다.
대표적인 출발점은 이미지–텍스트나 오디오–텍스트처럼 대응 관계가 있는 자료다.
모델은 입력 표현을 바탕으로 대응 텍스트를 생성하도록 학습하면서 connector와 LLM의 연결을 맞춘다.
일부 접근에서는 앞서 학습한 encoder와 LLM을 고정하고 connector만 학습하며, 다른 접근에서는 더 많은 parameter를 함께 갱신한다.

이후 instruction tuning에는 사용자 지시, 입력, 원하는 응답의 형태를 갖춘 자료를 사용한다.
예를 들어 “무슨 악기가 들리는가?”라는 질문에 오디오를 함께 주고 “피아노가 들린다”라는 답을 예측하도록 한다.
영상과 오디오를 동시에 보아야 하는 질문도 학습에 포함할 수 있다.
입력의 순서나 출력 형식이 달라져도 지시를 따르는 행동을 익히는 것이 목적이다.[^survey]

단일 modality 데이터 여러 종류를 섞는 것과, 한 예제에서 여러 modality를 **함께 사용하도록 요구하는 것**은 구별해야 한다.
이미지 질문만 따로, 오디오 질문만 따로 잘 푼다는 결과만으로 화면의 특정 인물과 동시에 들리는 목소리를 연결할 수 있다고 결론 낼 수는 없다.
그 관계를 요구하는 평가 자료가 있어야 해당 능력을 확인할 수 있으며, 학습 자료의 구성도 그 능력에 영향을 준다.

### 2-2. Interleaved sequence

이미지와 텍스트가 교차하는 interleaved sequence는 여러 이미지와 문맥의 관계를 표현한다.[^flamingo]
같은 구성 원리를 오디오와 비디오까지 확장하면 시간 관계를 표현하는 문제가 생긴다.

입력은 개념적으로 다음과 같이 표현할 수 있다.
대괄호는 데이터의 종류를 알아보기 위해 붙인 표시이며 특정 모델의 실제 특수 token 이름이 아니다.

```text
[영상: 0–2초] [오디오: 0–2초] [영상: 2–4초] [오디오: 2–4초]
[질문: 박수는 언제 들렸는가?] [답변]
```

각 구간의 영상과 오디오를 가까이 배치하더라도 구간 내부의 사건 시각은 별도로 나타내야 한다.
입력 형식이 interleaved라는 사실은 그 자료가 실제 시간에 동기화되어 있다는 뜻과는 다르다.
문서 속 이미지 순서는 문서의 서술 순서일 수 있지만, 동영상과 오디오에서는 각 조각이 실제로 언제 발생했는지가 중요하다.

### 2-3. 영상과 소리의 시간 관계

두 사람이 차례로 말하는 영상에서 “누가 박수가 들릴 때 말했는가?”를 묻는다고 하자.
모델이 영상에서 두 사람이 모두 등장한다는 사실과 오디오에서 박수와 말소리가 난다는 사실만 알아서는 답할 수 없다.
박수 소리 주변의 연속 frame에서 입의 움직임을 보고 음성과 대조해야 한다.
입의 움직임만으로 화자를 확정할 수는 없으므로 시각·음향 단서의 불확실성도 남는다.
이처럼 사건의 순서와 동시성에 관한 정보가 필요하다.
명시적인 시간 위치는 이 정보를 제공하는 한 가지 방법이다.

가상 예시로 0초와 1초에 영상 frame을 뽑고, 오디오는 0–0.5초와 0.5–1초의 구간으로 나눈다고 하자.
각 오디오 구간에는 시작 시각을 위치로 붙인다.
0.7초의 박수는 두 번째 구간에 들어가지만, 그 구간의 시작 시각만으로 박수의 정확한 시각이 자동으로 알려지는 것은 아니다.
영상에도 0.7초의 frame이 없으므로 그 순간의 화면을 직접 확인할 수 없다.
더 촘촘한 영상 표본과 시간 위치는 단서를 제공하지만, 모델이 그 관계를 정확히 이해한다고 보장하지는 않는다.

촘촘히 추출하면 빠른 움직임과 짧은 소리를 포착할 가능성은 커지지만 입력 feature와 계산량도 늘어난다.
반대로 압축과 표본 추출을 강하게 하면 LLM에 넣는 길이는 줄어들지만, 입 모양과 음절이 맞는지 같은 세부 관계가 사라질 수 있다.

## 3. 시간 동기화

### 3-1. 위치와 실제 시간

텍스트의 위치는 보통 token sequence 안의 순서로 나타낼 수 있다.
영상은 시간과 더불어 각 frame 안의 세로·가로 위치가 있으며, 오디오는 영상과 서로 다른 속도로 표현이 만들어진다.
따라서 단순히 첫 번째 입력, 두 번째 입력이라는 번호만 주면 서로 다른 modality의 위치가 실제 시간상 얼마나 떨어져 있는지 잃을 수 있다.

Qwen2.5-Omni는 영상과 오디오 표현을 실제 시간에 맞춰 배열하고 TMRoPE(time-aligned multimodal rotary position embedding)로 시간과 공간 위치를 표현한다.[^qwen25]
모델의 위치 정보는 시간·높이·너비라는 세 축을 사용한다.
예를 들어 교육용 위치 좌표가 `(0, 2, 3)`과 `(1, 2, 3)`이라면 두 patch는 이미지 안의 행과 열은 같지만 시간 위치가 다르다.
이 숫자는 세 축의 역할을 보여 주는 가상 예시로, 특정 영상의 실제 위치 ID는 아니다.
이미지의 patch들은 같은 시각에 속하지만 이미지 안의 행과 열은 다르다.
영상은 frame 시각이 달라지므로 시간 위치도 함께 바뀐다.
오디오는 시간에 따라 진행하지만 이미지처럼 2차원 공간 위치를 나타내지는 않는다.

| 가상 입력 | 시간 위치 | 공간 위치 |
| --- | --- | --- |
| 첫 영상 frame의 patch | 0 | 행 2, 열 3 |
| 다음 영상 frame의 같은 위치 patch | 1 | 행 2, 열 3 |
| 첫 frame과 같은 시각의 오디오 표현 | 0 | 2차원 이미지 위치 없음 |

이 표는 세 축의 역할을 설명하는 가상 예시다.
두 입력의 시간 위치가 0이라는 것은 해당 예시에서 같은 시각에 대응한다는 뜻이지, 영상과 오디오의 전체 위치 표현이 같다는 뜻은 아니다.
실제 모델의 위치 부여 방식은 [Qwen2.5-Omni 원논문](https://arxiv.org/html/2503.20215v1)에서 확인할 수 있다.
위치 정보만 있으면 모델이 그 관계를 반드시 이해한다는 뜻은 아니다.
“박수가 난 순간 말한 사람”처럼 시간 관계가 필요한 질문으로 모델의 능력을 평가하고, 학습 데이터의 구성이 성능에 미치는 영향도 살펴야 한다.

### 3-2. Chunk와 동기화의 단위

Qwen2.5-Omni는 영상과 오디오를 실제 시간 기준으로 2초씩 나누고 각 구간의 시각 표현 다음에 오디오 표현을 배치한다.[^qwen25]
예컨대 0–2초의 영상 표현과 오디오 표현을 둔 다음, 2–4초의 영상 표현과 오디오 표현을 둔다.
이 순서는 처리 단위를 시간에 가깝게 묶어 주지만, 구간 안에 들어간 token이 한 개씩 정확히 시간 순으로 정렬된다는 뜻은 아니다.
실제 시간 차이는 각 표현의 위치 정보를 통해 별도로 표현한다.
이 모델에서 시간 ID 한 칸은 40 ms에 해당하므로 2초는 시간 ID의 50칸에 해당한다.
즉 2초는 영상과 오디오 표현을 묶어 배열하는 구간이지 audio token 하나의 길이가 아니다.

Qwen3-Omni는 정렬을 위한 고정 2초 묶음 대신 실제 시간에 대응하는 위치 ID를 이용해 영상과 오디오 표현을 정렬한다고 설명한다.[^qwen3]
이는 모든 chunk 처리를 없앤다는 뜻은 아니며, 긴 입력의 prefill을 조각으로 나눠 먼저 들어온 부분부터 처리하는 chunked prefilling은 streaming을 위해 별도로 사용한다.
이 모델에서 오디오 표현의 시간 ID 간격은 80 ms이고, 영상 frame에도 실제 timestamp에 따라 시간 ID를 부여한다.
이 간격은 Qwen3-Omni의 audio encoder인 AuT가 초당 12.5개 feature를 내는 출력 시간 해상도와 맞물린다.
정확한 단위와 chunk 방식은 모델의 설계 선택이며, 모든 Omni 모델의 공통 규칙은 아니다.

MiniCPM-o 4.5는 시간 분할 다중화(time-division multiplexing, TDM)를 사용해 동시에 흐르는 입력과 출력을 짧은 시간 구간별 정보 묶음으로 바꾸어 언어 모델에서 함께 처리한다.[^minicpmo45]
예를 들어 한 구간에 해당하는 영상과 소리, 응답 정보를 시간 순서에 맞게 배치하고 다음 구간을 이어 붙이는 것이다.
이는 여러 흐름을 하나의 sequence로 다루기 위한 방법이며, 각 modality의 token이 같은 속도로 생성된다는 뜻은 아니다.

## 4. 통합 입력과 출력

### 4-1. Cascade와 native multimodal

음성 질문이 들어왔을 때 음성 인식기로 텍스트를 만들고, 이미지 모델의 설명을 생성한 다음, 텍스트 LLM이 두 결과를 보고 답하게 만들 수 있다.
이런 cascade는 각 부품을 따로 바꾸거나 오류를 추적하기 쉽다.
하지만 앞 단계가 버린 정보는 다음 단계가 직접 복구할 수 없다.
예를 들어 “정말 잘했어”라는 문장만 전달되면 칭찬인지 비꼬는 말인지 판단하는 억양이 사라질 수 있다.
이미지 caption에 빠진 시각 정보도 LLM이 확인할 수 없다.

오디오와 이미지 표현을 모델에 직접 전달하면 텍스트로 요약하기 전의 정보에 접근할 경로가 생긴다.
이때 native multimodal이라는 표현을 쓰기도 하지만, 이 말만으로 학습 방식이나 내부 구조가 하나로 정해지는 것은 아니다.
입력을 직접 처리하는지, 생성도 해당 modality로 하는지, 여러 modality를 어떤 데이터로 함께 학습하는지 확인해야 한다.
중간에 텍스트로 확정하는 단계 없이 입력부터 출력까지 하나로 이어 학습한 구성을 end-to-end라고 부르며, modality별 encoder나 음성 출력용 decoder 같은 부품이 남아 있어도 이렇게 학습할 수 있다.
OpenAI는 2024년 GPT-4o를 발표하면서 텍스트·시각·오디오를 하나의 신경망에서 end-to-end로 학습하는 방식을 소개했다.[^gpt4o]
ChatGPT의 이전 Voice Mode가 쓰던 음성 인식 → 텍스트 모델 → 음성 합성 cascade와 비교하면, 모델이 음성의 억양 같은 정보를 텍스트 변환 전에 이용할 수 있는 방향이다.
다만 모델이 만들 수 있는 출력과 특정 시점의 제품이나 API에서 제공하는 기능은 구분해야 한다.
Qwen2.5-Omni는 Qwen2.5 언어 모델과 사전학습된 시각·audio encoder를 초기값으로 사용한다.[^qwen25]
먼저 LLM을 고정하고 각 입력 경로를 이미지–텍스트와 오디오–텍스트 자료에 맞춘다.
이후 parameter를 함께 갱신하며 여러 modality가 섞인 자료로 학습하고, 긴 sequence 자료로 문맥 길이를 확장한다.
처음부터 입력 경로와 언어 모델이 이미 정렬되어 있다고 가정하지 않고 단계적으로 연결하는 것이다.

<Callout type="note">
Vision에서 사용하는 native resolution은 다양한 이미지 크기와 종횡비를 처리하는 방식에 관한 말이다.
Native multimodal은 여러 modality를 다루는 모델과 학습 방식에 관한 말이다.
같은 native라는 단어가 들어가지만 서로 다른 설계 축이다.
</Callout>

### 4-2. Thinker와 Talker

음성으로 답하는 모델은 입력을 이해할 뿐 아니라 말소리를 생성해야 한다.
텍스트는 짧은 token 몇 개로 표현되는 반면, 자연스러운 음성은 발음·길이·억양 등의 정보를 시간에 따라 담아야 한다.
음성 출력을 생성하는 일과 입력을 이해하고 답의 내용을 구성하는 일의 계산 특성이 다르므로, 두 역할을 분리하는 설계가 가능하다.

Qwen2.5-Omni의 Thinker는 텍스트와 함께 vision·audio encoder가 만든 연속 표현으로 이미지·오디오·비디오 입력을 받아 텍스트와 내부 표현을 만들고, Talker는 Thinker의 정보와 텍스트를 조건으로 음성 token을 생성한다.[^qwen25]
생성된 음성 token은 flow matching 모델에서 Mel spectrogram으로 변환되고, vocoder가 이를 파형으로 복원해 사용자에게 전달한다.
이 모델의 경우 여러 입력을 받아 텍스트와 음성으로 답하는 구성이 대표적이다.

여러 입력을 받는 모델이라도 출력 경로는 다를 수 있다.
예를 들어 Google DeepMind가 공개한 Gemini 4 Argon 모델 카드는 텍스트·이미지·오디오·비디오 입력과 텍스트 출력을 명시한다.[^gemini4argon]

전체 답변이 완성된 뒤에만 음성을 만들면 사용자는 기다려야 한다.
Streaming은 입력과 출력을 작은 조각으로 처리해 앞부분부터 전달한다.
그렇지만 첫 조각을 빨리 내는 것과 사용자가 말하는 동안 시스템도 듣고 말하는 full duplex는 서로 다른 특성이다.
Streaming 출력이 가능하다는 사실만으로 끼어들기를 자연스럽게 처리한다고 단정할 수 없다.
Thinker와 Talker를 나누었다는 구조만으로도 full duplex 지원을 판단할 수 없으므로, 실제 대화에서 입력과 출력을 겹쳐 처리하는지 별도로 확인해야 한다.

Qwen3-Omni는 Thinker–Talker를 유지하면서 음성 출력을 여러 codebook의 token으로 구성한다.[^qwen3]
입력은 Qwen2.5-Omni처럼 encoder의 연속 표현으로 받고 음성 출력은 이산 token으로 내는 비대칭 구성이다.
Qwen2.5와 달리 Qwen3의 Talker는 Thinker의 고수준 텍스트 hidden representation 대신 텍스트 token과 Thinker의 audio·visual feature를 조건으로 쓴다.
기술 보고서 안에서도 Talker의 조건을 설명하는 문장이 audio·visual feature만 언급하는 곳과 텍스트 token까지 언급하는 곳으로 엇갈리므로, 이 문장은 두 설명을 합친 것이다.
Talker가 현재 음성 frame의 첫 codebook token을 예측하고, 추가 예측 모듈이 나머지 codebook을 만든다.
한 frame의 여러 codebook을 작은 모듈에 맡긴다는 점에서 Moshi의 Depth Transformer와 같은 문제를 푸는 설계다.[^moshi]
이 token들은 causal convolutional decoder를 통해 파형으로 바뀌므로 앞선 문맥을 이용해 순차적으로 음성을 내보낼 수 있다.
이 변경은 이전의 flow matching 기반 음향 복원 대신 첫 codec frame부터 streaming하기 위한 설계다.
이 구조는 Qwen2.5-Omni와 세부 설계가 다르므로 두 버전의 decoder와 token 경로를 하나로 섞어 설명하면 안 된다.

같은 Qwen3-Omni 계열에서도 공개 checkpoint를 구분해야 한다.[^qwen3card]
Qwen3-Omni-30B-A3B-Instruct는 Thinker와 Talker를 모두 포함해 텍스트와 음성을 출력하지만, Thinking은 추론에 집중한 Thinker만 포함하며 텍스트를 출력한다.
따라서 모델 계열 이름만으로 음성 출력 지원 여부를 판단할 수 없다.

MiniCPM-o 4.5는 사전학습된 vision encoder, 음성 encoder와 생성기, 언어 모델을 출발점으로 사용하는 또 다른 통합 사례다.[^minicpmo45]
앞의 TDM으로 입력 흐름과 응답 흐름을 짧은 시간 구간마다 한 sequence에 끼워 넣어, 사용자의 영상과 음성을 받아들이는 동안 음성으로 응답하는 full duplex 상호작용을 지향한다.
이처럼 여러 부품을 사용하더라도 전체 시스템을 통합해 학습하거나 실시간으로 동작하도록 설계할 수 있다.

기기에서 실행하는 모델에도 같은 문제가 나타난다.
Liquid AI의 LFM3-Omni-2B는 약 22억 개 parameter를 사용하며 텍스트·이미지·비디오·오디오를 입력으로 받아 텍스트나 음성, 또는 두 출력이 교차하는 sequence를 만든다.[^lfm3omni]
vision encoder와 audio encoder가 입력을 언어 모델에 연결하고, 음성 출력은 별도의 생성 모듈과 audio codec을 거쳐 파형으로 복원한다.
모델 크기를 줄여 기기 실행을 지향하면서도 입력과 출력의 표현을 각각 설계해야 한다는 예다.

## 5. 상호작용과 평가

### 5-1. 관찰과 행동

영상과 음성 입력을 처리하는 모델은 사용자 지시를 이해한 뒤 외부 도구를 호출하는 시스템의 일부가 될 수도 있다.
예를 들어 화면을 보여 주며 “이 문서를 열어 줘”라고 말하면, 모델은 음성과 화면을 바탕으로 대상과 행동을 정하고 시스템은 클릭 같은 도구를 실행한다.
실행 결과로 바뀐 화면을 다시 받아 성공 여부를 확인해야 한다.
영상·음성을 이해하는 모델의 능력과 실제 도구를 실행하는 환경의 능력은 구분해야 한다.

### 5-2. 평가의 단위

입력 modality별 점수와 modality를 함께 써야 하는 문제의 점수는 서로 다른 능력을 측정한다.
이미지 질문과 오디오 질문을 각각 잘 풀어도, 두 신호를 함께 연결하는 문제에서는 실패할 수 있다.
평가 데이터에는 한 modality만 보고도 맞힐 수 있는 지름길이 있을 수 있으므로, 한 입력을 가리거나 시간 순서를 바꾼 비교가 도움이 된다.
예를 들어 박수 소리를 다른 순간으로 옮겼을 때 정답이 바뀌는 문제라면 시간 관계에 모델이 민감한지 확인할 수 있다.
가령 같은 영상에서 A가 먼저 말하고 B가 나중에 말한다면, A가 말하는 구간에 박수를 넣은 예시의 정답은 A다.
발화는 그대로 두고 박수만 B의 발화 구간으로 옮긴 예시에서는 정답이 B로 바뀐다.
두 경우에 같은 답을 낸다면 영상에 두 사람이 있다는 사실은 알아도 박수와 발화의 시간 관계를 충분히 사용하지 못했을 수 있다.

실시간 시스템은 정답의 내용 외에도 입력 시작부터 첫 응답까지의 지연, 응답을 지속적으로 생성하는 속도, 입력이 겹쳤을 때의 행동을 살펴야 한다.
이 수치는 하드웨어, 입력 길이, 동시 요청 수, 측정 시작점에 영향을 받는다.
논문이 보고한 지연을 다른 환경에서도 그대로 재현할 수 있다고 가정하지 않는다.
모델의 환각, 시각적으로 보이지 않거나 오디오에 없는 정보의 추론, 민감한 음성 정보의 처리도 별도로 평가해야 한다.

## 6. 국내 Omni 모델의 통합 방식

카카오의 Kanana-o는 이미지·음성·텍스트를 함께 다루고 텍스트나 음성으로 답하도록 설계된 Omni 모델이다.[^kanana-o]
예를 들어 사진을 보여 주며 음성으로 “이 물건은 무엇인가?”라고 물으면, 사진과 질문을 함께 조건으로 답변을 만들 수 있다.
2025년 개발 설명에서는 이미지와 음성을 각각 encoder의 연속 표현으로 언어 모델에 넣고, 음성으로 답할 때는 이산 음성 token을 생성한다.

카카오가 2025년에 설명한 개발 과정에서 Kanana-v와 Kanana-a는 같은 언어 모델을 출발점으로 각각 시각과 음성을 다루도록 학습되었다.
Kanana-o는 두 모델을 model merging으로 결합하고, 시각과 음성 경로를 갖춘 모델을 추가로 학습하는 방식으로 만들었다.
Model merging은 별도로 조정된 모델의 parameter를 결합하는 접근이다.
모든 모델을 아무렇게나 합치면 두 능력이 자동으로 보존되는 것은 아니며, 이 사례에서는 공통 언어 모델을 바탕으로 한 두 모델과 추가 학습이 중요하다.

카카오의 [Kanana-o 개발 발표 영상](https://www.youtube.com/watch?v=S4CMtHfscis)은 시각과 음성을 각각 다루는 모델을 통합하는 과정과 실제 서비스에서 고려한 선택을 소개한다.
2025년 발표 내용과 이후 공개된 모델의 버전은 구분해서 보자.

여러 입력을 함께 이해하려면 구조뿐 아니라 그 조합을 보여 주는 데이터도 필요하다.
카카오는 이미지–텍스트 자료의 질문이나 답변을 음성으로 합성해 이미지·음성·텍스트가 함께 쓰이는 학습 예시를 구성했다고 설명한다.
예를 들어 같은 이미지에 대한 질문을 음성으로 제시하고 텍스트로 답하게 하거나, 텍스트 질문에 음성으로 답하게 할 수 있다.
합성 음성이 학습 자료를 늘려 주더라도 실제 환경의 잡음이나 다양한 말투를 모두 대표하는지는 별도로 평가해야 한다.

카카오가 공개한 다음 영상은 여러 입력·출력 조합을 가진 Omni 학습 데이터의 예시다.
하나의 이미지와 질문·답변이 글이나 음성으로 어떻게 제시되는지 살펴보자.

<Video src="https://www.youtube.com/watch?v=3qJooAWnk8M" caption="kakao tech, Omni-modal 학습 데이터셋 예시 (2025)" />

카카오의 2025년 후속 개발 글은 이미지·오디오·텍스트를 다양한 조합으로 사용하는 지시 이행 자료와 여러 차례 질문과 답이 이어지는 대화 자료를 구축한 과정을 설명한다.[^kanana-o-update]
예를 들어 같은 이미지에 대한 질문이 글이나 음성 중 어느 쪽으로 들어오더라도 지시에 맞게 답하도록 학습하는 것이다.
이 글에서는 발화가 겹칠 때의 full duplex 상호작용도 연구 방향으로 다루므로, 해당 글만으로 완성된 기능이라고 단정하지 않는다.

### 6-1. 음성 생성과 발화 지시 학습

2026년 후속 개발에서 카카오는 LM-SPT를 Kanana-o의 음성 생성에 적용했다.[^kanana-o-speech]
언어 모델이 질문과 대화 문맥을 처리한 표현과 화자 정보를 Voice Token LM에 전달하면, 이 모델이 의미·음향 token을 생성한다.
LM-SPT decoder는 token들을 받아 Mel spectrogram을 거치지 않고 waveform을 복원한다.
하나의 시간 frame에 여러 codebook이 있으므로 Voice Token LM은 codebook별 출력 head를 사용한다.
각 codebook의 출력을 한 단계씩 지연시키면, 뒤쪽 codebook이 같은 frame에 해당하는 앞쪽 codebook의 결과를 참고하면서도 여러 시간 위치의 token을 병렬로 생성할 수 있다.
생성 후 지연된 token을 원래 frame 순서로 다시 맞춰 decoder에 넣는다.

두 frame과 의미 codebook 하나, 음향 codebook 하나만 있는 가상의 예로 순서를 살펴보자.
`S1`은 첫 frame의 의미 token, `A1`은 같은 frame의 음향 token이다.

| 생성 단계 | 의미 token | 음향 token |
| --- | --- | --- |
| 1 | S1 | 대기 |
| 2 | S2 | A1 |
| 3 | 종료 후 대기 | A2 |

두 번째 단계에서는 다음 frame의 `S2`와 첫 frame의 `A1`을 함께 예측한다.
`A1`을 만들 때는 이미 생성한 `S1`을 참고할 수 있다.
생성이 끝나면 `S1`과 `A1`, `S2`와 `A2`를 각각 같은 frame으로 다시 묶는다.
실제 모델은 음향 codebook이 여러 개이므로 각 스트림의 지연을 더해 처리하며, 위 표는 시작·종료 token을 생략한 단순한 예다.

음성 token을 생성할 수 있다는 것과 “아주 빠르게 말해 줘”라는 지시를 정확히 따르는 것은 별개다.
카카오는 같은 문장과 화자 조건에서 발화 속도 등 비교 대상만 바꾼 음성들을 만들고, 지시에 따라 어느 음성이 더 적절한지 선호 쌍을 구성했다.
예를 들어 같은 두 음성이라도 “빠르게”라는 지시에서는 빠른 음성이, “천천히”라는 지시에서는 느린 음성이 선호될 수 있다.
이 자료로 Kanana-a를 기반으로 한 보상 모델이 발화 지시와 생성 음성의 적합도를 평가하도록 학습한다.

그다음 Voice Token LM이 학습 중 직접 생성한 음성을 평가해 모델을 갱신하는 online RL을 적용한다.
발화 지시 점수만 높이면 빠르게 말하는 대신 단어를 빠뜨리는 식의 문제가 생길 수 있으므로, 지시 이행 외에 발화 오류율·화자 유사도·음질도 함께 고려한다.
공개 글은 이 목표와 선호 데이터 구성 원리를 설명하지만, 전체 데이터의 크기와 배합, 보상 가중치와 모든 학습 설정을 제공하지는 않는다.
이는 2026년 음성 생성 개선의 설명이며, 2026년 2월 API 모델이 같은 구현을 사용한다고 단정할 근거는 없다.

### 6-2. 공개된 입출력과 범위

`Kanana-1.5-o-9.8B-instruct-2602` API 문서에 명시된 입력은 텍스트·이미지·오디오이고, 출력은 텍스트와 오디오다.[^kanana-o-api]
모델 이름에 Omni가 들어간다는 이유만으로 이미지나 영상 출력까지 지원한다고 가정하지 않는다.
또한 2025년 개발 설명과 이후에 공개된 API 모델은 시점과 버전이 다르므로 세부 구현을 그대로 동일시하지 않는다.

### 6-3. HyperCLOVA X 8B Omni의 통합과 학습

네이버의 HyperCLOVA X SEED 8B Omni는 텍스트·이미지·video·audio를 입력으로 받고 텍스트·이미지·음성을 출력한다.[^naver-omni-card]
예를 들어 사진과 질문을 받아 텍스트로 답하거나, 텍스트 지시를 받아 이미지를 생성할 수 있다.
Video 입력을 받는 것과 video 자체를 생성하는 것은 다르다.
이 모델 카드의 출력 목록에는 video가 없다.

이 모델은 언어 모델에 연속적인 vision·audio encoder 표현과 이산 image·audio token을 함께 연결한다.[^naver-omni-report]
연속 feature는 입력을 세밀하게 이해하는 데 쓰이고, 이산 token은 입력과 출력 양쪽에 쓰인다.
생성된 이산 image token은 diffusion 기반 이미지 decoder의 조건이 되어 이미지를 만들고, 이산 audio token은 음성 decoder를 통해 waveform으로 변환된다.
예를 들어 음성 질문은 audio encoder와 tokenizer의 표현을 통해 처리하고, 답변을 말할 때는 생성한 audio token을 음성 decoder가 파형으로 바꾼다.
입력과 출력이 하나의 언어 모델을 공유해도 vision encoder나 음성 decoder가 없어지는 것은 아니다.

학습 과정도 한 번에 모든 부품을 처음부터 학습하는 방식으로 단순화하면 안 된다.
기술 보고서는 먼저 텍스트 언어 모델을 학습하고, image와 audio의 이산 token을 추가해 확장한 다음 여러 modality 데이터로 언어 모델을 함께 학습하는 단계를 설명한다.
이후 연속 vision encoder와 audio encoder를 연결해 입력 표현을 정렬한다.
예를 들어 vision encoder와 언어 모델을 고정하고 그 사이 adapter를 먼저 학습한 뒤, vision을 중심으로 추가 학습한다.
Audio encoder는 보고서에서 사전학습된 encoder를 사용하고 고정한다.
모든 구성 요소가 같은 단계에서 동시에 갱신된다는 뜻은 아니다.
후속 SFT(supervised fine-tuning)에서는 대화와 다양한 입력·출력 task를 학습하고, video와 긴 문맥 데이터를 추가해 시간에 따른 사건을 다루도록 한다.

Video에는 화면과 소리가 함께 들어갈 수 있다.
보고서는 video의 긴 audio 입력을 효율적으로 다루기 위한 audio token compressor도 설명한다.
8B Omni의 연속 audio encoder는 초당 25개 feature를 만들고, video의 audio에는 MambaMia compressor를 적용해 초당 1개로 줄인다.
예를 들어 10초라면 약 250개 feature가 약 10개가 된다.
이는 video 입력 feature의 압축이며 음성 출력 token의 생성 속도가 아니다.
예를 들어 “문이 닫힌 뒤 어떤 소리가 나는가?”라는 질문에서는 frame의 순서와 audio의 발생 시점을 함께 사용해야 한다.
이는 video를 frame의 모음으로만 취급하는 경우보다 많은 정보를 활용하지만, 시각과 소리를 시간에 맞게 처리하는 것은 별도의 문제다.

2026년 공개된 HyperCLOVA X SEED 4B 개발 글은 별도로 개발한 vision·audio encoder를 연결해 이미지·video·audio를 이해하고 텍스트로 답하는 모델을 소개한다.[^naver-omni4b]
텍스트 사전학습을 마친 언어 모델에 encoder를 연결한 뒤 multimodal pre-training, SFT, video를 포함한 추가 SFT와 RLVR(reinforcement learning with verifiable rewards)을 진행한다.
Video 학습에는 frame 추출, audio 추출과 시간 정렬이 필요하며, 긴 video에서는 audio feature를 압축해 입력 길이를 줄인다.
SEED 4B가 설명한 audio 압축은 초당 10개 feature를 평균 pooling으로 2개로 줄이는 방식이다.
8B Omni의 25개에서 1개로 줄이는 경로와 다른 모델의 설정이다.
SEED 4B의 설명을 8B Omni의 이미지·음성 생성 지원과 동일시하지 않는다.

두 국내 모델의 공개된 개발 설명을 비교하면 Kanana-o는 공통 언어 모델에서 출발한 vision·audio 모델의 병합과 추가 학습을 소개하고, 8B Omni는 하나의 언어 모델에 여러 modality token과 encoder를 단계적으로 추가하는 과정을 설명한다.
이는 각 보고서가 설명한 모델과 시점의 비교이며, 이후 버전도 모두 같은 구조로 만들어졌다는 뜻은 아니다.
네이버의 8B Omni는 가중치를 공개했지만 이용 조건은 모델 라이선스를 확인해야 하며, 공개된 설명이 전체 학습 데이터의 재현을 보장하지는 않는다.

| 비교 대상 | 출발점과 결합 방식 | 공개된 입출력의 예 |
| --- | --- | --- |
| Kanana-o의 2025년 개발 설명 | 공통 LLM으로부터 vision·audio 모델을 학습하고 병합한 뒤 추가 학습 | 이미지·음성·텍스트 입력과 텍스트·음성 응답 |
| HyperCLOVA X 8B Omni | 텍스트 기반 모델에 이산 modality token을 추가해 공동 학습하고 연속 encoder도 연결 | 텍스트·이미지·video·audio 입력과 텍스트·이미지·음성 출력 |
| HyperCLOVA X SEED 4B | 자체 vision·audio encoder와 언어 모델을 연결해 multimodal 학습 | 이미지·video·audio·텍스트 이해와 텍스트 응답 |

표의 입출력은 각 공개 자료에서 확인한 범위다.
같은 이름의 모든 버전이 같은 기능을 제공한다는 뜻은 아니다.

## 7. 다른 modality로의 확장

연속 표현과 이산 token 사이의 선택은 이미지와 음성에만 있는 문제가 아니다.
시계열·표·분자처럼 텍스트가 아닌 데이터를 다루는 foundation model에서도 같은 두 갈래가 나타난다.

시계열에서 Chronos는 값의 크기를 맞춘 뒤 값의 범위를 일정한 구간(bin)으로 나누어 시점마다의 값을 구간 번호로 바꾼다.
이렇게 특수 token을 포함한 4,096개 항목의 고정 어휘를 만들고, T5 구조의 언어 모델을 cross-entropy로 학습한다.[^chronos]
반면 TimesFM은 연속된 시점의 값을 patch로 묶어 벡터로 넣고, 지난 patch들로 다음 patch의 값을 회귀로 예측하는 decoder-only 모델이다.[^timesfm]
표 데이터의 TabPFN은 셀 값을 어휘로 바꾸지 않고 실수 그대로 벡터로 넣는 연속 방식이다.
사전 분포에서 뽑은 합성 데이터로 미리 학습한 Transformer가 학습용 행과 label을 문맥으로 받아, 가중치 갱신 없이 in-context learning으로 test 행의 label을 예측한다.[^tabpfn]
분자에서는 MolT5처럼 원자와 결합을 한 줄의 문자로 적는 SMILES 표기를 텍스트와 같은 이산 token으로 다루는 방식과,[^molt5]
MolCA처럼 분자 graph를 graph encoder로 표현한 뒤 Q-Former로 언어 모델에 연결하는 연속 방식이 함께 쓰인다.[^molca]

어느 쪽을 고를지는 이미지·음성에서와 마찬가지로, 데이터가 원래 유한한 기호에 가까운지와 출력을 어떤 형태로 만들어야 하는지에 따라 달라진다.
Chronos처럼 원래 연속인 데이터라도, 출력을 어휘 위의 확률분포로 다루려고 일부러 이산화하기도 한다.
